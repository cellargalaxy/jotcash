## 四、已修复：`calendar.DateOf` 绕过年份校验，可静默产出非法 Date

### 4.1 问题

`internal/base/calendar/calendar.go` 的 `DateOf(t time.Time) Date` 是全包**唯一不调 `checkYear` 的构造入口**。`time.Time` 的年份取值域远宽于本包的 `[MinYear, MaxYear] = [1, 9999]`，越界即静默产出非法值：

| 输入 | 修复前 `String()` | 长度 | `IsZero()` |
|---|---|---|---|
| `10000-03-05` | `"10000-03-05"` | **11**（应恒为 10） | false |
| `0000-03-05` | `"0000-03-05"` | 10 | false |
| `-0001-03-05` | `"-001-03-05"` | 10 | false |

### 4.2 为什么这是缺陷，而不是有意为之

三条依据，全部来自本包自己写下的契约：

1. `calendar.go` 第 24–26 行（全局性质一）：「三个类型的字段全部私有，只能经 NewXxx / ParseXxx / **DateOf** 构造，**构造时即校验**。于是全仓库成立：一个值要么 IsZero，要么合法」——`DateOf` 被点名在内，但它恰恰没校验。
2. `calendar.go` 第 28–31 行（全局性质二）：「Date 恒为 10 字符……**store/sqlite 直接依赖这条性质**……**这也是本包把年份限制在 [MinYear, MaxYear] 的原因——越界会破坏定长**」。
3. `checkYear` 自身注释（第 106–107 行）：「保证越界一律返回错误**而不是静默产出破坏定长的值**」。

且 `DateOf` 的注释只声明「取 t 在其自身时区下的年月日，不做任何时区换算」，**从未声明豁免年份校验**。对照 `NewDate(10000,1,1)`、`ParseDate("0000-01-01")`、`AddDays`、`AddMonths` 全部正确返回 `ErrYearRange`，唯独 `DateOf` 例外——是漏写，不是设计。

另经确认排除了「已知代价」的可能：全仓库无任何测试钉住 `DateOf` 的年份范围（`date_test.go` 原有的 `TestDateOfKeepsOwnZone` 只验时区语义），前 5 轮 answer 文档 grep `DateOf` 亦无任何登记。

### 4.3 实际危害（已实测复现）

该旁路能被数据库驱动触达：`Date.Scan` 与 `Month.Scan` 的 `case time.Time` 分支都直接调 `DateOf`。四项后果：

| 后果 | 实测 |
|---|---|
| **写得进库、读不回来** | `Value()` 返回 `"10000-03-05"` 可落库，再用 `ParseDate` 读回报 `ErrDateFormat`（长度 ≠ 10） |
| **破坏「字典序 = 时间序」** | `"10000-01-01"`（更晚）按字符串比较 **小于** `"2026-01-01"`（更早），而 `After()` 为 true——store/sqlite 的排序（F-3）、区间筛选（F-4）、摊分穿刺（8.2）全部依赖朴素字符串比较，此处会给出错误结果 |
| **真实日期退化为「未指定」** | `DateOf(0000-01-05).ToMonth()` 的 `IsZero()` 为 true、`String()` 为空——0 年被当成「无值」 |
| 污染下游 | `Date.Scan(10000-03-05)` 返回 `err=nil`，非法值进入实体字段 |

> 补充：`amortize.Derive` / `NewSchedule` 因内部另有月份算术，接到该越界日期时仍能返回 `ErrYearRange`——但这是下游偶然拦住，不能替代入口校验。

### 4.4 修法与取舍

**采用**：`DateOf` 改为 `func DateOf(t time.Time) (Date, error)`，越界返回零值 + `ErrYearRange`。

三个候选方案的取舍：

| 方案 | 结论 |
|---|---|
| **改签名返回 error**（采用） | 与同包 `NewDate` / `ParseDate` 完全同构，把错误暴露在调用点。代价是破坏现有签名 |
| 保签名、越界返回零值 `Date{}` | 否决：零值语义是「未指定」，把「10000 年」这个明确输入静默转成「没填」，是用一个静默错误换另一个 |
| 只在两处 `Scan` 分支补 `checkYear` | 否决：治标。`DateOf` 是导出函数，直接调用方（如 `service` 层按时区取「今天」）仍可越界 |

签名变更的波及面已全部适配，且**很小**——`DateOf` 目前只有两个生产调用点：

- `internal/base/calendar/date.go`（`Date.Scan` 的 `case time.Time`）→ 改为接错误并返回
- `internal/base/calendar/month.go`（`Month.Scan` 的 `case time.Time`）→ 同上

两处均遵循「出错时不写目标变量」，保证 `Scan` 失败后目标值仍是零值而非半成品。

### 4.5 补充的回归测试

在 `date_test.go` 新增两个测试，钉住这条性质：

| 测试 | 覆盖 |
|---|---|
| `TestDateOfRejectsYearRange` | 上界外 10000 年、下界外 0 年与公元前均返回 `ErrYearRange` 且返回值为零值；同时钉住边界内 `0001-01-01` / `9999-12-31` 必须放行（防止校验写成误拒） |
| `TestScanTimeRejectsYearRange` | `Date.Scan` 与 `Month.Scan` 接到越界 `time.Time` 时返回 `ErrYearRange`，且目标值保持零值 |

原有 `TestDateOfKeepsOwnZone` 同步适配新签名，时区语义断言不变。

## 五、经核验**不是**缺陷的 5 处（保留原样）

审查中曾疑似有问题、但核对文档后确认属**已登记的设计取舍**或**分层职责划分**，故不改：

| 疑点 | 不改的依据 |
|---|---|
| `decimal` 的 `Add`/`Sub`/`Mul`/`Sum` 不做量级校验（16 位 × 16 位可得 32 位整数） | `decimal.go` 第 268–269 行已登记理由：F-6 筛选态合计与 J 域月度聚合是多笔累加，给聚合结果设上界会**误拒合法统计**。越界值最终在 `Units(scale)` 落库口径处被 `ErrUnitsOverflow` 拦下（已实测） |
| `RoundTruncate` 负数向零截断（`-1.999` → `-1.99`） | 与其自身声明的「向零截断」口径一致，非错误 |
| `dedup` 不过滤已删除候选 | 包注释明确把「比对范围为在库且未删除」归给 store 层；分层 §六 store 承载亦写「查重候选批量匹配……一次取回在库**未删除**候选」。属职责划分 |
| `entity.User` 的 `%+v` 会打印密码哈希与盐 | `entity.go` 第 96–100 行**已显式登记为残留**：JSON 侧由 `json:"-"` 兜住（已实测不泄露），日志侧无编译期兜底、只能靠约定。属已知并已记录 |
| `calendar.AddMonths` / `NewMonthRange` 的极端整数溢出 | 实测 `math.MaxInt`、`math.MinInt`、以及刻意构造使月序回绕的 `MaxInt-seq+1` 全部正确返回 `ErrYearRange`，无溢出旁路 |

另有两处**核验后判为不需本轮处理**：

- `amortize.NewShares` 无月数上限（`All()` 按 `months` 分配切片）：规格 §5、H-1 三处明写摊分月数「**无上限**」，不能加业务上限；`Derive` 已把实际可用月数限到 ~95688（2026-01 至 9999-12），该合法上界下实测 `All()` 正常返回且守恒成立。属调用方（service 层）应保证的规模问题，非本层口径错误。
- `decimal.FromInt` 不调 `checkMagnitude`：其注释自述用途为「供『摊分月数』这类整数参与金额运算」，唯一生产调用点是 `shares.go` 的 `decimal.FromInt(int64(months))`（作 QuoRem 除数），不承载金额入口职责；越界值仍会在 `Units()` 处被拦。

## 六、已复算确认成立的不变式（无反例）

以下为独立复算通过、可作后续开发前提的结论：

**decimal**
- `String()` 恒为规范形式（无尾随零），**运算产物同样规范**：`1.1*10`→`"11"`、`1.5+0.5`→`"2"`、`Round("100.00",2)`→`"100"`。
- `Equal(a,b) ⇔ a.String()==b.String()`：对 Parse 来源、运算来源、`Round`/`RoundRate` 产物、`0` vs `-0` 等十余组样本**0 对不一致**。这是 dedup 键正确性的前提。
- `RoundHalfUp` 确为四舍五入而非银行家舍入（`1.005`→`1.01`、`2.5`→`3`），负数对称。
- `QuoRem` 恒等式「商 × 除数 + 余 = 被除数」在正/负/零、scale 0/2 下全部成立。

**calendar**
- `AddMonths` 与「绝对月序」独立重算对照：4 起点 × 11 偏移（含跨年与负数）**不一致数 0**。
- `FirstDate`/`LastDate` 闰年正确（2024/2000 二月 29 日、1900 二月 28 日）；`MonthRange.Contains` 穿刺语义 `起始月 ≤ M ≤ 结束月` 正确；「字典序 = 时间序」在 1900-03 → 9999-12 全区间成立。

**currency**
- 表 27 条，位数分布 `{0:3, 2:23, 3:1}`；`BaseCandidates()` = 26 条，与独立重算「启用且 Scale ≤ 2」完全一致，**无违反 T38 的候选**；`ParseBase` 正确拒绝 3 位小数的 KWD。
- 零值币种与 JPY 可区分（零值 `CanBeBase=false`；JPY `Scale=0` 但 `CanBeBase=true`）——这正是 `amortize.NewShares` 必须「先判零值币种再取 Scale」的原因，代码顺序正确。

**enum**
- `Scan`/`UnmarshalJSON` 走白名单（`"ADMIN"`、`"root"` 均拒）；`Value()`/`MarshalJSON()` 对非法值拒绝落库/下发；11 类审计操作类型齐备，与分层 §九 的 9 个 service 写入方对照一致。

**rule/convert**
- `triggerTable` 与规格 §8.1 六行表**逐行一致**：仅 `TriggerAmountChanged` 为 `{recalc:true, adoptBase:false}`，其余重算项均 `{true,true}`，`TriggerAmortizeMonthsChanged` 为 `{false,false}`。
- 舍入基准取 `base.Scale()` 而非硬编码 2 位——正是分层 §三 问题 1 的修法；JPY 本位币下实测得整数结果且 `FitsScale(2)` 为 true。
- 汇率规整点唯一（T39）：「先 `RoundRate()` 再乘」与 convert 输出一致；极小汇率规整后为 0 时有二次判正。

**rule/amortize**
- 「份额之和 == 原金额」，尾差归末月不轮转：`100.00/3` → `33.33/33.33/33.34`（与被否决的 go-money 方向相反，符合 §8.2）；负金额对称；JPY 0 位 `1400/3` → `466/466/468`；m=1/2/7/1200 全部守恒。
- 「原币与本位币各自独立均分」成立：CNY 100.00 与 JPY 1400 摊 3 月，两侧位数不同且各自独立守恒——正是分层 §六 强调「用其中一个去推另一个必然错」的场景。

**rule/dedup**
- 键为四元组「(归属用户ID, 支出日期, 金额, 币种)」，与规格 §8.3 一致；金额取 `String()` 故 `100.50`/`100.5`/`100.500` 归同一键；跨用户不比对、本批互查、编辑态 `ExcludeID` 排除自身（D-6）全部正确。

**rule/passwd、errs、idgen、pwdhash、config、log、entity**
- `passwd.Check` 长度按 `RuneCountInString` ≥ 10 + 至少两类字符；`Generate` 生成后**再跑一遍 `Check` 自校验**。
- `errs`：`Wrap(nil)` 返回 nil、非法 kind 兜底 `KindInternal`、`Params()` 返回副本（实测外部篡改不影响内部）。
- `config` 对 `TokenSecret`/`FxRateSecret` 脱敏为「已设置(N字符)」；`log.PrintAdminInitPassword` 是全系统唯一打印明文处（A-3）。
- `entity.User` 的 JSON 不含密码哈希与盐（实测）。
