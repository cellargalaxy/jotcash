**承载原文**（分层 §六 L2 表 `rule/amortize` 行）——本包职责的唯一定义：

> **不变式 1b 的唯一实现处**：起止月派生（`起始月 = 支出日期所属月`、`结束月 = 起始月 + 月数 − 1`）；8.2 摊分：**按币种小数位数均分**（原币按支出币种、本位币按本位币，均**不是**存储用的 2 位）、**尾差归末月**、原币与本位币各自独立均分、负金额对称处理；**H-4 的「覆盖月份区间 + 每月分摊金额」派生输出**，同时是 J 域摊分口径份额的唯一来源
> 依赖：`entity`、`currency`、`base/calendar`

四项职责逐一落到代码，见 §三。

### 二、选型：不引第三方库，理由是实测而非偏好

prompt 要求「优先采用 github 上成熟稳定 star 多的代码库」。调研了 4 个候选，**结论是不引入**，但底层算术**已经**下沉给第三方（经 `base/decimal` 用 `shopspring/decimal` 1.4.0，7470★）。本包只做业务口径决策。

| 候选 | ★ | 有无「均分 + 尾差」能力 | 否决理由 |
|---|---|---|---|
| `Rhymond/go-money` | 1912 | 有：`Split(n)` / `Allocate(rs...)` | **尾差分配规则与 8.2 相反**，见下 |
| `bojanz/currency` | 644 | 无均分 API | 已在 `currency` 那一轮被否决为运行时依赖（`Register` 改包级 map、与读并发即 DATA RACE），不重新引入 |
| `govalues/decimal` | 248 | 无均分 API | 只是算术内核，替代的是 `base/decimal` 而非本包；且默认银行家舍入 |
| `shopspring/decimal` | 7470 | 无均分 API | **已在用**（`base/decimal` 的内核） |

**否决 `go-money` 的实质理由**——读其 `money.go` 源码（`Split`/`Allocate`）：

```go
// Split：余数轮转分给最前面的几方
r := mutate.calc.modulus(m.amount, int64(n))
for p := 0; l != 0; p++ { ms[p].amount = add(ms[p].amount, v); l-- }
```

它把尾差**轮转分给前 N 方**（注释原文：`parties listed first will likely receive more pennies`），而 8.2 要求**尾差固定计入末月**。两者对 `100.00 / 3` 的输出分别是 `33.34/33.33/33.33` 与 `33.33/33.33/33.34`——数值都平，归属月份不同，直接影响 J-1 月度总额与 J-6 未来待摊分段。这个差异无法通过配置消除，只能改库。

其余三条同 `rule/convert` 的记录：币种表必须来自本仓库 `currency.Code.Scale()`（已按 CLDR 48.2.0 校验，IDR 刻意取账面位数 2）；`go-money` 自带币种表会形成第二个位数来源；`Money` 内部是 `int64` 最小单位，与本仓库 `decimal.Decimal` 的定点表示往返需再写一层转换，反而增加失配面。

**结论**：本包约 3 行核心算术（`QuoRem` 取商与余 → 尾差加到末月），引库的收益为负。

### 三、方案：四项职责 → 三个类型

#### 模块职责与输入输出

| # | 承载职责 | 实现 | 输入 | 输出 |
|---|---|---|---|---|
| 1 | 不变式 1b 起止月派生 | `Derive` | 支出日期、摊分月数 | `calendar.MonthRange` |
| 2 | 8.2 单币种均分 + 尾差归末月 | `NewShares` / `Shares` | 总额、月数、币种 | `Shares`（O(1) 存储） |
| 3 | H-4 覆盖月份区间 + 每月分摊金额 | `NewSchedule` / `Schedule.Rows` | `Input` 六元组 | `[]Row{月, 原币份额, 本位币份额}` |
| 4 | J 域摊分口径份额的唯一来源 | `Schedule.At` | 目标月 | `Row`, `bool`（O(1) 查表） |

#### 关键设计取舍（5 条）

**取舍 1：不收 `entity.Expense`，收最小入参**——与 `rule/convert` 同一手法。
承载的依赖列写着 `entity`，但**前提 6** 规定摊分起止月是只读派生项、无人工指定入口。若签名收 `Expense`，传进来的 `AmortizeStart`/`AmortizeEnd` 在语义上就是「存在却必须被无视」的字段，迟早有人当它有意义。收最小入参则这两个字段根本不在入参里（准则 6「结构缺席 > 运行时忽略」）。
副作用：本包实际依赖收敛为 `currency` + `base/calendar` + `base/decimal`，**不依赖 `entity`**，比承载允许的边界更窄。字段装配由 `service/expense`/`service/intake` 完成。

**取舍 2：`Shares` 用 O(1) 存储，不预先展开数组**——这条由 H-1「摊分月数无上限」倒逼。
一笔 600 个月的支出，若 J 域每次穿刺都展开 600 个 `decimal.Decimal` 只为取其中 1 个月，代价与月数成正比。而摊分的数学结构决定了只有两个不同值：前 N−1 月都是商，末月是商 + 尾差。故 `Shares` 只存 `{月数, 商, 尾差, 总额, 币种}` 五个字段，`At(i)` 是一次比较加一次可能的加法。
`Rows()`（H-4 全量展开）仍然提供，但只在真的要逐月展示时才付出分配代价。上界由 `calendar` 的年份上限兜住（实测 2026-01 起最多 95688 个月到 9999-12）。

**取舍 3：总额位数超过币种位数时报错，不静默舍入**——本轮实测发现的静默出错路径，见 §四。

**取舍 4：币种零值必须显式拦下**——`currency.Code.Scale()` 对零值返回 0，与 JPY 的 0 位**无法区分**（该方法注释明写「调用前须先判 IsZero」）。实测放行的后果：`712.35` 被按 0 位均分成 `237/237/238.35`，钱的形态整个变了且不报错。故 `ErrCurrencyEmpty`。同 `rule/convert` 的 `ErrBaseCurrencyEmpty`。

**取舍 5：错误是哨兵，不选 `base/errs` 档位**——同 `base/decimal`、`base/calendar`、`currency`、`enum`、`rule/convert`。同一个「摊分月数非法」经 dto 进来是用户输入错误，经 J 域统计出现则是数据损坏（库里存了非法月数），本包无从判断被谁调用。故 **不 import `base/errs`**。

#### 异常处理（6 个哨兵）

| 哨兵 | 触发条件 | 不拦的后果 |
|---|---|---|
| `ErrMonthsNotPositive` | 摊分月数 < 1 | `QuoRem` 除零；`shares[months-1]` 越界 panic |
| `ErrCurrencyEmpty` | 币种为零值 | 静默按 0 位均分，见取舍 4 |
| `ErrAmountScale` | 总额位数 > 币种位数 | 末月份额突破币种位数，见 §四 |
| `ErrSpendDateEmpty` | 支出日期为零值 | `calendar` 会报 `ErrMonthValue`，但语义指向「月份超出 1~12」，与真实原因不符 |
| `ErrShareIndex` | `At(i)` 下标越界 | 越界 panic |
| （透传） | 结束月越界 9999 | `calendar.ErrYearRange`，不重新包装 |

### 四、实测发现：一条静默出错路径（本包拦下，非依赖包 bug）

用探针跑 `QuoRem` 的语义边界，发现**当总额的小数位数多于币种小数位数时，末月份额会突破币种位数**：

| 总额 | 月数 | 币种位数 | 商 | 余 | 末月 = 商+余 | 末月合规 |
|---|---|---|---|---|---|---|
| `100.00` | 3 | 2 (CNY) | 33.33 | 0.01 | **33.34** | ✓ |
| `1400` | 3 | 0 (JPY) | 466 | 2 | **468** | ✓ |
| `100.005` | 3 | 2 (CNY) | 33.33 | 0.015 | **33.345** | ✗ 3 位 |
| `1400.5` | 3 | 0 (JPY) | 466 | 2.5 | **468.5** | ✗ 1 位 |

**定性：这不是 `base/decimal` 的 bug。** `QuoRem` 的契约是「商 × 除数 + 余 = 被除数」，三例全部满足；`base/decimal` 的 `TestAmortizeChain` 也只用位数已对齐的总额做用例。真正的问题是**没有任何一层校验过「`Expense.Amount` 的位数是否与 `Expense.Currency` 的位数相符」**——`decimal.Parse` 放行到 18 位，parser 从账单读到的金额位数不受约束。

**处置：在本包入口拦下并报 `ErrAmountScale`，不静默舍入。** 舍入会改钱（`100.005 → 100.00` 丢掉 0.005）；放行会让末月份额落库时被 2 位定点列截断，错误发生在离出错点很远的地方。报错是唯一不改钱又不留隐患的选择。这与 `rule/convert` 拒绝 3 位本位币（`ErrBaseCurrencyNotCandidate`）是同一条取向：**本该不可能，发生了就必须响亮失败**。

### 五、依赖包 bug 排查：未发现本包路径上的 bug

prompt 要求「如果依赖的代码有 bug，也需要进行修复」。用 4 组探针 + 2 组属性测试（共 30 万次随机用例）扫了 `base/decimal`、`base/calendar`、`currency` 在本包路径上的行为，**未发现需要修复的 bug**，故本轮**未改动任何既有文件**。排查记录如下，供复核：

| 探查项 | 方法 | 结论 |
|---|---|---|
| `QuoRem` 恒等式与符号 | 20 万次随机（金额 × 月数 1~600 × 位数 {0,2,3}） | 恒等式 100% 成立；余数恒与被除数同号，负金额天然对称 |
| `MonthRange` 逆运算 | 10 万次随机（年 1~9999 × 月数 1~1200） | `Len() == count`、`Months()` 首尾与端点一致，无偏差 |
| `AddMonths` 整数溢出 | `MaxInt`/`MinInt`/`1<<62` | 全部被 `ErrYearRange` 拦下。手工推演两次补码回绕：正溢出落入 `[-2^63,-1]`，`seq/12 ≤ 0`；负溢出不可达（`m.seq + MinInt64 > -2^63`）。**无可达的溢出穿透** |
| 月区间上界 | 二分搜索 | 2026-01 起最大 95688 个月（到 9999-12），越界报 `ErrYearRange`，与 H-1「无上限」的实际边界一致 |
| `LastDate` 世纪边界 | 9999-12 / 闰年 2028-02 | 分别得 9999-12-31 / 2028-02-29，未越界 |
| 零值传播 | 零值 `Date`/`Month`/`Code` | 均返回可判定的零值或错误，无 panic |
| 巨额 + 巨量月数 | `9999999999999999.99 / 95688` | 求和仍精确等于原额 |

**一处记录但不修的观察（不在本包路径）**：`decimal.Round` 舍入后不复查量级——`Round(9999999999999999.99, 0)` 得 `10000000000000000`（17 位），超过 `MaxIntDigits = 16`。该方法由 `rule/convert` 调用（本包不调用 `Round`），且 `rule/convert` 正由并行轮次实现。属**待确认**，本轮不越界改动，登记在此供该轮或后续轮次判断。

### 六、对现有链路的副作用

**无。** 纯新增包（`internal/rule/amortize/`），未改动任何既有文件，未新增第三方依赖（`go.mod` 不变），既有 10 个包测试无回归。

**性能**：`Derive` 与 `NewShares` 均为 O(1)，无分配（`Shares` 是值类型）。`Rows()` 是唯一的 O(月数) 分配点，只在 H-4 逐月展示时调用。J 域穿刺走 `At()`，O(1)。

**对下游的约定**（已写进对应符号的注释）：
1. `Schedule` 的两个 `Shares` **各自独立均分**——原币按 `Currency`、本位币按 `BaseCurrency`，两者位数可以不同（如 CNY 支出折算到 JPY 本位币）。不得用一个的份额去推另一个。
2. 不变式 1b 与 1a **必须在同一次保存内一并调用**（分层 §九 不变式 1b 行）：8.1 第 3 行「改支出日期」同时触发两者。本包只管 1b。
3. **准则 7**：L6 不得跨层直接调本包，H-4 预览须经 `service/expense` 暴露的派生入口转调。
