# entity 包实现（对话1）

## 一、结论

**无阻塞性问题，已完成代码编写。**

`internal/entity` 按分层设计 §六 L1.1 落地：5 个实体、62 属性、**零方法**、零函数、零包级变量与常量，`go doc -all` 实测「0 functions」、`go test -cover` 实测「no statements」——它是一个纯声明包。

三项前置判断先行说明：

| 判断 | 结论 | 依据 |
|---|---|---|
| 是否引入第三方库 | **不引入**，仅用标准库 `time` + 仓库内 4 个包 | 见 §三 |
| 是否有阻塞性问题 | **无** | 见 §四，1 项「待确认」不阻塞实现 |
| 62 属性如何锁死 | 三向点算 + AST + 反射，共 18 个顶层用例 / 67 个子测试 | 见 §六 |

规模：生产 747 行（6 文件）/ 测试 1424 行（2 文件）。**生产代码里没有一行可执行语句**，因此本轮的质量保证完全落在「字段形状是否正确」上，而这一点覆盖率无法度量——故采用 11 项变异测试逐条验证断言有刃（§六 3）。

## 二、依据来源与承载边界

本包承载的内容逐字来自分层设计 §六 L1.1 表 `entity` 行：

> 5 实体 62 属性的结构体定义（User 15 / ExpenseCategory 5 / Expense 22 / File 11 / AuditLog 9），**零方法**；币种、角色、状态、操作类型等字段直接用 L1.0 的枚举类型，金额与汇率用 base/decimal、日期与年月用 base/calendar，不用裸 string

62 项属性的**字段名、类型、顺序**逐项对应终版《记账系统功能与模型》§四 1~5 的五张属性表，无一项增补或省略。三段分组（Expense 的可编辑 8 / 只读派生 4 / 系统只读 10）来自终版 F-1、F-2 与 §四 3 的可写性标注。

依赖恰为 4 个仓库内包，与 §六 L1.1 依赖列逐字一致：`currency`、`enum`、`base/decimal`、`base/calendar`（+ 标准库 `time`）。**刻意不依赖** `base/errs`（零方法即无错可返）与 `base/idgen`（标识由 service 生成后赋值，本包只声明 `int64`）——由 `TestDependencyBoundary` 以 AST 扫描双向锁死（越界报错 + 依赖未用也报错）。

prompt 要求「优先采用 github 上成熟稳定 star 多的代码库」。已实测查询候选库的当前 star 与维护状态：

| `go-playground/validator` | 20.1k | 2026-09-03 | 标签驱动校验。本包**不做校验**：合法性由字段类型自身保证（`currency.Code` / `calendar.Date` / `calendar.Month` 私有字段 + `Parse` 构造），加它等于在 L1.1 开第二处校验入口，违反准则 1 |

**根本原因**：L1.1 的产出是 62 个字段声明，其全部价值在于「字段名、类型、可空语义是否与终版 §四 逐项吻合」。这是一份**领域契约的转录工作**，不存在可复用的算法或数据结构，任何库都无法代劳；引入库只会把库的抽象（标签、DSL、生成器）叠加到契约上，让契约变得间接。

对照参考：`currency` 用了 `pkg/errors`（现已按上一轮复查改回标准库），`base/decimal` 自建定点数而未用 `shopspring/decimal`，`base/pwdhash` 用了官方 `golang.org/x/crypto/argon2`——**该用则用**。本包属于确实无可用之处的一类。

## 四、方案取舍

### 1. 零值表达「不适用」，全包无一个指针字段

终版 §四 表头定义「业务上「不适用」的场景以零值表达，不留空」。9 个可空属性（Expense 的 `Counterparty` / `Remark` / `CategoryID` / `SourceFileID` / `BankName` / `CardLast4` / `CardCurrency` / `DeletedAt`，File 的 `Password`）一律用零值。

取舍的实质是「取值前是否必须判空」：全值类型后 `var e Expense` 即是可用的空明细（D-4 手工录入行、F-8 复制初值的起点），任何字段可直接访问而不 panic。用指针则每个消费方都要判空，**漏写不报错**，只在某条没有对手方的明细上突然崩掉。

唯一豁免 `File.Content []byte`：其 `nil` 与空切片有**不同语义**——§六 L3 定死「File 元信息与二进制内容分接口」，故 `nil` 表示「只查了元信息、内容未加载」，`len==0` 且非 nil 表示「确实是零字节文件」。这条差异写进了该字段注释，并在 `TestNoPointerField` 中作为唯一白名单。

### 2. 三处刻意不加标签

- **不加 db / gorm 标签**：列名、列类型、NULL 口径归 store/sqlite（§六 L4「唯一知道 SQL 的地方」）。在 L1.1 写列名 = 换存储引擎要改 L1.1。
- **不加 json 标签、不作 JSON 契约**：§六 L6 定死「dto **不复用 entity 结构体**」，前提 6 正是靠「只读派生字段在写请求 dto 里根本不存在」守住的。
- **不定义 `Expenses []Expense`**：集合类型的价值在于挂方法，而本包零方法；排序归 store 的 `ORDER BY`（F-3）、筛选归 store 的查询条件（F-4）。

**唯一例外**：`User.PasswordHash` 与 `User.Salt` 上的 `json:"-"`。它是密码红线（§九「连三类出口都不得出现」）的兜底而非契约声明——三处裁剪都是「记得做才有效」的运行期约定，`json:"-"` 让「万一有人直接 `json.Marshal(entity.User)`」这条路径也漏不出去。`TestConsumerDtoPasswordRedline` 的第 4 个子测试把「除这两处外全包无任何标签」也锁死了。

反向确认 `File.Password` **刻意不加** `json:"-"`：K-3 明写「File 的 文件内容 与 文件密码 照导」，加了会与终版导出口径直接冲突。这一条也有对应断言。

### 3. `AuditLog` 的归属字段命名为 `UserID` 而非 `OwnerUserID`

另外 3 个归属实体统一用 `OwnerUserID`，`AuditLog` 独用 `UserID`。这不是不一致，而是终版 §四 5 的语义要求：

> **登录失败记录中它表示被尝试账号的归属，不代表操作人身份**（尝试者不可知，不留字段）

即该字段在 11 类审计中并非纯粹的「归属」，叫 `OwnerUserID` 会掩盖这条例外。`TestConsumerStoreOwnership` 的表格显式记录了这一差异及其理由。

### 4. `Language` 用裸 string——全包唯一一处，理由是依赖方向

终版 §四 1 定义它是「语言配置文件的键」，本该有取值域；但语言集由 `i18n` 持有，而 `i18n` 在 L3，本包（L1.1）import 它会**反向依赖成环**（§七 依赖图无 L1.1 → L3 的边）。

故用 `string`，合法性由 `service/preference` 调 i18n 的语言键校验兜住（§六 L5.4：「界面语言走 i18n 语言键校验，两者都不接受任意值」）。这与 `currency.Code` 的「反序列化即校验」形成对比，**差异纯粹来自依赖方向，不是口径不一致**——已写入该字段注释与包注释。

### 5. 已登记的残留：`%+v` 会打出密码哈希与盐

零方法约束使本包无法像 `base/config` 那样用 `String()` 做脱敏，因此 `fmt.Sprintf("%+v", user)` 或 `logrus.Fields{"user": user}` 会把密码哈希与盐打进日志。JSON 一侧已由 `json:"-"` 兜住，**日志一侧无编译期兜底**，只能靠约定：L5 与 L6 一律不整体打印 `entity.User`，需要时只打用户ID 与用户名。

这与 §四 的 R1/R2/R3 同类——Go 的机制修不掉，登记后靠评审守住。已写入包注释末节。

### 6. 待确认项（1 项，不阻塞）

**`Language` 的默认值形态**。终版 §四 1 写「默认中文」，但未给出键的字面形式（`zh-CN` / `zh_CN` / `zh`）。本包不定义默认值（约定 8：业务默认值写死在对应包，不在 L1.1），故**不阻塞本轮**；该字面量将在 `i18n` 与 `service/preference` 那一轮确定。测试中用 `zh-CN` 仅作占位，不构成对键格式的断言。

## 七、对下游的影响与后续

**对现有链路无影响**：纯新增包，未改动任何既有文件，未引入依赖，既有 9 个包测试无回归。

**下游需要注意的 3 点**（均已写入对应字段注释）：

1. **`AuditLog.ObjectType` 的零值是合法业务取值**。11 类审计中有 5 类（登录 / 数据入库 / 批量删除 / 本位币重算 / 数据导出）就该落零值，故判定须写 `t.IsZero() || t.Valid()`，不能只写 `Valid()`。
2. **`Expense` 不可用 `==` 比较**（含 `decimal.Decimal`，刻意不可比较）。8.3 判重只能逐字段走 `Equal`——这是编译期保障，已在 `TestZeroValueUsable` 中反向确认该性质仍成立。
3. **14 个 `int64` 标识字段在 dto 侧必须以字符串输出**。18 位 ID 超过 `float64` 安全整数上界，经 JavaScript `Number` 往返会变成另一个数（`base/idgen` 已有实测，本包复核确认）。

**后续轮次的衔接**：本包定死了 62 个字段的形状，L2 的 3 个 rule 包、L3 的 store 接口、L6 的 dto 都以它为输入。若后续轮次发现某字段类型需调整，`field_golden_test.go` 会作为第一道拦截——它的失败信息直接指向终版的对应章节，便于判断是「定义错了」还是「消费方用错了」。
