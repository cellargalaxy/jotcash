### 2.2 承载边界：本包**不做**什么

- **不做模糊匹配**。E-1 是「等值匹配」，金额差一分、日期差一天都不是重复。
- **不查库、不落库、不打日志**（L2 纯逻辑层）。`TestNoIODependency` 锁死。
- **不碰 `time`**。判重必须是纯函数——引入时间会让同一份账单今天报重复、明天不报，
  且不会有任何报错。`TestNoTimeDependency` 锁死。
- **不判定哪条该保留、不自动去重**。`TestNoDispositionAPI` 用命名扫描拦截
  `Remove/Filter/Merge/Dedupe/Drop/Reject` 等处置动词出现在导出面上。
- **不校验业务合法性**。空币种、零日期由 dto 与 service 拦截；本包一视同仁地
  算键分组（零值自成一组）。在此报错等于开第二处校验入口。

### 2.3 未决问题的定夺：「在库且未删除」的过滤职责

**决定：落在 store 侧，本包不再兜一道 `DeletedAt.IsZero()`。**

依据是分层 §六 L3 store ④ 已把「取回**在库未删除**候选」写进 store 的口径。
若本包再过滤一次，比对范围就有了两处实现，两处口径将来必然漂移——典型症状是
一处改了软删语义而另一处没改，判重范围悄悄变化且无人报错。

这个分工用 `TestCandidatesRangeIsCallerDuty` 正面钉住：传入一条已删除明细，
本包照样比对（这不是缺陷，是分工的直接后果）；同时用 AST 扫描确认源码里
没有任何 `DeletedAt` 的**字段引用**。

> 实现细节：这条断言最初写成原文匹配 `strings.Contains(src, "DeletedAt")`，
> 结果把包注释里「为什么不过滤 DeletedAt」那段解释也判为违规——那会逼着后来人
> 删注释来让测试通过，恰好抹掉设计理由。改为扫 AST 的 `SelectorExpr`。

### 2.4 未决问题的定夺：是否显式 import `calendar`/`decimal`/`currency`

**决定：不显式 import，依赖列保持 `entity` 一项。**

四要素的类型由 `entity.Expense` 的字段自带，本包只调它们已有的 `String()`，
不需要三个包的任何包级函数。显式 import 会让依赖列从 1 项虚涨到 4 项，
掩盖真正的耦合面。`TestDependencyBoundary` 双向锁死：表外 import 失败，
表内列了却没用到也失败（防依赖列虚高）。

测试文件不受此限——构造用例需要 `calendar.MustParseDate` 等构造器。

## 三、第三方库评估

prompt 要求优先采用成熟稳定的库。**结论：不引入任何第三方库**，用标准库 `map`
加自建规范键。以下 star 数与最近推送时间均为 2026-09-07 经 GitHub API 实测，
非凭印象：

| 库 | star | 最近推送 | 不采用的理由 |
|---|---:|---|---|
| `samber/lo` | 21428 | 2026-09-07 | `GroupBy`/`UniqBy` 只能省掉三五行 for 循环，却要为 L2 纯逻辑层引入仓库内其他包都未使用的依赖 |
| `emirpasic/gods` | 17464 | 2025-03-12 | 提供的是树/堆/集合等容器，本包需要的 `map[string][]T` 标准库已足够 |
| `golang/groupcache` | 13336 | 2024-11-29 | 分布式缓存，与「一次请求内的分组」不是同一问题 |
| `thoas/go-funk` | 4931 | 2024-07-24 | 反射式函数库，性能与类型安全均劣于泛型；同上，收益仅为省几行循环 |
| `google/go-cmp` | 4676 | 2026-06-18 | 官方明确不建议用于生产判等，只作测试比较 |
| `cespare/xxhash` | 2141 | 2024-07-03 | 哈希只是加速手段，仍需处理碰撞回退到逐字段比较；当前规模（一次导入数百行）用不上 |
| `elliotchance/pie` | 2038 | 2025-12-22 | 同 `lo`，收益不足以抵消依赖成本 |
| `mitchellh/hashstructure` | 763 | 2023-01-03 | **已归档**；且反射式哈希会把 `Amount` 按内部表示参与，`1.50` 与 `1.5` 会算出不同哈希——正好踩中本包必须避免的坑 |
| `dgryski/go-metro` | 119 | 2025-01-06 | 同 xxhash，且体量与维护度更低 |

**关键判断**：本包的实质是「按四要素建索引 + 分组求交」，标准库 `map` 就是
最直接的表达。而 `hashstructure` 这类「看起来最贴合」的库恰恰是最危险的——
它对 `decimal.Decimal` 的反射式哈希会按内部表示（`coeff`/`exp`）计算，
`Parse("1.50")` 与 `Parse("1.5")` 内部表示不同，会被判为不同的哈希，
导致**静默漏判重复**。

这与仓库既有做法一致，不是一味排斥第三方库：`base/decimal` 采用了
`shopspring/decimal`、`base/pwdhash` 采用了 `golang.org/x/crypto/argon2`、
`currency` 把 `bojanz/currency` 降为 test-only 交叉校验依赖——该用则用。
本包属于「确无可用之处」的一类。

## 四、方案取舍

### 4.1 用规范键索引，而非两两比较

朴素实现是双重循环逐对 `Equal` 比较，O(n×m)。本包改为按四要素算一个规范
字符串键、用 `map` 分组，整体 **O(n+m)**（三趟线性扫描）。一次银行账单导入
常有数百行，库内同期候选也是同一量级，平方级比较在预览页上是可感知的等待。

这一步依赖一条**必须先证实**的性质：

> `decimal.Decimal` 的 `String()` 是数值的规范形式，即
> `a.Equal(b)` 当且仅当 `a.String() == b.String()`

若该性质不成立，两笔金额相等的重复账会因为文本不同而落进不同的 map 桶，
**静默漏判**——没有任何报错。这是本包最关键的一条前置验证，见 6.1。

### 4.2 为什么金额键用 `String()` 而非定点文本

这是本轮最实质的一处取舍，也是依赖侧缺陷的成因。

`StringFixed(n)` 要求先定位数。而 8.3 的「支出金额」是**原币**金额，
其小数位数**随支出币种而定**：`currency` 表中 KWD 是 3 位（该表刻意保留 KWD，
正是为了让「支出币种不受本位币候选限制」这条规则可被测试），JPY/KRW/VND 是 0 位。
`BaseAmountStoreScale = 2` 是**本位币**的存储位数，不适用于原币金额。

实测：`StringFixed(2)` 对 `0.001` / `1.234` / `100.505` 一律返回
`ErrPrecisionLoss`（「值 0.001 需 3 位, 目标 2 位」）——用 KWD 记的账
**根本生成不出判重键**。而 `String()` 已剥掉尾随零，对任意位数都成立。

### 4.3 为什么不用结构体作 map 键

`decimal.Decimal` 刻意不可比较（内嵌零宽 `noCmp`），因此 `entity.Expense`
整体不可比较，`map[entity.Expense]T` 与 `a.Amount == b.Amount` 都是**编译错误**。
这是好事：它在编译期就拦下了「用 `==` 比金额」这个会导致 `1.50 vs 1.5` 漏判的写法。

本包的键是 `string`，绕开这一限制的同时**保持了 `Equal` 的语义**——这正是
4.1 那条性质的价值所在。而导出的 `Key` 结构体四个字段全部可比较（金额已转为
规范文本），故 `Key` 本身可作 map 键，供 store 侧去重查询条件。

### 4.4 分隔符取 U+001F 而非逗号

四要素中没有自由文本字段（日期定长 10、币种定长 3、金额只含数字与 `.` `-`），
任何可打印字符都不会被取值本身包含。选控制字符是为了让这条性质**对将来也成立**：
若哪天有人往键里加了自由文本字段，用逗号会立刻产生歧义。

分隔符本身也不是可有可无的——无分隔符时「用户110 + 金额0.5」与
「用户1 + 金额100.5」都拼成 `1100.5`，两笔毫不相干的支出会被判为重复。
`TestKeySeparatorNoCollision` 用这一对取值把它钉死。

### 4.5 两类冲突分开返回，不合并

D-6 对二者的展示形态不同：库内冲突要并列展示那条**已入库明细**，
批内冲突指向**同批的另一行**；「取消勾选」的处置方式也不同。合并成一个集合
会让前端无法区分。故 `Conflict` 用 `InStore` 与 `InBatch` 两个字段，
并额外给 `InBatchIndexes`——预览页要高亮的是「行」，仅有明细内容无法定位到第几行。

### 4.6 只含命中行的映射

`Result.Conflicts` 只放 `HasConflict()` 为真的行，调用方遍历它即是遍历
「需要高亮的行」，不必逐行判空。配套给 `RowIndexes()` 返回**升序**行号——
map 遍历顺序随机，直接遍历会让 D-6 的高亮顺序每次刷新都不同。

## 六、验证说明

### 6.1 前置验证：`String()` 确是规范键（决定算法正确性）

`TestAmountKeyIsCanonical` 用 **29 个样本 841 对穷举交叉**断言
`Equal(a,b) ⇔ a.String()==b.String()`，**0 对不一致**。

样本刻意混两条来源：`Parse` 来源 19 个（含 `100.50`/`100.5`/`100.500`/`+100.50`/`1.005e2`
五种同值写法、五种零写法含负零、负金额、`1e3`/`1000`/`1000.000`、`0.001`、`1e-8`、
16 位上界），以及**非 Parse 来源** 10 个（零值、`Sum()`、`FromInt(0)`、`Neg(0)`、
`Sub→0`、`1.5*2`、`1.55+0.45`、`Round(4)`、`FromUnits(10050,2)`）。

混入运算来源是关键：若 `decimal` 只在 `Parse` 里规范化而运算不规范化，
只测 `Parse` 发现不了这道裂缝。实测运算产物同样不带尾随零
（`1.5*2`→`"3"`、`1.55+0.45`→`"2"`、`FromUnits(10050,2)`→`"100.5"`）。

另在独立 scratch module 直接探底层 `shopspring/decimal@v1.4.0`，确认其
`String()` 走 `d.string(true)`（`trimTrailingZeros=true`，源码 `decimal.go:1908`），
且极端量级下**不退化为科学计数法**（`1e15`→`"1000000000000000"`、
`1e-18`→`"0.000000000000000001"`），排除了「大额或极小额时键形态突变」的风险。

### 6.2 变异验证：测试是否真能抓到 bug

覆盖率 100% 只说明每行都被执行过，不说明断言有效。故对实现注入 **14 处变异**，
检验测试是否失败：

| M3 | 判重键漏掉支出币种 | 被捕获 |
| M4 | 判重键漏掉支出日期 | 被捕获 |
| M5 | 不排除编辑态自身 | 被捕获 |
| M6 | 批内互查未排除自身下标（每行自报重复） | 被捕获 |
| M7 | 只查库内，不查批内重复 | 被捕获 |
| M8 | 只查批内，不查库内重复 | 被捕获 |
| M9 | `RowIndexes` 不排序 | 被捕获 |
| M10 | 两类冲突合并返回 | 被捕获 |
| M11 | `InStore` 共享底层数组 | 被捕获 |

| M13 | `HasConflict` 漏判批内冲突 | 被捕获 |
| M14 | 去掉键分隔符（串键） | 被捕获 |

**首轮 14 个变异中有 3 个存活**（M9、M11、M14），即测试写得不够。逐个查明原因后
修正测试，二轮 **14/14 全部捕获，0 存活**：

- **M9 存活**：原用例只有 3 个命中行。实测 Go map 遍历顺序虽随机，但键少时
  「恰好升序」概率很高——3 个键 75.3%、5 个键 49.6%、8 个键 12.7%、9 个键 1.1%、
  16 个键 0%。3 个键的用例对未排序实现有 75% 概率蒙混过关，会变成**间歇性失败的测试**，
  比没有测试更糟。改为 32 行中 16 个命中行 + 打乱候选顺序 + 重跑 20 次。
- **M11 存活**：原用例用 `append` 检测切片共享——`append` 在切片已满时会重新分配，
  共享的实现照样通过，**检测方向是假的**。改为直接修改元素，并补一条
  「不得与入参 `Candidates` 共享」的断言。
- **M14 存活**：原用例的样本没有一对能在去掉分隔符后真正串位。补上
  「用户110+金额0.5」与「用户1+金额100.5」这对——无分隔符时都拼成 `1100.5`。

变异测试结束后已 `diff` 确认 `dedup.go` 完整还原，无变异残留。

## 七、对下游的影响与后续

1. **store** 实现「查重候选批量匹配」时应直接用 `dedup.Keys(rows)` 拿元组集合，
   不要另写一套四要素提取——两处口径必然漂移，症状是「预览页提示重复但查不出那条明细」。
   查询条件**必须带归属用户**（前提 3）。
2. **store 需保证候选已过滤软删**（`DeletedAt` 非零者不得进入候选），本包不再兜底，
   理由见 2.3。
3. **service/intake** 拿到 `Result` 后按 `RowIndexes()` 顺序渲染，不要直接遍历
   `Conflicts`（map 顺序随机）。
4. **判重键的金额一律用 `String()`**，不要用 `StringFixed`——原币金额位数随币种而定。
   这条已在 `base/decimal` 的消费方走查里订正并加了反向断言。
5. **扩展预留**：分层 §十二 场景 A（接结构化数据源、加银行流水号）时，
   按文档是「加一条**硬去重前置**」，而非改本包的四要素——`Check` 的入参保持不变，
   在其之前插入一层按流水号的精确去重即可。
