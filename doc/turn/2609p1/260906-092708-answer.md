## 一、承载与约束的提取

### 1.1 本包必须做到的（分层 §六 L1.0 `currency` 行逐句拆解）

| # | 承载原文片段 | 落到实现上的要求 |
| - | ------------ | ---------------- |
| 1 | 「**币种枚举**：代码、名称、符号、**小数位数**、是否启用、**汇率获取实现的标识**」 | 枚举项恰含这 6 项属性，一项不多一项不少 |
| 2 | 「实现体不在此，由 `fxrate` 注册表按该标识路由」（准则 3） | 只存**标识**，不得出现任何汇率获取代码——否则 L1.0 依赖 L3 必成环 |
| 3 | 「只存代码入库」 | 需要 `driver.Valuer` / `sql.Scanner`，且落库形态就是代码本身 |
| 4 | 「提供合法性校验——应用层是唯一校验点」（终版 §五 1） | 校验必须**收敛到构造函数**，不能只出一个 `IsValid` 由各调用方自觉调用 |
| 5 | 「**另出本位币候选口径（T38）**：`可作本位币 = 已启用 且 小数位数 ≤ 2`」 | 两个判据合取，且**候选集**与**单值校验**两种形态都要有 |
| 6 | 「对外提供候选集（K-1 下拉）与单值校验」 | 候选集要有**确定顺序**（map 遍历随机，下拉每次不同即为缺陷） |
| 7 | 「**支出币种不受此限**（3 位币种仍可正常记账与摊分）」 | 「可作本位币」与「可作支出币种」是**两个独立判据**，不得合并 |
| 8 | 依赖列 `base/*` | 只准 import 标准库、第三方库与 `base/*`；**不得 import `enum` / `entity` / `i18n`** |
| 9 | 终版 I-1「枚举项只能停用不能删除（历史明细存着旧代码）」 | 「已知」与「已启用」必须是**两个不同谓词**——停用后历史明细仍须能读出来 |

## 二、方案取舍（8 项，逐项给依据）

### 取舍 1：币种数据自建枚举表，`bojanz/currency` 降为**测试期**交叉校验基准

本 prompt 要求「优先采用 github 上成熟稳定 star 多的代码库（如果有），避免自己造轮子」。实际调研并**实测**的 4 个候选：

| 候选 | star | 状态 | 是否原生支持「6 项属性」 | 判定 |
| ---- | ---- | ---- | ------------------------ | ---- |
| `github.com/bojanz/currency` | 644 | 活跃（2026-09-06 有提交），MIT，CLDR 48.2.0 | ❌ 有代码/名称/符号/小数位数，**无「是否启用」与「汇率源标识」** | **降为 test-only 基准** |
| `golang.org/x/text/currency` | 807（`golang/text` 整仓） | 官方扩展库，**但数据停在 CLDR v32** | ❌ 同上，且**数据已过时**（见下） | 不采用 |
| `github.com/Rhymond/go-money` | 1912 | 活跃，MIT | ❌ 主打 Money 值类型与分配算法，与 `base/decimal` 职责重叠 | 不采用 |
| `github.com/JohannesJHN/iso4217` | — | 仓库已迁移（API 返回 301） | — | 不采用 |

**决策依据（四条，每条都是实测结论而非文档推断）**：

1. **两个必需属性没有任何一家提供**。承载要求的 6 项里，「是否启用」（终版 I-1 的停用机制）与「汇率获取实现的标识」（准则 3 的路由键）是本系统专有语义，四家都没有。照用第三方库仍要自建一张并行表来放这两项，于是「小数位数」会出现两个来源——这正是最该避免的形态。

2. **`bojanz/currency` 的全局可变注册表是一条远程篡改路径（已实测）**。它的 `Register` 直接改包级 map，任何 import 到它的包都能把任意币种的小数位数改掉：

   ```
   实验1 Register 篡改: CNY digits 2 -> 0
   ```

   而小数位数是 8.1 折算舍入基准与 8.2 摊分均分基准（分层 §九 不变式 1a / 1b）。被改掉即全系统金额静默出错。**这与 `base/decimal` 拒绝暴露第三方库 `Div`（受包级可变量 `DivisionPrecision` 控制）是同一条取向**，不能在这里自相矛盾。

3. **`bojanz/currency` 的 `Register` 与读操作并发不安全（已实测）**。`go run -race` 下 50 个读 goroutine 与 1 个 `Register` 并发即报：

   ```
   WARNING: DATA RACE
   Write at 0x00c00011a6c0 by goroutine 56:
     github.com/bojanz/currency.Register()
         .../currency@v1.5.0/currency.go:162
   Previous read at 0x00c00011a6c0 by goroutine 35:
     runtime.mapaccess1_faststr()
   ```

   本包的读取方遍布全部 HTTP 请求协程，一旦有任何包调用 `Register`，就是一条生产环境的 data race。

4. **`bojanz/currency.IsValid("")` 返回 `true`（已实测）**。空串被判为合法币种：

   ```
   实验2 IsValid("") = true ；GetDigits("") = 0,false
   ```

   而 `Expense.支出币种` 与 `User.本位币` 都是**必填**（终版 §四）。照用其校验，「币种为空」会静默通过、随后取小数位数又失败——一个本该在入口拦下的错误被推迟到折算时才炸。

**但不采用它做运行时依赖，不等于自己拍脑袋编数据**。本包把它引为 **test-only 依赖**（生产二进制不链接，因生产代码不 import 它），在 `table_test.go` 中对全部 27 个币种逐项断言「本包的小数位数 == CLDR 48.2.0 的小数位数」。收益有三：小数位数这项「算错就静默出错」的数据有权威来源可交叉核对；CLDR 升级导致的数据漂移会由测试自动暴露；`Register` 的可变性与并发问题被隔离在测试进程内，不进生产。

> **数据分歧登记（不得默默取一方）**：`x/text/currency` 与 `bojanz/currency` 对 7 个币种的小数位数结论不同（实测 IDR / COP / PKR / MMK / LAK / MGA / MRU），其中与本包清单相交的是 **IDR**：`x/text` 给 **0**，`bojanz` 给 **2**。核查 CLDR 原始数据 `currencyData.json` 得 `"IDR": {"_digits": "2", "_cashDigits": "0"}`——即 CLDR 本身区分「账面位数 2」与「现金位数 0」，`x/text` 取的是旧版本（CLDR v32，2017 年）的 cash 口径。ISO 4217 官方对 IDR 的 minor unit 亦为 2。**本包采用账面位数 2**，依据是终版记的是银行账单流水（§一定位「以银行账单导入为主要数据来源」）而非现金找零，账面口径才是账单上的口径。`x/text` 因数据过时整体不予采用。

### 取舍 2：不提供任何注册 / 修改入口，表是编译期常量

终版 I-1 定死「新增币种须改代码，枚举项只能停用不能删除」。据此，本包的表是**包级私有、初始化后只读**的 map，且：

- **不导出 `Register` / `Set` / `Remove` 任何写入口**——提供它等于把「改代码」降级成「运行期任意包可改」，终版 I-1 当场失效；
- 表在包初始化时一次构建，此后只读，因此**天然并发安全**，无需加锁（与取舍 1 否决 `bojanz` 的第 3 条理由呼应）；
- 「是否启用」是表里的**静态字段**，改它同样要改代码并重新构建——这正是 I-1 的原意。

有回归用例 `TestNoMutationAPI` 扫描全部导出标识符，出现 `Register` / `Set` / `Add` / `Remove` / `Delete` / `Enable` / `Disable` 任一即失败。

### 取舍 3：`Code` 做成私有字段的结构体，保证「非零值必合法」

三种形态各自实测过后果：

| 形态 | 问题 |
| ---- | ---- |
| 裸 `string` | 分层 §六 L1.1 明令「不用裸 `string`」 |
| `type Code string` | 任何字符串可强转：`currency.Code("蛋炒饭")` 编译通过。校验就退化成「各调用方自觉调 IsValid」，与承载 4「应用层是唯一校验点」相悖 |
| `struct{ code string }`（**采用**） | 字段私有 ⇒ 包外无法构造非法值 ⇒ **一个 Code 要么 IsZero，要么是表内已知币种**，上层不必逐处校验 |

这与同为基础类型的 `calendar.Date`（私有 `civil.Date` 字段，「非零值必合法」）完全同构，是复用现有实现风格而非另起一套。结构体仍**可比较**（`==` 与 `map[Code]T` 都可用）——这一点与 `decimal.Decimal` 刻意做成不可比较相反，理由是币种是**标称值**：两个 Code 相等当且仅当代码字符串相同，不存在 `1.50` 与 `1.5` 那种「表示不同而数值相同」的情形。8.3 判重的四要素含支出币种，`==` 在此是正确语义。有用例 `TestCodeIsComparable` 把这条钉住。

### 取舍 4：「已知」与「已启用」分成两个谓词，`Scan` 只要求「已知」

这是终版 I-1「枚举项只能停用不能删除（历史明细存着旧代码）」的直接结构化表达。三个谓词严格分层，缺一不可：

| 谓词 | 判据 | 用在哪 |
| ---- | ---- | ------ |
| **已知** `Parse` 成功 | 在表内（含已停用） | `store` 回读历史明细（**已停用币种必须读得出来**）、K-3 导出 |
| **已启用** `Enabled()` | 已知 且 `enabled` | D-2 / F-5 新记账时选支出币种、F-4 筛选下拉 |
| **可作本位币** `CanBeBase()` | 已启用 **且** 小数位数 ≤ 2 | K-1 本位币下拉与 `service/preference` 的切换校验（T38） |

若把 `Scan` 建立在「已启用」上，则某个币种一旦停用，所有引用它的历史明细当场读不出来——F-4「显示已删除」查看、K-3 整库导出、I-7 逐笔重算（含已软删明细）三处同时失效。这条由用例 `TestDisabledCurrencyStillReadable` 覆盖。

反向的失败必须响亮：`Scan` 到**表里根本没有**的代码（意味着有人违规删了枚举项）一律返回错误，不静默降级为零值——零值意味着「未指定」，把一个有主的历史币种读成「未指定」会让该笔明细的折算基准凭空消失。

### 取舍 5：名称出「中文名 + 文案键」两件，符号直接内置

承载要求枚举项含「名称」，而终版 K-4 要求界面文案走语言配置、加语种不改代码；同时本包依赖列只有 `base/*`，**不能 import `i18n`**（L3，反向依赖成环）。三者的唯一交集：

- `Name()` 返回**中文名**，用途限定为**日志与排错**——这与 `base/errs` 的 `Kind.String()` 返回中文档位名（`用户输入错误`）是同一取向，注释中已写死「不得作为面向用户的文案下发」；
- `NameKey()` 返回文案键 `currency.name.<代码>`，供 `i18n` 那一轮在语言文件里落词、由 L6 渲染。加语种只需加语言文件，不改本包代码，K-4 成立；
- `Symbol()` 直接内置（`¥` / `$` / `€`）。符号是**语言无关**的记号，不进语言文件。

> **对 `i18n` 那一轮的契约（阶段 4 需接住）**：语言文件须包含本包 27 个币种的 `currency.name.<代码>` 键。本包导出 `NameKeys()` 返回全部文案键，供那一轮做穷尽性校验，避免漏词。

### 取舍 6：汇率源标识本轮定为单一默认值，机制先行、取值域后定

分层 §六 L4 写明「`fxrate/<源>` 的具体包名随汇率源选定后确定」，§十二 亦将汇率源选型登记为不影响分包的未结项；`configs/jotcash.example.yaml` 的 `fx_rate_endpoint` / `fx_rate_secret` 两项当前留空并注明「汇率源尚未选定」。故：

- 本包定义 `RateSource` 类型与 `RateSourceDefault` 常量，**27 个币种当前一律指向它**；
- `fxrate` 的注册表路由机制因此已经成立（它按 `Code.RateSource()` 取实现），选定具体源后**只需改表中该列的取值**，不改任何签名；
- 这**不是阻塞项**：分层 §四 已判定「阻塞性问题：无」，且本包的形状不随取值域变化。已在 §五 登记为「待确认（非阻塞）」。

### 取舍 7：币种清单取 27 个常见币种，但代码不假设「小数位数只有 0/2」

T38 写明「本仓库中长期只实现常见场景币种」。清单以个人记账真实场景为准（人民币 + 主要外币 + 亚太常用），并**刻意保留 KWD（3 位）**——它是「支出币种不受本位币候选限制」（承载 7）这条规则唯一可被测试的载体，删掉它这条规则就无从验证。

一处实测事实需要记录：CLDR 48.2.0 全部 165 个币种的小数位数分布为 **0 位 17 个 / 2 位 139 个 / 3 位 7 个 / 4 位 2 个**，**不存在 1 位小数的币种**。而 `base/decimal` 的注释与 T38 均按「本位币小数位数 ∈ {0,1,2}」表述。二者不冲突——`{0,1,2}` 是判据的**值域上界**，`{0,2}` 是当前数据的**实际取值**。本包的代码与测试一律按值域写（不硬编码「非 0 即 2」），否则将来 CLDR 若出现 1 位币种，本包会静默走错分支。4 位的 CLF / UYW 是记账单位（fund）而非流通货币，不纳入清单。

### 取舍 8：小数位数对外类型取 `int32`，与 `decimal.Round` 的参数类型对齐

`bojanz` 用 `uint8`，CLDR 原始数据是字符串。本包对外出 `int32`，理由是唯一的两个消费方 `rule/convert` 与 `rule/amortize` 拿到它以后立刻要喂给 `decimal.Round(scale int32, mode)` 与 `QuoRem(divisor, scale int32)`。出 `uint8` 会让每个调用点写一次 `int32(...)` 转换——转换写多了迟早有人写成别的类型，而位数写错就是金额算错。类型直接对齐可让这类错误在编译期消失。

## 三、模块职责与 API 形状

### 3.1 文件划分（3 个实现文件 + 4 个测试文件）

| 文件 | 职责 |
| ---- | ---- |
| `currency.go` | 包注释、`Code` 类型、哨兵错误、构造与解析、6 项属性访问器、三个谓词 |
| `table.go` | 27 个币种的枚举表（唯一的数据来源）、`RateSource` 类型、可测的构建自检 `buildTable`、包初始化 |
| `codec.go` | `MarshalJSON` / `UnmarshalJSON`（dto 契约）、`Value` / `Scan`（store 落库） |
| `currency_test.go` / `table_test.go` / `codec_test.go` / `consumer_check_test.go` | 分别覆盖类型行为、表数据（含 CLDR 交叉校验）、编解码往返、6 个下游消费方走查 |

### 3.2 对外 API（全集）


### 3.3 关键逻辑与异常分支

| 场景 | 处理 |
| ---- | ---- |
| `Parse` 收到未知代码 | 返回 `ErrUnknownCode`，**不做大小写归一**（理由见下） |
| `Parse` 收到空串 | 返回 `ErrEmptyCode`（与未知代码分档，便于 L5 给不同文案） |
| `ParseBase` 收到已知但非候选的代码（如 KWD） | 返回 `ErrNotBaseCandidate`——**这正是 T38④「非候选一律拒绝」的落点** |
| `Scan` 收到 NULL / 空串 / 空字节 | 回到零值（「未指定」，用于 `卡片币种` 解析不出的场景） |
| `Scan` 收到表里没有的代码 | 返回错误（响亮失败，见取舍 4） |
| 零值调用任一属性访问器 | 返回该类型零值（`""` / `0` / `false`），**不 panic**——实体以零值创建，上层不应被迫先判空 |

**不做大小写归一**（`cny` 不被接受）：本包的输入来自 JSON 契约、URL 参数与库中已落的代码，三者都是机器生成的规范形态。放行 `cny` 会让同一币种出现多种文本写法，`store` 的分组聚合（J-4 币种维度统计）与 8.3 四要素判重就不再能按字符串比对。这与 `calendar` 拒绝 `2026-1-2`、`idgen.ParseString` 拒绝 `007` 是同一条取向。

### 6.2 三处复核结论（实施中新发现，已并入代码）

1. **`Scale()` 的零值返回 0 有歧义风险**。0 既是「JPY 的小数位数」也是「零值 Code 的返回」。若 `rule/convert` 拿一个零值 Code 去做舍入基准，会静默按 0 位舍入——把 `712.35` 舍成 `712`，钱少一截且无任何报错。**处理**：`Scale()` 保持返回 0（不 panic，符合「零值可用」），但在 `consumer_check_test.go` 中钉死消费方契约——`rule/convert` / `rule/amortize` 取位数前**必须先判 `IsZero`**，并在 `Scale()` 的注释中写明这条前置要求与后果。这是本轮唯一一处「靠约定 + 用例兜底」的地方，成因与分层 §四 R1~R3 同类（Go 的类型系统无法表达「非零值才可取位数」）。

2. **本位币候选集与 `base/decimal` 的存储精度必须闭合**。T38 的全部意义在于让「按本位币位数算出的金额」能被 2 位定点列无损容纳。**处理**：`consumer_check_test.go` 中对全部候选币种逐个断言 `decimal.MustParse(...).Round(c.Scale(), RoundHalfUp)` 的结果满足 `FitsScale(decimal.BaseAmountStoreScale)`，把这条前提变成可执行断言而非文档承诺。**这是本包与 `base/decimal` 之间唯一的语义耦合点，现已被机器锁死。**

3. **本包最终无需 import `base/*`**。承载依赖列写的是 `base/*`（普遍依赖口径），但实际实现下来：小数位数只是个 `int32` 常量、错误用哨兵表达（与 `base/decimal` / `base/calendar` 同为 L0 风格的取向，且本包位于 L1.0，其错误同样由上层映射到 `base/errs` 五档）。**故本包实际零仓库内依赖**，比承载要求更收敛，不构成违反。已由 `TestConsumerNoUpwardDependency` 用 AST 扫描生产代码的 import 钉死，并经 `go list -deps` 实证。测试文件中 import `base/decimal` 仅用于复核 2 的走查，不进生产依赖。

4. **编码中被测试抓到的两处自身缺陷**（记录在此，因为它们正是「验证要用可能失败的动作」的实例）：
   - `TestNoMutationAPI` 初版用**前缀匹配**判定修改入口，把只读访问器 `Enabled()` 误判为 `Enable` 的写入口而失败。修正为「完整单词 + 后接大写」的判据，并给判据本身加了正反例自检（`Register`/`SetScale` 必须被抓，`Enabled`/`Settings` 必须放过）。
   - 首轮覆盖率 **97.3%**，缺口全在 `init` 的自检 panic 分支——这些分支只在「表被改坏」时触发，写在 `init` 里**无法被测试构造**，等于一个从未验证过的保险。故把构建逻辑抽成返回 `error` 的纯函数 `buildTable`，`init` 只负责把 error 转成 panic；随后补 `TestBuildTableRejectsBadTable` 覆盖全部 5 条拒绝分支，覆盖率升至 **99.4%**。剩余 1 条未覆盖语句是 `init` 中的 `panic` 本身（表正确时不可达，构造它需要改坏生产表）。

5. **额外补充的 API 面冻结用例**。`TestNoMutationAPI` 按命名判断，仍可能被「命名绕开动词表的写入口」骗过。故追加 `TestExportedAPISurface`：冻结全部 23 个导出标识符，任何新增导出都必须显式登记，任何消失都会因下游可能编译失败而报错。
