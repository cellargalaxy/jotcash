### 三、第三方库调研与否决

prompt 要求「优先采用 github 上成熟稳定 star 多的代码库」。本轮**逐项核对后不引入**，理由分两类。

#### 3.1 本包是端口包，可复用的第三方能力为零

本包交付的三样东西——接口形状、原始交易行的字段集合、按解析器类型键路由的注册表——**全部是本系统专有语义**：

- `RawRow` 的 8 个字段直接取自终版 §四 3 的 `Expense` 属性子集（且刻意**不含**摊分月数、折算汇率、本位币金额、支出类型，见 §四 2）；
- 注册表的键是 `enum.ParserType`，即本仓库自己的枚举；
- 五类错误的分档与文案键由 `base/errs` 与 i18n 契约决定。

没有任何第三方库提供这三样。

#### 3.2 候选库属于 L4 的选型，不属于本轮

调研的候选与它们的真实归属：

| 候选 | 定位 | 为什么不在本轮引入 |
| --- | --- | --- |
| `encoding/csv`（标准库） | CSV 词法 | 属 `parser/csv`（L4）内部实现细节。本包若 import 它，等于把「CSV」这一选型固化进端口层，违反准则 4——`parser` 的存在意义恰是让新增银行/格式不影响上层（D-1） |
| `gocarina/gocsv`（约 1.1k★，**已在 `go.mod` 间接依赖中**） | CSV ↔ struct 映射 | 同上，属 L4。且本轮不写实现，引入即成未使用依赖 |
| `railslove/cmxl`（MT940 SWIFT 账单解析） | 银行账单格式 | 是**具体格式**的解析器，对应 D-1 的「新增银行 = 新增 L4 平级子包」，不是端口 |
| `benjaminheng/bankparse`、`sebastienrousseau/bankstatementparser` 等 | 特定国家/银行的账单解析 | 同上；且 D-1 明写「**适配各银行原生导出格式**，不定义统一模板」，这类库自带的统一模板与本系统取向相反 |
| PDF 解析类库（`pdfcpu` 等） | PDF 文本与解密 | 属将来的 `parser/pdf`（L4）。本轮 `enum.ParserType` 只声明了 `generic_csv` 一项（见 `enum/file.go` 注释「本轮为什么只有一项」），PDF 解析器本轮不实现 |

**结论**：`go.mod` / `go.sum` 本轮零改动。底层能力已经下沉到第三方库——金额经 `base/decimal` 用 `shopspring/decimal`、日期经 `base/calendar` 用 `cloud.google.com/go/civil`，本包不重复造它们，也不越过它们直接 import。

### 四、方案取舍（8 项）

#### 取舍 1：注册表做成**实例类型**，不做包级可变全局表

**采用**：`Registry` 为结构体，由 `app` 经 `NewRegistry(parsers...)` 构造后注入 L5；构造完成即只读，**没有任何 `Register` / `Unregister` 导出方法**。

否决「包级 map + 包级 `Register(pt, p)`」这一常见形态，理由是 `currency` 那一轮已经把同一个坑登记在案（`currency/currency.go` 包注释「为什么不直接用第三方库」与「不做什么」）：

| 问题 | 包级可变表 | 本包的实例表 |
| --- | --- | --- |
| 任何 import 到本包的包都能改路由 | 能——把 `generic_csv` 换成一个恶意实现，全系统静默改数 | 不能，无导出写入口 |
| 注册与读取并发不安全 | 是（`currency` 那轮实测 `bojanz/currency` 的 `Register` 与读并发即 `DATA RACE`） | 构造后只读，天然并发安全，无需锁 |
| 注册顺序依赖 `init`，与 `app` 装配顺序耦合 | 是 | 否，装配点唯一且显式 |

这同时满足约定 8「所需外部参数由 `app` 注入」与分层 §六 L3 表头「端口包……注册项由 `app` 从 L4 注入」。

#### 取舍 2：`Parser` 自报类型键，注册表不接收独立的 key 参数

`Parser` 接口含 `Type() enum.ParserType`，`NewRegistry` 从实现自身读键。

否决 `Register(key, parser)` 双参形态：那样「键」与「实现」是两个可以各自写错的输入，实测形态是把 CSV 实现注册到 PDF 的键下——上传 PDF 选 PDF 解析器，走进 CSV 实现，报「格式不符」，而根因在装配处，离现场极远。自报键使这种错配在结构上不可能。

#### 取舍 3：`RawRow` 恰 8 个字段，**不含**摊分月数 / 折算汇率 / 本位币金额 / 支出类型

承载明列 8 项，本包一项不多。四项被刻意排除的字段各有其唯一来源，放进 `RawRow` 就等于开了第二个入口：

| 被排除的字段 | 唯一来源 | 放进来的后果 |
| --- | --- | --- |
| 折算汇率 | `service/fx`（I-3/I-4，同币种短路取 1） | 解析器凭账单文本猜汇率，绕过 I-5 的「重拉失败转必填、不静默按 1:1」 |
| 本位币金额 | `rule/convert`（不变式 1a 唯一实现处） | 直接违反终版前提 6「本位币金额是只读因变量，无人工指定入口」 |
| 摊分月数 / 起止月 | 用户输入默认 1（H-1）+ `rule/amortize`（不变式 1b） | 起止月在第二处派生 |
| 支出类型 | G-3 自动打标随 T4 挂起，**当前一律留空** | 凭账单猜类型，等于把挂起的 T4 偷偷实现了一半 |

#### 取舍 4：`RawRow` 全部字段零值合法，本包不做业务校验

承载明写「解析不出则留空」。终版 D-2 只要求卡片三属性可留空，但**支出日期/金额/币种**在 `Expense` 上是必填。必填性校验放在哪里？

**采用**：本包不校验，由各 L4 实现按自己的账单版式判定并抛 `字段缺失`；`RawRow` 本身只是数据载体。

理由是准则 1「一条不变式只有一处实现」的同构推论：必填性的判据是「这个账单版式里该列在第几列、空了算不算缺」，只有具体实现知道；端口层若加一道 `Validate()`，就出现「实现判一遍、端口再判一遍」两处口径，且端口层那遍必然更弱（它不知道行号与列名，给不出 D-3 要求的「明确错误提示」）。本包改为提供 `ClassifyValueError` / `NewFieldMissingError` 等**分类工具**，让所有实现产出形状一致的错误——统一的是错误形状，不是校验位置。

#### 取舍 5：解析失败**快速失败**，不收集全部行的错误

`Parse` 返回 `([]RawRow, error)`，遇首个不可解析的行即返回错误（带行号与列名）。

否决「尽力解析 + 返回错误列表」：D-3 要求的是「给出明确错误提示」，而账单是机器导出的规整文本——一行解不出通常意味着选错了解析器或文件损坏，后续行几无例外全错，报 400 条同样的错误对用户毫无增益。且 D-7 是「一次提交生成一条审计」的整批语义，半批数据不可入库。

**扩展余量已留**：`error` 是接口，将来若真需要多错聚合，由 L4 实现返回一个聚合错误即可，`Parser` 接口与本包的分类函数都不必改。

#### 取舍 6：`Parse` 收 `context.Context`

与 `rule/passwd.Generate(ctx)` 同一取向：本包是**跨进程边界层**，L4 实现可能做 PDF 解密、大文件扫描这类耗时工作，ctx 用于取消与向 `base/log` 透传请求标识。端口层不读 ctx 里的任何值。

#### 取舍 7：D-3 五类的**边界定死在「判断层级」上**，不靠语感

五类错误的名字很容易两两混淆（「格式不符」与「内容损坏」尤其）。本包按**判断层级**划界，写进包注释并由用例锁死：

| 类别 | 层级 | 判据 | 典型 |
| --- | --- | --- | --- |
| 类型不匹配 `type_mismatch` | 文件 × 用户选择 | `ParserType.Format() != File.Format` | 选 CSV 解析器传了 PDF |
| 解密失败 `decrypt_failed` | 文件整体 | 口令错或缺 | 加密 PDF 未给密码 |
| 格式不符 `format_mismatch` | 文件版式 | 表头、列数、分隔符不符合该解析器预期 | 少一列、表头对不上 |
| 字段缺失 `field_missing` | 单元格**存在性** | 必填单元格为空或该列不存在 | 金额列空 |
| 内容损坏 `content_corrupt` | 单元格**内容** | 单元格有值但解释不出 | 金额 `abc`、日期 `2026-02-30`、币种 `XXX` |

这条划界直接决定分类器的映射表（§五 3），也解释了为什么 `currency.ErrEmptyCode` → 字段缺失、而 `currency.ErrUnknownCode` → 内容损坏。

#### 取舍 8：注册表的两类失败**分属不同档位**，不合并

| 情形 | 档位 | 文案键 |
| --- | --- | --- |
| 解析器类型键非法或为零值（用户没选 / 选了不存在的） | `KindInvalidInput` | `parser.type_unsupported` |
| 键合法但注册表里没有对应实现（装配漏配） | `KindInternal` | `parser.not_registered` |

合并成一档必有一方是错的：前者是 400（用户可改），后者是 500（用户改不了，是 `app` 少注册了一个 L4 子包）。这与 `enum` 包注释「错误是哨兵，本包不选错误档位」中同一个论证结构一致——只是本包位于 L3、已知调用语境，因此可以并且应当定档。

**新增两个文案键是对 i18n 的硬性契约**（与 `rule/passwd.KeyGenerateFailed` 同例），已写入包注释。

#### 6.3 编码期发现并修复的一个真实缺陷：`isBlank` 漏判 7 个 Unicode 空白

这不是「事后补的测试」，而是**差分测试在编写时当场抓到的**。

初版 `isBlank` 为避免 `strings.TrimSpace` 的分配而手列空白字符集（ASCII 空白 + U+3000）。差分用例 `TestIsBlankMatchesTrimSpace` 逐码点对照标准库后报出 7 个漏判：

```
isBlank(U+1680) = false，strings.TrimSpace 判定为 true
isBlank(U+2000) = false, U+2001, U+2028, U+2029, U+202F, U+205F 同
```

**为什么这是真缺陷而不是可接受的取舍**：漏判会让空单元格走进「有值」分支，于是 D-3 的归类从 `字段缺失` 变成 `内容损坏`——提示语从「该字段缺失，请补」变成「内容损坏，请查文件」，**指向完全错误的用户动作**。而 U+2000 系列（en/em space）与 U+202F（窄不换行空格）恰是 PDF 文本抽取的常见产物，`parser/pdf` 是已规划的 L4 实现。

**修法**：改用 `unicode.IsSpace` 逐 rune 判定。range 遍历字符串本身不分配，`IsSpace` 对 Latin-1 走查表快路径，因此原先的性能顾虑不成立——既无分配也不更慢。

已实测确认修复有效，并保留差分形态（而非只断言那 7 个码点），使将来 Unicode 增补空白字符时用例依然有效。另钉住 U+FEFF（BOM）**不算**空白，与标准库一致：CSV 文件头常带 BOM，判成空白会让只含 BOM 的单元格被误报缺失。

#### 6.5 第三方库：调研后不引入，`go.mod` 零改动

`go list -deps` 确认本包的第三方依赖仅经由基础层间接引入：`shopspring/decimal`（经 `base/decimal`）、`cloud.google.com/go/civil`（经 `base/calendar`）、`pkg/errors`（经 `base/errs`）。本包自身只 import 4 个标准库包（`context`/`errors`/`fmt`/`unicode`），并由 `TestDependencyBoundary` 的标准库白名单钉死。
