### 二、背景对齐（来源均已核对代码，非引用历史结论）

`rule/convert` 的职责在 `仓库代码包的层级设计与划分.md` §六 L2 表中明确：

> 不变式 1a 的唯一实现处：8.1 六种触发的三字段联动矩阵；入口先把折算汇率规整到 8 位小数（T39，全仓库唯一规整点，自动获取与手填共用）；本位币金额 = round(支出金额 × 折算汇率, 本位币的 currency.小数位数, 四舍五入)（全仓库唯一一处金额乘法与舍入）；折算本位币币种 仅在「汇率重拉或用户手填」时更新；输出三元组含规整后的汇率，落库以它为准

关键点是**不变式 1a 由两件事组成**，缺一不可：

1. 恒等式 `本位币金额 = 支出金额 × 折算汇率` 恒成立；
2. `折算本位币币种` 仅在「汇率按当前本位币重拉或手填」时更新。

第 2 条**没有任何数值后果**——算错了不报错、金额也对，要到下一次 I-7 重算才暴露成「手填汇率被覆盖」或「未收敛行永远收敛不了」（`记账系统功能与模型.md` 8.1 末段）。这决定了「触发」必须是本包的一等概念，而不是一个 bool 参数。

**已确认的上游契约**（三个包在本包动工前各自写好的消费方走查，非我方臆测）：

- `internal/base/decimal/consumer_check_test.go:171` `TestConsumerConvertRule`——给出 0/1/2 位本位币、负金额、零金额、汇率为 1 的期望值；
- `internal/currency/consumer_check_test.go:56` `TestConsumerConvertRounding`——给出 CNY/USD/JPY/KRW 的期望值，并要求零值本位币被拦下；
- `internal/entity/consumer_check_test.go:41`/`:120`——给出恒等式、JPY 0 位、负金额对称，以及 8.1 第 1 行「改支出金额不改折算本位币币种」。

### 三、方案取舍

#### 1. 第三方库：调研后**不采用**，但底层算术已下沉

按「优先采用成熟稳定 star 多的库」的要求，实测了 3 个候选（`go run` 实跑，非读文档）：

| 库 | star | 实测结论 |
| --- | --- | --- |
| `Rhymond/go-money` | 1912 | 整数分建模，无法表达 8 位汇率 |
| `bojanz/currency` | 644 | `Round()` 确为四舍五入，但自带币种表；`Register` 改包级 map，与读并发即 DATA RACE |
| `govalues/money` | 56 | **银行家舍入**：实测 `RoundToCurr(0.005 USD)=0.00`、`(5.445)=5.44` |

**不采用的三条实据**（均为实测，非推测）：

- **币种表冲突**。本包舍入基准必须来自 `currency.Code.Scale()`——那张表已按 CLDR 48.2.0 交叉校验，且在 IDR 上刻意取账面位数 2 而非 CLDR 现金位数 0。引入库自带的表 = 同一币种有两个位数来源。
- **舍入方式实测分歧**。`govalues/money` 用银行家舍入，与已定案的四舍五入差一分钱，且签名一致，误用后极难在评审中发现。
- **联动矩阵是本系统专有语义**，任何库都不提供——而这恰是本包的实质价值，恒等式那一半只是一次乘法加一次舍入。

**但轮子并没有自己造**：底层定点算术经 `base/decimal` 已下沉给 `shopspring/decimal`。本包只做三项本系统业务决策：取哪个位数、何时规整、哪种触发改哪个字段。

#### 2. API 形状：收三元组，不收 `entity.Expense`

分层 §六 L2 的依赖列写着 `entity`，但本包**实际比允许边界更收敛**，不依赖它。依据是终版**前提 6**：本位币金额是只读因变量、无人工指定入口。若签名收 `Expense`，「传进来的那个 `BaseAmount`」在语义上就是个必须被无视的输入——存在却无意义的字段迟早被当成有意义。收三元组则该字段根本不在入参里。

`Input` 中 `BaseCurrency`（当前本位币）与 `PriorBaseCurrency`（该行原有口径）**必须分开**：二者在未收敛行上恰恰不同，而这个差异正是不变式 2 识别待重算行的判据，合并就没了。

#### 3. 错误：哨兵，不选 `base/errs` 档位

与 `base/decimal`、`currency`、`enum` 一致。同一个「本位币未指定」经 dto 进来是用户输入错误（400），经 I-7 批处理出现则是数据损坏（500）。本包无从判断被谁调用，一旦选档必有一方错。故本包**不 import `base/errs`**。

### 四、两处「只在实测中才会暴露」的静默错误路径

这两条不在任何文档里，是实跑 `base/decimal` 后发现并已拦下的：

**① 汇率规整后下溢为零。** 极小汇率本身为正、能过入口校验，但规整到 8 位后变成 0：

```
RoundRate(0.000000001)  = 0     ← 静默把本位币金额算成 0，恒等式照样成立（0 = 金额 × 0）
RoundRate(0.000000005)  = 0.00000001  ← 边界另一侧，应放行
```

故**规整后必须再判一次正**，仅在规整前判会漏掉整条路径。

**② 3 位本位币落库被静默截断。** T38 把本位币限定为小数位 ≤ 2，实测印证其必要性：

```
100.00 × 7.12345678 按 3 位 = 712.346 → FitsScale(2) = false
```

币种表中 KWD 即为 3 位。故用 `CanBeBase()` 拒绝非候选，而非信任上游已拦。

**③ 顺序敏感（已在代码注释与用例中锁死）**：先乘后规整 vs 先规整后乘，结果确实不同——

```
100000000 × 7.123456785：先乘后舍入 = 712345678.5；先规整再乘 = 712345679
```

小额金额测不出来，用例专门构造了放大到分位的数据。

### 五、实施结果

**`trigger.go`**——8.1 六种触发的矩阵，逐行对应终版表格：

| 触发 | 重算金额 | 置为当前本位币 |
| --- | --- | --- |
| 改支出金额 | 是 | **否**（唯一一个） |
| 改折算汇率（含 D-7 入库首次获取） | 是 | 是 |
| 改支出日期 | 是 | 是 |
| 改支出币种 | 是 | 是 |
| I-7 重算 / 切换本位币 | 是 | 是 |
| 改摊分月数 | 否 | 否（纯直通，恒不返回错误） |

零值 `Trigger(0)` 不默许任何一种触发，直接报错。

**`convert.go`**——`Apply(in Input, trigger Trigger) (Output, error)`，纯函数，三步顺序不可换：规整汇率（T39）→ 乘（不中途舍入）→ 按本位币位数四舍五入（T35+T38）。

一处刻意维持的性质：**舍入基准与输出的 `折算本位币币种` 恒为同一个变量 `base`**，从结构上杜绝「用 A 币种位数算出标着 B 币种的金额」。

四项校验，每项放行都会得到「不报错但错误」的金额：触发合法、本位币非零且属候选、汇率为正、**规整后**汇率仍为正。
