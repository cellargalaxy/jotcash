## 二、方案取舍（8 项，逐项给依据）

### 取舍 1：不引入第三方枚举库，自建 100 行泛型内核

本 prompt 要求「优先采用 github 上成熟稳定 star 多的代码库（如果有），避免自己造轮子」。实际调研的 6 个候选（star 数为 2026-09-07 经 GitHub API 实测）：

| 候选 | star | 形态 | 是否支持本包的核心诉求 | 判定 |
| ---- | ---- | ---- | ---------------------- | ---- |
| `abice/go-enum` | 957 | **代码生成器**（注释指令 + `go:generate`） | 支持 JSON/SQL/名称，但**元数据要靠注释里的自定义字段**，且生成物不可手改 | 不采用 |
| `dmarkham/enumer` | 522 | **代码生成器**（`stringer` 增强版） | 只做 `string ↔ 值` 映射，**无元数据概念** | 不采用 |
| `orsinium-labs/enum` | 462 | 运行期泛型库 | 泛型 + 成员集合，**无 SQL/JSON 编解码**，元数据需自建 | 不采用 |
| `zarldev/goenums` | 374 | 代码生成器 | 支持元数据，但生成风格与本仓库差异大 | 不采用 |
| `xybor-x/enum` | 43 | 运行期泛型库 | star 过少，最后提交 2025-01 | 不采用 |
| `go-pkgz/enum` | 9 | 代码生成器 | star 过少 | 不采用 |

**不采用的三条实质理由**（不是「不想用」，是「用了更差」）：

1. **代码生成器与本包的注释体量正面冲突**。约定 3 要求注释中文且本仓库既有风格是「每个决策都写清为什么」——`base/calendar` 的 `Date` 类型注释就有 20 余行。生成物不可手改，这些「为什么」无处安放，只能退化成一行 `// Role is an enum`，等于把本仓库最重要的资产（决策可追溯）扔掉。
2. **两个运行期库都不覆盖 SQL 编解码**，而准则 3 的「只存代码入库」使 `Valuer`/`Scanner` 成为硬需求；引入后仍要自己写这部分，只换来一层额外依赖。
3. **本包的复杂度不在「枚举机制」，而在「7 个枚举各自的业务约束」**——`ObjectType` 的零值合法、`ParserType` 的停用不删除、11 类的项数锁定，没有任何通用库能表达这些。机制部分实测只有约 100 行泛型内核（`enum.go` 的 `set`/`parse`/`marshal`/`scan`），引入 600+ star 的生成器来省这 100 行，代价是丢掉注释与生成物治理成本。

**采纳的折中**：机制部分自建但**只写一份**——7 个类型共用同一套泛型内核，避免「造 7 个轮子」。这正是第三方库要解决的重复问题，用 Go 1.24 的泛型在包内解决即可，无需外部依赖。本包**只 import 标准库**（`database/sql/driver`、`encoding/json`、`errors`、`fmt`）。

### 取舍 2：底层类型用 `string`，码值即列值

准则 3「枚举即代码」只说「存代码 / 键」，未指定整数还是字符串。选字符串的依据是**终版前提 1**（无人直接读写数据库、数据一律明文存储）与 **K-3 整库导出**：导出产物与 SQLite 库文件都要人能直接看懂。整数码则必须另配一份映射表才能解读，而那份表一旦与代码漂移就无从发现。

代价是列宽略大与「码值不可改」的强约束，两者都可接受——后者本来就是枚举即代码的应有之义（历史行存着旧码值）。**已由 `code_golden_test.go` 把全部码值逐字锁死**。

### 取舍 3：`String()` 出中文名，`Code()` 出码值——两者刻意不同

与 `base/errs` 的 `Kind` 同构。关键在于**必须让二者不同**：若中文名恰好等于码值，`fmt.Sprintf("%s", role)` 这类误用就永远不会被发现，直到某天中文名被改动才在契约面爆发。用例 `String 是中文名而非码值` 直接断言二者不等。

零值返回「未指定」、未知码值返回 `未知(码值)`，而非空串——`String()` 会被 `%v` 隐式调用，空串会让日志里出现看不见的字段，反而更难排查。

### 取舍 4：零值落**空串**而非 NULL，与 `base/calendar` 刻意相反

`base/calendar` 的 `Date` 零值落 NULL，本包零值落空串。这不是口径不一致，差异来自**零值是否为合法业务取值**：

- `Expense.支出日期` 的零值本就该被 NOT NULL 拦下 → 落 NULL 是对的；
- `AuditLog.操作对象类型` 的零值是**合法取值**（终版 §四 5：「零值 = 本次操作无具体对象或为批量操作」，11 类里有 5 类该落零值），且 §四 5 表头明写 9 项「全部必填」 → 落 NULL 会被 NOT NULL 约束当场拒绝掉一个合法值。

因此 7 个类型统一落空串（统一比分类更不易错），并在包注释里写明这条与 `calendar` 的差异来由。

### 取舍 5：`Valid()` 对零值一律返回 false，即使零值合法

`ObjectType` 的零值合法，但 `Valid()` 仍返回 false。理由：`Valid` 判定的是「**是否为某个具体对象类型**」，而零值恰恰表示「不是任何对象类型」——两者不矛盾。审计写入方应写 `t.IsZero() || t.Valid()`，这一用法已在 `TestConsumerAuditWriter` 中按 §8.4 的 12 行对应表逐行走查。

反过来若让 `Valid()` 对零值返回 true，`Role`/`UserStatus` 等 6 个类型的零值（非法状态）就会被判为合法，损失远大于收益。

### 取舍 6：解析、反序列化、扫描三条路径**一律严格全等匹配**

不做大小写折叠、不裁剪空白。码值是机器契约（库里的列值与 JSON 契约），不是用户输入。宽松匹配会让 `Admin` 与 `admin` 两种写法同时可用，落库后成为两份互不相等的历史数据，而这类问题**在写入时毫无征兆**。用例对每个类型都跑了大小写变体与前后空白变体，断言全部被拒。

### 取舍 7：`Scan` 与 `UnmarshalJSON` 都**校验码值合法性**，但都不校验「是否启用」

- **校验合法性**：dto 是外部可控入口，放行未知码值会让一个拼错的角色名一路写进库；store 侧读到未知码值意味着数据损坏（枚举项只能停用不能删除），静默放行会让坏数据在后续每次判定里都走错分支。
- **不校验启用状态**：反序列化与扫描是**形态转换**，而「停用项不得被新选择」是**业务规则**，属 `service/file` 的 C-1 校验。混在一起会让「读取历史 File 行」这个正常操作因该键已停用而失败——这恰恰违背 §五 2「只停用不删除」的初衷（停用的目的就是保住历史数据可读）。

### 取舍 8：`ParserType` 本轮只声明 1 项，形态先行

终版 §四 4 举了「招商银行 · 信用卡账单 · PDF」作为**命名格式示例**，但 D-1 明写「本轮仅实现 CSV」，L4 现有且仅有 `parser/csv` 一个实现子包。枚举项与解析实现必须一一对应：**多声明一个键，D-2 的下拉就会出现一个选了必然报「未注册解析器」的死选项**。故本轮只声明 `generic_csv` 一项，四项元数据（键 / 名称 / 适用格式 / 启用位）形态完备，加银行只是往表里追加一行 + 加一个 L4 平级子包。

码值取 `generic_csv` 而非 `csv`，是为了与 `FileFormatCSV` 的码值区分——二者是正交的两列，码值相同会让人在库里误当成同一个东西。已由 `TestParserTypeDistinctFromFileFormat` 锁死。

### 3.2 对外 API（每个类型同构，共 7 套）

以 `Role` 为例，其余 6 个完全同构：

```go
// 包级
func Roles() []Role                        // 全集，保持声明序，返回副本
func ParseRole(v string) (Role, error)     // 严格全等匹配

// 值方法
func (r Role) Valid() bool                 // 是否为合法项（零值 false）
func (r Role) IsZero() bool                // 是否零值
func (r Role) Code() string                // 码值（落库 / 契约面）
func (r Role) String() string              // 中文名（日志面）
func (r Role) MarshalJSON() ([]byte, error)
func (r Role) Value() (driver.Value, error)
func (r *Role) UnmarshalJSON([]byte) error
func (r *Role) Scan(src any) error
```

**类型专属出口**（只有需要的类型才有，不做无谓对称）：

| 出口 | 所属 | 用途 |
| ---- | ---- | ---- |
| `IsAdmin()` | `Role` | 让「哪些地方依赖管理员身份」可被 grep 穷举（前提 3 无编译期兜底） |
| `IsEnabled()` | `UserStatus` | A-4 登录判定，**默认拒绝**语义 |
| `IsSuccess()` | `OperationResult` | 同上 |
| `EnabledParserTypes()` | `ParserType` | D-2 上传页下拉数据源（已过滤停用项） |
| `Meta()` / `Enabled()` / `Format()` | `ParserType` | C-1 合法性校验与 D-3 第五类匹配校验 |

### 3.3 关键逻辑与异常分支

| 场景 | 行为 | 依据 |
| ---- | ---- | ---- |
| JSON `null` / `""` / 字段缺失 | 一律得零值，不报错 | 三者在 Go 中不可区分，行为必须一致 |
| SQL `NULL` / `""` | 一律得零值，不报错 | 兼容历史列与可选列 |
| SQL `[]byte` 形态 | 与 `string` 等价 | 部分驱动返回 `[]byte` |
| 未知码值（JSON / SQL / Parse） | 返回 `ErrUnknownCode`，**目标保持零值** | 不得写入半个坏值 |
| JSON 非字符串（数字 / 对象 / 布尔） | 返回 `ErrCodeType` | 外部入口须严格 |
| SQL 扫描到 int / float / bool | 返回 `ErrScanType` | 同上 |
| 枚举表自身写错（空串码值 / 重复码值） | **包初始化期 panic** | 编程错误须在进程启动第一刻响亮失败 |
| 解析器元数据不自洽（4 种） | **包初始化期 panic** | 同上，且错误信息指明是哪个键、哪条不符 |

## 四、对现有链路 / 性能 / 兼容性 / 下游的副作用

| 维度 | 评估 |
| ---- | ---- |
| **现有链路** | **无影响**。本包为新增，`base/*` 与 `currency` 均未改动；`go build ./...` 与全仓库 `go test ./...` 复跑全绿 |
| **性能** | 枚举表在包初始化时一次性构建，此后只读；`Valid`/`String`/`Meta` 均为 O(1) map 查表。`Roles()` 等全集出口返回副本（O(n) 拷贝，n ≤ 11），仅用于下拉与穷举场景，不在热路径 |
| **并发** | 表构建后不可变、无写入口，可并发使用；`-race` 通过 |
| **兼容性** | 无存量数据。**码值一经发布即冻结**——已由 golden 表锁死，后续任何改动都会在 CI 失败并被迫回答「存量数据怎么迁移」 |
| **下游** | 分层 §十一 阶段 2 的 `entity` 可立即消费；`parser`/`store`/`service/*` 所需出口已按 §1.3 逐个对齐并写了走查用例 |

### 6.3 变异测试：37 处，**6 处首轮存活**（本轮最有价值的产出）

覆盖率 100% 不等于用例有拦截力。逐一把实现改坏后复跑用例，验证「测试真的会失败」：

| 批次 | 变异内容 | 结果 |
| ---- | -------- | ---- |
| M1–M3 | 改码值（`admin`→`administrator`、`data_intake`→`intake`、`generic_csv`→`csv`） | 全部杀死 |
| M4–M6 | 增删枚举项（11 类删成 10 类、加回「登出」、删对象类型） | 全部杀死 |
| M7–M17 | 行为语义（零值落 NULL、`IsEnabled` 改成 `!= disabled`、跳过码值校验、放宽大小写、`all()` 返回内部切片、`String()` 返回码值、去掉重复码值校验……） | 全部杀死 |
| M18–M25 | 边界与防线（`IsAdmin` 放行未知角色、去掉空串校验、JSON 类型错误静默放行、拒绝 `[]byte`、引入 `base/errs` 依赖、错误信息丢失上下文） | 全部杀死 |
| M26–M31 | 过滤逻辑（过滤取反、缺元数据默认放行、打乱声明序、`Meta()` 第二返回值恒真） | 全部杀死 |
| **M24** | **`EnabledParserTypes` 不过滤停用项** | **首轮存活** |
| **M29 / M30** | **`Enabled()` 恒真 / `Format()` 恒返回 CSV** | **首轮存活** |
| **M32 / M33 / M37** | **跳过元数据缺项校验 / 名称为空校验 / `init` 不 panic** | **首轮存活** |

**三个盲区的成因与修法**（都不是补个断言了事，而是改了代码结构使其可测）：

1. **M24（启用过滤形同虚设）**：本轮所有解析器都是启用状态，遍历包级表时「有过滤」与「无过滤」结果完全相同，用例区分不出来。
   → 把过滤逻辑抽成 `filterEnabledParserTypes(codes, metas)` 以表为参数，测试喂进含停用项的表，真正验证**机制**成立而非依赖「当前恰好没有停用项」这个随时会变的事实。

2. **M29/M30（访问器写死也测不出）**：唯一解析器恰好是「启用 + CSV」，`return true` / `return CSV` 与真实实现在正常路径上无差别。区分点在**异常路径**——`Enabled()` 恒真会让已删除的键被判为可用（C-1 校验形同虚设）；`Format()` 恒为 CSV 会让 D-3 第五类匹配校验对坏数据永远不成立。
   → 补 `TestParserTypeAccessorsDefaultDeny`，对零值、未知键、大小写变体等 5 种输入断言默认拒绝。

3. **M32/M33/M37（校验之间互相兜底掩盖失效）**：删掉「缺元数据」校验后，末尾的项数核对照样会报错——错误仍被拦下，但**报成了错误的原因**，排错时会指向错误方向。原用例只断言 `err != nil`，放不出这个区别。M37 更进一步：`init` 里把 `panic` 改成 `_ = check(...)`，校验函数的用例照样全绿，因为它们测的是「函数返回什么」而不是「调用方拿到错误后做了什么」。
   → ① 校验体抽成 `checkParserMetas` 返回 error，用例**断言精确到报错原因**（`strings.Contains` 匹配「缺少元数据」「名称为空」等）并要求错误信息指明出问题的键；② `init` 的 panic 抽成 `mustCheckParserMetas`，使「校验失败必须 panic」这条行为本身可被测试。

修复后复跑：**37 处变异全部杀死**，覆盖率同时从 96.7% 升至 100.0%。
