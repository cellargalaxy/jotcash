## 一、承载与约束的提取

### 1.1 本包必须做到的（分层 §六 L0 `base/errs` 行逐句拆解）

| # | 承载原文片段 | 落到实现上的要求 |
| - | ------------ | ---------------- |
| 1 | 「统一错误类型与错误码」 | 全仓库唯一的错误类型；错误码要有稳定的机器可读形态 |
| 2 | 「**五档**：用户输入错误 / **唯一冲突** / 归属越权 / 未登录 / 系统错误」 | 档位是**闭集**，恰 5 项，不多不少 |

| 7 | 依赖列 `—`、L0 表头「仅依赖标准库与第三方库」「层内零依赖」 | 只准 import 标准库与第三方库，不得 import 本仓库任何包 |

## 二、方案取舍（7 项，逐项给依据）

### 取舍 1：错误库选型 —— 采用 `github.com/pkg/errors` v0.9.1 作为包装与栈底座，五档 + 文案键机制自建

本 prompt 要求「优先采用 github 上成熟/稳定/star 多的代码库（如果有），避免自己造轮子」。实际调研的 6 个候选：

| 候选 | star | 状态 | 是否原生支持「五档闭集 + 文案键 + 占位参数」 | 判定 |
| ---- | ---- | ---- | -------------------------------------------- | ---- |
| `github.com/pkg/errors` | 8.3k | 事实标准，API 冻结 | ❌ 只有 Wrap/Cause/栈 | **采用为底座** |
| `github.com/cockroachdb/errors` | 2.5k | 活跃 | ❌ 无文案键；主打网络可移植与 PII 脱敏 | 不采用 |
| `github.com/joomcode/errorx` | 1.3k | 2024-11 后无提交 | ❌ namespace/trait 是开放层级，与「恰 5 档闭集」语义不合 | 不采用 |
| `github.com/rotisserie/eris` | 1.8k | 2025-04 后无提交 | ❌ 主打栈格式化 | 不采用 |
| `github.com/hacomono-lib/go-errorsx` | 16 | 新 | ⭕ 有 translator 概念 | star 过少，不满足「成熟/稳定/star 多」 |
| `github.com/gomooth/xerror` | 0 | 新 | ⭕ 双消息体系 | 同上 |

**决策依据（三条，任一独立成立）**：

1. **仓库一致性优先**：兄弟 prompt（`260904-153910`、`260904-153915`）已把 `base/log` 与 `base/idgen` 定为直接使用 `github.com/cellargalaxy/go_common/util`。而 `go_common` 的 `go.mod:20` 依赖 `github.com/pkg/errors v0.9.1`，其 `util/error.go` 通篇即 `errors.Errorf`，`util/error_test.go` 全部用例围绕 `errors.Is` / `errors.Cause` 编写。选 `pkg/errors` 使全仓库**只有一个错误库家族**；换任何一家都会与 `base/log` 拉进来的 `pkg/errors` 并存。
2. **没有一家能替掉自建部分**：五档闭集 + 文案键 + 占位参数是本系统 K-4（加语种不改代码）与 L6 状态映射的专有契约，上述任一库都得再包一层适配。适配层的代码量 ≈ 直接自建，还多一个依赖。
3. **本包自建的只是「数据载体」，不是「轮子」**：栈捕获、Wrap 链、`Is`/`As`/`Unwrap`/`Cause` 互操作**全部委托** `pkg/errors` 与标准库 `errors`，本包零行栈处理代码。
   - 已实测确认 `pkg/errors` v0.9.1 在 Go 1.27.0 下 `As` / `Is` / `Cause` / `Unwrap` / `%+v` 栈打印五项全部正常（其 `go113.go` 用的是老式 `// +build` 标签，实测不影响 1.27 构建）。

`go_common` 的 `util/error.go` 仅有一个哨兵 `HttpBan`（HTTP 封禁判定），与本包五档无交集，**无可复用内容**；本包因此不引入 `go_common` 依赖（`base/log` 那一轮再引）。

### 取舍 2：错误码不引入第三根轴，五档本身即错误码

承载原文是「统一错误类型与错误码；**五档**：……」——把「五档」直接读作错误码的取值域，即「错误类型 = 错误码 = 5 个枚举值」。

- **不做**「五档 + 独立数字业务码（如 300004）」的两层设计：全仓库已有「文案键」承担细粒度身份（D-3 的 5 类靠键区分，不靠码），再加一根数字轴等于同一件事编三次码（档位、数字码、文案键），必然漂移。
- 每档同时给出**数字值**（`Kind` 底层 `uint8`，便于 switch 与存储）与**稳定字符串码**（`Code()`，如 `invalid_input`，便于日志与将来的 API 契约），二者一一对应、不可分裂。
- 另给 `String()` 返回**中文档位名**（`用户输入错误` 等）——遵约定 3「注释与日志一律中文」，这是日志面文案，不是用户面文案。

### 取舍 3：占位参数用**具名** `map[string]any`，不用位置参数 `...any`

这是本包唯一会外溢到 `i18n` 与全部上层包的形态决策，依据是 **K-4「新增语种只需增加配置、无需改动代码」**（终版 §二 K-4）：

- 位置参数（`%s` 风格）要求**所有语种的占位符顺序一致**。而语序是语言属性：`第 12 行的「金额」字段缺失` 与 `field "amount" missing on line 12` 的两个变量顺序天然相反。一旦某语种需要调序，就只能回头改产错误的 Go 代码——**K-4 当场失效**。
- 具名参数（`{{.Line}}` / `{{.Field}}` 风格）与顺序无关，任何语种自行决定语序，不回改代码。
- 旁证：主流方案 `nicksnyder/go-i18n`（3.5k star，K-4 的候选实现）即 `text/template` 具名占位。本包因此**不锁死** `i18n` 的具体选型，只锁死「按名取参」这一契约。

配套两条防御（都在本包实现）：

- **构造时深拷贝一层、读出时再拷一层**：错误对象一旦产生即不可被调用方改写（错误会同时流向日志与渲染两条路径，共享 map 会出串改）。
- **`Error()` 输出按键名排序**：保证日志与单测输出确定，不受 map 遍历随机序影响。

### 取舍 4：栈只在「有 cause」时补，且不重复补

- **有 cause**（`store/sqlite` 包 SQLite 驱动错误、`service/*` 包 IO 错误）：这类是诊断向的，需要栈。本包在 `Wrap` 时检测 cause 链上是否已有 `StackTrace()`，**没有才** `errors.WithStack` 补一次——避免 `pkg/errors` 常见的「每层 Wrap 各自捕栈」噪音。
- **无 cause**（`parser` 判定出的格式不符、`rule/passwd` 判定出的密码不合策略）：这类是**预期内的用户输入错误**，不是故障，不需要栈；`base/log` 走 `go_common` 的 logrus hook，本身已在每条日志上打 `caller`（`util/log.go:118` `getCaller`），定位足够。
- 收益：`%+v` 打印时，底层栈能透传出来；`%v` / `%s` 保持单行、适合 logrus 字段。

### 取舍 5：本包持有**唯一一个**文案键常量 `KeyInternal`，用于兜住「未分档的裸 error」

`middleware` 拿到的 err 可能完全没分档（`database/sql` 直吐的错误、第三方库 panic 转 error）。若本包只提供「读出档位」而在无档时返回空，L6 就必须自己再造一套兜底文案逻辑，且**有把底层错误原文直接吐给用户的安全风险**（终版前提 1 下应用层是唯一防线）。

因此定死三条**总函数**语义（数学意义上的 total，任何输入都有确定输出）：

| 输入 | `KindOf` | `MsgKeyOf` |
| ---- | -------- | ---------- |
| `nil` | `KindUnknown` | `""` |
| 已分档的 `*Error`（含被 Wrap 多层） | 该档 | 该错误的文案键 |
| **未分档的任意 error** | `KindInternal` | `KeyInternal` |

`KeyInternal = "errs.internal"` 是**纯技术兜底键**，不含任何业务语义，故不违反约定 5；同理为 5 档各配一个 `DefaultMsgKey()`（`errs.invalid_input` 等），当调用方漏传键时归一到它，保证「档位一定有键可渲染」。

> **对 `i18n` 那一轮的契约（阶段 4 需接住）**：`internal/i18n/locales/zh-CN.*` 必须包含 `errs.internal`、`errs.invalid_input`、`errs.conflict`、`errs.forbidden`、`errs.unauthorized` 共 5 个兜底键，否则未分档错误渲染不出文案。

### 取舍 6：`Wrap(nil, …)` 返回 `nil`

沿用 `pkg/errors` 的既有语义（`WithStack`/`Wrap` 对 nil 返回 nil，见 `errors.go:145`），使 `return errs.Wrap(err, …)` 在 err 为 nil 时天然返回 nil，避免「包出一个非 nil 的空错误」这类最难查的 bug。

### 取舍 7：不做多错误聚合

逐条核对过需要「一次报多个问题」的候选场景，均不落在 error 上：D-6 查重的冲突集合是**返回值数据**（分层 §六 L2 `rule/dedup`：「输出「命中行 → 冲突明细集合」映射」）；I-7 逐笔重算允许部分失败但记的是**成功/失败笔数**（终版 I-7）；A-8 密码策略两条判据先命中先返回即可。故不引入 `errors.Join` 式聚合，保持单错误单键。若将来 F-5 表单要一次报多个字段错，届时加 `Errors []*Error` 字段即可，不影响现有 API。

## 四、实施步骤（已执行）

1. `internal/base/errs/kind.go`（190 行）：`Kind` 五档闭集 + `Kinds()` / `Code()` / `String()` / `Valid()` / `DefaultMsgKey()` + 五个兜底文案键常量。
2. `internal/base/errs/errs.go`（327 行）：`Params` 具名占位参数、`Error` 结构体（档位 / 文案键 / 占位参数 / cause 四字段，全部私有 → 构造后不可变）、7 个构造函数、5 个提取函数、4 个方法。
3. `internal/base/errs/errs_test.go`（750 行）：30 个顶层用例（含子用例 45 项）。
4. `go.mod` / `go.sum`：`github.com/pkg/errors v0.9.1` 落为直接依赖。

**导出 API 全貌**（共 3 类型 + 5 常量 + 12 函数 + 7 方法）：

| 组 | 标识符 | 用途 |
| -- | ------ | ---- |
| 档位 | `Kind`；`KindUnknown` / `KindInvalidInput` / `KindConflict` / `KindForbidden` / `KindUnauthorized` / `KindInternal`；`Kinds()`；`Code()` / `String()` / `Valid()` / `DefaultMsgKey()` | 五档闭集。`Kinds()` 供 `middleware` 写穷尽映射表并用单测锁死 |
| 兜底键 | `KeyInvalidInput` / `KeyConflict` / `KeyForbidden` / `KeyUnauthorized` / `KeyInternal` | 五个纯技术键，`i18n` 语言文件必须包含 |
| 错误类型 | `Error`；`Params` | 四字段全私有，构造后不可变 |
| 构造 | `New` / `Wrap` + `NewInvalidInput` / `NewConflict` / `NewForbidden` / `NewUnauthorized` / `NewInternal` | 快捷函数让调用点少写一个参数，也让 grep「谁会产生越权错误」可行 |
| 提取 | `From` / `KindOf` / `MsgKeyOf` / `ParamsOf` / `IsKind` | 后四个是总函数，`middleware` 与 service 分流的入口 |
| 方法 | `Kind()` / `MsgKey()` / `Params()` / `Error()` / `Unwrap()` / `Cause()` / `Format()` | `Unwrap` 供标准库、`Cause` 供 `pkg/errors`，两套判定方式仓库内都会出现 |

**`New` 返回 `*Error` 而 `Wrap` 返回 `error`，这处不对称是刻意的**：`Wrap` 存在「cause 为 nil 即返回 nil」的语义，若返回 `*Error`，`return errs.Wrap(err, …)` 会把「类型化的 nil 指针」装进 error 接口，使调用方 `if err != nil` 恒为真；`New` 恒返回非 nil，无此陷阱，返回具体类型更便于链式取值与断言。两处均已在函数注释里写明原因（详见 §五 表中第 9 行）。

**风格对齐**（约定 3 与兄弟包 `base/calendar` / `base/log` / `base/config` 的既有风格）：包名短小无下划线、集合语义用复数（`errs`）；包注释采用「为什么需要本包 → 关键设计 → 依赖边界」的分节体；注释全中文且**解释「为什么」而非复述「做了什么」**；导出标识符英文；短接收者名（`e` / `k`）——`go_common` 用 `this`，但本仓库 `internal/` 已落地的 67 处方法中 63 处用短名（`d` 39、`m` 17、`r` 7）、仅 4 处 `this`，故从仓库内既成风格。

**单测捕获的真实缺陷（1 个，已修）**：`TestWrapNilReturnsNil` 的第二段断言（返回值赋给 `error` 接口后仍应为 nil）**首次运行即失败**——`Wrap` 原本返回 `*Error`，Go 会把类型化的 nil 指针装进非 nil 的接口值，导致 `return errs.Wrap(err, …)` 在成功路径上也返回「非 nil 的错误」，上层会把成功当失败、进而回滚事务。修法是把 `Wrap` 的返回类型改为 `error`（与 `pkg/errors.Wrap` 口径一致），并补一条回放仓储层「成功 → 包装 → 返回」的用例。这正是方案 §二 取舍 6 想要防的那类 bug，只是它藏在返回类型而非 nil 判断里。
