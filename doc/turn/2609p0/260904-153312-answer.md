## 一、背景对齐：这个包被谁依赖、要扛什么

`base/errs` 位于 **L0 基础层**，是 41 包中依赖它的包最多、但它自己**零依赖**的一个。四处承载来自分层方案：

| 出处 | 原文要点 | 对本包的硬约束 |
| ---- | -------- | -------------- |
| §六 L0 `base/errs` 行 | 「统一错误类型与错误码；**五档**：用户输入错误 / **唯一冲突** / 归属越权 / 未登录 / 系统错误；**每个错误携带文案键与占位参数**，错误对象内不写死面向用户的文案」 | 五档齐备、顺序即码；错误对象里**不能有已渲染的中文提示** |
| §六 L0 表头 + §十 约定 5 | 「零业务语义，仅依赖标准库与第三方库，**层内零依赖**」；「`base/` 是纯技术层：任何带业务语义（角色、币种、语言、归属）的类型都不得放入」 | 不得 import 任何 `jotcash` 内部包；不得出现 `currency`/`enum` 类型 |
| §六 L6 `middleware` 行 ① | 「**`base/errs` 五档 → HTTP 状态映射**（唯一冲突 → 409、归属越权 → 403、未登录 → **401 且不做服务端跳转**）+ 经 `i18n` 渲染文案键」 | 档位必须可被**从任意错误链上**取出；本包**不得**感知 HTTP |
| §六 L3 `i18n` 行 | 「按「语言 + 文案键」取词并**填充占位参数**」 | 占位参数必须**按名索引**（不是位置参数），否则模板无法取值 |

另有三条来自终版的功能性要求，决定文案键的**收录范围**：

- **D-3 五类解析错误**（终版 §二 D-3）：格式不符 / 内容损坏 / 字段缺失 / 解密失败 / 类型不匹配——§六 L3 `parser` 行明写「一律返回带文案键的 `base/errs`」；
- **G-1 与 A-7 的重名**（§六 L3 `store` 行 ⑤）：唯一索引冲突「返回 `base/errs` 的「唯一冲突」档」；
- **K-4 加语种不改代码**（终版 §二 K-4）：这正是「错误对象内不写死文案」的**唯一理由**——文案写进代码，加语种就必须改代码。

## 二、选型：为什么是 `github.com/pkg/errors`，而不是自研或 cockroachdb/errors

本轮 prompt 要求「优先采用 github 上成熟稳定 star 多的代码库（如果有），避免自己造轮子」。**但「错误库」在本项目里是两件事**，必须拆开选：

| 层面 | 需求 | 结论 |
| ---- | ---- | ---- |
| **通用错误设施**（堆栈、包装、`Is`/`As`） | 通用能力，业界有成熟实现 | **复用 `github.com/pkg/errors` v0.9.1**，不自研 |
| **五档 + 文案键 + 占位参数** | 这是本项目**特有的领域契约**（档位取值来自分层方案、键的命名口径与 `i18n` 对齐） | **必须自己定义**——没有任何现成库的档位划分等于「用户输入 / 唯一冲突 / 归属越权 / 未登录 / 系统」这五档 |

### 2.1 通用设施选 `pkg/errors` 的依据（**决定性依据是项目既有事实，不是 star 数**）

`go_common` 是本项目**已指定复用**的基础库（同批次 prompt `260904-153910`/`153915` 分别指定 `base/log` 用其 `util/log.go`、`base/idgen` 用其 `util.GenId()`）。核对其代码：

- `go_common/go.mod` 直接依赖 `github.com/pkg/errors v0.9.1`；
- `go_common/util/error.go` 全文即 `var HttpBan = errors.Errorf("HTTP请求封禁")`，用的就是 `pkg/errors`；
- `go_common/util/json.go:12/37`、`util/gorm.go:112/127/144/162` 一律 `errors.Errorf("...异常: %+v", err)` + `errors.WithStack(err)` + `errors.Is(...)`；
- `model/http.go:46` 同样是 `errors.Errorf`。

**换用 `cockroachdb/errors` 或 `eris` 的代价**：`base/log` 与 `base/idgen` 已经把 `go_common` 引入本仓库，`go_common` 内部产出的错误全部是 `pkg/errors` 的类型；再引入第二个错误库，等于同一条错误链上出现两套堆栈实现与两套格式化协议，`%+v` 的输出会不一致。**一个仓库只应有一套错误设施**，因此跟随既有事实。

### 2.2 关于 `pkg/errors` 已归档（已知代价，登记）

`pkg/errors` 官方声明进入维护模式、不再接受新特性，社区（keda、ghostunnel 等）正在迁往标准库 `errors` + `fmt.Errorf("%w")`。**本轮仍选它**，理由与代价如下：

- 它 v0.9.1 已为 Go 1.13+ 补齐 `Unwrap`（`go113.go:36`）、`Is`（`:16`）、`As`（`:31`），`withStack.Unwrap()`（`errors.go:163`）也在——**与标准库错误链完全互通**，不存在「用不了 `errors.Is`」的问题；
- 它提供标准库**没有**的能力：`WithStack` 记录堆栈 + `%+v` 打印堆栈。`go_common` 全库靠这个能力做日志；
- **代价**：库不再演进。缓解——本包**只用它的 4 个函数**（`WithStack`/`As`/`Is`/`Wrap`，后者仅测试用），且全部收敛在 `errs.go` 与 `error.go` 内；将来若要换库，改动面是本包 2 个文件，不外溢到任何调用方（调用方只见 `errs.New`/`errs.Wrap`/`errs.KindOf`）。

### 2.3 领域契约自研的取舍（3 处）

| 取舍点 | 采用 | 放弃的方案与原因 |
| ------ | ---- | ---------------- |
| 档位表达 | **`Kind uint8` 枚举 + `iota + 1`** | 放弃「每档一个哨兵 `error` 变量」：哨兵只能表达「是哪档」，没法同时带文案键与占位参数；`iota + 1` 而非 `iota` 是为了让**零值不合法**，`KindOf(nil)` 因此能用零值表达「无错误」，与「系统错误」区分得开 |
| 占位参数 | **`map[string]any` + `A(name, value)` 可变参数** | 放弃 `...any` 位置参数：`i18n` 的模板是按**名**取值（`{{.Name}}`），位置参数无法索引；放弃直接暴露 map 字面量：调用点噪声大，且外部可改内部状态 |
| 出口归一化 | **`From(err)` 把任意 error 归一化为 `*Error`** | 放弃「middleware 自己做类型断言」：断言失败时就没有文案键可取词，会出现「500 但界面空白」；`From` 保证**出口处一定有档位、一定有键** |

## 三、方案：模块职责、输入输出、关键逻辑

### 3.1 文件划分（4 个源文件 + 2 个测试文件）

| 文件 | 职责 | 关键导出 |
| ---- | ---- | -------- |
| `kind.go` | 五档枚举本身 | `Kind`、`KindInput`/`KindConflict`/`KindForbidden`/`KindUnauthorized`/`KindSystem`、`Kind.Code()`/`String()`/`Valid()` |
| `error.go` | 统一错误类型 | `Error`（含 `Kind()`/`Code()`/`Key()`/`Args()`/`Error()`/`Unwrap()`/`Is()`/`Format()`） |
| `errs.go` | 构造与判定入口 | `A`/`New`/`Wrap`/`WithArgs`/`From`/`KindOf`/`IsKind` + 五档快捷构造 `NewXxx` + 五档快捷判定 `IsXxx` |
| `key.go` | 文案键与占位参数名常量 | `Key*` 30 个、`Arg*` 10 个 |
| `errs_test.go` | 包内单测（白盒），26 个用例 | — |
| `consumer_check_test.go` | 包外单测（`errs_test` 包，黑盒），2 个用例，模拟 `middleware`/`service` 真实用法 | — |

### 3.2 `Error` 的四个字段与不可变语义

```
kind  Kind            // 五档之一，决定性质与 middleware 的状态映射
key   string          // 文案键，i18n 取词的唯一依据；本包不解释其取值
args  map[string]any  // 占位参数，按名索引，供 i18n 填充；可为 nil
cause error           // 底层原因，可为 nil；保留错误链供 Is/As 穿透
```

四个字段**全部小写不导出**，只经方法读取。两条不可变保证：

1. `Args()` 返回 **副本**——否则调用方（如 `handler` 打日志时顺手改 map）会污染错误对象；
2. `WithArgs()` 返回 **新对象**——支撑「下层定档位与键、上层补上下文参数」而不产生共享可变状态。

### 3.3 关键逻辑：三条容易写错、且错了会静默出问题的地方

**① `Is` 按「档位」匹配，而非按「档位 + 键」**

`middleware` 的状态映射、`service` 的分支处理**都只看档位**（唯一冲突 → 409，不关心是用户名重名还是类型重名）。若 `Is` 连键一起比，`errors.Is(err, errs.NewConflict(anyKey))` 会因键不同而为假，调用方只能退化成手写类型断言。因此 `Error.Is` 只比 `kind`（`error.go` 的 `Is` 方法），键与占位参数不参与匹配。

**② `New` 不记堆栈，`Wrap` 才记**

「用户输入错误」是**预期内的业务分支**（如 I-5 汇率未填），不是异常。若 `New` 也 `WithStack`，日志会被大量无意义堆栈淹没。因此：`New` 产出的错误在 `%+v` 下等于 `Error()`（有 `TestNewHasNoStackNoise` 钉住）；只有 `Wrap` 把**外部原因**（SQLite 驱动、解析库）包进来时才 `errors.WithStack(cause)`，让 `%+v` 能打印原始出错位置——与 `go_common/util` 的既有用法一致。

**③ 占位参数在 `Error()` 里按参数名升序输出**

`map` 遍历顺序随机。若不排序，同一个错误每次打印的日志文本都不同，无法做日志比对与告警去重。`formatArgs`（`error.go`）因此先 `sort.Strings` 再拼接，`TestErrorTextFormat` 连取 20 次断言完全一致。

### 3.4 异常与边界处理（5 条）

| 边界 | 处理 | 理由 |
| ---- | ---- | ---- |
| `kind` 非五档之一（含零值） | `normalizeKind` 收敛为 `KindSystem` | 落到未知档位，`middleware` 的状态映射无从下手 |
| `Wrap(nil, ...)` | 退化为无 cause 的错误（`errors.WithStack(nil)` 返回 nil） | 不产生「有包装层但里面是空」的假错误链 |
| 空名占位参数 `A("", v)` | 丢弃 | 无名参数在文案模板里无法索引，留着只会静默失效 |
| 同名占位参数重复传 | 后者覆盖前者 | 行为确定可预期，有 `TestArgsLastWins` 钉住 |
| `*Error` 为 nil 接收者 | 全部方法安全返回（`Kind()` 返回 `KindSystem`、`Error()` 返回 `""`、`Format` 直接 return） | 日志与 `middleware` 可能在错误为空时调用，不能 panic |

### 3.5 非本包错误的兜底：`From` 的三分支

```
From(nil)                       → nil                                  （无错误）
From(链上有 *Error)             → 最外层那个 *Error                    （保留档位/键/参数）
From(第三方错误)                → KindSystem + KeySystemInternal       （原错误留在 cause）
```

第 3 支是「未分类错误不得泄漏给用户」的兜底：`middleware` 拿到的**一定**是有档位、有键的错误，因此不会出现「500 但没有文案键、界面空白」。第 2 支取**最外层**，是为了让上层能重新定档位（如把存储层的唯一冲突重新定性为输入错误）。

## 四、对现有链路 / 性能 / 兼容性 / 下游的副作用

| 维度 | 评估 |
| ---- | ---- |
| 现有链路 | **无**。本轮开工前 `internal/` 不存在，本包是纯新增，不改任何既有文件（除 `go.mod`/`go.sum` 增加依赖声明） |
| 分层与依赖 | `go list -deps` 实测：本包**唯一的非标准库依赖是 `github.com/pkg/errors`**，对 `jotcash` 内部包的依赖为**空集**——§六 L0「层内零依赖」与表头「仅依赖标准库与第三方库」双双成立 |

| 兼容性 | 与标准库错误链**完全互通**：`Error` 实现 `Unwrap`，`errors.Is`/`errors.As`（无论标准库还是 `pkg/errors` 的）都能穿透；`service` 层按项目风格用 `errors.Wrap` 加中文上下文后，`KindOf`/`IsXxx` 仍能取到档位（`TestIsThroughWrappedChain` + 包外 `TestMiddlewareMapping` 双向钉住） |
| 下游（尚未实现的包） | 下游只需 3 个动作：① 产错误用 `errs.NewXxx(key, errs.A(...))`；② 包外部错误用 `errs.Wrap(cause, kind, key, ...)`；③ `middleware` 在出口 `errs.From(err)` 取 `Kind()`/`Key()`/`Args()`。**`i18n` 侧的契约是 `Key() string` + `Args() map[string]any`**，与 go-i18n 系库的 `MessageID` + `TemplateData` 形状天然对齐，将来 `i18n` 选型不受本包约束 |
| `go.mod` | 新增直接依赖 `github.com/pkg/errors v0.9.1`。注：本轮并行会话同时在实现 `base/idgen`，它引入了 `go_common`，故 `go.mod` 中另有 `go_common` 及其间接依赖——**非本包所需**，本包不 import 它们 |
