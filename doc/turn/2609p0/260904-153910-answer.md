## 二、实测结论（决定方案走向的 4 条，均可复现）

在 `/tmp` 建独立探针模块、以 `GOPROXY=off` 走本地 modcache 实跑 `go_common@500c0b32bf4e` 所得：

| # | 实测现象 | 根因（代码定位） | 对本包的约束 |
| - | ------- | -------------- | ---------- |
| **P1** | 只调 `util.Init("jotcash")`，日志 `sn` 仍是随机 18 位数字，日志落在 `log/<随机ID>/log.log` | `util.Init` → `InitOs` **只赋值 `defaultServerName`**（`util/os.go` 第 24~26 行），**不重做日志**。而 `util` 的 `init()` 早于调用方的任何代码执行，那一刻 `defaultServerName` 为空 → `InitLog` 用 `GenStringId()` 兜底（`util/log.go` 第 29~31 行） | `util.Init` **必须**搭配一次 `InitLog` 重做，否则服务名与日志路径全错。这是本包存在的首要理由 |
| **P2** | 进程内**必然**先产生一个 `log/<随机ID>/log.log` | `util.init()` 里的 `initHttp` 会起守护协程并**立即打日志**（实测 2 行「单协程池」，`util/sync.go` 第 219/230 行），lumberjack 随即建目录建文件 | Go 的包初始化顺序不可绕（被 import 的包先初始化），**进程内无法消除**。唯一彻底解法是**进程启动前**置环境变量 `server_name`（`GetServerName` 优先读环境变量，`util/os.go` 第 28~30 行）。实测置 `server_name=jotcash` 后：`sn:jotcash`，且**只有** `log/jotcash/log.log`，无游离目录 |
| **P3** | `log_level=error` 时，`Info`/`Warn` 级的日志被丢弃 | logrus `IsLevelEnabled`（`logger.go` 第 436~438 行）按级别门控 | **A-3 的致命风险**：初始密码若按普通 `Info` 打印，运维把级别调成 `error` 就**永久丢失**；而终版 A-3 明写「不设计恢复路径……唯一出路是重新部署」。故 A-3 打印**必须绕过级别门控**。实测「临时抬级别 + `defer` 恢复」可让该行稳定落盘，且恢复后 `Info` 仍被正常吞掉 |
| **P4** | 重复 `InitLog` 会让 `paramHook` **累积**（1→2 个） | `logrus.AddHook` 是 `append`（`hooks.go` 第 18~22 行），无去重 | `Fire` 里 `getCaller` 会 `runtime.Caller` **循环走栈**（`util/log.go` 第 118~141 行），是每条日志的重头开销，挂 2 个 hook 等于**每行日志走栈两次**。故重做初始化前须 `ReplaceHooks` 清空，保证 `Init` 幂等 |

> 佐证 P2 并非推测：作者本人的 `survive_monitor/log/` 里**同时存在** `log/survive_monitor` 与 `log/250424161206117367` 两个目录——前者是 `-e server_name=` 生效时的正常产物，后者正是没有该环境变量时的游离产物；其 `install-docker.sh` 第 71 行 `-e server_name=$server_name` 即官方规避手段。

## 三、方案取舍

| 议题 | 采用 | 弃用及理由 |
| ---- | ---- | -------- |
| **是否封装 `Info/Warn/Error` 等门面** | **不封装**。全仓库直接用 `logrus.WithContext(ctx).WithFields(...)`，与 `go_common` 生态、`survive_monitor` 完全一致 | 实测封一层后 `caller` 字段指向**包装函数自身**（探针里指到 `main.go:12` 而非调用点 `main.go:22`）——`getCaller` 的 `skip` 是**硬编码 6**，加一层就整体错位，等于亲手废掉日志里最有用的定位字段。分层 §六 也只要求本包"承载日志"，未要求门面 |
| **日志级别来源** | 由 `app` 以 `string` 入参注入 | 不 import `base/config`：违反**约定 8**（`base/config` 仅被 `app`/`cmd` import）与 L0 层内零依赖 |
| **服务名来源** | 包内常量 `DefaultServerName = "jotcash"`，环境变量 `server_name` 可覆盖（go_common 既有机制） | 不进 `configs`：样例第 9~12 行明示配置**只装 5 类部署参数**，服务名不在其中；且它是日志目录名与 `sn` 字段这类纯技术标识，符合**约定 5**（`base/` 不放业务语义） |
| **空/非法级别** | 空串（含纯空白）→ 默认 `info`；非法 → **返回错误、启动失败** | 非法值静默退回 `info` 会让运维以为改生效了。注意 `logrus.ParseLevel` **不接受**带空白的 `" info "`（实测报错），故必须先 `TrimSpace`——这正是 `util/os.go` 里 `GetEnvInt` 注释警告过的同一类坑 |
| **A-3 打印级别** | `Warn`，并临时抬级别保证不被吞 | 不用 `Info`（P3 会丢）；不用 `Error`（这不是错误，会污染错误告警与统计） |
| **A-3「一次性」由谁保证** | 由调用方 A-1 保证（用户名唯一索引使重复初始化天然幂等，分层 §六 `service/account` 行），本包不加 `sync.Once` | 加 `Once` 会**静默吞掉**第二次打印，掩盖上游 bug，且让单测无法重复验证；而 A-1 已在结构上保证只调一次 |

### 登记两处与既有资料的冲突（非阻塞，已按下述依据取舍）

1. **密码红线白名单**：分层 §九 红线行写「**内存流转白名单仅四包**：`rule/passwd`、`service/account`、`service/auth`、`base/pwdhash`」，但同一行的**出口 ③** 又把「A-3 初始密码日志打印」定在 `base/log`。二者互斥——要打印就必须先在内存里拿到明文。**采用**：以出口 ③ 为准，`base/log` 是第 5 个可接触明文的包，其职责严格限定为「接收→打印」，不存储、不返回、不二次加工。建议后续把红线行的白名单补为五包。
2. **`sn` 字段与「一次性打印」的可见性**：`base/log` 打印的行，`caller` 会指向本包而非 `service/account`。**采用**：这是期望行为——红线现场集中在一处，便于评审用 `caller` 反查是否有第二处打印明文。

## 四、模块设计

包路径 `internal/base/log`（分层 §十 目录树第 326 行），包名 `log`。**零业务依赖**，只依赖 `go_common/util` + `logrus`（第三方库，符合 L0「仅依赖标准库与第三方库」）。

| 导出项 | 签名 | 职责 / 关键逻辑 | 异常分支 |
| ------ | ---- | ------------- | ------- |
| `DefaultServerName` | `const = "jotcash"` | 日志目录名 `log/jotcash/` 与 `sn` 字段值；环境变量 `server_name` 优先 | — |
| `DefaultLevel` | `const = "info"` | 与 `configs/jotcash.example.yaml` 第 39 行默认值对齐 | — |
| `Init` | `func Init(level string) error` | ①`TrimSpace`，空则取 `DefaultLevel`；②`ParseLevel`；③`util.Init` 落服务名；④`ReplaceHooks` 清空旧 hook（P4）；⑤`util.InitLog` 重做（P1）。**幂等**，可重复调用 | 级别非法 → 返回错误，`app` 据此启动失败 |
| `ParseLevel` | `func ParseLevel(level string) (logrus.Level, error)` | 供 `base/config` 在**读配置阶段**提前校验 `log_level`，把错误暴露在配置校验而非日志初始化 | 同上 |
| `PrintAdminInitPassword` | `func PrintAdminInitPassword(ctx context.Context, username, password string)` | **A-3 唯一落盘明文口**。加锁 → 若当前级别低于 `Warn` 则临时抬到 `Warn` 并 `defer` 恢复 → 打一行 `Warn` | `password` 为空 → 打 `Error` 告警而**不**打印空密码（上游必有 bug，静默会让 admin 拿不到密码） |

**输入输出**：`Init` 入 `level` 出 `error`，副作用是 logrus 全局单例被配置为「stdout + `log/<服务名>/log.log`（1MB 切分 / 保留 100 个 / 30 天）」——沿用 `InitDefaultLog` 的既有参数（`util/log.go` 第 25 行），不自定义，避免与生态其它服务的运维口径分叉。

## 六、副作用评估

- **对现有链路**：仓库此前只有 `go.mod`/`README.md`/`doc/`/`configs/`，**无存量 Go 代码**，本包为首个包，无兼容性影响。
- **性能**：每条日志经 `paramHook` 一次 `runtime.Caller` 走栈 + 一次原子读 IP。已通过 `ReplaceHooks` 保证 hook 不累积（P4），避免成倍开销。
- **下游**：`app`（L7）须在启动早期调 `log.Init(cfg.LogLevel)`；`service/account` 在 A-1 调 `PrintAdminInitPassword`；`middleware` 的请求日志待 HTTP 框架选定后再落（分层 §十三 明示"不选具体框架与库"，本轮不预设 gin）。
- **运维**：建议部署时置 `server_name=jotcash`（对齐 `install-docker.sh` 做法），以消除 P2 的游离日志目录。`.gitignore` 第 37~38 行的 `/log/` + `*.log` 已能覆盖正常与游离两种产物，**无需改动**；其刻意不写 `log/` 的注释也证实 `internal/base/log` 源码不会被误忽略。
- **安全**：`log/jotcash/log.log` 含 admin 初始密码明文（终版前提 1 + A-3 已显式接受）。已在代码注释与本文件登记：该文件的存放与分享范围需受控。

## 九、结论

**阻塞性问题：无。** prompt 两处引用偏差已按代码实际纠正（§一），4 条实测结论已全部转化为设计约束（§二→§三/§四），2 处资料冲突已登记并给出取舍依据（§三）。代码与单测已实施并验证通过（§七）。

需你**知会/确认**的 3 项（均已按上述依据取默认值，不阻塞后续开工）：

1. **服务名定为 `jotcash`**——它决定日志目录 `log/jotcash/` 与 `sn` 字段值。
2. **部署时建议置环境变量 `server_name=jotcash`**——这是消除 P2 游离日志目录的唯一彻底手段，属部署动作，代码侧无法代劳（作者本人的 `survive_monitor` 即以 `-e server_name=` 规避，其 `log/` 下同时留有正常与游离两个目录，是该问题的现成实例）。
3. **分层方案 §九 密码红线的「内存流转白名单四包」建议补为五包**（增 `base/log`），以消除与同行出口 ③ 的自相矛盾。
