## 一、核心目标与范围边界

| 项 | 内容 |
| -- | ---- |
| 核心目标 | 落地 L0 的 `base/log`：① 全仓库日志的**统一初始化入口**（承接 `base/config` 的 `LogLevel`）；② **A-3 admin 初始密码的一次性打印**——§六 L0 `base/log` 行原文「这是全系统唯一把**密码明文写入持久介质**的地方」 |

## 三、对指定依赖 `util/log.go` 的实测核验（4 处坑，全部有实证）

不凭签名猜行为。探针为 `/tmp` 下的临时模块，**未污染本仓库**，用后即弃。

先读清源码事实（`go_common/util/log.go` + `util/os.go` + `util/util.go`）：

- `util/util.go` 的**包级 `init()`** 会执行 `InitDefaultLog()`；`InitDefaultLog` = `InitLog(GetServerName(), "", 1, 100, 30, logrus.InfoLevel)`。
- `GetServerName()`（`util/os.go`）= `GetEnvString("server_name", defaultServerName)`，而 `defaultServerName` **只由 `InitOs` 赋值**；`util.Init(serverName)` 的全部内容就是 `InitOs(serverName)`。
- `InitLog` 里 `serverName == ""` 时回退为 `GenStringId()`（一个 18 位随机 ID），日志落到 `log/<serverName>/log.log`。

| # | 坑 | 实测证据 | 后果与本包对策 |
| - | -- | -------- | -------------- |
| **1** | **照参考写法只调 `util.Init` 是无效的**——包级 `init()` 早于任何用户代码执行，此时 `defaultServerName` 仍为空，日志已按随机 ID 配好；之后再调 `util.Init` 只改了那个变量，**不会重配日志** | 探针只调 `util.Init("jotcash")`：日志字段 `[sn:260906020551358988]`，落盘目录 `log/260906020551358988/`；而 `util.GetServerName()` 却已返回 `jotcash`——**二者不一致**即证明「改了变量、没重配日志」 | 这正是两个兄弟 answer 观察到的「服务名回退为一个随机 ID」的成因。**对策**：`util.Init` 之后**必须再调一次 `util.InitLog(...)`** 重新配置。实测补调后 `[sn:jotcash]`、目录 `log/jotcash/`，符合 `.gitignore` 注释所述的 `log/<服务名>/log.log` 形态 |
| **2** | **进程启动瞬间必然多出一个随机名日志目录**，无法在 Go 代码里消除（它由 import 副作用在 `main` 之前产生） | 同上探针：`log/` 下同时存在 `260906020551358988/`（init 阶段）与 `jotcash/`（补调后）。仓库现状亦可见此证据——`internal/base/config/log/260906020206191881/` 等 3 个随机名目录、`internal/base/idgen/log/…` 4 个，都是兄弟包测试期留下的 | **只能在进程外规避**：`server_name` 环境变量在**进程启动前**即生效，`GetEnvString` 第一顺位读它。实测 `server_name=jotcash go run .` → 全程只有 `log/jotcash/`，**无随机目录**。本包把该键名与用法写成导出常量 `ServerNameEnvKey` + 包注释，供部署方选用；Go 侧不做无用挣扎 |
| **3** | **把 logrus 包一层薄封装会永久破坏 `caller` 字段**——`paramHook.getCaller` 用固定 `skip := 6` 回溯栈帧，多一层包装就整体错位一帧 | 探针同时打两条：直连 `logrus.WithContext(...).Info()` → `caller:"…/probe2/main.go:27"`（**正确**，指向调用点）；经一层 `wrapInfo()` → `caller:"…/probe2/main.go:20"`（**错误**，指向封装函数自己那一行） | **决定性依据**：本包**不封装** `Info/Warn/Error`。全仓库继续直写 `logrus.WithContext(ctx).WithFields(...)`——这既是 `go_common` 与两个兄弟包既有的写法（`config.go` 通篇如此），也是唯一能让 `caller` 指向真实出错位置的写法。本包只做「初始化」与「A-3 专用通道」两件事 |
| **4** | **A-3 打印会被日志级别静默吞掉**——`log_level` 是部署方可配的（`configs/jotcash.example.yaml:39`），配成 `error`/`warn` 时按 `Info` 打印的密码**不会出现在任何地方** | 探针在 `ErrorLevel` 下打三条：`Info`/`Warn` **均无输出**，仅 `Error` 落盘 | **这是本包最要紧的一条**。A-3 是 admin 初始密码的**唯一交付路径**，而 §二 A-3 明写「初始化那一次的日志若丢失，`admin` 将**永久无法登录**，唯一出路是重新部署」。让一个部署参数能把它静默抹掉，等于把「系统无法登录」做成一个配置项。**对策见 §四 决策 3**：A-3 走 `util.CreateLog` 独立日志器，**级别写死 `Info`、独立文件名**，不受全局级别影响。实测：全局 `error` 下，`log/jotcash/log.log` 里没有密码行，`log/jotcash/init_password.log` 里**正常写入** |

> 补充核实（lumberjack v2.0.0 源码 `lumberjack.go:78-99` 与 `oldLogFiles()`）：`MaxAge`/`MaxBackups` 的清理**只作用于带时间戳的已轮转备份文件**（`oldLogFiles` 靠 `timeFromName` 解析文件名，解析失败即「不是备份文件」而跳过），**当前正在写的 `init_password.log` 永远不会被按天数删除**。这对 A-3 是必要性质：初始密码日志不能在 30 天后自动消失。但备份文件仍会被清理，故留存责任仍在部署方（见 §六 B2）。

## 四、方案与关键取舍

**总体思路**：本包是 `go_common/util` 之上的**极薄适配层**，只做三件不可省的事——① 把「服务名」这一项收敛为唯一常量并修正 `util` 的初始化时序（坑 1）；② 承接 `base/config.LogLevel`（冲突 2）；③ 为 A-3 提供一条**不受级别影响、独立成文件**的落盘通道（坑 4）。日常打点一律直写 logrus，本包不插手（坑 3）。

| # | 决策 | 取舍与依据 |
| - | ---- | ---------- |
| 1 | 出 **`Init(level string) error`** 与 **`MustInit(level string)`** 两个入口；服务名不作参数，取包常量 `DefaultServerName = "jotcash"` | 服务名是**本仓库的身份**而非部署差异，`internal/base/config/config.go:319` 已把它排除在配置之外，故不开参数（要覆盖用 `server_name` 环境变量，见坑 2）。级别用 `string` 而非 `logrus.Level`：`base/config` 已把它规整为 logrus 规范名（`config.go:292` `level.String()`），传字符串使两包契约与 `zz_consumer_check_test.go:134` 的桩函数 `func(level string)` 逐字对齐，`app` 无需引入 logrus 类型。返回 `error` 供 `app` 决定是否终止；`MustInit` 供无处理分支的场合 |
| 2 | **不封装** `Info/Warn/Error/Debug` 等日常打点函数 | 实测坑 3：任何封装都会让 `caller` 指向封装函数自身，全仓库日志的定位能力当场作废（`skip` 固定为 6，无法从外部修正）。且直写 logrus 已是 `go_common` 与两个兄弟包的既有风格（约定 3「注释与日志一律中文」约束的是语言而非形式）。**代价**：无法在本包统一给日志加字段——但 §六 L6 `middleware` 的全局链本就是加请求级字段的正确位置 |
| 3 | **A-3 走独立日志器**：`util.CreateLog(DefaultServerName, "init_password.log", …, logrus.InfoLevel)`，级别**写死**，与全局 `logrus` 完全解耦 | 备选有二，均被否：<br>① **走全局 logrus 的 `Info`** —— 实测坑 4，`log_level=error` 时密码静默消失，等于 admin 永久无法登录；<br>② **走 `Error` 级** —— 能穿透绝大多数级别配置，但把一条正常的初始化事件记成错误，会污染「有无 ERROR」这一最常用的巡检信号，且 `panic`/`fatal` 级仍会吞掉它。<br>选独立日志器：级别在包内写死（部署方**无法**调低），且**独立文件名**带来两个额外好处——A-3 的证据不与海量业务日志混在一起（§二 A-3 要求用户去日志里找这一次的密码），且不会被业务日志的滚动切割挤出去（`MaxSize=1MB` 下 `log.log` 轮转很快）。代价是多一个文件与一个 lumberjack 句柄，可忽略 |
| 4 | **「一次性」用 `sync.Once` 在包内兜死**，重复调用记警告并忽略 | §二 A-3 原文「**仅在初始化创建的那一次**……此后不再生成也不再打印」。语义上的一次性由 `service/account` 的 A-1 保证（用户名唯一索引使重复初始化幂等），但本包作为**唯一落盘出口**再加一道结构性兜底：即便上层将来出现循环或重试，明文也只可能落盘一次。这是准则 6「约束优先用结构表达」在本包的落点 |
| 5 | **入口签名只收 `用户名 + 明文密码`，不收 `User` 实体、不收哈希与盐** | §九 红线行：「`密码哈希` 与 `盐` **连三类出口都不得出现**」。签名里根本没有这两个参数，就不存在「传进来但忘了过滤」的可能——与 `dto` 用「字段根本不存在」表达前提 6 是同一手法。同时本包**不 import `entity`**（L0 不得有业务语义类型，约定 5），传 `User` 实体在分层上也不成立 |
| 6 | 明文**只出现在 `password.go` 这一个文件**，且该文件不打印任何其他内容 | 让「哪一行代码会把密码写进磁盘」这个问题有一个单文件的答案，评审与 `grep` 都只需看一处。`log.go` 负责初始化，与明文完全无关 |

## 五、模块职责 / 输入输出 / 关键逻辑 / 异常处理

| 文件 | 职责 | 输入 → 输出 | 异常处理 |
| ---- | ---- | ----------- | -------- |
| `log.go` | 统一初始化。`Init` 校验并解析级别 → `util.Init(DefaultServerName)` 修正服务名 → `util.InitLog(...)` **重新配置**全局 logrus（修正坑 1） | `level string` → `error` | 级别非法即返回 error（**不静默降级**，与 `base/config.checkAndReset` 同一取向：静默降级会造成「配置看似生效实则未生效」）；空串按 `logrus.InfoLevel` 回落，与 `config.DefaultLogLevel` 一致 |
| `password.go` | A-3 唯一出口。`sync.Once` 内构造独立日志器并打印一条 | `username, plainPassword string` → 无 | 明文为空即视为调用方缺陷，记 `Error` 并**不落明文**（不 panic：A-1 已在事务中，崩掉会让初始化半途而废，而空密码本身已由 `rule/passwd` 保证不会发生）；重复调用记 `Warn` 后忽略 |

**调用方（§六 与 §八 A 域已定，无第三个）**：

```
app            → log.MustInit(config.LogLevel)   启动装配时初始化（约定 8：配置只在 L7 读）
service/account → log.PrintInitPassword(用户名, 明文)  A-1 建 admin 时一次性打印（§八 A 域协作包列 base/log(A-3)）
```

> 注：§六 L6 `middleware` 行的依赖列含 `base/log`，指的是它挂载「请求日志」中间件——本包不提供该中间件（范围外①），届时直接用 `util.GinLog` 或直写 logrus。

## 六、副作用评估与已知边界

| 维度 | 评估 |
| ---- | ---- |
| 现有链路 | **无破坏**。本包为新增，无存量调用方；`go.mod` 依赖零新增（`go_common` 已由 `base/idgen`、`base/config` 引入） |
| 分层合规 | 合规。仅 import `go_common/util` + `logrus` + 标准库，**不 import 任何 `base/` 兄弟包**，L0 层内零依赖成立；无业务语义类型（用户名与密码以 `string` 传入，不引 `entity`） |
| 全局副作用 | `util.InitLog` 会**重设全局 logrus** 的级别、输出与格式化器，并**追加一个 hook**。因此 `Init` 应在启动阶段调用一次；重复调用会累加 hook（同名字段被覆盖为同值，不产生重复字段，实测无异常），但仍不建议 |
| 性能 | 初始化一次性开销；A-3 打印一次。`log.log` 与 `init_password.log` 各持一个 lumberjack 句柄，`MaxSize=1MB / MaxBackups=100 / MaxAge=30`（沿用 `util.InitDefaultLog` 的既有参数，不自定，L0 表只列「日志级别」一项） |

| # | 已知边界（登记，非阻塞） | 说明 |
| - | ------------------------ | ---- |
| B1 | 进程启动瞬间的**随机名日志目录**无法在 Go 内消除 | 由 `util` 的包级 `init()` 在 `main` 之前产生（实测坑 2）。部署时设 `server_name=jotcash` 可完全避免；`.gitignore` 的 `/log/`、`*.log` 已覆盖仓库内的产物 |
| B2 | A-3 日志的**留存责任在部署方** | 本包保证「写下去且不被级别吞掉」，且实测确认 lumberjack 不会按天数删除当前文件；但**备份文件**仍受 `MaxBackups`/`MaxAge` 清理，且磁盘丢失、目录被清等情形不在本包能力范围。§二 A-3 已显式接受该风险（「日志若丢失，admin 将永久无法登录」），`configs/jotcash.example.yaml:37-38` 亦已提示 |

## 七、跨包影响登记

**`app` 的启动时序有一处硬约束**：`log.Init` 必须在 `config.Load` **之后**、在其余装配**之前**。理由是 `config.Load` 自己就会打日志（`config.go:187/200/214` 等），那些日志会落在 `util` 包级 `init()` 配好的**随机名目录**里；只有 `log.Init` 执行之后，日志才进入 `log/jotcash/`。这不构成缺陷（配置加载的日志本就在服务名确定之前发生，且 `server_name` 环境变量可让两者一致），但 `app` 实现时若把顺序写反——先 `log.Init` 再 `config.Load`——则拿不到级别，故登记。

## 二、对话1 未能复现的一项：单测并非全部 PASS

对话1 §九 第 3 行称 `go test ./internal/base/log/... -race -count=1` **全部 PASS**。实测（同命令、同 Go 1.27.0、同依赖）：

**根因（已实证，属测试缺陷而非生产缺陷）**：

- `initPasswordOnce` 是**包级** `sync.Once`，在**整个测试二进制**内只生效一次；
- 包内测试 `password_test.go` 靠私有助手复位它，逐条验证语义；

- 文件按名排序执行，`zz_` 前缀又刻意让它排在最后 → 轮到它时 `Once` 已被耗尽 → `PrintInitPassword` 直接走「重复调用」分支 → 专用日志文件**根本不被创建** → 断言失败。

**对照实验（证明是顺序依赖，而非功能损坏）**：

| 命令 | 结果 |
| ---- | ---- |
| `go test -run TestAppStartupThenInitAdminFlow` | **ok**（单独跑，`Once` 未被消耗） |
| `go test -run 'TestPrintInitPasswordEmpty\|TestAppStartupThenInitAdminFlow'` | **FAIL**（前序用例先耗掉 `Once`） |

推测对话1 大概只跑了单个用例或子集便记为全绿。这也说明：**只在「全量 + 乱序」下跑过的测试结果才可采信**。
