## 一、范围与承载对齐

本轮**只实现 `base/calendar`**（prompt「具体任务」第 52 行）。层级第 94 行给该包定了四项承载，与本轮交付逐项对应：

| # | 层级第 94 行的承载原文 | 落点 | 说明 |
|---|---|---|---|
| 1 | **不带时区的日历日期类型**（前提 7：账单字面值，解析、存储、归月全程不做时区换算） | `Date`（`date.go`） | 三处结构性拦截，见 §四 |
| 2 | 年月类型 | `Month`（`month.go`） | 内部以月序号存储，见 §三.4 |
| 3 | 区间运算（`起始月 + N − 1`、`起始月 ≤ M ≤ 结束月`） | `MonthRange.EndMonth` / `Contains`（`monthrange.go`） | 以 (起始月, 月数) 表示，见 §三.5 |
| 4 | **日期 → 所属月** | `MonthOf`（`month.go`） | H-2 与 J 域未摊分口径的共同基础 |

**依赖约束**：层级第 94 行该包的依赖列是 `—`，即 **L0 层内零依赖**。已验证：本包不 import 任何 `jotcash/internal` 兄弟包，非标准库依赖只有既有的 `github.com/pkg/errors`（与 `base/decimal`、`base/pwdhash` 一致），**`go.mod` / `go.sum` 本轮零改动**（§七 已给出逐字节比对结果）。

**明确划在范围外**（避免越界实现别人的职责）：

- 金额如何均分、尾差如何归末月 → `rule/amortize`（层级第 115 行「**不变式 1b 的唯一实现处**」）。本包只提供它所需的纯月份算术，符合层级约定 5「`base/` 是纯技术层」。
- 账单字段的 trim / 清洗 → `parser`（层级第 127 行「原始交易行」）。本包的 `ParseDate` 刻意不 trim 空格，理由同 `base/decimal.NewFromString`。
- 业务时间戳（创建 / 更新 / 操作时间）→ **不属本包**。层级第 304 行明确「业务时间戳…不受此限」，故本包不碰 `time.Time` 型的时间戳字段。

## 三、方案取舍

### 3.1 「避免自己造轮子」的落法：历法委托标准库，**不引第三方日期库**

prompt 第 57 行要求「优先采用 github 上成熟稳定 star 多的代码库（如果有），避免自己造轮子」。我按此要求实测了业界主流的 `cloud.google.com/go/civil`（google-cloud-go 主仓），**结论是不引入**——但「避免造轮子」的要求本身是达成了的：本包**不含任何一行闰年判断、月长表或儒略日换算**，历法全部委托标准库 `time`：

```
日期是否真实存在 → time.Date(y,m,d,…) 规范化后三字段是否原值不变
                   （2026-02-30 被规范化为 2026-03-02，比对即知非法）
定长文本解析     → time.Parse("2006-01-02" / "2006-01")
月末日           → 下月 1 号减一天
```

不引 `civil` 的两条理由都是**实测出来的，不是主观取舍**：

**理由①：成本与收益不对等。** `civil` 包本身只有约 500 行、编译期确实只依赖标准库；但它属于 google-cloud-go **主仓根模块** `cloud.google.com/go`（其 `go.mod` 有 59 行 `require`）。在本仓库实测 `go get cloud.google.com/go/civil`：

| 指标 | 引入前 | 引入后 |
|---|---|---|
| `go list -m all` 模块图 | 100 条 | **143 条（+43）** |
| `go.mod` require | 原样 | +65 行 |

换来的只是一个标准库已完全覆盖的 `IsValid` 判据。而层级第 94 行给本包的依赖列是 `—`。

**理由②（决定性）：`civil` 的月份算术在本仓库的核心场景上是错的。** `civil.AddMonths` 经 `time.AddDate` 实现，**带日溢出**：

```
civil.Date{2026,1,31}.AddMonths(1) = 2026-03-03   ← 所属月是 3 月，不是 2 月
```

而本包承载的「起始月 + N − 1」恰恰服务 H-2 摊分：**1 月 31 日的消费摊 2 个月，结束月必须是 2026-02**。实测仅 2026 一年就有 **7 个起始日会算错**（1/29、1/30、1/31、3/31、5/31、8/31、10/31）。这类错误不会抛异常，只会让 §8.2 的均分份数与区间穿刺**静默错一位**。

因此 `Month` 的月份算术走**纯整数月序号**（`年 × 12 + 月 − 1`）：结构上不存在「日」这一维度，日溢出无从发生（层级§五准则 6「约束优先用结构表达」）。

> 附：也评估过轻量 fork `github.com/golang-sql/civil`（模块图仅 +1）。但它是 2022 年的快照、`civil.go` 与上游同源，**同样带日溢出的 `AddMonths`**，理由②依旧成立，故一并不采用。

### 3.2 标准库判据与 `civil` 的等价性已逐条验证

不能只凭「标准库应该没问题」就替换掉候选库，故做了三层比对（§七 有完整结果）：

1. **18 组边界用例**与 `civil.IsValid` 逐条一致（平年闰日、2 月 30 日、月份 0/13、日 0/32、世纪闰年 1900/2000 等）；
2. **1~9999 年全量回归**：可构造的 2 月 29 日共 **2424** 个，恰等于公式 `9999/4 − 9999/100 + 9999/400`；
3. **119 988 组月末日** `String → Parse` 往返**零失败**。

### 3.3 `Date` **可比较**（与 `base/decimal.Decimal` 刻意相反）

`decimal.Decimal` 内含 `*big.Int`，`==` 比的是指针，故那边刻意不可比较。`Date` / `Month` 则三字段全是值类型：**`==` 即相等、可作 map 键**。这是刚需而非顺手：

- §8.3 判重的四要素「归属用户 + 支出日期 + 支出金额 + 支出币种」等值匹配，要按「(日期, 金额, 币种)」元组批量取候选（层级第 94 行 `store` ④），**元组必须能进 map**；
- J 域按月分组聚合直接拿 `Month` 当键。

### 3.4 `Month` 内部存**月序号**，不存 (年, 月) 两字段

承载的两项运算（`起始月 + N − 1`、`起始月 ≤ M ≤ 结束月`）在序号上都退化为**整数加减与比较**，没有进位 / 借位分支，也就没有「12 月加 1 月忘了进年」这类错法。代价是 `splitMonthIndex` 对负序号不成立——已由所有出口的 `checkYear` 前置拦住，并有 `AddMonths(-1/-12/-13/-100000)` 与 `1<<40` 的用例锁死。

### 3.5 `MonthRange` 以 **(起始月, 月数)** 而非 (起始月, 结束月) 表示

终版§四把 `摊分月数` 定为用户可编辑字段、把 `摊分起始月` / `摊分结束月` 定为**只读派生**。若存 (起始, 结束)，就等于承认「起始月 > 结束月」这种非法状态可被构造出来；存 (起始, 月数) 并强制月数 ≥ 1，则 `结束月 ≥ 起始月` **由结构保证**。

`IndexOf` **从 1 起计**，是为了让 `rule/amortize` 判「是否末月」（尾差归末月）能写成 `IndexOf(m) == Count()`，与 H-2 原文「第 1 个摊分月」逐字对应；从 0 起计就得写 `== Count()-1`，与规则文字差一位，是典型易错点。

### 3.6 定长文本 + TEXT 列落库：让**字典序恒等于时间序**

`String` 一律补零到定长，因此 `"2026-09-01" < "2026-10-01"`、`"2026-09" < "2026-10"` 恒成立。`store/sqlite` 无原生日期类型，定长文本让 F-3 排序、F-4 区间筛选、§8.2 区间穿刺**全部可直接下推给 SQL**，无需额外转换。§七 有「SQL 侧字典序排序 vs 内存侧时间序排序」逐位比对的用例。

### 3.7 零值语义：`Date{}` / `Month{}` 即「未设置」，且**不可能被误当成合法值**

零值年份为 0 而 `MinYear = 1`，故零值恒非法。`String()` 输出刻意非法的 `0000-00-00` / `0000-01`（肉眼与日志可辨），且**无法被 `ParseDate` / `ParseMonth` 读回**。落库与序列化遇零值一律报 `ErrZeroValue`——`Expense.支出日期` 与摊分起止月都是必填（终版§四），静默输出非法形态只会把问题推到下游。

### 3.8 `isOutOfRangeErr` 的判据：**实测推翻了初版写法**

要把标准库解析错误分成「形态不符」与「值越界」两档。初版按 `*time.ParseError.Message != ""` 判定，实测发现**是错的**：`Message` 还会取 `: extra text: "…"` 形态（尾随空格、带时刻的输入都属此类），会把形态不符误判成值越界。改判据为 `strings.HasSuffix(Message, "out of range")`，并针对两类陷阱做了对抗性验证：

- 用 `Message` 而非 `err.Error()`：后者含**输入文本本身**，账单里若出现 `out of range` 字面内容会被误判；
- 用 `HasSuffix` 而非 `Contains`：`extra text` 会把用户文本嵌在引号里，`Contains` 会把 `2026-01-05out of range` 误判成越界。

**24 组用例**（含 3 组对抗性输入）全部通过，见§七。

## 四、前提 7 的三处结构性拦截

终版第 22 行与层级第 304 行要求「**任何包不得引入带时区的时间类型参与支出日期的解析、存储与归月**」。仅靠注释约定守不住，故落成三处结构拦截：

| # | 拦截点 | 做法 | 若不拦的后果（实测） |
|---|---|---|---|
| ① | `Today(loc)` | 强制显式传时区、**不接受 nil**；本包不读 `time.Local` | 回落 `time.Local` 会让归月随部署机器 TZ 变化 |
| ② | `Scan` | **拒收 `time.Time`**，只接受文本 | 同一瞬间 `2026-01-31T20:00:00Z` 在 UTC 下是 1 月 31 日、在 `Asia/Shanghai` / `Pacific/Kiritimati` 下是 **2 月 1 日**——**跨月即跨归月口径** |
| ③ | 无 `time.Time → Date` 通用转换 | 只有 `Today` 一个例外（「今天是几号」本身必须先选时区） | 任何中转都会重新引入时区维度 |

**连带的建表要求（须在阶段 5 `store/sqlite` 遵守）**：支出日期 / 摊分起止月列**必须是 TEXT**，且 DSN 不得开启把该列自动解析为时间的选项；否则 `Scan` 会返回 `ErrScanUnsupported`——这正是期望行为，**配置错配当场暴露**，而不是静默换个日期。此项已写入 `Date.Scan` 的代码注释。

### 7.3 反向故障注入：确认用例真的能失败

「测试通过」若因为用例根本抓不到问题，则毫无价值。故逐个注入本包最该防住的三类缺陷，确认用例会失败，并在每次注入后**还原到逐字节一致**：

| 注入的缺陷 | 触发的失败用例 | 报错摘要 |
|---|---|---|
| 月份算术改成带日溢出的日期级加减（即模拟改用 `civil.AddMonths`） | **7 个**测试失败，含 `TestMonthAddMonthsAvoidsDayOverflow`、`TestMonthArithmeticAgainstIndependentTuple` | `日溢出: 支出日期 2026-01-31 摊 2 月，结束月应为 2026-02，实际 2026-03` |
| `Scan` 放行 `time.Time`（违反前提 7） | `TestDateScanRejectsTimeTime`、`TestNoTimezoneTypeInPublicAPI` | `应拒收 time.Time，实际 <nil>` |
| `EndMonth` 漏减 1（`起始月 + N`） | **8 个**测试失败，含 `TestAmortizeFlowAsRuleAmortize`、`TestIntervalPierceAsStore` | 区间与摊分份数全线不符 |

> 过程中还发现一次**我自己的注入写错了**（造成编译失败而非用例失败），已修正后重跑，确认注入生效且用例正确捕获——否则会得出「用例抓不到时区缺陷」的错误结论。
