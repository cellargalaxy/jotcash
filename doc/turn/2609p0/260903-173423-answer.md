## 一、先界定「规范」——它不是一个标准，是五个

「记账系统是否符合规范」没有单一答案，因为记账系统同时坐在五个互不相干的标准族交叉点上。不先拆开，任何「符合 / 不符合」都是空话。

| # | 规范域 | 代表标准 | 对本系统是否强制 | 总判定 |
| - | ------ | -------- | ---------------- | ------ |
| 1 | **会计记账原理** | 复式记账、科目表（Chart of Accounts）、期间关账、《会计基础工作规范》红字更正法 | 个人自用**不强制**（无对外报送、无审计义务） | **不符合**，且是结构性的 |
| 2 | **外币折算** | IAS 21 / 《企业会计准则第19号——外币折算》、ISO 4217 | 不强制，但直接决定**数字对不对** | **主干符合**，3 处偏离 |
| 3 | **金融数据交换** | ISO 20022 camt.052/053/054、OFX、SWIFT MT940、QIF | 不强制，但决定**能不能接生态** | **缺关键机制**（无唯一标识、无余额对账） |
| 4 | **审计与留痕** | NIST SP 800-92、ISO 27001 A.12.4、OWASP ASVS 4.0 V7、《会计档案管理办法》 | 个人不强制 | **主体齐备**，缺 3 类字段 |
| 5 | **安全与隐私** | OWASP ASVS、NIST SP 800-63B、PCI DSS v4.0、等保 2.0、GDPR Art.20 / PIPL 第45条 | 个人自建**不适用**；对外提供服务即全部触发 | **已显式接受偏离** |

**一句话结论**：

- 在你自己声明的边界内（个人、只记支出、假定无人能直接读写数据库），当前方案**自洽、克制、而且比多数个人记账工具更规范**——尤其是汇率快照、软删除终态、批次即审计这三处。
- 但「规范」在记账领域的**默认含义**是第 1 类：复式记账 + 科目表 + 期间关账。按这个默认含义，当前方案**不符合**，而且这不是补几个字段能解决的——它是「一行 = 一笔单边支出」这个数据形态的必然结果。
- 真正需要你决策的不是「规不规范」，而是「**要往哪个方向扩**」。三个方向的改造成本相差两个数量级（见第七节）。

## 三、❌ 结构性不兼容（4 项）

### C-1 单式记账 vs 复式记账

| 项 | 内容 |
| -- | ---- |
| **现状** | 前提 2「**只记支出**，不涉及收入、结余、资产负债；负金额表示退款/冲正，作抵扣而非收入」（终版 §一 前提表第 2 行） |
| **溯源** | ⚠️ **这条从未被你确认过**。`260901-223131-answer.md:478` 待确认表 Q3「是否只记支出不记收入 / **仍未回答，本轮继续按『只记支出』设计**」——它是我方的推断前提，不是你的决策。原始诉求（`260901-223131-prompt.md` 对话1）通篇只谈支出字段，但从未排除收入 |
| **规范** | 业界记账系统（GnuCash / Beancount / Ledger / QuickBooks / 用友、金蝶）**一律复式**：一笔交易展开为 ≥2 条分录，借贷相等，恒等式是 `资产 = 负债 + 权益`，而不是本系统的 `本位币金额 = 支出金额 × 折算汇率` |
| **为什么不能增量加** | `Expense` 是「一行一笔单边支出」，没有对手科目。加收入**不是加一个「方向」字段就行**：8.2 摊分按单边金额均分、8.1 恒等式只有一个金额、E-1 四要素查重不含方向、J 域一律「按数据库字面数值相加」——四处规则全部按单边写死 |
| **改造形态** | `Expense` 必须拆为 `Transaction`（交易头）+ `Entry`/`Split`（分录行）两层，`Expense` 的 22 项属性要重新划分到两层，8.1 / 8.2 / 8.3 / J 域全部重写 |
| **判决标准（很简单）** | **只要出现「转账」**——同一笔钱从 A 账户到 B 账户——单式记账就会重复计数或漏计，没有补丁可打。信用卡「还款」就是转账 |

### C-2 无账户实体 → 导入完整性无法验证

| 项 | 内容 |
| -- | ---- |
| **现状** | 卡片信息是 `Expense` 上的三个冗余属性（`银行名称` / `卡号后四位` / `卡片币种`，终版 §四 3「系统只读」组）；「银行卡片档案」在 §六「刻意不建实体」中被明确排除 |
| **溯源** | 你的决策，`260901-223131-prompt.md` 对话2 J-01「银行卡片在上传的文件中自动解析（如果有的话），不额外进行手动维护」 |
| **规范** | ISO 20022 camt.053 的 `Bal`（`OPBD` 期初 / `CLBD` 期末）、OFX 的 `<LEDGERBAL>`、MT940 的 `:60F:` / `:62F:` **全部强制携带账户余额**。它们存在的唯一目的就是让导入方验证「这批交易是否完整」——期初 + 本期发生额 = 期末 |
| **后果** | 当前系统**没有任何机制能发现漏解析**。去重（E-1/E-2）只能防「多」不能防「少」。唯一曾经的候选是对话2 的 C-07「解析出的笔数/金额合计与账单汇总值比对，防止漏解析」，被你明确批注「**这个不采纳**」（`260901-223131-prompt.md` 对话2 C-07 条）。终版 D 域 7 项（D-1~D-7）中确认无任何完整性校验 |
| **为什么结构性** | 余额对账需要 `Account` 实体 + 账户级期初/期末余额 + **收入与还款行也要入库**——最后一条直接把 C-1 拖进来。这两项是成对出现的，不能只做一个 |

### C-3 本位币金额只读 → 无法登记银行实际入账金额

| 项 | 内容 |
| -- | ---- |
| **现状** | 前提 6「**本位币金额是只读因变量**，恒等于「支出金额 × 折算汇率」，**无人工指定入口**」；不变式 1；终版 §八 8.1 末段「代价（已知并接受）：用户无法直接指定本位币金额，只能通过填入反推的汇率逼近」 |
| **溯源** | 你在 `260902-214813-prompt.md:83` 原本要求「用户手动改本位币金额时…系统联动修改的都应该是支出金额」，即本位币金额**可编辑**；对话4（T24 结案）把它推翻为只读因变量，并在 §七 明确登记了代价，举的正是「3 USD 入账 21.71 CNY，需汇率 7.236666…，截位后本位币金额会有分位偏差」 |
| **规范** | 外币交易的本位币金额，权威值是**发卡行实际入账金额**——它直接印在账单上。汇率是它除出来的结果，不是反过来。IAS 21.21 要求按交易日即期汇率折算，但**当存在实际结算金额时，实务一律以实际结算金额入账**，因为银行实际用的汇率含点差与手续费，与任何公开日汇率都不相等 |
| **后果** | 库里的本位币金额与账单**系统性对不上**（不只是除不尽的情形——只要银行汇率与你抓到的日汇率不同就对不上）。J 域月度总额是这些偏差的累加，且无法核对 |
| **为什么结构性** | 唯一改法是把 `本位币金额` 从因变量改回自变量，不变式 1 的三元恒等式随之作废，8.1 的 6 种触发矩阵全部重写。这正是对话2 → 对话3 → 对话4 反复推翻过的那条线，改回去等于把三轮讨论的结论全部作废 |

### C-4 支出类型 ≠ 科目表

| 项 | 内容 |
| -- | ---- |
| **现状** | `ExpenseCategory` 仅 5 项属性（类型ID / 归属用户ID / 名称 / 创建时间 / 更新时间，终版 §四 2）；单层、无编码、**无状态字段**、不提供改名、无引用才可物理删（G-1 / G-4） |
| **溯源** | 你的决策，`260902-214813-prompt.md:186-189`「支出类型只允许新建和删除 / 只有未被使用的支出类型才允许被删除（**使用外键就能实现，实现简单**）/ 此时无论是列表筛选框还是明细编辑，支出类型的下拉范围都是一样的」。注意这条**推翻了你自己上一轮的相反决策**（同文件 :162「直接去除删除能力，只保留禁用即可，但是禁用后能重新启用」），早期模型 `260902-004426-answer.md:170-173` 中的「状态 启用/停用」「排序」「是否内置」三个属性也是这一路删掉的 |
| **规范** | 科目表标准形态 = **科目编码 + 层级（父子）+ 科目类别（资产/负债/权益/收入/费用）+ 启用状态 + 助记码**。IFRS COA、德国 SKR、《企业会计准则——应用指南》会计科目表，无一例外。「停用而不删除」是科目表的核心机制，因为历史凭证永远引用着它 |
| **后果** | 终版「已知代价③」已登记：**支出类型一旦被任何明细（含已软删除）引用即永久不可删除**——已删除明细只读、其类型不可改（8.5），系统又无停用能力、下拉恒含全部类型（G-4）→ **废弃类型无任何清理手段，随时间单调膨胀** |
| **改造成本** | 加「编码 / 父级 / 类别」是纯增量；但**加回「停用」是推翻你的用户决策**，且要重新分离 G-4 的筛选下拉与编辑下拉两套范围——这一点在对话10 §三、对话11 §一 已被反复改过两次，改回去要连带重做 |

## 四、⚠️ 有意识偏离（6 项，个人自用定位下成立）

| # | 偏离项 | 终版依据 | 对应标准 | 成立条件 / 触发重估的条件 |
| - | ------ | -------- | -------- | ------------------------- |
| 1 | **全量明文存储** | 前提 1；`File.文件内容`「原始二进制随记录存储」、`File.文件密码`「**明文保存**」（§四 4） | OWASP ASVS 静态加密、等保 2.0 数据保密性、PCI DSS v4.0 存储要求 | 你在 `260901-223131-prompt.md` 对话3 已论证：「只加密文件不加密明细，其实就是没加密…假设不应该有人能直接读写数据库」。逻辑成立。**但要注意 `File.文件内容` 存的是原始银行账单，其中通常含完整卡号与身份信息**——这与「明细明文」不是同一量级的暴露面。一旦对外提供服务或多租户，PCI DSS 的存储要求即被触发 |
| 2 | **密码策略范式** | A-8「长度 ≥ 10 且字母/数字/符号至少含两类；连续失败 5 次锁定 10 分钟」；全文只写「加盐哈希」，未指定算法 | NIST SP 800-63B | 现行 800-63B **已取消组合复杂度要求**，改为「长度优先 + 比对已泄露口令库 + 限速」。当前策略不违规，但属于被现行标准弃用的旧范式。另：OWASP 现行推荐 Argon2id（次选 scrypt / bcrypt），终版把算法留给技术轮次是合理的，但**算法选择本身是安全规范问题，不是纯技术细节** |
| 3 | **用户名不存在的登录失败不记审计** | 8.4 枚举第 2 类「用户名**不存在**则**不记审计**（无归属、无消费方）」 | OWASP ASVS 4.0 V7、ISO 27001 A.12.4 要求**所有鉴权失败必须记录** | 单租户 + 无对外暴露时成立。代价是**用户名枚举与撞库在系统里完全无痕**——这类攻击的特征恰恰是「大量不存在的用户名」，当前设计把这一类信号全部丢弃 |
| 4 | **无期间关账 / 锁月** | 前提 7「**无关账/锁月**，历史月份永远可改」；T13 由你在 `260902-214813-prompt.md:74` 明确裁定「不需要关账/锁月」 | 会计期间锁定 + 调整分录 | 个人分析用途成立。⚠️ 但需登记一个联动：**I-7 全量重算与 F-5 编辑都会改写任意历史月份**，将来若加锁月，这两条链路必须加拦截。这一点 `260901-223131-answer.md:187` 已提前登记过：「若未来引入『关账/锁月』，则重算落在已关账月份的份额需要拦截或走调整分录」 |
| 5 | **允许重复上传、无文件级查重** | C-4「文件只留存不物理删除；**允许重复上传、重复保存，不做文件级查重**」 | 幂等导入惯例 | 由明细级四要素查重兜底，个人自用成立。但见 C-2 与口径空白 ❓-3：结构化数据源接入后应改用银行流水号 |
| 6 | **去重只提示不阻断** | E-2「系统只标记『疑似重复』…**只提示不阻断**，不做任何自动处置」；E-1 四要素等值匹配、不设指纹字段 | OFX `<FITID>` / camt `AcctSvcrRef` 的硬幂等 | **在 PDF 解析这个数据源下，这是唯一正确的做法**——银行流水号不可得，四要素必然误报（同日同额同币的两杯咖啡），交人工裁定是对的。你在 `260901-223131-prompt.md` 对话2 D-01 已论证过。交易指纹字段的删除见 `260902-004426-answer.md:775` Q3，属正确简化（指纹本就是四要素的派生冗余） |

## 五、❓ 口径空白 / 增量可补（8 项）

> 这一节全部是**低成本高收益**：补一句话或加 2~3 个字段，不动任何既有规则。

| # | 空白项 | 终版现状 | 规范做法 | 补法 |
| - | ------ | -------- | -------- | ---- |
| 1 | **I-7 重拉的是哪一天的汇率** | 8.1 表「改支出日期」行明写「重拉**新日期**日汇率」，而「I-7 重算 / 切换本位币」行只写「重拉汇率」；I-7 正文（§二 I 域）同样只说「按当前本位币逐笔重算」——**全文未指明取哪一天** | 两种答案在规范上都存在：报表可复现取**支出日期**汇率（与 I-4「按支出日期的日汇率」一致）；IAS 21.35 功能货币变更则要求按**变更日**汇率折算并自此后适用 | **必须写死一条**，否则实现必然二义。倾向「支出日期」（与 I-4 及「历史不漂移」的既有取向一致）——**需你确认，见 T31** |
| 2 | **汇率无来源、无报价类型、无取数时间** | `Expense.折算汇率` 只有一个数值（§四 3）；早期模型的 `ExchangeRate.获取来源 / 获取时间`（`260902-004426-answer.md:191-195`）随 §六「刻意不建汇率实体」一并消失，`Expense.汇率来源` 则在 `260902-004426-answer.md:892` 被明确删除并登记后果：「**I-5 手工指定汇率的行与自动取值的行在数据上不可分辨，排查汇率异常时无从判断来源**」 | CAS 19 要求即期汇率通常取央行中间价；IFRS 要求汇率来源可审计；实务还需区分中间价 / 现汇买入价 / 银行结算价——三者数值不同 | 加 2~3 个字段（`汇率来源标识` / `报价类型` / `取数时间`），**不动任何规则**。收益：`折算本位币币种 ≠ 本位币` 之外多一条排查维度，且 I-5 手填行可被识别 |
| 3 | **缺记账日期（posting date）** | 全模型只有 `支出日期` 一个日期（前提 7 定义为「账单字面值，不做时区换算」） | camt.053 区分 `BookgDt`（记账日）与 `ValDt`（起息日）；OFX 用 `<DTPOSTED>`；信用卡账单普遍**同时印「交易日 / 记账日」**，两者常跨月 | 加一个可空 `记账日期` 字段，**归月与取汇率口径完全不变**（仍用支出日期），只作留存与将来对账用。零风险 |
| 4 | **审计缺 where 维度** | `AuditLog` 9 项属性（§四 5）中无来源 IP、无用户代理、无请求/会话标识。早期 `Session` 实体的 `会话ID`（`260902-004426-answer.md:87`）随「登录态不落库」一并消失 | NIST SP 800-92 与 ISO 27001 A.12.4 的日志最小集是 **who / what / when / where / outcome**——当前 who✓ what✓ when✓ outcome✓，**唯独缺 where** | 加 2~3 个字段。这是全表最划算的一处：账户被盗时，没有 IP 就完全无法判断「哪些操作是我做的」 |
| 5 | **`变更内容` 结构未定** | 8.4 仅写「编辑类操作的**前后值快照**；零值 = 非编辑类操作」，未规定是自由文本还是字段级结构化 | 可审计性要求变更记录能被**程序化重放**，而非只能人眼看 | 定为「字段级 `{字段名, 旧值, 新值}` 列表」即可，一句话，不动模型。否则实现成自由文本后，「这条明细改过几次、每次改了什么」只能靠读文本 |
| 6 | **金额与汇率的精度、舍入规则未定** | 8.2 只定了摊分侧：「按币种小数位数均分，除不尽的尾差固定计入末月」。但 `本位币金额 = 支出金额 × 折算汇率` **这一步乘法的舍入方式与汇率保留位数，全文未定**。终版「未做」清单把字段类型归入技术轮次 | **舍入规则是业务规则，不是技术细节**——四舍五入 / 银行家舍入 / 截断，在同一批数据上给出不同的月度总额 | 一句话补进 8.1。另需明确金额一律定点小数（`DECIMAL`），永不使用浮点——这条虽属实现，但错了会直接违反不变式 1 的「恒等式恒成立」 |
| 7 | **ISO 4217 / BCP 47 / 时间戳时区未显式声明** | §五 1 只写「币种代码」；早期 `260902-004426-answer.md:180` 曾写「**ISO 代码**，主键（USD、CNY、JPY 等）」，该约束在终版中**丢失**。同理 `User.界面语言`（§四 1）只写「语言配置文件的键」；`创建时间 / 更新时间` 未声明时区基准 | ISO 4217（币种代码 + minor unit）、BCP 47 / ISO 639（语言标签）、ISO 8601 + UTC 存储（时间戳） | 纯措辞补写，零改造。不写清楚，将来接汇率 API、接账单格式、做多语言时会各自造一套代码 |
| 8 | **导出格式未定** | K-3 只说「导出本人在 5 个实体上的全部记录」，未定格式 | GDPR Art.20 / PIPL 第45条 要求「结构化、通用、机器可读」；记账生态的通用交换格式是 OFX / QIF / Beancount / CSV | 若仅自用备份，JSON 即达标；若要能被其他记账软件读入，目标格式应明确选一个——**需你定，见 T32** |

## 六、✅ 已经符合规范、不要动的 7 项

这一节同样重要：下面每一条都是**对的**，而且其中几条比多数个人记账工具规范。将来任何「向规范靠拢」的改造都不应碰它们。

| # | 做法 | 终版依据 | 为什么它是规范做法 |
| - | ---- | -------- | ------------------ |
| 1 | **汇率快照固化** | I-4「按支出日期的日汇率折算，所用汇率随明细留存」 | 正是 IAS 21.21「交易日即期汇率」的做法，且保证**报表可复现、历史不漂移**。`260901-223131-answer.md:151-157` 的三方案对比里，方案 C（查询时实时折算）「同一张报表不同时间看到的数字不同，无法对账」——你选了方案 B，这个选择是准则级正确的 |
| 2 | **币种小数位数驱动尾差** | §五 1 币种枚举含「**小数位数**（摊分取整与尾差的基准）」；8.2「按币种小数位数均分，尾差归末月」 | 等价于 ISO 4217 的 minor unit，JPY=0 / USD=2 / KWD=3 这类差异天然被处理。尾差归末月是「最大余数法」的一种确定化，可接受且可复现 |
| 3 | **软删除终态不可逆，找回靠复制新增** | 前提 8；8.5「写 `删除时间`，**终态不可逆**，无恢复入口」 | 与会计「不得涂改、更正另立凭证」（红字更正法 / 补充登记法）的精神一致。**比「删了又能恢复」更可审计**——恢复会制造「同一条记录有两段生命」的歧义。复制生成新审计（8.5 复制字段表）等价于「另立一张更正凭证」 |
| 4 | **一次提交 = 一条审计 = 一个可追溯批次** | 不变式 4；8.4；`AuditLog.审计ID`「唯一标识，兼**入库批次号**」 | 等价于会计的「记账凭证 + 凭证号」，且省掉一张批次表。批次撤销靠 K-2 跳转 → F-4 筛选 → F-6 核对 → F-8 批量删除（8.4 撤销路径），**撤销前可核对**，比一键回滚更符合「不可逆操作须先复核」的通行要求 |
| 5 | **双口径月度统计** | J-1「未摊分口径（按支出日期归月）」与「摊分口径（按份额所属月归月）」双口径，**明示当前口径** | 未摊分口径 ≈ 收付实现制，摊分口径 ≈ 权责发生制。**同一系统内并存、并强制明示口径**，这是准则级的正确直觉——多数个人记账工具只有前者 |
| 6 | **不建聚合表，份额实时派生** | 8.2「份额不落库、查询时实时派生…**不建聚合表**」+ §六「月度摊分增量 / 摊分份额」列入不建实体 | 单一事实来源，统计可由明细完全重建。8.2 已正确指出：「聚合表是纯派生的统计缓存，可由明细完全重建，将来真需要时作为纯技术优化加回，**不改业务模型**」——这个边界划得很准 |
| 7 | **归属校验无死角 + 导出记审计、其余读操作不记** | 不变式 3；B-4 边界①「**除「数据导出」外，读操作不记审计**」 | 「导出是唯一记审计的读操作」与 GDPR / PIPL 关注**数据流出**的取向一致，比「全记」实用得多——全记会把审计表淹没在查询日志里，反而找不到真正的风险事件 |

## 七、按扩展方向的优先级（三种场景，成本相差两个数量级）

**这一节是本文的实际结论。** 上面 25 条判定，哪些要动完全取决于你要往哪扩。

### 场景 A：只是接更多银行 / 换成结构化数据源（CSV、Excel、OFX、camt.053）

**成本：低。不需要动任何结构性项。**

必须先做：
1. ❓-3 加 `记账日期`；
2. ❓-2 加汇率来源三字段；
3. **重新引入行级原文与银行流水号**——这是关键。你当初删掉「原始摘要」的理由是 `260902-004426-prompt.md:110`「**解析PDF不会有那么干净，没有所谓的一行数据，所以去除该字段**」。这个理由完全成立**但只对 PDF 成立**：CSV / OFX / camt.053 天生就是行级结构化的，而且自带唯一标识（OFX `<FITID>`、camt `AcctSvcrRef` / `NtryRef`、多数银行 CSV 的「交易流水号」）。有了它，E-1 的四要素查重可降级为兜底，主键改用银行流水号即可**真正幂等**——重复上传同一份账单会被硬去重，而不是靠人眼。

不需要动：C-1 复式记账、C-2 账户实体、C-3 本位币金额可编辑。

### 场景 B：从「只记支出」扩到「收支 + 资产负债 + 净值」

**成本：推倒重来级。这不是扩展。**

- C-1 与 C-2 **成对必须重构**，C-3 顺带一起改（有了账户，就要记账户实际扣款金额）。
- 判断触发点很简单：**只要出现「转账」**（信用卡还款就是转账），单式记账必然重复计数。
- 如果这个方向有**任何**可能性，正确的做法是**现在就在 `Expense` 之上预留 `Transaction` 层**（哪怕暂时每笔交易只有一条分录），而不是等有了几万条数据再拆。事后拆分要迁移全部历史数据，且 8.1 / 8.2 / 8.3 / J 域的规则要在迁移期同时支持两种形态。
- 已被排除在范围外的一整批需求（`260901-223131-answer.md:14`：收入与收支结余、预算与超支提醒、账本共享、资产负债与净值、报销与对账工作流、发票与凭证管理、还款与分期负债跟踪）**几乎全部落在这个场景**——它们不是七个独立需求，是同一次重构的七个副产品。

### 场景 C：从个人扩到多人 / 团队 / 对外提供服务 / 需要通过审计

**成本：中高，且全部集中在安全与留痕，不碰业务模型。**

必须先做（按优先级）：
1. **前提 1 整条作废**——静态加密 + `File.文件密码` 加密存储。注意 `File.文件内容` 存的是原始银行账单（含完整卡号），一旦对外提供服务，这就落入 PCI DSS 的存储要求，不再是「个人自建不适用」；
2. ❓-4 审计补 where 三要素（IP / UA / 请求ID）——不补这个，任何审计要求都过不了；
3. ⚠️-3 登录失败**必须全记**（含用户名不存在），否则撞库无痕；
4. ⚠️-2 密码策略按 NIST SP 800-63B 现行版重写，哈希算法定为 Argon2id；
5. ⚠️-4 加期间关账，并同步给 I-7 / F-5 加拦截（见 ⚠️-4 的联动登记）；
6. ❓-5 `变更内容` 结构化。

不需要动：C-1 ~ C-4 全部结构性项——**多人不等于复式**，数据隔离模型（不变式 3）本身是干净的。
