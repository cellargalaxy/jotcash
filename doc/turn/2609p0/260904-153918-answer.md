## 一、范围与承载对齐

本包承载来自分层 §六 L0 表，逐字拆开是 4 件事：

| # | 承载原文 | 落到本包的什么 |
| - | -------- | -------------- |
| 1 | 定点小数类型 | `Decimal` 类型（值语义、零值即 0、不可用 `==` 比较） |
| 2 | `round(值, 位数, 舍入方式)` | 包级函数 `Round(d, scale, mode)`，签名与承载逐字对齐 |
| 3 | **金额一律不用浮点** | 本包**不提供任何 `float32/float64` 入口与出口**（见 §三 取舍 2） |
| 4 | 三处精度口径 | ① `RoundAmount`（按币种小数位）② `RoundAmount` + `StoreBaseAmount`（算按本位币位、存 2 位）③ `RoundRate`（8 位） |

**边界（本包不做）**：

- **不认识币种**。约定 5「`base/` 是纯技术层，任何带业务语义（角色、币种、语言、归属）的类型都不得放入」+ L0「层内零依赖」，故「小数位数」一律由调用方以 `int32` 传入；本包不 import `currency`（它在 L1.0，方向反了），也不 import 兄弟包 `base/errs`。
- **不做折算、不做均分**。不变式 1a 的唯一实现处是 `rule/convert`、1b 是 `rule/amortize`（分层 §九）；本包只提供它们所需的算子。
- **不做「原币金额的存储位数」**。承载①原文是「原币金额**按 `currency.小数位数`**」——这是**算**的基准，不是存储列宽；存储列宽属 `store` ⑥，且与 T38② 有冲突（§四 冲突 1）。

## 二、模块设计

### 2.1 文件与职责

| 文件 | 职责 |
| ---- | ---- |
| `internal/base/decimal/decimal.go` | 包注释、`Decimal` 类型、哨兵错误、构造（文本/整数/1）、算术（加减乘除取负取绝对值）、比较、文本与 JSON 序列化 |
| `internal/base/decimal/precision.go` | 位数常量、舍入方式枚举、`Round`/`RoundAmount`/`RoundRate`/`Truncate`、定点文本与两个落库规整入口 |
| `internal/base/decimal/decimal_test.go` | 类型与算术、序列化、零值、入口边界 |
| `internal/base/decimal/precision_test.go` | 三处精度口径、舍入方向、负数对称、断言无损、摊分算子 |
| `internal/base/decimal/zz_consumer_check_test.go` | **外部消费者验证**（黑盒，包名 `decimal_test`）：模拟 `rule/convert`、`rule/amortize`、`store/sqlite`、`api/http/dto` 四个真实调用方；并以 `math/big.Rat` 独立回算舍入结果作为比对基准。文件命名与 `base/errs`、`base/config`、`base/pwdhash` 既有的 `zz_consumer_check_test.go` 约定一致 |

### 2.2 对外 API（输入 / 输出 / 异常）

**构造（唯一数值入口）**

| 函数 | 输入 → 输出 | 异常分支 |
| ---- | ----------- | -------- |
| `NewFromString(s)` | 十进制文本 → `(Decimal, error)` | 文本非法 → `ErrParse`；小数位 > `MaxScale`(18) 或有效数字 > `MaxDigits`(38) → `ErrOverflow` |
| `NewFromInt(i)` | `int64` → `Decimal` | 无 |
| `One()` | → `Decimal(1)` | 无。对应 I-4「支出币种 = 本位币时汇率直接取 1」 |

**算术**

| 方法 | 语义 | 异常分支 |
| ---- | ---- | -------- |
| `Add` / `Sub` / `Neg` / `Abs` | 精确，无舍入 | 无（指数取两者较小值，不放大，不会溢出） |
| `Mul` | **精确**乘法，不预舍入 → `(Decimal, error)` | 指数和溢出 `int32` → `ErrOverflow`（底层此处是 `panic`，本包转为错误） |
| `DivRound(divisor, scale)` | 商按 `scale` 位四舍五入 | 除零 → `ErrDivZero`；`scale` 越界 → `ErrScale` |
| `DivTruncate(divisor, scale)` | 商按 `scale` 位**向零截断** | 同上 |

**比较**：`Cmp` / `Equal`（数值相等，忽略标度，`1.50 == 1.5`）/ `Sign` / `IsZero` / `IsNegative`。

**舍入与三处精度口径**

| 函数 | 口径 | 依据 |
| ---- | ---- | ---- |
| `Round(d, scale, mode)` | 通用，承载字面签名 | 分层 §六 L0 |
| `RoundAmount(d, scale)` | 金额四舍五入到 `scale` 位 —— 口径①原币（传支出币种位）与口径②本位币的「算」（传本位币位）共用 | 分层 §三 问题 1 修法、§九 不变式 1a 行 |
| `RoundRate(d)` | 汇率四舍五入到 **8 位** | T39① |
| `Truncate(d, scale)` | 向零截断 —— 供 8.2「尾差归末月」 | 终版 8.2 |
| `FixedString(scale)` | 定点文本（补零），**断言无损**：不可无损表示则 `ErrPrecisionLoss` | `store` ⑥ + `store/sqlite`「定点文本、禁 REAL」 |
| `StoreBaseAmount()` | = `FixedString(2)`，本位币金额落库 | T35 |
| `StoreRate()` | = `FixedString(8)`，汇率落库 | T39③ |

**序列化**：`String()`（最简文本，去尾零，供日志与 8.4 审计摘要）；`MarshalJSON`/`UnmarshalJSON`（**JSON 字符串形态**，供 `api/http/dto` 契约）。

**哨兵错误**：`ErrParse` / `ErrScale` / `ErrRoundMode` / `ErrDivZero` / `ErrOverflow` / `ErrPrecisionLoss`，均可 `errors.Is` 判定 —— 供上层（`parser` 五类错误、`dto` 校验）转成 `base/errs` 的对应档与文案键，不必靠字符串匹配。

### 2.3 常量

| 常量 | 值 | 性质 | 依据 |
| ---- | -- | ---- | ---- |
| `RateScale` | 8 | **业务口径** | T39①，约定 8「汇率 8 位写死在对应包」 |
| `BaseAmountStoreScale` | 2 | **业务口径** | T35，约定 8「本位币 2 位写死在对应包」 |
| `MaxScale` | 18 | **技术防御**，非业务口径 | 见 §三 取舍 5 |
| `MaxDigits` | 38 | **技术防御**，非业务口径 | 同上 |

## 三、方案取舍（7 项）

**取舍 1 · 用 `shopspring/decimal` 做底层，但不把它的类型直接暴露 —— 采用「薄包装结构体」而非类型别名。**

- 备选 A：`type Decimal = shopspring.Decimal`（类型别名，零成本）。
- 备选 B：`type Decimal struct { v shopspring.Decimal }`（包装）。**采用 B**。
- 理由：别名等于把底层库的**全部** API 直接开放给全仓库 —— 其中 `NewFromFloat`/`NewFromFloat32` 会当场违反承载「**金额一律不用浮点**」，`Div` 的默认精度取自**包级全局可变变量** `DivisionPrecision`（默认 16），`MarshalJSON` 的形态取自另一个全局变量 `MarshalJSONWithoutQuotes` —— 任何依赖方（含第三方库）改动它们都会全局改变本仓库的金额语义。包装后本包完全控制出口面，两个全局变量对本包语义无影响（本包不用 `Div`、自行实现 `MarshalJSON`）。这是准则 6「约束优先用结构表达」在本包的落法。
- 代价：需转发一批薄方法（约 10 个）。已接受。

**取舍 2 · 不提供任何浮点入口与出口。**

- 承载「金额一律不用浮点」若只写在注释里，等于没有。本包**不导出** `NewFromFloat`、也不导出 `Float64()`。
- 已核对四类数值来源均无需浮点：原币金额来自 `parser` 解析的账单文本；汇率来自 `fxrate`（外部源）与 I-5 用户手填（JSON 文本）；本位币金额与摊分份额都是算出来的。
- **对下游的硬约束（须在阶段 6 `fxrate/<源>` 遵守）**：汇率源若以 `float64` 解码 JSON 再转字符串，精度已在解码那一步损失，本包无从补救 —— 必须以 `json.Number` 或字符串解码后交 `NewFromString`。此条与 T39②「规整点唯一」配套。
- 将来若 Excel 解析（`parser` 的 Excel 分支，当前 D-1「本轮仅实现 CSV」不在范围）确实只能拿到 `float64`，再补一个显式命名的入口，属**加法**，不改现有口径。

**取舍 3 · 阻断 `==`。**

`Decimal` 内含 `*big.Int`，`==` 比较的是指针 —— 同一数值经不同路径构造必然得到不同指针，`a == b` 会**静默**给出 `false`。以一个零尺寸的 `noCmp [0]func()` 字段令类型不可比较，把误用变成**编译错误**，强制走 `Equal`/`Cmp`。金额比较错正是准则 2 点名的「算错就静默出错」类。

**取舍 4 · `Mul` 返回 `error`，`Add`/`Sub` 不返回。**

底层 `Mul` 在两个指数之和溢出 `int32` 时**直接 panic**（`decimal.go:566`）。本包位于 L0、被全仓库依赖，对外零 panic 是硬要求，故 `Mul` 先自行判定并转为 `ErrOverflow`。`Add`/`Sub` 的结果指数取两者较小值，不放大、不可能溢出，因此不返回 error，避免无意义的啰嗦。代价：`rule/convert` 与 `rule/amortize` 的乘法处要处理一次 error —— 这正是不变式 1a 唯一一处乘法，值得显式。

**取舍 5 · 入口即校验位数上限（`MaxScale` 18 / `MaxDigits` 38），且明示为技术防御。**

- 目的：把极端指数（如 `1e-2000000000`）挡在入口，使后续 `Mul`/`Round` 既不 panic 也不做百万位的 `big.Int` 幂运算。
- 选值理由：业务侧最大小数位是汇率 8 位（T39），ISO 4217 币种最多 4 位小数，18 已宽松到不可能挡住任何合法业务值，且 T39②「`fxrate` 返回值精度不设限」的现实取值（常见 6~12 位）也在其内；38 对齐主流数据库 `DECIMAL(38, x)` 的精度上限惯例。
- **明确登记：这两个数是技术上限，不是业务口径**，业务口径只有 `RateScale=8` 与 `BaseAmountStoreScale=2` 两个。

**取舍 6 · 落库规整「断言无损」而不是「静默舍入」。**

`FixedString(scale)` 在发现当前值无法以 `scale` 位无损表示时返回 `ErrPrecisionLoss`，而不是顺手舍一下。理由：T38 已保证本位币小数位 ∈ {0,1,2}，所以「算按本位币位舍入 → 存 2 位」必然无损（分层 §三 问题 1 修法）；若某天 §十二「本位币候选放开到 3 位币种」被执行而 2 位列宽没跟着改，静默舍入会让恒等式 `本位币金额 = 支出金额 × 折算汇率` 在库里悄悄破裂且无人察觉，报错则当场暴露。同理，`StoreRate()` 报错即意味着有人绕过了 T39② 的唯一规整点 `rule/convert`。

**取舍 7 · 不实现 `driver.Valuer` / `sql.Scanner`。**

底层库实现了这两个接口（`decimal.go:1831/1867`），其中 `Scan` 遇到 SQLite 送来的 `float64` 会走 `NewFromFloat` —— 与承载「金额一律不用浮点」正面冲突；`Value` 直接输出 `String()`，位数不受控，等于把 `store` ⑥「金额 2 位定点 / 汇率 8 位定点」的列口径绕开。本包因此**有意不实现**，迫使 `store/sqlite`（阶段 5）显式经 `StoreBaseAmount`/`StoreRate`/`FixedString` 与 `NewFromString` 往返 —— 规整点唯一、可审查。

**附：错误库的选择 —— 与既有 `base/*` 兄弟包对齐，用 `github.com/pkg/errors`。**

本项原先拟用标准库 `fmt.Errorf` + `%w`，理由是「L0 依赖越少越好」。**实际交叉核对既有代码后改为 `github.com/pkg/errors`**：本轮开工时同批次的 `base/errs`、`base/config`、`base/pwdhash`、`base/log` 已落盘，四者**一致**使用 `github.com/pkg/errors`（如 `base/errs/errs.go` 用 `errors.WithStack` 记录 cause 栈、`base/pwdhash/pwdhash.go` 用 `errors.Errorf`），且该库已是 `go.mod` 的直接依赖 —— 本包另用一套等于在同一层制造两种错误风格，违反 prompt 约束「命名/注释语言/代码组织与项目既有风格一致，优先复用现有实现」。

具体写法上有一处必须留意：一律用 `errors.Wrapf(哨兵, ...)` 附加上下文，**不能**用 `errors.Errorf` 另造错误 —— 后者返回的 `fundamental` **没有 `Unwrap` 方法**（已核 `pkg/errors@v0.9.1/errors.go:112`，其 `go113.go` 只是转发标准库的 `Is`/`As`/`Unwrap`），`errors.Is` 判不出哨兵值，调用方就只能退化为匹配错误字符串，而字符串会在文案微调时静默失效。本包 6 个哨兵错误全部经 `Wrapf`/`WithStack` 包装，单测中逐个用 `errors.Is` 断言可判定。

## 四、冲突与待确认登记（2 项，均不阻塞本包）

### 冲突 1 · `store` ⑥「金额 2 位定点」与 T35 边界① / T38② 互斥 —— **阻塞阶段 4 `store`，不阻塞本包**

三处原文放在一起不成立：

| 出处 | 原文 |
| ---- | ---- |
| 分层 §六 L3 `store` ⑥ | 「**数值列口径**：金额 2 位定点、汇率 8 位定点（T39），一律非浮点」 |
| `260903-201810-answer.md` §二 T35 边界① | 「**原币金额（`支出金额`）不适用本条**，其精度按 `currency.小数位数`」 |
| 分层 §二 T38② | 「**只约束本位币，不约束支出币种** —— KWD（3 位）等仍可作 `支出币种` 正常记账与摊分」 |

**冲突点**：`store` ⑥ 把「金额」笼统写成 2 位定点，而 `Expense` 有两个金额列（终版 §四：`支出金额` 与 `本位币金额`）。按 T38② 允许 KWD（3 位小数）作支出币种，则 `支出金额 = 1.234 KWD` 存进 2 位列必然丢精度，随后 8.2「按支出币种小数位数均分」与 8.1 的恒等式全部对不齐 —— 属「算错就静默出错」。T35 只针对**本位币金额**，从未覆盖原币金额。

**采用依据与本轮处理**：T35 边界① 与 T38② 是**逐条决策原文**，`store` ⑥ 是承载概述，冲突时以前者为准 —— 即 `store` ⑥ 应拆成两列口径：`本位币金额` 2 位定点、`支出金额` 按支出币种小数位数所需的位宽。

**为什么不阻塞本包**：本包承载①只规定原币金额的**舍入基准**（`currency.小数位数`，由调用方传入），未规定其存储位宽；本包因此只定义 `BaseAmountStoreScale = 2`（T35 明确指向本位币）与 `RateScale = 8`，并另出通用的 `FixedString(scale)` 供 `store` 落列宽后调用。

**待你确认（阻塞阶段 4）**：`支出金额` 列取几位定点？它等于「币种枚举装哪些币种」的最大小数位数 —— 而该项在 T38 提出时即注明「本轮币种枚举装哪些币种本身也未定」，**属不可推断，本轮不脑补**。参考：ISO 4217 常见最大 3 位（KWD/BHD/OMR/JOD/TND），极端 4 位（CLF/UYW）。

### 待确认 2 · 8.2 均分的每月取整方式 —— **落阶段 3 `rule/amortize`，不阻塞本包**

终版 8.2 只写「金额按币种的小数位数均分，除不尽的尾差固定计入末月」，未写死前 N−1 月那个值是**向零截断**还是**四舍五入**得来。两种取法都满足字面，但结果不同：截断时末月吸收的尾差与总额同号、其余月恒等；四舍五入时末月可能反向偏离一个最小单位。

本包**不代为决定**，两种算子都提供（`DivTruncate` / `DivRound`），由 `rule/amortize` 在阶段 3 定案。本包 API 不因该选择变化，故不阻塞。

> 另：`折算汇率` 是否允许为 0 / 负（终版 §四 只写「必填」、I-5 只写「未填不可保存」），属 `rule/convert` 的入参校验范围（阶段 3），本包按纯数值处理，不代为限制。

## 五、库行为复核（实测，不靠文档承诺）

`shopspring/decimal v1.4.0` 的以下行为经本地实测确认，并已逐条固化为单测（防换版本时行为漂移）：

| 行为 | 实测结果 | 为什么必须核 |
| ---- | -------- | ------------ |
| `Round` 的方向 | `2.5→3`、`-2.5→-3`、`0.005→0.01`、`-0.005→-0.01` —— **半值远离零，负数对称** | 这就是中文「四舍五入」（T35 口径）。若是银行家舍入（库里另有 `RoundBank`）则不符 T35，且会破坏终版前提 2 / 8.2「负金额规则完全对称」 |
| 零值可用性 | `String()="0"`、`StringFixed(2)="0.00"`、`Add`/`Cmp`/`Round`/`Mul`/`Neg`/`Abs` 均不 panic | `entity` 62 属性「以零值表达不适用」（终版 §四表头）要求零值直接可算 |
| `Mul` 是否精确 | `123.45 × 7.12345678 = 879.390739491`（指数 −10，无损）；`Round(2)=879.39` | 不变式 1a 要「唯一一处乘法与舍入」—— 乘法必须精确、只在末端舍一次，否则二次舍入误差 |
| `Equal` 是否忽略标度 | `1.50.Equal(1.5) = true` | 落库 2 位与内存 1 位必须判等，否则 I-7「`折算本位币币种 = 当前本位币` 的行跳过」等幂等判断会误判 |
| 除零 | `QuoRem`/`DivRound` **panic**（`decimal division by 0`） | L0 对外零 panic，必须前置判定转 `ErrDivZero` |
| `Mul` 指数溢出 | 源码 `decimal.go:566` 显式 `panic` | 同上，转 `ErrOverflow` |
| `NewFromString` 的严格性 | 接受 `1e3` / `1.5e-2` / `+1.5` / `.5`；拒绝 `""` / `" 1.5"` / `"1.5 "` / `1_000` / `0x10` / `Inf` / `NaN` / `1.5.6` | 前后空格被拒 → 账单字段的 trim 责任在 `parser`（其承载即含字段清洗）；`Inf`/`NaN` 被拒是好事，杜绝浮点毒值入账 |
| `StringFixed` | `1.5→"1.50"`、`1.567→"1.57"`（会舍入） | 它自身**会静默舍入**，故本包在其外层加「断言无损」再输出（取舍 6） |
| `MarshalJSON` | 默认输出**带引号**的字符串（受全局变量 `MarshalJSONWithoutQuotes` 影响） | 前后端分离下必须是字符串（JS number 会丢精度）；不能依赖一个可被任何依赖方改写的全局变量，故自行实现 |
| `rescale` | 注释明示 **truncate, NOT round** | `Truncate` 的语义来源；也说明 `Round` 内部先截到 `places+1` 再补 5 的实现是可信的 |
| `QuoRem` 商方向 | 底层 `big.Int.QuoRem` 向零截断 | `DivTruncate` 据此实现，负数对称 |

### 对现有链路 / 性能 / 兼容性 / 下游的副作用

- **现有链路**：无。本包为纯新增，未修改任何既有文件（除 `go.mod`/`go.sum`）。
- **依赖面**：本轮新增 1 个直接依赖 `github.com/shopspring/decimal v1.4.0`（MIT，其 `go.mod` 仅一行 `go 1.10`、零间接依赖），不引入 cgo，不影响 T33⑤「纯 Go 驱动以保持免 cgo 交付」的取向。
  **需说明**：`go.mod` 当前还含 `go_common`、`gin`、`gorm`、`excelize`、`logrus`、`quic-go` 等约 60 个 indirect 依赖，它们**不是本包引入的** —— 本包实际依赖经 `go list -deps` 核实仅为「标准库 + `pkg/errors` + `shopspring/decimal`」；那些依赖来自同批次其他 base 包对 `go_common/util` 的引用（`base/idgen` 用 `util.GenId()`、`base/config` 用 `util`），`go_common` 是个大杂烩库故拖入大量传递依赖。此项属跨包事实，本轮不擅自收敛。
- **性能**：底层为 `big.Int`，单笔金额运算在个人系统规模下无压力；`MaxScale`/`MaxDigits` 入口校验把大整数幂运算的最坏情况挡住。K-3 整库导出与 I-7 逐笔重算是逐行运算，每行 1 次乘法 + 1 次舍入，与 `store` 的游标迭代口径配合即可。
- **下游约束（3 条，需在对应阶段遵守）**：① 阶段 3 `rule/convert` 必须「先 `RoundRate` 规整 8 位 → `Mul` → `RoundAmount`（本位币位）」，顺序不可换（T39②）；② 阶段 5 `store/sqlite` 必须经 `StoreBaseAmount`/`StoreRate`/`FixedString` 与 `NewFromString` 往返，不得使用底层库的 `Valuer`/`Scanner`（取舍 7）；③ 阶段 6 `fxrate/<源>` 必须以 `json.Number` 或字符串解码汇率（取舍 2）。
- **对 `dto` 的提示**：I-5「汇率未填不可保存」要求区分「填了 0」与「未填」，而 0 是合法金额值（终版前提 2 允许负金额，0 同理）；`dto` 须以指针或显式「已填」标记表达，不能靠零值判断。本包 `UnmarshalJSON` 遇 JSON `null` 保持接收者不变（Go 惯例），遇空串返回 `ErrParse`。
