## 三、实测证据（决定方案形状的 7 条）

在 `go1.27.0 darwin/arm64` 上对 v1.4.0 的实测输出，**非文档转述**。

| # | 实测 | 结果 | 影响 |
| - | ---- | ---- | ---- |
| 1 | `Round` 舍入方向 | `1.005→1.01`、`-1.005→-1.01`、`2.5→3`、`-2.5→-3`、`5.45→5.5` | `Round` = **四舍五入且负数对称**，正是 T35 口径。`RoundBank` 是银行家舍入（`5.45→5.4`），**误用即静默违反 T35** → 本包不暴露它 |
| 2 | `==` 运算符 | `1.50 == 1.5` → **`false`**；`Equal` → `true`；零值 `== NewFromInt(0)` → **`false`** | **最危险的坑**：`Decimal` 是 comparable，`==` 编译通过却静默算错。8.3 四要素含支出金额，写成 `==` 即静默漏判重复 → 采用不可比较包装（§四 取舍 1） |
| 3 | `IntPart()` 溢出 | 23 位数 → 返回 `200376420520689663`，**无错误** | 静默算错的金额换算，禁用；改用 `BigInt().IsInt64()` 显式判溢出（§四 取舍 4） |
| 4 | 巨大指数 | `NewFromString("1e1000000")` 成功（167ns）；其 `Round(2).String()` 产生 **100 万字符、64ms、约 8MB** | `parser` 喂入不可信账单文本 → 入口必须设量级上界（§四 取舍 3） |
| 5 | `Mul` 指数溢出 | `1e-2000000000 × 1e-2000000000` → **panic** `exponent -4000000000 overflows an int32!` | 入口设界后（≤18 位小数）乘积 ≤36 位，结构性不可达 |
| 6 | `QuoRem` 均分 | `100.00÷3@2` → `q=33.33, r=0.01`；`-100.00÷3@2` → `q=-33.33, r=-0.01`；`1000÷3@0` → `q=333, r=1`；7 组 `q×n+r == 总额` **恒成立** | 8.2「按币种小数位数均分 + 尾差归末月 + 负金额对称」的算术底座；除零 **panic** → 本包改为返回错误 |
| 7 | 序列化 | 默认输出**带引号字符串**，但受包级可变量 `MarshalJSONWithoutQuotes` 控制；`UnmarshalJSON("1e999999")` **成功**；未实现 `Marshaler` 的包装类型静默序列化成 `{}` | dto 是外部入口 → 必须自实现 JSON 且走本包有界 `Parse`；包装类型**必须**自实现 `MarshalJSON` |

补充实测（锁定实现细节）：零值全链路安全；`Truncate` 向零截断且负数对称（`-1.999→-1.99`）；`Round(2)` 后 `Exponent()` 恒为 `-2`；**`Div` 受包级可变量 `DivisionPrecision` 影响**（改成 3 后 `2/3=0.667`），而 `QuoRem` 不受影响；`NewFromString` 拒绝 `""`/`" 1.5"`/`"1,000.5"`，接受 `"1e3"`/`".5"`/`"1."`；文本排序会把 `100.00` 排在 `9.99` 之前。

## 四、六处关键取舍

### 取舍 1：自定义**不可比较**包装类型，而非 `type Decimal = decimal.Decimal` 别名

- **取**：`type Decimal struct { _ noCmp; v sdecimal.Decimal }`，`noCmp = [0]func()`。
- **弃**：类型别名（等于把实测 2/3/7 三个坑原样暴露给 41 个包）。
- **依据**：准则 6「**约束优先用结构表达**」（分层第 75 行）；准则 2 把 8.1/8.2/8.3 列为「全系统仅有的**算错就静默出错**的逻辑」（第 71 行）。`==` 正是让这三处静默出错的语言级入口。
- **效果**（已由单测机器断言）：`a == b`、含金额字段的**结构体整体比较**、`map[Decimal]T` **全部为编译错误**。手法取自标准库 `hash/maphash.Hash` 的 `_ [0]func() // not comparable`（`$GOROOT/src/hash/maphash/maphash.go:109`），零内存开销（实测包装前后均 16 字节）。
- **代价**：必须自实现 JSON 编解码（实测 7），已实现并单测锁定。

### 取舍 2：**不提供任何 float 入口**

承载写「**金额一律不用浮点**」。若提供 `FromFloat`，这句话只是约定。故本包**不导出**任何 `float32/float64` 参数或返回值（对比：`go_common/util/math.go` 的 `FloatRoundInt`/`IntDivFloat` 是浮点工具，与本包定位相反，不复用）。已由 `TestNoFloatInPublicAPI` 用 AST 扫描所有导出函数签名机器断言——「不用浮点」从口头约定变成**编译期不可达**。

### 取舍 3：量级上界设在**入口**，算术**不设界**，落库**再校验**

- 入口（`Parse` / `FromUnits` / `UnmarshalJSON`）：拒绝**整数位 > 16** 或**小数位 > 18**。
- 算术（`Add`/`Sub`/`Mul`/`Neg`/`Abs`/`Sum`）：**不返回错误、不设界**——F-6 筛选态合计、J 域月度聚合是多笔累加，给聚合结果设上界会误拒合法统计。入口设界后实测 5 的 panic 结构性不可达。
- 落库（`Units` / `StringFixed`）：`int64` 溢出与「目标位数无法无损容纳」一律显式报错，绝不静默舍入。
- **理由**：实测 4 表明入口不设界即为 DoS 向量；分层第 125 行 `store` ⑥ 要求「金额 2 位定点、汇率 8 位定点，一律非浮点」，且允许「整数最小单位**或**定点文本」两种形态，两者都要求落库前有一次无损性判定。

### 取舍 4：`Units(scale)` 用 `BigInt().IsInt64()` 判溢出，禁用 `IntPart()`

实测 3 证明 `IntPart()` 静默溢出。实现路径为 `FitsScale 校验 → Shift(scale) → BigInt() → IsInt64() 判定 → Int64()`。同时提供 `FromUnits` 反向还原，使「整数最小单位」形态可无损往返（实测 `FromUnits(712345678,8)="7.12345678"`）。

### 取舍 5：只暴露**两种**舍入方式，且**不暴露 `Div`**

承载签名是 `round(值, 位数, 舍入方式)`，故提供 `RoundMode`：

| 模式 | 语义 | 唯一消费方 | 依据 |
| ---- | ---- | ---------- | ---- |
| `RoundHalfUp` | 四舍五入、负数对称 | `rule/convert`（本位币金额、汇率） | T35 舍入方式、T39① |
| `RoundTruncate` | 向零截断、负数对称 | `rule/amortize`（8.2 份额切分，尾差另计） | 终版第 320 行「尾差归末月」的算术前提 |

**刻意不暴露**：`RoundBank`（实测 1 证明会静默违反 T35）、`RoundUp/Down/Ceil/Floor/Cash`（无消费方）、**`Div`**（实测：受包级可变量 `DivisionPrecision` 影响，任何包都能远程篡改金额除法；改用必须显式给定位数的 `QuoRem`）。负位数（`Round(-1)` 把 545 舍成 550）无消费方且是误用入口，一并拒绝。以上全部由 `TestDangerousAPIsNotExposed` 用反射机器断言。

### 取舍 6：`QuoRem` 只给「商 + 余」，**不决定尾差归属**

本包返回 `(商, 余)` 并保证 `商 × 除数 + 余 = 被除数`（实测 6，7 组恒成立）；**尾差归末月是业务规则**，留在 `rule/amortize`——否则不变式 1b 就有第二处实现，违反准则 1。同理 `RateScale` 常量在本包，但「何时规整汇率」由 `rule/convert` 作为唯一规整点决定（T39②）。

## 五、API 面（`internal/base/decimal`）

| 分组 | 导出项 | 说明 |
| ---- | ------ | ---- |
| 类型 | `Decimal`、`RoundMode` | `Decimal` 不可比较；零值 = 0 且全方法可用 |
| 精度常量 | `RateScale=8`、`BaseAmountStoreScale=2`、`MaxScale=18`、`MaxIntDigits=16` | 前两个为 T39①/T35 定死值 |
| 舍入方式 | `RoundHalfUp`、`RoundTruncate`（+ `String()`） | 零值不默许任何方式，忘传即报错 |
| 构造 | `Parse`、`MustParse`、`FromInt`、`FromUnits`、`Sum` | 无 float 入口；`MustParse` 仅供包内常量与测试 |
| 算术 | `Add`、`Sub`、`Mul`、`Neg`、`Abs`、`QuoRem` | 除 `QuoRem` 外均无错误返回 |
| 比较 | `Equal`、`Cmp`、`IsZero`、`IsNegative`、`IsPositive`、`Sign` | `Equal` 按数值比较，`1.50` 与 `1.5` 相等 |
| 舍入与位数 | `Round(scale, mode)`、`RoundRate()`、`Scale()`、`FitsScale(scale)` | `Scale` 为剥掉尾随零后的有效位；`RoundRate` 无参数、不会失败 |
| 输出与落库 | `String()`、`StringFixed(scale)`、`Units(scale)` | 后两者无损失败即报错 |
| JSON | `MarshalJSON`、`UnmarshalJSON` | 恒输出带引号字符串；入站走有界 `Parse` |
| 错误 | `ErrSyntax`、`ErrIntDigitsExceeded`、`ErrScaleExceeded`、`ErrScaleInvalid`、`ErrRoundMode`、`ErrDivideByZero`、`ErrPrecisionLoss`、`ErrUnitsOverflow` | 均可 `errors.Is` 分类 |

**刻意不提供 `driver.Valuer` / `sql.Scanner`**——这是与同层 `calendar.Date` 的**有意分歧**，已在包注释登记：`Date` 只有一种规范文本（定长 `2006-01-02`），而金额有**两种目标位数**（金额列 2 位、汇率列 8 位）。实现隐式 `Value()` 就得在包内替 `store` 猜一个位数，猜错即静默改钱。改为要求 `store/sqlite` 显式调 `Units(scale)` 或 `StringFixed(scale)`。副作用是把 `Decimal` 直接塞进 `db.Exec` 会以「unsupported type」当场失败——**响亮失败优于静默错值**，符合准则 6 取向。

## 六、三处精度口径的落点

| 口径 | 取值 | 本包提供 | 由谁调用 |
| ---- | ---- | -------- | -------- |
| ① 原币金额 | 按 `currency.小数位数`（含 KWD 等 3 位币种） | `Round(scale, RoundHalfUp)`、`FitsScale` | `rule/amortize`（8.2 均分基准）、`parser`→`service/intake` |
| ② 本位币金额 | **算**：按本位币 `currency.小数位数`（T38 保证 ∈{0,1,2}）；**存**：2 位定点 | `Round(scale, RoundHalfUp)` + `BaseAmountStoreScale` | `rule/convert`（不变式 1a 唯一实现处）、`store/sqlite` |
| ③ 折算汇率 | 8 位小数、四舍五入 | `RateScale`、`RoundRate()` | `rule/convert`（T39② 唯一规整点，自动获取与 I-5 手填共用） |

**T38 无损性已由单测机器验证**：`TestThreePrecisionScopes` 对本位币 0/1/2 位 × 5 组样本共 15 组，逐组断言「按本位币位数舍入的结果满足 `FitsScale(2)`，且经最小单位与定点文本两种形态往返后与原值 `Equal`」——这正是分层 §三 问题 1 的闭合前提，也覆盖了阶段 3 要求的「0/1/2 位本位币各一组舍入用例」在算术层的先行锁定。

## 七、异常与边界处理

| 场景 | 行为 | 依据 |
| ---- | ---- | ---- |
| 非法文本（`""`、`" 1.5"`、`"1,000.5"`、`"abc"`、`"NaN"`） | `ErrSyntax`（含原文本） | 实测 7；D-3 由 `parser` 转文案键 |
| 前后空格、千分位分隔符 | **不做**隐式清洗，返回 `ErrSyntax` | 清洗属 `parser`（D-1 不定义统一模板，各行版式不同）；本包若擅自 trim，格式判定就分散到两层。与同层 `calendar` 拒绝 `"2026-1-2"` 同一取向 |
| 量级越界（`1e1000000`、23 位整数） | `ErrIntDigitsExceeded` / `ErrScaleExceeded` | 实测 4 的 DoS 向量 |
| 目标位数非法（负数、> `MaxScale`） | `ErrScaleInvalid` | 负位数无消费方且是误用入口 |
| 未知舍入方式（含零值 `RoundMode(0)`） | `ErrRoundMode` | 忘传参数必须报错，不能静默按某种方式舍入 |
| 除数 / 份数为零 | `ErrDivideByZero`（**不 panic**） | 实测 6 库行为是 panic；摊分月数来自用户输入（F-1），不能崩掉请求 |
| 落库无损性不足 | `ErrPrecisionLoss` | 绝不静默舍入掉钱 |
| `int64` 溢出 | `ErrUnitsOverflow` | 实测 3 的静默溢出 |
| 零值 `Decimal{}` | 等价 0，全方法可用不 panic | 终版第 364 行；实体以零值创建 |
| JSON `null` / 缺字段 | 均为零值 0，不报错 | 两者在 Go 中不可区分，行为必须一致 |

与 `go_common/util/math.go` 的**有意分歧**（已在代码注释登记）：`IntDivFloat` 对除零返回 0（注释：「不让调用方在一次普通换算里崩掉」）。本包对除零**返回错误**——那是浮点工具的容错取向，而金额除法静默得 0 会让摊分份额全为 0 且无人察觉。

### 故障注入验证（证明单测能拦住真实回归）

覆盖率与「测试通过」都不能证明断言有效，故对三处最危险的实现各注入一次故障，确认对应测试**确实失败**，随后完整还原：

| 注入的故障 | 触发的失败 | 说明 |
| ---------- | ---------- | ---- |
| 移除 `noCmp` 内嵌字段 | `TestDecimalIsNotComparable` **3 条断言全部报错**（类型可比较 / 含金额结构体可比较 / `map[Decimal]T` 可构造） | 证明取舍 1 的防线由机器守住，不靠评审 |
| `Round` 改用银行家舍入 | `TestRoundHalfUp` **9 条报错**：`1.005→1`（应 1.01）、`2.5→2`（应 3）、`5.45→5.4`（应 5.5）、`-2.5→-2`（应 -3）等 | 正是「差异只有一分钱、几乎不可能被评审发现」的静默违反 T35，已被逐条钉住 |
| `Units` 改用 `IntPart()` | `TestUnitsPrecisionLossAndOverflow` 与 `TestConsumerParserSentinelErrors` 报错：期望 `ErrUnitsOverflow`，实际 `<nil>` | 证明实测 3 的静默溢出有测试兜底 |

还原后已用 `diff` 与 `grep` 逐文件确认三处实现与注入前完全一致，并重跑全量测试通过。

### 一处需下游注意的口径

`StringFixed` 保证**小数位定长**，但不保证**整数位定长**。若 `store/sqlite` 选用「定点文本」列形态并依赖字典序做排序或区间筛选，需自行保证整数位宽一致（或改用「整数最小单位」列形态——该形态的 `int64` 数值序天然正确）。`TestStringFixedIsFixedWidth` 已把这条差异连同反面对照（文本序下 `100.00` 排在 `9.99` 之前）一并记录在测试里。
