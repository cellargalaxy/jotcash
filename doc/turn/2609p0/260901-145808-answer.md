## 1. 系统定位与业务目标

### 1.1 一句话定位

**jotcash 是一个「多用户、数据互相隔离」的个人支出记账系统，以银行 PDF 对账单为主要数据来源，通过「支出类型打标」和「跨月摊分」两项加工，回答「我每个月真实花了多少、花在哪里」。**

### 1.2 业务目标（按优先级）

| 序号 | 目标 | 需求依据 |
|---|---|---|
| G1 | 让支出数据「进得来且不重复」：从 PDF 对账单批量录入，重复账期不产生重复记账 | Prompt 第 58-61 行 |
| G2 | 让支出数据「说得清」：补齐机器无法从对账单得到的业务语义（支出类型、摊分月数、备注） | Prompt 第 62-65 行 |
| G3 | 让支出数据「算得准」：多币种可汇总、摊分口径可解释、逐笔与按月两个视角能对账 | Prompt 第 66、69-71 行 |
| G4 | 让数据「不外泄」：登录校验 + 数据归属隔离，管理员集中管控账户 | Prompt 第 55-57 行 |

### 1.3 明确的非目标（本期不做）

`【设计】` 以下内容**不在本次功能范围**，理由是 Prompt 未提出、且缺失它们不影响 G1-G4 闭环：

| 非目标 | 为什么本期不做 | 什么条件下重新考虑 |
|---|---|---|
| 收入管理、结余/净资产核算 | Prompt 全篇只涉及「支出」（第 58 行明确「作为支出的数据来源」） | 用户提出要看收支两端或结余时 |
| 预算与超支预警 | 需求未提出；且预算口径依赖摊分口径先稳定 | 摊分口径验收通过后 |
| 复式记账（借贷平衡）、账户余额对平 | 数据源是单边支出流水，不具备做平衡表的信息 | 需要对接完整银行流水（含收入、转账）时 |
| 银行 API/邮件自动同步 | 需求指定的入口是「上传 PDF」（第 58 行） | 出现高频导入诉求时 |
| 多人协作账本（共享账本、家庭账本） | 需求第 57 行明确要求「只能查询到用户自己的数据」，与共享语义冲突 | 用户明确提出共享诉求，需先定义授权模型 |
| 附件/发票影像管理、报销流程 | 需求未提出 | 出现报销场景时 |

> 取舍说明：这里刻意不把「多人账户」理解成「协作记账」。Prompt 第 55 行的「多人账户」+ 第 57 行的「不能越权」组合起来，语义是**多租户式的各记各账**，而不是共享账本。这是全文权限模型的基石。

## 2. 业务域划分与全景

系统拆为 6 个业务域，域之间的依赖是单向的，便于分期交付：

```
┌─────────────────────────────────────────────────────────────┐
│  D1 身份与账户域                                              │
│  管理员建号 / 登录会话 / 全局访问校验 / 数据归属             │
└────────────────────────┬────────────────────────────────────┘
                         │ 提供「数据归属人」这一前置
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  D2 导入域         │  D3 去重域                               │
│  上传PDF/解密/解析 │→ │ 指纹比对/重复判定/人工裁决            │
└────────────────────────┬────────────────────────────────────┘
                         │ 产出「已确认的支出流水」
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  D4 支出台账域                                                │
│  逐笔明细 / 字段修改 / 打标 / 筛选 / 累计统计                │
└──────────┬──────────────────────────┬───────────────────────┘
           │                          │
           ▼                          ▼
┌────────────────────────┐  ┌────────────────────────────────┐
│  D5 币种与折算域        │  │  D6 摊分与月度分析域            │
│  本位币/汇率/统一口径   │→ │ 摊分展开 / 月度报表 / 口径切换  │
└────────────────────────┘  └────────────────────────────────┘
```

**依赖说明**：D5 被 D4 和 D6 共同依赖（金额要先统一币种才能累计）；D6 依赖 D4 的「摊分月数」和 D5 的「统一金额」。D3 在业务上是 D2 的收尾环节，但独立成域，因为它有自己的人工裁决界面和规则维护诉求。

## 3. D1 身份与账户域

### 3.1 角色模型

`【需求】` Prompt 第 55 行：多人账户、有账户密码、只有管理员能添加新账户、系统初始只有一个管理员。

| 角色 | 能力 | 依据 |
|---|---|---|
| 管理员（admin） | 拥有普通用户全部记账能力 **+** 账户管理能力（新增账户、停用/启用、重置密码） | 第 55 行「只有管理员才能添加新的账户」 |
| 普通用户（user） | 仅自己的记账能力，无任何账户管理入口 | 第 55、57 行 |

`【设计】` 只设两个角色，不做细粒度权限矩阵。理由：需求只区分「能不能建号」这一件事，引入 RBAC 会增加复杂度却不解决任何真实问题（对应产品原则「没有真实状态问题时不制造状态机」）。

`【设计】` **管理员的记账数据同样受隔离约束**——管理员能管账户，但**不能查看其他用户的支出数据**。理由：第 57 行「页面与接口只能查询到用户自己的数据」是无主语的全局约束，且从数据最小权限角度，账户管理权不应自动附带数据查看权。`【待确认】` 若用户期望管理员可查看全员数据（例如家庭主账户场景），需在 §10-Q1 明确。

### 3.2 账户生命周期

```
[管理员创建] → 待激活(首次登录需改密) → 正常 ⇄ 停用 → (不删除)
```

`【设计】` 各状态的业务含义与流转条件：

| 状态 | 含义 | 进入条件 | 能否登录 | 其数据是否保留 |
|---|---|---|---|---|
| 待激活 | 管理员刚建号，密码为管理员设置的初始密码 | 管理员创建成功 | 能，但登录后**强制跳转改密**，未改密不能进入其他页面 | — |
| 正常 | 可正常使用 | 完成首次改密 | 能 | 是 |
| 停用 | 保留数据但禁止登录 | 管理员执行停用 | 不能 | 是（只是不可访问） |

`【设计】` **不提供账户删除，只提供停用**。理由：支出数据是长期资产，删除账户会造成数据孤儿或级联删除历史账目，属于不可逆高风险动作；停用即可满足「不让某人再用」的真实诉求。

`【设计】` **初始管理员**：系统首次启动时以既定方式生成唯一管理员账户，并**强制首次登录改密**后才能使用其他功能。理由：第 55 行「系统初始只有一个管理员」意味着这个账户不能由业务流程创建，只能由系统初始化产生；而初始凭据若不强制更换，等于长期敞口。

`【设计】` **不提供自助注册、不提供找回密码**。理由：第 55 行明确「只有管理员才能添加新的账户」，自助注册直接违背；密码重置由管理员执行（重置后账户回到「待激活」，需再次改密），避免引入邮箱/短信等外部依赖。

### 3.3 登录与全局访问校验

`【需求】` Prompt 第 56 行：需要登录页面；除登录业务外，其余全部页面与接口都需要校验登录。

> 说明：Prompt 第 56 行原文为「都需要校验denglt」，其中 `denglt` 为「登录」的拼音输入残留笔误。本文按「校验登录」理解。`【待确认】` 若原意并非「登录」，见 §10-Q2。

`【设计】` 访问控制清单（默认拒绝，白名单放行）：

| 范围 | 是否需要登录 |
|---|---|
| 登录页、登录动作、登出动作 | 否（白名单） |
| 其余全部页面与接口，含首页、上传页、明细页、月度页、改密页、账户管理页 | **是** |
| 账户管理相关的一切操作 | 是 + **额外校验管理员角色** |

`【设计】` 未登录访问受保护页面 → 跳转登录页并记住原目标，登录成功后回跳；会话过期后在页面上的操作 → 提示「登录已过期」并跳登录页，**不静默丢弃用户正在填写的内容**（尤其是明细编辑和导入确认这类有输入成本的场景）。

### 3.4 数据归属与越权防护

`【需求】` Prompt 第 57 行：页面与接口只能查询到用户自己的数据，不能越权。

`【设计】` 用一条统一规则覆盖，而不是逐页面写权限：

> **归属规则**：一切业务数据（导入批次、支出流水、支出类型、自定义汇率等）在产生时即绑定「归属用户」；任何读取、修改、删除操作的作用域强制收敛到「当前登录用户 = 归属用户」。

`【设计】` 越权行为的**统一表现**：对「存在但不属于我」的数据和「根本不存在」的数据，**给出相同的『未找到』响应**，不区分提示。理由：若提示「无权访问」，等于告知攻击者该条数据真实存在，属于信息泄露。

`【设计】` 需要特别防守的越权面（这些是最容易漏的）：

| 越权面 | 场景 | 处理 |
|---|---|---|
| 直接改 ID | 修改明细时把流水标识换成别人的 | 按归属规则拒绝，返回「未找到」 |
| 导入批次 | 查看/撤销别人的导入批次 | 同上 |
| 统计聚合 | 月度报表、累计统计的数据范围 | 聚合的输入集本身就限定归属，避免「明细看不到但总额算进去了」 |
| 去重比对 | 新导入的流水与**别人的**流水比对，从而推断出他人消费 | **去重比对范围严格限定在本人数据内**（关键设计，见 §5.2） |
| 支出类型字典 | 使用/看到别人的自定义类型 | 类型字典按用户隔离（见 §6.3） |

## 4. D2 导入域：PDF 对账单导入

### 4.1 业务流程（主路径）

`【需求】` Prompt 第 58-59 行：需要一个页面能上传银行 PDF 对账单，解析 PDF 作为支出数据来源；PDF 可能有密码，需支持输入密码解密。

```
① 选择文件 → ② 选择银行/账单模板 → ③ 输入密码（如需） → ④ 解析预览
   → ⑤ 去重检查与裁决 → ⑥ 补充打标（可跳过） → ⑦ 确认入账 → ⑧ 批次归档
```

分步说明：

| 步骤 | 用户做什么 | 系统做什么 | 用户看到什么 |
|---|---|---|---|
| ① 选择文件 | 上传 PDF | 校验格式与大小 | 文件名、页数 |
| ② 选择模板 | 指定这是哪家银行/哪种账单 | 若能自动识别则预选，允许改 | 已识别的银行与账期 |
| ③ 输入密码 | 仅当 PDF 加密时输入 | 尝试解密 | 密码错误可重试，不丢失已上传文件 |
| ④ 解析预览 | 核对解析结果 | 抽取流水行 + 抽取账期 | **逐笔预览表** + 解析质量摘要 |
| ⑤ 去重裁决 | 确认/取消系统的重复判定 | 执行去重（详见 §5） | 重复项分组高亮 |
| ⑥ 补充打标 | 批量或逐笔设类型、摊分月数 | 应用打标规则给出建议值 | 待打标条数提示 |
| ⑦ 确认入账 | 提交 | 生成正式支出流水 | 入账成功 N 笔 / 跳过重复 M 笔 |
| ⑧ 批次归档 | — | 保留批次记录与原始文件 | 导入历史可查、可撤销 |

`【设计】` **「预览-确认」两段式，解析结果不直接入账**。理由：PDF 解析天然不可能 100% 准确，直接入账会把脏数据混入台账，事后清理成本远高于事前确认；而账单导入是低频操作，多一步确认的成本可接受。

### 4.2 加密 PDF 的处理

`【设计】` 业务规则：

- 密码**仅用于本次解密，不做保存**。理由：保存银行对账单密码属于高敏凭据留存，收益（免去下次输入）远小于泄露风险。`【待确认】` 若用户希望「记住密码」，见 §10-Q3。
- 密码错误允许**有限次重试**（`【设计】` 建议初始 5 次/文件，设定逻辑：既容忍手误，又避免被用作离线爆破工具；可按实际调整），超限则本次导入终止，需重新发起。
- 需要区分并给出不同提示的失败原因：**密码错误** / **文件本身损坏** / **虽解密成功但内容无法解析**（如扫描件纯图片）。理由：三者的用户下一步动作完全不同（重输密码 / 重新下载账单 / 换用手工录入）。

### 4.3 解析质量与异常分支

`【设计】` 解析结果按行分为三类，分别有不同去向：

| 解析结果 | 判定 | 去向 |
|---|---|---|
| 完整行 | 日期、金额、币种、对手方都抽到 | 进入正常预览，可直接入账 |
| 残缺行 | 关键项缺失（如日期或金额抽不到） | 标为「待补全」，**必须人工补齐才能入账**，不允许猜默认值 |
| 噪声行 | 表头、小计、页脚、还款/退款等非支出行 | 默认排除，但**在预览中可展开查看**并允许手工恢复 |

`【设计】` **解析总额自检**：若对账单本身印有本期消费合计，则与解析出的明细合计比对，不一致时在预览页给出显著提示（不阻断，但要求用户确认）。理由：这是唯一能低成本发现「漏抽/多抽行」的校验手段。`【待确认】` 目标账单是否普遍含合计栏，见 §10-Q4。

`【设计】` **退款/冲正行的处理**：对账单中常出现负数金额（退款、撤销）。业务上应作为**负数支出流水**入账，而非丢弃。理由：丢弃会导致月度支出虚高，与银行账单对不上。`【待确认】` 是否需要把退款与原支出关联抵扣（而非各记一笔），见 §10-Q5。

### 4.4 导入批次与可撤销

`【设计】` 每次成功入账生成一个**导入批次**，记录：来源文件名、银行/模板、账期区间、入账笔数、跳过笔数、导入时间、归属用户。

`【设计】` 提供**整批撤销**能力，且规则如下：

- 撤销会移除该批次入账的流水；
- 但**已被人工修改过的流水**（改过类型/金额/摊分等）不静默删除，而是列出让用户确认，避免抹掉人工劳动；
- 撤销后，这些流水占用的「去重指纹」同步释放，使得重新导入同一份账单不会被误判为重复。

理由：导入是批量动作，一旦选错模板或选错文件，逐笔删除代价极高；撤销能力是批量导入的必要配套。撤销与去重指纹的联动是易漏点，必须显式说明。

## 5. D3 去重域

### 5.1 需要解决的真实问题

`【需求】` Prompt 第 60-61 行：对重复的支出数据进行去重；例如两个 PDF 之间的账期时间有重叠，需要去重，避免重复录入。

`【设计】` 把问题拆成三个不同层级，因为它们的判定手段和风险完全不同：

| 层级 | 场景 | 特征 |
|---|---|---|
| L1 同文件重复导入 | 同一份 PDF 被上传两次 | 文件级可判定，风险最低 |
| L2 账期重叠重复 | 两份账单账期有交集，交集区间的流水被录两遍 | **Prompt 明确点名的核心场景** |
| L3 真实的相同消费 | 同一天在同一商户消费了两笔一样的金额（如两杯同款咖啡） | **不是重复，是两笔真实支出——绝不能自动合并** |

> 核心取舍：L3 的存在决定了**去重不能做成全自动**。把 L3 误判为重复会造成**账目缺失且用户无感知**，这是比「重复录入」更严重的错误（重复录入至少看得见）。因此本设计的原则是：**系统只做「疑似」判定，删除动作由用户确认**。

### 5.2 三层去重规则

`【设计】` L1 文件级：

- 依据：文件内容指纹 + 归属用户。
- 处理：命中时提示「这份账单已于某时导入过（批次可查）」，**默认阻断**，但允许用户显式选择「仍然继续」（应对同名不同内容、或上次导入被撤销的情况）。
- `【设计】` 比对范围**限定本人已导入文件**，不跨用户（否则会泄露他人是否持有同一份账单）。

`【设计】` L2 流水级（核心）：

- **重复指纹** = 归属用户 + 交易日期 + 金额 + 币种 + 对手方（规范化后）。
- 规范化处理（否则同一笔交易在两份账单里的写法差异会导致漏判）：对手方去除多余空白、统一大小写、剥离常见的流水号/终端号尾缀；金额按最小货币单位整数比对，规避小数误差。
- 判定与处理：
  - **完全一致** → 判为「疑似重复」，在预览中**默认不入账**并分组高亮，用户可逐条改为「确认入账」；
  - **不一致** → 正常入账。
- `【设计】` **同一份账单内部的重复**（L3 在单份账单内的表现）不参与自动跳过，只做提示——因为同一份对账单里出现两行相同交易，几乎必然是两笔真实消费。

`【设计】` L3 保护机制（防误杀）：

- 当同一指纹在**同一批次内出现 N 次**、而历史已有 M 笔时，按「多出来的部分」入账，而不是全部跳过。举例：历史已有 1 笔「3/15 星巴克 35 元」，新账单该指纹有 2 笔 → 判定 1 笔重复、1 笔新增，而不是 2 笔全跳。理由：这样才能同时正确处理「账期重叠」和「当天真的买了两杯」。
- 去重裁决界面必须展示**被判为重复的那条历史流水**（日期/金额/对手方/来源批次），让用户有据可判。

`【设计】` **账期重叠的提前预警**：在解析预览阶段，若本次账单账期与已导入批次的账期有交集，直接在页面顶部提示「账期与某批次重叠，重叠区间 X 笔已做重复检查」。理由：这正是 Prompt 第 61 行描述的场景，提前告知能让用户带着预期去核对，而不是在结果里困惑。

### 5.3 手工录入的去重

`【设计】` 手工新增单笔支出时**同样走 L2 指纹检查**，但只做**提示不阻断**。理由：手工录入通常是用户明知故为（补录现金支出），阻断会造成困扰；但提示能避免「以为没录成功又录一遍」。

## 6. D4 支出台账域

### 6.1 支出流水的业务字段

`【需求】` Prompt 第 62-63 行要求「至少涉及」：支出日期、支出金额、支出币种、交易对手方、交易备注、支出类型、摊分月数。

| 业务字段 | 含义 | 来源 | 是否必填 | 可否修改 |
|---|---|---|---|---|
| 支出日期 | 交易发生日期 | PDF 解析 / 手工 | 是 | 是`【需求】`第 68 行 |
| 支出金额 | 原币金额 | PDF 解析 / 手工 | 是 | 是`【需求】` |
| 支出币种 | 原币种 | PDF 解析 / 手工 | 是 | 是`【需求】` |
| 交易对手方 | 商户/收款方 | PDF 解析 / 手工 | 是 | 是`【需求】` |
| 交易备注 | 用户自己写的说明 | 手工 | 否 | 是`【需求】` |
| 支出类型 | 打标结果（交通/餐饮/住宿之类）`【需求】`第 64 行 | 规则建议 + 人工确认 | `【设计】` 允许暂时为「未分类」 | 是`【需求】` |
| 摊分月数 | 这笔支出摊到几个月`【需求】`第 65 行 | `【设计】` 默认 1 | 是`【需求】` |

`【设计】` 为形成闭环而补充的字段（非 Prompt 明列，属设计增补）：

| 补充字段 | 为什么必须有 |
|---|---|
| 归属用户 | §3.4 数据隔离的基础，没有它无法实现「不能越权」 |
| 来源类型（导入/手工） | 区分数据可信度；批次撤销、解析问题排查都依赖它 |
| 来源批次 | 支撑「整批撤销」和「这笔哪来的」溯源 |
| 折算金额（本位币）+ 所用汇率 | §7 多币种统一的落点；不存下来则历史统计会随汇率变动而漂移 |
| 摊分起始月 | §8 摊分展开的锚点；不显式定义则「摊分从哪个月开始」有歧义 |
| 打标方式（规则命中/人工） | 让用户知道类型是系统猜的还是自己定的，避免误信 |

> 说明：「摊分月数」的字面语义只说了「摊几个月」，没说「从哪个月起摊」。设计上必须补一个起始月概念，否则统计口径无法确定。默认取支出日期所属月份（见 §8.2）。

### 6.2 明细页能力

`【需求】` Prompt 第 67 行：能逐笔查看支出明细，支持一些实用维度的筛选与累计统计。第 68 行：上述七个字段都需要支持修改。

`【设计】` 筛选维度（选取「实用」而非「穷尽」，每一项都对应一个真实提问）：

| 筛选维度 | 回答什么问题 |
|---|---|
| 日期区间（含本月/上月/本年等快捷档） | 这段时间花了多少 |
| 支出类型（多选 + 「未分类」单独可选） | 钱花在哪类事上 / 还有多少没打标 |
| 币种 | 外币消费有哪些 |
| 对手方（关键词模糊匹配） | 在某个商户花了多少 |
| 金额区间 | 有哪些大额支出 |
| 摊分月数（=1 / >1） | 哪些是需要摊分的长期支出 |
| 来源（导入批次 / 手工） | 某次导入到底进了什么 |
| 数据质量（待补全 / 未分类 / 疑似重复） | 还有哪些数据要收拾 |

`【设计】` **累计统计随筛选联动**，展示：笔数、按本位币的合计、以及**按币种分组的原币小计**。理由：只给本位币合计会隐藏汇率折算的影响，用户核对银行账单时需要看到原币数。

`【设计】` 明细页统计**固定采用「不摊分」口径**（即整笔金额计入交易日期），并在界面上明示。理由：明细页是「逐笔核对」场景，用户在这里的心智模型是与银行账单对齐，摊分口径会让明细行金额与统计合计对不上，造成困惑。摊分视角统一在月度页提供（§8）。

### 6.3 打标（支出类型）

`【需求】` Prompt 第 64 行：支出类型需要打标，是交通/餐饮/住宿之类的。

`【设计】` 类型字典：

- 系统提供**预置类型**作为起点（依据 Prompt 举例：交通、餐饮、住宿，`【设计】` 另建议补充：购物、日用、娱乐、通讯、医疗、居住、学习、其他）；
- 允许用户**自定义类型**，且类型字典**按用户隔离**（否则一个人新建的类型会出现在别人的下拉框里，属 §3.4 的越权面）；
- `【设计】` 采用**单层扁平结构，不做多级分类**。理由：需求举例全是同一层级的并列概念；多级分类会让每次打标都要多做一次层级选择，而月度分析用扁平类型已足够。`【待确认】` 若需要「餐饮>外卖/堂食」这类下钻，见 §10-Q6。
- 已被流水引用的类型**不允许直接删除**，只能停用（停用后不再出现在打标下拉，但历史流水的展示不受影响）。理由：删除会造成历史流水的类型悬空，破坏历史统计。

`【设计】` 打标效率机制（这是决定系统好不好用的关键，因为打标是唯一的高频人工操作）：

| 机制 | 说明 |
|---|---|
| 打标规则 | 用户可维护「对手方关键词 → 类型」的规则，导入时自动给出建议类型，并标记为「规则命中」 |
| 历史学习提示 | 同一对手方历史上被打成某类型时，在打标时提示该类型（`【设计】` 仅作建议，不自动落库） |
| 批量打标 | 明细页支持多选后批量设置类型 / 摊分月数 |
| 未分类聚焦 | 提供「未分类」快捷筛选，让用户能集中清理 |

`【设计】` 自动建议**不覆盖人工结果**：一旦某笔的类型是人工设定，后续规则变更不回改这笔。理由：人工输入代表明确意图，被规则默默改掉是严重的信任损伤。

### 6.4 修改与可追溯

`【设计】` 修改规则：

- 七个业务字段均可修改`【需求】`第 68 行；
- 修改**金额或币种**时，重新按 §7 规则确定折算金额；
- 修改**摊分月数**时，按 §8.4 规则重建摊分展开；
- 保留**修改记录**（改了什么、从什么改成什么、何时改）。理由：金额类数据被改动后若无痕迹，用户无法解释「上个月的报表数为什么变了」，这在记账系统里是硬需求。
- `【设计】` 支持单笔删除（软删除，不参与任何统计，但可在回收视图中恢复）。理由：误删一笔账目若不可恢复，用户只能重新导入整份账单。

## 7. D5 币种与折算域：多币种如何统一处理

`【需求】` Prompt 第 66 行提出开放问题：「对于多币种如何进行统一处理？」

### 7.1 结论（推荐方案）

`【设计】` 采用「**原币留痕 + 本位币折算 + 折算结果固化**」三件套：

| 要素 | 规则 |
|---|---|
| 原币 | 永久保留原始金额与原始币种，任何情况下不被折算结果覆盖 |
| 本位币 | 用户级配置一个本位币（`【设计】` 默认人民币），所有跨币种汇总统一以本位币口径进行 |
| 折算 | 每笔支出在入账时确定一个「所用汇率」，算出「折算金额」并**随流水固化保存** |
| 展示 | 明细页展示原币（附折算金额），跨币种汇总只展示本位币，并注明「按入账时汇率折算」 |

### 7.2 为什么要「固化」而不是「每次查询实时折算」

这是本域唯一真正需要取舍的点：

| 方案 | 优点 | 致命问题 | 结论 |
|---|---|---|---|
| A. 查询时按当前汇率实时折算 | 实现简单，无需存汇率 | **历史月度报表数字会随汇率波动而变**——今天看 3 月支出 8000，明天看变 8050。记账系统的历史数据必须稳定，否则无法用于任何对账与复盘 | **不采用** |
| B. 入账时固化折算金额（推荐） | 历史数字稳定、可复算、可解释 | 需要维护汇率来源；汇率取错需要重算 | **采用** |
| C. 只存原币，各币种分别统计，不做统一 | 绝对准确，无折算误差 | 无法回答「这个月一共花了多少」——直接违背 G3 与第 69 行「按月查看支出金额」 | 不采用（但保留为 B 的补充展示） |

> 取舍要点：记账的核心价值在于历史可比。方案 A 会让「同一个月的支出金额」变成一个浮动值，这不是精度问题而是可信度问题。

### 7.3 汇率的来源与缺失处理

`【设计】` 汇率按以下优先级确定，并把实际用到的来源随流水记录下来：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | 对账单自带的折算金额 | 若账单同时印了外币原额与折算后的本币额，**优先采用账单自身数据**——它才是银行实际结算的金额，与真实扣款一致 |
| 2 | 用户维护的汇率表 | 用户按「币种+生效期间」自行维护，适用于想用固定预算汇率的场景 |
| 3 | 用户在导入时手工指定 | 一次性处理零星外币交易 |
| 4 | 缺失 | **不猜、不用 1:1 兜底** |

`【设计】` 汇率缺失时的行为（关键异常分支）：

- 该笔流水正常入账，但标记为「**待折算**」；
- 明细页可通过「数据质量」筛选出全部待折算流水；
- 月度汇总遇到待折算流水时，**在报表上显式提示「N 笔待折算未计入本位币合计」**，绝不静默按 0 或按 1:1 计入。

> 理由：静默兜底会产出一个看起来正常、实际错误的总额，这是财务类系统最危险的失败模式——错误必须可见。

`【设计】` 精度与舍入：金额一律按**最小货币单位的整数**记录与比对（避免浮点误差影响 §5.2 的指纹比对与合计对账）；折算采用四舍五入到本位币最小单位。已验算：`88.50 × 0.9123 = 80.73855 → 80.74`；`100.00 × 7.1234 = 712.34`。

`【设计】` 汇率修正后的行为：修改某笔的汇率或金额时，**只重算该笔**，并留下修改记录；不做全局批量回溯重算。理由：全局重算会一次性改动大量历史月份的数字，用户无法预期其影响范围；`【设计】` 若确需批量修正，走「筛选 → 批量重算 → 预览影响的月份与差额 → 确认」的显式流程。

## 8. D6 摊分与月度分析域

`【需求】` Prompt 第 65 行：摊分月数代表这笔支出需要摊分多少个月，有些收益时间比较长的支出，需要将支出摊分到多个月中。
`【需求】` 第 69-70 行：需要一个页面能按月查看支出金额、支出类型；能查看不经过摊分的每月支出金额，也能查看经过摊分的每月支出金额。
`【需求】` 第 71 行开放问题：修改摊分月数之后，会影响多个月的金额累计，当查询时如何处理筛选和统计数据的范围。

### 8.1 两个并列口径（核心概念）

`【设计】` 系统明确定义两个**并列且都正确**的口径，用户可在月度页一键切换：

| 口径 | 定义 | 回答的问题 | 特点 |
|---|---|---|---|
| **现金口径**（不摊分） | 整笔金额计入「支出日期」所属月份 | 「这个月我的卡实际被扣了多少」 | 与银行账单一致，可逐笔核对 |
| **摊分口径**（经过摊分） | 金额按摊分月数分摊到连续 N 个月 | 「这个月我真实的消费水平是多少」 | 平滑掉年费、大额耐用品的尖峰 |

`【设计】` 两个口径**同时保留、互不覆盖**，且界面上必须标注当前口径。理由：Prompt 第 70 行明确要求两者都能看；且它们服务于不同决策（对账 vs 分析），任何一个都不能替代另一个。

### 8.2 摊分展开规则

`【设计】` 规则定义：

| 规则项 | 定义 |
|---|---|
| 起始月 | 默认为「支出日期」所属月份`【设计】`，允许用户按笔调整 |
| 覆盖月份 | 起始月起**连续 N 个自然月**（N = 摊分月数） |
| 每月金额 | 原则上均分；除不尽的余数计入**最后一期** |
| N=1 | 等价于不摊分，与现金口径一致 |
| 币种 | 摊分基于**本位币折算金额**进行（否则跨币种无法在同一个月内相加）；原币金额不做摊分 |

`【设计】` 余数入末期的算例（已用计算器逐项验算）：

| 原始金额 | N | 每期金额 | 末期金额 | 合计校验 |
|---|---|---|---|---|
| 1000.00 | 3 | 333.33 × 2 | 333.34 | 333.33×2+333.34 = **1000.00** ✅ |
| 100.00 | 7 | 14.28 × 6 | 14.32 | 14.28×6+14.32 = **100.00** ✅ |
| 12345.67 | 12 | 1028.80 × 11 | 1028.87 | 1028.80×11+1028.87 = **12345.67** ✅ |

`【设计】` **摊分不变量（系统的核心正确性约束）**：

> 对任意一笔支出，其摊分到各月的金额之和 **恒等于** 该笔的本位币折算金额，不因摊分月数、金额大小或除不尽而产生任何误差。
>
> 推论：**在足够长的时间窗内（覆盖所有摊分尾巴），摊分口径合计 = 现金口径合计。** 这是两个视角唯一的对账等式。

`【设计】` 跨年摊分：允许跨自然年（例如 2026-03 起摊 12 个月 → 覆盖至 2027-02，已验算：`2026×12+3 = 24315`，`24315+11 = 24326 → 2027年2月`）。不因跨年做特殊截断。

`【设计】` 边界约束：摊分月数为 **≥1 的整数**，并设上限（`【设计】` 建议 120 个月，设定逻辑：覆盖 10 年是个人消费类支出的合理上限，同时防止误输入极端值产生海量摊分月份；可调整）。

### 8.3 月度页能力

`【需求】` Prompt 第 69 行：按月查看支出金额、支出类型。

`【设计】` 页面组成：

| 区域 | 内容 |
|---|---|
| 口径开关 | 现金口径 / 摊分口径（**必须常驻可见，不可折叠隐藏**） |
| 月度趋势 | 逐月总额，按选定口径 |
| 类型构成 | 选定月份（或选定区间）内各支出类型的金额与占比 |
| 月份下钻 | 点某个月 → 该月构成明细（见 §8.5 的下钻规则） |
| 口径差异提示 | 当两口径差异显著时提示「本月含摊分金额，与实际扣款不同」 |

`【设计】` 类型构成中，**「未分类」必须作为独立项显示，不允许并入「其他」**。理由：把未打标数据混进「其他」会让用户误以为已经分类完毕，掩盖数据质量问题。

### 8.4 修改摊分月数后的影响（回答 Prompt 第 71 行）

`【设计】` 这是本次设计中最需要说清的一点。分两层回答：

**第一层：修改行为本身如何处理**

| 规则 | 说明 |
|---|---|
| 全额重铺 | 修改摊分月数后，该笔的摊分**整体按新参数重新展开**（旧展开整体作废），而不是「已过去的月份保持不动、只改未来」 |
| 不变量恒成立 | 重铺后各月之和仍恒等于原折算金额（§8.2） |
| 现金口径不受影响 | 改摊分月数**完全不影响**现金口径的任何月份数字 |
| 影响预览 | 提交前给出「将影响哪些月份、各月增减多少」的预览，**用户确认后才生效** |
| 留痕 | 记录摊分月数的修改历史（§6.4） |

> 取舍：为什么选「全额重铺」而不是「只改未来月份」？
> 「只改未来」会破坏 §8.2 的不变量——各月之和不再等于原金额，导致摊分口径与现金口径**永久无法对账**，系统失去自证正确的能力。个人记账不存在会计期间已结账锁定的约束，因此重铺是更简单且更正确的选择。
> `【待确认】` 若用户有「历史月份一经查看即锁定」的诉求，需引入结账期概念，见 §10-Q7。

**算例（已用计算器逐项验算）**：某用户有两笔支出——A：2026-03 支出 1200.00，摊分 3 个月；B：2026-03 支出 300.00，不摊分（N=1）。

现金口径（恒定不变）：

| 月份 | 金额 |
|---|---|
| 2026-03 | 1500.00（=1200.00+300.00） |

摊分口径 · 修改前（A 摊 3 个月，每月 400.00）：

| 月份 | A 贡献 | B 贡献 | 合计 |
|---|---|---|---|
| 2026-03 | 400.00 | 300.00 | **700.00** |
| 2026-04 | 400.00 | — | **400.00** |
| 2026-05 | 400.00 | — | **400.00** |
| 合计 | 1200.00 | 300.00 | **1500.00** ✅ 等于现金口径 |

摊分口径 · 把 A 改为摊 6 个月后（每月 200.00）：

| 月份 | A 贡献 | B 贡献 | 合计 | 与修改前对比 |
|---|---|---|---|---|
| 2026-03 | 200.00 | 300.00 | **500.00** | −200.00 |
| 2026-04 | 200.00 | — | **200.00** | −200.00 |
| 2026-05 | 200.00 | — | **200.00** | −200.00 |
| 2026-06 | 200.00 | — | **200.00** | +200.00（新增月份） |
| 2026-07 | 200.00 | — | **200.00** | +200.00（新增月份） |
| 2026-08 | 200.00 | — | **200.00** | +200.00（新增月份） |
| 合计 | 1200.00 | 300.00 | **1500.00** ✅ 不变量成立，仍等于现金口径 |

**这个算例揭示的关键风险**：修改摊分月数会让摊分口径**长出新的月份**（本例新增 2026-06/07/08）。如果用户当前的查询区间是 2026-03～2026-05，他会看到总额从 1500.00 变成 900.00（=500+200+200，已验算），差额 600.00 并未消失，而是落在了查询区间之外。这直接引出第二层。

**第二层：查询时如何处理筛选与统计范围**

`【设计】` 这是 Prompt 第 71 行的正面回答，共四条规则：

**规则 1 —— 明确「筛选区间」的语义随口径而变（最重要）**

| 口径 | 日期区间筛选的语义 |
|---|---|
| 现金口径 | 筛「**支出日期**落在区间内」的流水 |
| 摊分口径 | 筛「**摊分归属月**落在区间内」的摊分份额 |

> 这意味着：在摊分口径下，一笔 2025-12 的支出若摊 12 个月，查询 2026-03 时**它必须被计入**（尽管其支出日期不在 2026-03）。这是摊分口径能否正确工作的前提。
> 反之，一笔 2026-03 的支出摊 12 个月，在查询 2026-03 时**只计入其 1/12**，而不是全额。

**规则 2 —— 区间外的摊分尾巴必须显式披露，不能静默截断**

`【设计】` 在摊分口径下，若当前查询区间内的支出存在延伸到区间之外的摊分份额，报表须给出摘要：

> 「本区间统计 900.00；另有 600.00 摊分至区间之后的月份（2026-06 ~ 2026-08）」

理由：这是唯一能防止用户误以为「钱变少了」的手段。截断本身是正确的（用户就是要看这几个月），但**不告知**会造成严重误解。同理，区间之前的支出摊入本区间的部分，也应可展开查看来源。

**规则 3 —— 修改摊分月数后，已打开的查询结果必须刷新，不沿用缓存**

`【设计】` 修改生效后，明细页与月度页的统计结果一律重新计算；若用户停留在旧结果上，界面须提示数据已变更。理由：摊分修改是「一笔改动影响多个月」的跨行影响，缓存不失效会让用户看到自相矛盾的数字。

**规则 4 —— 提供「不变量自检」作为用户可见的对账工具**

`【设计】` 提供一个足够长区间（例如「全部时间」）的对账视图，展示：

| 指标 | 值 |
|---|---|
| 现金口径合计 | 1500.00 |
| 摊分口径合计（全部时间） | 1500.00 |
| 差额 | 0.00 ✅ |
| 待折算笔数（未计入） | 0 |

理由：这让用户能自行确认系统没算错，也是验收摊分逻辑的直接手段（对应 §9 验收 AC-10）。

### 8.5 月份下钻的展示规则

`【设计】` 在摊分口径下点击某个月下钻，展示的是「**摊分份额**」而不是「原始流水」，每行须同时显示：本月计入金额、原始支出全额、原始支出日期、摊分进度（如「第 2/6 期」）。

理由：若下钻直接展示原始流水全额，行金额之和会远大于月度总额，用户会立刻认为系统算错了。摊分进度信息则让用户能理解这笔钱的来龙去脉。

## 9. 端到端业务流程与验收

### 9.1 主流程（新用户首次使用）

```
管理员建号 → 用户首次登录并改密 → 设置本位币
  → 上传 PDF（必要时输密码）→ 预览解析结果
  → 处理去重裁决 → 补齐待补全项 → 批量打标 → 设置需摊分的支出
  → 确认入账 → 明细页核对（现金口径，与银行账单对平）
  → 月度页分析（两口径切换）
```

### 9.2 关键验收场景

`【设计】` 每项覆盖一个成功场景与一个主要风险场景：

| 编号 | 场景 | 给定 | 当 | 则 |
|---|---|---|---|---|
| AC-1 | 全局登录校验 | 未登录 | 直接访问明细页/月度页/任一接口 | 跳转登录页；登录后回跳原目标 |
| AC-2 | 数据隔离 | 用户乙已登录 | 尝试访问属于用户甲的流水或导入批次 | 返回「未找到」，**不提示「无权限」**（§3.4） |
| AC-3 | 建号权限 | 普通用户已登录 | 尝试进入账户管理 | 无入口且直接访问被拒 |
| AC-4 | 加密 PDF | 上传加密 PDF | 输入错误密码 | 明确提示密码错误、可重试、已上传文件不丢失；超限终止 |
| AC-5 | 账期重叠去重 | 已导入 1-3 月账单 | 导入 2-4 月账单 | 顶部提示账期重叠；2-3 月重复流水默认不入账并高亮；4 月流水正常入账 |
| AC-6 | 去重防误杀（L3） | 历史有 1 笔「3/15 星巴克 35 元」 | 新账单含 2 笔同指纹交易 | 判定 1 笔重复、1 笔新增；不出现 2 笔全跳 |
| AC-7 | 摊分不变量（整除） | 1200.00 摊 3 个月 | 查看全部时间的摊分口径合计 | 每期均为 400.00（整除，无余数）；合计等于 1200.00，误差为 0 |
| AC-7b | 摊分不变量（除不尽，**必测**） | 1200.00 摊 7 个月 | 查看全部时间的摊分口径合计 | 前 6 期各 171.42、末期 171.48；合计等于 1200.00，误差为 0 |
| AC-8 | 改摊分月数 | 1200.00 已摊 3 个月 | 改为摊 6 个月 | 先出影响预览（列出受影响月份与增减）；确认后各月重铺，合计仍为 1200.00 |
| AC-9 | 区间截断披露 | 1200.00 摊 6 个月自 2026-03 | 查询 2026-03~2026-05（摊分口径） | 显示 600.00，**并提示另有 600.00 摊分至 2026-06~2026-08** |
| AC-10 | 两口径对账 | 任意数据集 | 对比全部时间的两口径合计 | 差额为 0；若有待折算流水，明确列出未计入笔数 |
| AC-11 | 汇率缺失 | 一笔外币无可用汇率 | 入账并查看月度汇总 | 该笔标为待折算；汇总显式提示「N 笔未计入」，**不按 1:1 静默兜底** |
| AC-12 | 历史稳定性 | 一笔外币已入账折算 | 此后汇率变动 | 历史月度报表数字**保持不变**（§7.2） |
| AC-13 | 批次撤销与指纹释放 | 某批次已入账 | 撤销该批次后重新导入同一份账单 | 不被误判为重复；已人工修改过的流水在撤销前需用户确认 |
| AC-14 | 明细修改联动 | 一笔已入账流水 | 修改金额/币种 | 折算金额重算、摊分重铺、留下修改记录、月度两口径同步变化 |
| AC-15 | 打标不被覆盖 | 某笔类型为人工设定 | 此后修改打标规则并再次导入 | 该笔类型保持人工结果不被规则覆盖 |

## 12. 关键设计取舍汇总

供快速回顾本文的六个核心判断：

| # | 取舍点 | 选择 | 核心理由 |
|---|---|---|---|
| 1 | 「多人账户」的语义 | 多租户各记各账，非协作账本 | Prompt 第 57 行的越权约束与共享语义互斥 |
| 2 | 去重是否全自动 | **不全自动**，系统判「疑似」+ 用户裁决 | 同日同商户同金额可能是两笔真实消费；误杀导致账目静默缺失，比重复录入更严重 |
| 3 | 多币种统一方式 | 入账时固化折算金额，而非查询时实时折算 | 保证历史月度数字稳定可比；实时折算会让历史报表数字漂移 |
| 4 | 汇率缺失兜底 | 标「待折算」并在报表显式提示，**不按 1:1 兜底** | 错误必须可见，不能产出看似正常实则错误的总额 |
| 5 | 摊分与现金口径 | 两口径并列共存，界面常驻切换 | 分别服务对账与分析，互不能替代（第 70 行明确要求两者） |
| 6 | 改摊分月数的处理 | 全额重铺 + 影响预览 + 区间外尾巴显式披露 | 维持「各月之和 = 原金额」不变量，使两口径可对账、系统能自证正确 |
