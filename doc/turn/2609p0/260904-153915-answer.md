## 二、背景调研：承载边界与「为什么需要这个包」

### 2.1 存在理由：它是不变式 4 的实现前提，不是工具类

分层版 §十 约定 9：「**标识由应用层生成**：`base/idgen` 是全仓库唯一 ID 来源，`store` 不生成 ID、不依赖自增回填」。这条不是风格偏好——终版 §九 不变式 4 要求「一次提交 = 一条审计 = 一个可追溯批次」，其实现时序（分层版 §六 L5 `service/audit` 行）是：

> 「**先落审计取 ID**（`base/idgen` 生成，不依赖自增回填）→ 业务数据挂载该 ID → 同事务提交」

若审计ID 依赖数据库自增回填，则**同一事务内取不到已提交的自增值**，`Expense.来源审计ID` 与 `File.来源审计ID` 就无从挂载，终版 §八 8.4 的批次追溯与 §十 流程 5 的批次撤销随之失去边界。所以本包是该时序的**结构性前提**。

### 2.2 承载 → 接口分工

分层版 §六 L0 表 `base/idgen` 行写明「调用方**恰为 5 个创建方**」。本包为每类各出一个具名函数，而非只出一个通用 `GenID()`：

| 承载原文的调用方 | 本包函数 | 对应实体标识（终版 §四） |
| ---------------- | -------- | ------------------------ |
| `service/audit`（审计ID） | `GenAuditID` | `AuditLog.审计ID`，兼入库批次号 |
| `service/account`（用户ID） | `GenUserID` | `User.用户ID`，全部业务数据的归属键 |
| `service/category`（类型ID） | `GenCategoryID` | `ExpenseCategory.类型ID` |
| `service/file`（文件ID） | `GenFileID` | `File.文件ID` |
| `service/intake`（明细ID） | `GenExpenseID` | `Expense.明细ID` |

**为什么拆成 5 个而不是 1 个**：让「谁在造哪类 ID」在调用点即可见，越权生成在评审时一眼可查（分层版 §四 R3 承认「`base/idgen` 是普通包，任何包 import 得到」，无编译期兜底，只能靠约定 + 评审——具名入口是让评审可执行的最低成本手段）。5 个函数**共用同一实现**，因此取值空间统一，见 2.3。

### 2.3 五类 ID 必须共用取值空间（终版 §七 推出的硬约束）

终版 §七 末行：「`AuditLog.对象ID` **是历史指针，不是外键**」；§四 `AuditLog.对象ID` 说明同样写「指向的对象可能已被删除」。该列**跨实体存放**——8.4 的 11 类审计里，它可能是用户ID（第 1/3/4 类）、文件ID（第 5 类）、明细ID（第 7 类逐笔）或类型ID（第 9 类）。

若五类 ID 各有独立取值空间，同一个数值可能既是类型ID 又是文件ID，K-2 的跳转就无从判断该跳向哪个实体。故本包**只有一个发号入口 `gen()`**，五个具名函数是它的语义外壳。已在 `TestFiveEntryPointsShareSpace` 与 `TestConsumerNoIDReuseAcrossEntities` 中钉住。

### 2.4 明确**不**放进本包的

- **不放** ID 与时间的互转（`ParseId`）。`GenId()` 的 ID 内嵌东八区时间戳，`go_common` 也提供 `ParseId`，但**业务时间一律用实体自己的时间字段**（终版 §四 的创建时间 / 更新时间 / 操作时间 / 上传时间）。把 ID 当时间用，等于给「ID 编码方式」这个实现细节建立业务依赖——上游一改实现，历史数据的时间语义就全变。
- **不放**「ID 属于哪类实体」的反查。ID 里没有实体类型标记（也不该有，见 2.3 的统一空间要求），K-2 的跳转靠 `AuditLog.操作对象类型` 列（终版 §四）判断，不靠解析 ID。
- **不放**任何随机串生成。分层版 §三 问题 2 已定：`base/pwdhash` 的安全随机串**只供 `rule/passwd` 采样初始密码**（A-2），与 ID 生成无关。

## 三、选型：直接用 `go_common/util.GenId()`，但加三层收窄

prompt 对话1 指定「需要使用该库：`go_common/util/gen.go` 的 `GenId()`」，故**不做选型比较**，直接采用。本包在其上只加三件事，每件都对应一处会静默出错的真实风险：

| # | 加的东西 | 不加会怎样 |
| - | -------- | ---------- |
| 1 | 5 个具名入口 | 「5 个创建方」这条约定在类型系统里无痕迹，越权生成无从评审（§四 R3 无编译期兜底） |
| 2 | **正整数断言**（`mustPositive`） | 见 §五 |
| 3 | `String` / `ParseString` | 见 §六（JSON 精度）与 §五（非法输入静默变合法 ID） |

### 3.1 `GenId()` 的实测形态（不是读代码推断，是跑出来的）

`GenId()` 返回「东八区年份后两位 + 月日时分秒 + 6 位微秒」的定长拼接（源码 `DateLayout_060102150405_0000000` 去小数点）。实测结果：

| 实测项 | 结果 |
| ------ | ---- |
| 形态 | `260906160236617234`，**18 位正整数**；`ParseId` 可还原为 `2026-09-06T16:02:36.617234+08:00` |
| 顺序唯一性 | 20 万次连续调用，**唯一 20 万、重复率 0.0000%**、严格递增 |
| 并发唯一性 | 64 goroutine × 5000 = 32 万次，**唯一 32 万、重复率 0.0000%** |
| `int64` 余量 | `9223372036854775807 / 260906160443337625 ≈ **35.4 倍**`，无溢出风险 |

唯一性来自其内部的 `sync.Mutex` + 「上次微秒时刻 +1」机制（源码注释记载：未修复前顺序 2 万次仅得约 2700 个不同值，碰撞率 86%）。本包的 `TestGenUnique` / `TestGenConcurrentUnique` 即对该机制的回归断言。

## 四、方案取舍（逐条给依据）

### 4.1 返回 `int64` 裸类型，不定义 `type ID int64`

**取**：`int64`。
**舍**：具名类型 `type ID int64`，或五个互不兼容的 `type AuditID int64` 等。

依据：
- 终版 §四 的 `AuditLog.对象ID` 跨实体存放（§2.3），若五类各有类型，该列的类型无从选定，赋值处必然到处强转，强转多了等于没有类型安全；
- `entity` 包按分层版 §六 L1.1 要求「**零方法**」的结构体定义，字段类型若用本包的具名类型，会让 `entity` 对 `base/idgen` 产生依赖——而 L1.1 的依赖列只有 `currency`/`enum`/`base/decimal`/`base/calendar`，**没有 `base/idgen`**。用 `int64` 则 `entity` 无需 import 本包，与分层表逐字一致；
- 对照：`base/calendar` 定义了 `Date`/`Month` 具名类型且被 `entity` 依赖——那是因为分层表**明确列了**该依赖，且日期有「非零值必合法」的不变量需要类型封装。ID 没有这类不变量（任何正整数都是合法 ID 形态）。

### 4.2 零值 `0` 即「无 ID」，不引入额外的哨兵值或 `sql.NullInt64`

依据终版 §四 的三处原文：
- `AuditLog.操作对象类型`：「**零值 = 本次操作无具体对象或为批量操作**」；
- `AuditLog.对象ID`：「零值 = 同上」；
- `Expense.来源文件ID`：「**手工录入时为空**；复制时继承被复制明细的值」；
- `Expense.支出类型ID`（G-2）：「**空即未分类**」，且「字典中不设『未分类』记录」。

这四处都要求「零值可直接表达缺失」。前提是**本包永不发出 0**，否则一条有主记录会被静默展示成「无具体对象」。故有 §五 的断言，与 `IsValid` 这个可判定形式。终版 §四 开头「业务上『不适用』的场景以零值表达，不留空」也是同一取向。

### 4.3 `ParseString` 只接受**规范形态**（本轮由测试发现并修正的一处真实缺陷）

首版实现只判 `err != nil` 与 `id <= 0`，测试立刻挂出两条：`"+123"` 与 `"007"` 被 `strconv.ParseInt` 接受。

这不是测试写严了，是实现与自己写的注释不符（注释已声明「含正负号……一律 ok=false」）。**修的是实现，不是测试**：改为以「`FormatInt(id,10) == s` 是否逐字节相同」作判据，一次覆盖正号前缀、前导零及其他所有非规范写法。

为何连数值合法的 `"+123"`、`"007"` 也拒绝：
- ID 来自机器生成的 JSON 与 URL，非规范写法即代表调用方拼装有误或是探测行为；
- 放行会让同一条记录有多种文本形态，缓存键、幂等判定与审计摘要里的 ID 不再能按字符串比对；
- 与同层 `base/calendar` 拒绝 `"2026-1-2"` 这类非定长日期写法**是同一条取向**（该包 §「两条全局性质」明确依赖定长）。

### 4.4 不复用 `go_common` 的 `util.String2Int` 做解析

其源码注释自陈：「溢出时 `ParseInt`/`ParseUint` 返回的是**钳制值**（`MaxInt64`/`MinInt64`/`MaxUint64`）而非 0，此处**丢弃 err** 即沿用该钳制语义」。

即：`String2Int("9223372036854775808")` 得 `MaxInt64`，`String2Int("abc")` 得 0，**非法输入静默变成一个看似合法的 ID**。终版 §九 不变式 3「归属校验无死角……漏一处等于全量泄露」的入口不能建立在这种语义上——一个非法路径参数会被钳成合法 ID 后进入归属查询。故本包自行用 `strconv.ParseInt` 并把失败显式暴露（`ok` 为假时 `id` 恒为 0，不返回钳制值），已由 `TestParseStringNoClampSemantics` 钉住。

### 4.5 非正值一律 `panic`，不返回 error

依据：
- 若 `gen()` 返回 `(int64, error)`，5 个创建方每次建实体都要处理一个「实际上只可能在环境级故障时发生」的错误，噪声远大于收益；
- 更关键的是**没有合理的降级路径**：ID 生成失败时，业务除了中止别无选择，而带着 0 继续写库会静默破坏 §4.2 的零值语义，且已落库的错 ID 无法回溯修正；
- `panic` 的信息里带上实际值，属进程启动期就该暴露的故障。

## 五、`mustPositive`：为什么要断言一件「看起来必然成立」的事

`GenId()` 恒为正的性质**源自其内部时间编码，属实现细节而非承诺**。实测两处证据说明它并非牢不可破：

| 实测输入 | `GenIdByTime` 输出 | 位数 |
| -------- | ------------------ | ---- |
| `2026-09-06T15:00:00+08:00` | `260906150000000000` | 18 |
| `2000-01-01T00:00:00+08:00` | `101000000000000` | **15**（年份 `00` 的前导零丢失） |
| `2100-01-01T00:00:00+08:00` | `101000000000000` | **15**（与 2000 年**同值**） |

即：ID 的位数与取值**依赖系统时钟落在哪个世纪**，且 2000 与 2100 会产出同一个值。本包不为「跨世纪重号」负责（那是上游的编码上限，且 2100 年前本系统的存续性不在本轮范围），但**必须为「零值语义不被静默破坏」负责**——一旦上游改实现或时钟异常导致发出 0 / 负值，`AuditLog.对象ID` 上「有主 vs 批量」的判定会当场失效。

故断言单独抽成 `mustPositive` 函数（而非内联在 `gen` 里），使这条守卫**本身可被单测覆盖**——否则只能靠改系统时钟或替换上游实现才能触发该分支。`TestMustPositivePanics` 对 `0` / `-1` / `MinInt64` 等输入验证 panic 且信息含实际值，正数原样透出。这也是覆盖率能到 100% 的原因。

## 六、实测发现：dto 的 ID **必须**走字符串（交给 L6 落实，不阻塞本包）

18 位 ID 超过 IEEE-754 双精度的安全整数上界 `2^53`（16 位），而 JavaScript 的 `Number` 即 `float64`。实测：

```
id = 260906160443337625        （库里的值，18 位）
裸 int64 序列化 → {"id":260906160443337625}
经 float64（即 JS Number）往返 → 260906160443337632
偏差 7，且全程不报错
```

`consumer_check_test.go` 里再跑一次也稳定复现（该次偏差 2）。**后果**：分层版 T34 定案前后端分离后，前端拿到的 ID 与库里不是同一个，据此发起的编辑 / 删除 / 下载请求会带着一个不存在的 ID——终版 §二 B-3「按 ID 访问的归属校验」会对着错 ID 做判定。

**结论（落点在 `api/http/dto`，非本包承载，故不阻塞本轮）**：dto 的全部 ID 字段须以字符串出入（`json:"...,string"` 或直接用 `string` 字段 + 本包的 `String`/`ParseString`）。本包已提供转换入口，并在 `TestConsumerDtoJSONPrecision` 里把「裸 int64 会失真、两种正确写法都不失真」三条同时钉成可执行断言——写到 L6 时若有人改回裸 int64，这条测试不会报警（它在 idgen 包内），但方案与注释均已留痕，`dto` 轮次可直接引用。

## 七、副作用评估与两项非阻塞登记

### 7.1 依赖体量（实测）

| 包 | 第三方模块数（依赖闭包） | 包总数 |
| -- | ------------------------ | ------ |
| `internal/base/calendar` | **1** | — |
| `internal/base/idgen`（本包） | **51** | 407 |

`go_common/util` 是单一大包，`GenId` 与 gin / gorm / excelize / quic-go / mongo-driver 等同处一包，import 即拉入全部。**这是 prompt 指定该库的既定代价**，本包无从规避（Go 的最小编译单元是包）。登记而不处理，理由：① prompt 明确指定；② 同批次的 `base/log` 轮次同样指定了 `go_common/util`，该依赖迟早进入仓库，本包不构成额外引入；③ 个人系统规模下二进制体积与编译时长可接受。

### 7.2 导入即创建 `log/` 目录（实测）

`go_common/util` 的 `init()` 调用 `InitDefaultLog()`，lumberjack 在**当前工作目录**下建 `log/<服务名>/log.log`。实测「仅 `import _`、不调用任何函数」即触发，并起 8 个 goroutine。

- 对本轮的影响：跑 `go test` 会在 `internal/base/idgen/` 下留下 `log/` 目录。**已确认被 `.gitignore` 第 38 行 `*.log` 覆盖**，不会误入库；本轮结束前已 `rm -rf internal/base/idgen/log` 清理。
- 对运行期的影响：落点在 `app` / `cmd`（`base/log` 轮次已按 prompt 引入 `util.Init(serverName)`），本包不做任何日志初始化——分层版 §六 L0 表 `base/log` 行才是日志的承载处，本包不越界。

### 7.3 `go_common` 无语义化版本标签

实测 GitHub tags 数 `0`，goproxy 的 `@v/list` 为空。故只能钉伪版本：`v0.0.0-20260905162556-500c0b32bf4e`（`go.sum` 已记录哈希，可复现）。登记：日后升级须人工核对 `GenId` 行为是否变化——本包的 `TestGenUnique` / `TestGenMonotonic` / `TestGenPositive` 即为此准备的回归网。

### 7.4 对现有链路的影响

`internal/` 下已有的 `base/calendar`、`base/config` 与本包**无依赖关系**（L0 层内零依赖），本包新增不影响二者。`go.mod` 新增 `github.com/cellargalaxy/go_common` 到 require 块（连带 50 个 indirect），`go build ./...` 全仓库通过。
