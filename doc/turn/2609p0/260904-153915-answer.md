## 二、对指定依赖 `util.GenId()` 的实测核验

不凭签名猜行为，先把 `GenId()` 的真实性质测出来再设计（探针为临时模块，未污染本仓库；已删除）。

`util/gen.go` 关键实现（逐行读过）：`GenId()` = `GenIdByTime(time.UnixMicro(nextIdMicro(time.Now())))`；`nextIdMicro` 用包级 `sync.Mutex` 保证「严格递增的 Unix 微秒」，同微秒内连续调用或时钟回拨时取 `上次值 + 1`；`GenIdByTime` 按 `E8Loc`(固定 UTC+8) 格式化为 `060102150405.000000` 后去掉小数点，得 18 位十进制。

| 性质 | 实测结果 | 对本设计的意义 |
| -- | -- | -- |
| 唯一性（顺序） | 20 万次调用，**碰撞 0** | 满足 5 实体主键要求 |
| 唯一性（并发） | 50 协程 × 4000 次 = 20 万次，**碰撞 0** | `nextIdMicro` 的互斥有效，服务层可并发调用 |
| 单调性 | **严格递增 = true** | SQLite 主键顺序写入，B-Tree 无随机插入放大 |
| 非零性 | 零值 **0 次**；且格式上不可能为 0（`Format` 的月/日恒 ≥ 01，最小值形如 `000101000000000000`） | **关键**：§四 多处以「零值 = 未设置」表意（`Expense.来源文件ID` 手工录入为空、`AuditLog.对象ID` 零值 = 批量），生成值一旦为 0 会与「未设置」混淆 |
| 宽度 | 恒 18 位（如 `260906010651208000`），`int64` 上限为 19 位，**不溢出** | 可用 `int64` 承载 |
| 吞吐 | 159.7 ns/次 | 远超本系统需求（D-7 单批 N 条明细） |
| 时间域漂移 | 20 万次连续调用后，ID 时间域**超前真实时钟 168ms** | 高频突发时 ID 会「借用未来微秒」；本系统量级下可忽略，登记于 §五 |
| `float64` 往返 | **5 个相邻 ID 全部失真，塌缩为同一个值**（该量级 `float64` 表示间隔 = 64） | 见 §六 跨包影响 |

> 唯一性只在**单进程内**成立（互斥量是进程级）。本系统为单二进制个人系统、`store/sqlite` 已定「写连接单例 + WAL」（§六 L4），单进程前提成立；多实例部署会破此前提，登记于 §五。

## 三、方案与关键取舍

**总体思路：`base/idgen` 是 `util.GenId()` 之上的一层薄封装，本身不发明 ID 方案。** 封装的价值不在算法，而在三处：① 它是约定 9「全仓库唯一 ID 来源」的**唯一落点**，评审只需检查「除本包外无人 import `go_common/util` 取 ID」；② 把 `go_common` 这个外部依赖**收敛到一个文件**，将来换方案（如雪花算法）只改本包，5 个调用方零改动；③ 承接「非零」这条跨实体不变式的兜底校验。

| # | 决策 | 取舍与依据 |
| - | ---- | ---------- |
| 1 | **出 5 个具名函数**（`GenAuditID` / `GenUserID` / `GenCategoryID` / `GenFileID` / `GenExpenseID`），内部统一委托一个私有 `gen()` | 备选是只出一个通用 `GenID()`。选具名：§六 L0 承载写的是「**5 类**实体的唯一标识生成」且逐一点名了 5 个调用方，具名函数让调用点自解释（`idgen.GenAuditID()` 一眼看出在造审计ID），也为「将来某类实体单独换方案」留出改一行的位置；成本是 5 个 3 行函数体，且全部委托同一实现，无重复逻辑 |
| 2 | **返回裸 `int64`，不定义 `type ID int64`** | 依据是 §六 L1.1 `entity` 的**依赖列 = `currency`、`enum`、`base/decimal`、`base/calendar`，不含 `base/idgen`**。若本包定义命名类型，`entity` 的 5 个 ID 字段要么被迫 import `base/idgen`（凭空多一条依赖边，与分层总表矛盾），要么在每个调用点写强制转换。裸 `int64` 使 `entity` 保持零 ID 依赖，与分层总表逐字一致 |
| 3 | **零值兜底：生成值为 0 则 panic** | §四 的「零值 = 未设置」语义（`来源文件ID`、`对象ID`）决定 0 是保留值。本包依赖列为 `—`，用不了 `base/errs`（那是 L0 的兄弟包，会成层内边）；签名也不宜加 `error`（会让 5 个调用方为一条不可达分支写错误处理）。故取 panic 作**不可达兜底**：数据一旦带 0 ID 落库，归属与批次追溯会静默错乱，属「宁可启动即崩，不可静默写坏」。§二 已论证该分支格式上不可达，实测 20 万次亦为 0 次 |
| 4 | **不重新实现单调与互斥** | `util.nextIdMicro` 已用包级互斥保证严格递增（源码已读、并发已实测）。本包再加一层锁只会串行化两次且不增加任何保证——违反「复用优先」 |
| 5 | 单测**不依赖真实时钟推进**，只断言可观测契约（唯一 / 非零 / 单调 / 并发 / 宽度 / 5 入口互不串号） | `GenId()` 的时间源不可注入（`time.Now()` 硬编码在 `util` 内），断言绝对时间会造出偶发失败的脆弱用例 |

### 冲突登记（1 处，不默默取一方）

| 冲突点 | 双方原文 | 采用依据与后果 |
| ------ | -------- | -------------- |
| ID 是否需要随机性 | **方案文档** §三 问题 2 修法 + §六 L0 表：`base/idgen` 的随机性「**直接取标准库密码学随机源**」；**本轮 prompt**：指定使用 `util.GenId()`，而该函数是**纯时间序、完全无随机性**（同文件的 `CreateRandString` 用的还是 `math/rand`，非密码学随机） | **采用 prompt**，依据是本 prompt 执行流程首部明写「流程冲突时以「任务 Prompt」为准」。另需说明：§三 问题 2 那条修法的**真实目的**是「`idgen` 不借道 `pwdhash` 取随机性，使 **L0 恢复层内零依赖**」（原文修法结论即「L0 恢复层内零依赖」），「取标准库」只是当时的手段。改用 `util.GenId()` 后该目的**完全达成且更彻底**——本包连随机源都不需要，依赖列 `—` 名副其实。<br>**后果（已评估，可接受）**：ID 变为**可预测、可枚举**（18 位时间戳，能猜出邻近 ID）。这不构成越权风险——§九 **不变式 3「归属校验无死角」**已定「任何按 ID 的访问都必须校验归属」，且 §六 `store` 的 4 个归属型仓储**签名强制带归属用户ID**、前提 3 明写该参数**无管理员旁路**。即安全性由归属校验兜底，本就不依赖「ID 不可猜」。次要后果：ID 泄露实体创建时刻——而 §四 中 5 实体本就都有 `创建时间`/`上传时间`/`操作时间` 属性，不构成新增信息泄露 |

## 六、跨包影响登记：ID 的 JSON 序列化形态（须在 L6 阶段落实）

**实测事实**：ID 为 18 位十进制，量级约 `2.6e17`，**超出 JS `Number.MAX_SAFE_INTEGER`（`9007199254740991`，16 位）约 29 倍**。在该量级下 `float64` 的相邻可表示值间隔为 **64**，实测**连续 5 个 ID 经 `float64` 往返后全部失真、塌缩为同一个值**。

**为什么现在就要登记**：T34 已定前后端分离，§六 L6 `api/http/dto` 是「前后端分离下即 JSON 契约」。若 ID 以 JSON number 下发，浏览器 `JSON.parse` 按双精度解析即**静默截断**——后果是 F-5 编辑、F-8 删除、K-2 跳转、D-7 提交全都可能带着**被改写过的 ID** 回传服务端，命中另一条记录或查不到记录，且因归属校验仍会拒绝而表现为「偶发的莫名 403/404」，极难定位。

**结论**：`api/http/dto` 定义时，5 类 ID **一律以字符串形态进出 JSON**（Go 侧 `int64` + `json:",string"` 或显式 string 字段）。本轮不实现 `dto`，故仅登记，不改本包——本包返回 `int64` 是对的，转换属 L6 边界职责。
