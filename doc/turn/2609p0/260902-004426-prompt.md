# 执行流程

> 你是一位拥有跨学科背景的顶尖资深专家，请以深厚的专业洞察力和严谨的大师视角进行回复

## 步骤

- 背景调研
    - 研读prompt中提及的文档/代码/配置
    - 对齐背景，梳理核心逻辑/组件依赖/改动点
- 需求分析与方案
    - 提取核心目标/交付物/范围边界/关键约束
    - 制定方案：最小改动/复用优先/任务拆解；说明模块职责/输入输出/关键逻辑/异常处理
    - 评估对现有链路/性能/兼容性/下游的副作用
    - 写入`answer.md`：依据来源/方案取舍/实施步骤/验证说明
- 实施
    - 按方案执行，命名/注释/文案与项目风格一致
    - 中文注释与日志，处理边界与异常分支
    - 同步更新类型定义/关联配置/文档
    - 复杂任务使用主agent调度子agent的方式实施
- 验证与交付
    - 执行测试/逻辑校验/数据校验/文档校对
    - 重读`prompt.md`，检查与交付结果是否一致
    - 核心产出同步至`answer.md`
    - 清理临时文件/调试代码/冗余产物，但无须提交变更

## 约束

- 依据：结论只能来自文档/代码/表结构/日志/SQL等明确来源；严厉禁止猜测业务逻辑/捏造接口字段，不能断言的内容都询问用户
- 引用：关键事实引用到具体章节/字段名/代码路径或枚举值，禁止笼统援引
- 信息不足：区分「已确认/待确认/不可推断」并标注，不得脑补
- 历史资料：历史Prompt/answer/旧方案仅供参考，必须与代码交叉核对后才能使用
- 冲突：资料冲突时列出冲突点与采用依据，不得默默取一方
- 风格：命名/注释语言/代码组织与项目既有风格一致，优先复用现有实现

### 对话4

+ ExpenseCategory 支出类型
    + 新用户创建后，默认没有支出类型
    + 因此是否默认未分类与是否内置都不需要
    + 排序也不需要，减少用户管理数据的成本
+ Expense 支出明细
    + 银行名称、卡号后四位、卡片币种：这是三个属性在一个字段里？是一个json字段？
    + 原始摘要：这是什么
    + 汇率来源：不需要
    + 交易指纹：能否直接查询「用户 + 支出日期 + 支出金额 + 支出币种」，而不需要再单独弄一个交易指纹字段
    + 删除：采纳软删除
+ File 文件
    + 存储位置：直接将文件的二进制数据存储在表中，减少数据迁移与备份成本
+ 支出金额允许为负，负金额也支持摊分
    + 负金额代表退款，需要通过摊分负金额抵消之前的正金额的支出结果
+ 摊分月数默认1
+ 自动打标的实现方向先不讨论，由于缺少打标的实现逻辑，因此先将标签都留空
    + 空支出类型作为默认支出类型，而不需要在ExpenseCategory中先定义一个默认支出类型
+ 汇率取日汇率，这涉及如何取汇率的具体实现，先不进行分析
+ 登录态不可续期，过期需要重新登录
+ 主动登出的口径：前端丢弃令牌即可
+ 是否保留月度摊分增量聚合：不保留
