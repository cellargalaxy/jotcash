## 步骤

- 背景调研
    - 研读prompt中提及的文档/代码/配置
    - 对齐背景，梳理核心逻辑/组件依赖/改动点
- 需求分析与方案
    - 提取核心目标/交付物/范围边界/关键约束
    - 制定方案：最小改动/复用优先/任务拆解；说明模块职责/输入输出/关键逻辑/异常处理
    - 评估对现有链路/性能/兼容性/下游的副作用
    - 写入`answer.md`：依据来源/方案取舍/实施步骤/验证说明
- 实施
    - 按方案执行，命名/注释/文案与项目风格一致
    - 中文注释与日志，处理边界与异常分支
    - 同步更新类型定义/关联配置/文档
    - 复杂任务使用主agent调度子agent的方式实施
- 验证与交付
    - 执行测试/逻辑校验/数据校验/文档校对
    - 重读`prompt.md`，检查与交付结果是否一致
    - 核心产出同步至`answer.md`
    - 清理临时文件/调试代码/冗余产物，但无须提交变更

## 约束

- 依据：结论只能来自文档/代码/表结构/日志/SQL等明确来源；严厉禁止猜测业务逻辑/捏造接口字段，不能断言的内容都询问用户
- 引用：关键事实引用到具体章节/字段名/代码路径或枚举值，禁止笼统援引
- 信息不足：区分「已确认/待确认/不可推断」并标注，不得脑补
- 历史资料：历史Prompt/answer/旧方案仅供参考，必须与代码交叉核对后才能使用
- 冲突：资料冲突时列出冲突点与采用依据，不得默默取一方
- 风格：命名/注释语言/代码组织与项目既有风格一致，优先复用现有实现

## 具体任务

+ 需要设计一套记账系统，先分析梳理业务功能，不要管技术实现
+ 以下是我想到的零碎的功能，梳理分析体系化整套系统的功能与业务流程
+ 多人账户，需要有账户密码，只有管理员才能添加新的账户，系统初始只有一个管理员
+ 需要有登录页面，除了登录业务以外，其余全部页面与接口都需要校验denglt
+ 页面与接口只能查询到用户自己的数据，不能越权
+ 需要有一个页面，能上传银行的PDF对账单，解析PDF作为支出的数据来源
    + PDF文档可能是有密码的，需要支持输入密码解密
+ 对于重复的支出数据进行去重
    + 例如重复两个PDF之间的账期时间有重叠，需要进行去重，避免重复录入
+ 支出的字段至少需要涉及：
    + 支出日期，支出金额，支出币种，交易对手方，交易备注，支出类型，摊分月数
    + 其中支出类型是需要进行打标的，是交通/餐饮/住宿之类的
    + 摊分月数代表这笔支出需要摊分多少个月，有些收益时间比较长的支出，需要将支出摊分到多个月中
    + 对于多币种如何进行统一处理？
+ 需要有一个页面，能逐笔查看支出明细，支持一些实用维度的筛选与累计统计
    + 支出日期，支出金额，支出币种，交易对手方，交易备注，支出类型，摊分月数，这些字段都需要支持修改
+ 需要有一个页面，能按月查看支出金额，支出类型
    + 能查看不经过摊分的每月支出金额，也能查看经过摊分的每月支出金额
    + 修改摊分月数之后，会影响多个月的金额累计，当查询时如何处理筛选和统计数据的范围
