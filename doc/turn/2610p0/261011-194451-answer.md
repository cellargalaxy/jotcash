### 2.2 云闪付账单截图离线识别器架构设计

由于系统要求**严禁调用在线 OCR 接口**，且云闪付截图为长达近万像素的高清移动端滚动截图，设计了「Go 宿主引擎 + 离线 ONNX 视觉推理 + 内存级哈希缓存」架构：

1. **离线 OCR 推理引擎**：
   - 使用工业级轻量离线 OCR 引擎 `RapidOCR`（基于 PP-OCRv3 模型与 ONNX Runtime），完全在本地 CPU 推理，模型权重内嵌于环境，零网络请求、零外泄风险；
   - 编写标准化离线 OCR 脚本 [`service/expense/unionpay_screenshot/ocr.py`](file:///home/ms/document/code/jotcash/service/expense/unionpay_screenshot/ocr.py)，通过标准输入流（stdin）接收图像原始字节，通过标准输出（stdout）返回结构化文本块（包含文字、多边形外接矩形坐标、置信度）；
   - 使用 Go 1.16+ `//go:embed ocr.py` 将脚本内嵌至 Go 二进制中，优先读取源码路径，若运行在独立编译二进制下则自释放至临时目录，实现跨平台与独立部署无缝兼容。
2. **内存级哈希缓存（`ocrCache`）**：
   - 针对长截图推理耗时的特点，在 `unionpay_screenshot` 包内实现基于 SHA-256 哈希的内容级结果缓存；
   - 当接入层依次执行 `Support(ctx, data)` 与 `Parse(ctx, data)` 时，OCR 仅在 `Support` 执行一次，`Parse` 直接毫秒级命中缓存，杜绝重复推理开销。

### 2.3 严格契约认领（`Support` 与 `checkContract`）

坚守《编码规范》§3.5「识别用内容不用外壳，宁可不认领也不能认错」：
1. **外壳层快速筛除**：
   - 检查文件前缀 Magic Bytes：仅放行 JPEG（`\xFF\xD8\xFF`）与 PNG（`\x89PNG\r\n\x1a\n`）；
   - CSV、PDF 等非图片格式在 0 微秒内安全拒绝，不产生任何子进程与推理消耗；
2. **页面顶层特征契约（`y <= 800` 区间）**：
   - 必须包含标题特征：`"交易记录"`；
   - 必须包含渠道特征：`"银联交易"` 或 `"云闪付"`；
   - 必须包含状态筛选标签：`"全部"` 且包含 `"支出"` 或 `"收入"`；
   - 若不满足上述特征组合，坚决不认领（返回 `false`），杜绝普通相册照片、微信截图或支付宝截图误认领。

### 2.4 流水数据抽取与时序解析

1. **时序与年份推断**：
   - 在页面顶层区域正则匹配账单年份（如 `(\d{4})年` 匹配 `2026年10月→`），获取基准年份；
   - 页面纵向扫描识别每日日期标头：正则匹配 `^(\d{1,2})\.(\d{1,2})\s*周[一二三四五六日天—\-]`，精准提取月份与日期；
   - 支持跨年推断：若账单标头为 1 月，而后续流水月份为 12 月，算法自动将年份折算为 `stmtYear - 1`。
2. **交易卡号、时间与银行名称归一化**：
   - 交易卡信息锚点行正则匹配：`([\p{Han}A-Za-z]+)\[(\d{4})\][］]?\s*·\s*(\d{1,2}:\d{2})`；
   - 提取银行名称、4 位卡号与时刻（`HH:MM`），与当前日期归并为精确的 `time.Time` 支出时间；
   - 银行名称通过映射表实现规范归一化（如繁体 `"滙豐"` 统一转换为标准 `"汇丰银行"`，`"招商"` 映射为 `"招商银行"` 等）。
3. **商户名聚合与长文本折行**：
   - 在卡信息锚点行上方（`y - 160 <= prev.Y < y - 20`）提取交易对手方文本；
   - 按横坐标 X 升序重组同一行的渠道前缀（如 `(特约)`、`美团` 等）与主商户名称，完整保留交易对手方明细。

### 2.5 交易类型识别与安全过滤规则

1. **预授权冻结/解冻与还款安全过滤**：
   - 严守保守过滤原则：在卡号锚点行附近识别状态标签，若为 `"冻结"` 或 `"解冻"`（为预授权验证，非实际结算支出），予以安全丢弃；
   - 针对商户名包含 `"还款"`、`"信用卡还款"`、`"转账"`、`"划转"` 的账户互转流水，予以安全丢弃；
2. **消费与退款判定**：
   - 带有 `"退款"` 标签或带有正号标头（`+￥...`）的流水，识别为退款抵扣，金额转为负数 `decimal.Decimal`，`Remark` 设为 `"退款"`；
   - 常规减号（`-￥...`）及支出列表明细，金额取正数，`Remark` 设为 `"消费"`。

## 二、RapidOCR 内存调优实测（本机，同一张样例）

| 配置 | 峰值 RSS | 耗时 | 结果 |
| ---- | -------- | ---- | ---- |

## 三、「效果更好、内存更少」的 OCR 方案评估

中文离线 OCR 里，PP-OCR 系列（RapidOCR 用的就是它）在轻量模型中精度已经是第一梯队，**不存在精度更高、内存又显著更少的现成替代**。能省内存的办法只能是换运行时或者换运行位置：

| 方案 | 服务器内存 | 识别效果 | 改动量 | 状态 |
| ---- | ---------- | -------- | ------ | ---- |
| A. 浏览器端离线 OCR（onnxruntime-web 跑同一套 PP-OCR 模型，或 tesseract.js），前端识别后只上传文字块 | 约 0 | 跟现在一致（PP-OCR） | 大：前端加 OCR、上传协议加文字块格式、解析器入参变化 | 待用户决策 |
| B. Tesseract（`tesseract-ocr` + `chi_sim`，C++ 原生） | 业界经验约 100~200MB，**本机没装，未实测** | 中文商户名不如 PP-OCR，数字/日期一般可用；输出粒度跟现在不同，解析器的坐标规则要重新适配 | 中 | 待实测 |
| C. PP-OCR 原生运行时（ncnn / RapidOcrOnnx 的 C++ 版本），去掉 Python | 预计能比 Python 版少几十到一百多 MB，**未实测**，能否压到 190MB 以内不确定 | 跟现在一致 | 中：要自己编译多架构二进制并放进镜像 | 待实测 |
| D. 不换方案：服务器加 1~2GB swap 文件，或升级内存到 ≥1GB | 不变 | 跟现在一致 | 0 代码 | 运维决策；用 swap 会明显变慢 |

建议：如果能接受加内存或加 swap，D 最省事，而且识别效果不变；不能动服务器的话，A 能把 OCR 负担从服务器彻底移走，效果也不降，是长期最稳的方案。B、C 都需要先实测才能下结论。

## 三、用户追问：RapidOCR 能否改在前端实现

结论：**可以**。RapidOCR 本质上是「PP-OCR 三个 ONNX 模型 + 前后处理」，模型可以直接在浏览器里用 onnxruntime-web（WASM）推理，前后处理移植成 JS。识别全在用户浏览器本地完成，不调任何在线接口，满足对话1 的约束。

### 改造后的链路

1. 前端选中图片 → 动态加载 OCR 模块（只在上传截图时才加载）→ 浏览器本地识别出文字块 `[{text,x,y,score}]`；
2. 上传时把文字块交给后端（具体格式待定：作为文件本身上传，或者图片和文字块一起上传），后端 `unionpay_screenshot` 解析器只做 `checkContract` + `parseBlocks`，毫秒级返回，**彻底消除超时**；
3. 后端去掉 Python、rapidocr、`ocr.py`、子进程和缓存，Dockerfile 可以回到轻量的 alpine 镜像，520Mi 的服务器不再有内存压力。

# 对话8 · RapidOCR 迁到前端、上传表单手选识别器

## 一、方案

### 1.1 接口（以后不再改）

`POST /api/expense/insert` 的 multipart 表单固定为三个字段：

| 字段 | 必填 | 含义 |
| ---- | ---- | ---- |
| `file` | 是 | 用户选的原文件，照旧作为 FileBlob 留档，文件页可以预览、下载原截图 |
| `parser` | 是 | 用户手选的识别器名，后端按名字直接分发，不再挨个 `Support` 试 |
| `content` | 否 | 前端提取出的内容。阻塞的识别（OCR 这类）在浏览器里做完，后端只解析这份内容；不需要前端提取的识别器不传 |

后端规则：有 `content` 就解析 `content`，否则解析 `file`。以后再有类似「重活」的识别器，只需在前端加一个提取函数、在后端注册一个吃提取结果的解析器，**接口字段不用变**。

### 1.2 后端

- `expense.Register(name, parser)` 按名注册，`expense.Parse(ctx, parserName, data, accountingCurrency)` 按名取。名字不存在报「识别器不存在」；手选了也照样先过 `Support`，内容对不上报「文件内容与所选识别器不符」——用户手选不能代替内容契约，宁可不认领也不能认错。
- `unionpay_screenshot` 改为吃前端 OCR 输出的文字块 JSON（`[{text,x,y,score}]`，跟原 `ocr.py` 输出逐字段一致）。`checkContract`、`parseBlocks` 不动；Python、`ocr.py`、`requirements.txt`、子进程和缓存全部删除。
- Dockerfile 运行阶段回到 `golang:1.27-alpine`（对话2 之前的形态），保留健康检查的修复。

### 1.3 前端

- 把 RapidOCR 1.2.3 的完整流程逐行移植为 `static/js/ocr.js`：同样的三个模型（det/cls/rec）、同样的缩放与归一化、DB 后处理（二值化、膨胀、找轮廓、最小外接矩形、box_score_fast、unclip）、排序、透视裁剪、方向分类、按宽高比分批识别、CTC 解码、0.5 置信度过滤。
- 依赖全部放在 `static/lib/` 本地托管，不走 CDN，不调用在线接口：onnxruntime-web（推理）、opencv.js（找轮廓、外接矩形、透视变换，跟 Python 用的 OpenCV 是同一套 C++ 代码编译的）、clipper-lib 6.4.2（跟 pyclipper 底层同为 Clipper 6.4.2）、RapidOCR 1.2.3 的三个 onnx 模型和识别字典。
- 上传弹窗新增必选的「识别器」下拉；选的识别器需要前端提取时，先在本地识别，再连同原文件一起上传。

### 1.4 验证思路

- 趁真实截图还在，用 Node 跑前端 OCR，跟 Python 版逐框对比，再把结果交给 Go 解析器核对 30 笔与月度金额；
- 合成长截图（全虚构数据）作为常驻防线：前端测试校验 OCR 输出跟提交的 `synthetic.json` 一致，Go 测试校验 `synthetic.json` 解析出 13 笔，两段拼起来覆盖整条链路。

1. **前端 OCR 与 Python 版一致性**（本机 Node，onnxruntime-web 单线程）：
