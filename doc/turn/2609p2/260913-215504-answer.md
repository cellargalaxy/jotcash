## 一、第一个问题：ping 的代码与调用链路，是否有错/有漏

### 1.1 结论先行：链路是断的，当前 100% 跑不通

实测（临时用例，已删除）：用 `tool.EnJwt(ctx, config.GetConfig().ServerToken, "<任意前端口令>", time.Hour)` 签一个完全合法的 JWT，打到 `POST /api/ping`：

```
[有jwt] status=200 body={"code":500,"msg":"获取数据库口令，为空","data":{"ip":"","sn":"jotcash","ts":...}}
[无jwt] status=200 body={"code":401,"msg":"Authorization非法","data":null}
```

也就是说：**无论前端口令对不对，这个接口永远返回「获取数据库口令，为空」**，A-4「口令校验（只读探针）」的功能为零。

### 1.2 错（3 条，都在同一个根因上）

#### E1 · Claims 类型对不上，前端口令根本进不了 ctx（致命）

| 位置 | 行为 |
| ---- | ---- |
| `handler/handler.go:40-42` `validate` | 调 `util.ValidateGin(ctx, config.GetConfig().ServerToken)` |
|  `go_common/util/gin.go:84` | `var claims model.Claims` —— 这是 **`go_common/model.Claims`** |
| `go_common/util/gin.go:126` | `c.Set(ClaimsKey, &claims)` —— 存进去的是 `*go_common/model.Claims` |
| `db/db.go:36` `getToken` | `tool.GetClaims(ctx)` |
| `tool/gin.go:11` | `util.GetCtxValue[*model.Claims](ctx, util.ClaimsKey)` —— 取的是 **`*jotcash/model.Claims`** |
| `go_common/util/ctx.go:8` | `object, _ := value.(T)` —— 类型断言失败，**吞掉 ok，返回零值 nil** |

`getToken`（`db/db.go:37-40`）拿到 nil 就直接 `errors.Errorf("获取数据库口令，为空")`，链路到此终止。

这个坑在 `260913-005452-answer.md`「对话17 §五.7」已经登记过原话——「`util.ValidateGin` 塞的是 `go_common/model.Claims`，类型对不上，必须自己写」——但 `handler` 包落地时没有按登记结论做。

#### E2 · 就算 key 的类型对上了，`client_token` 也已经在反序列化时被丢掉

`go_common/model/claims.go` 的 `Claims` 只有 `jwt.StandardClaims` + `Ip/ServerName/LogId/Uri/ReqId` 五个字段，**没有 `ClientToken`**。`util.ValidateGin` 第 85 行 `DeJwt(c, token, secret, &claims)` 反序列化到这个结构体上，JWT payload 里的 `client_token`（`model/claims.go:10` 定义的 `json:"client_token,omitempty"`）被直接丢弃。

所以 E1 不是「改个类型断言就行」，**必须换成 `tool.DeJwt`（`tool/jwt.go:30`）**——它反序列化到 `jotcash/model.Claims`，才留得住前端口令。结论：`util.ValidateGin` 在本项目不可用，中间件得自己写。

#### E3 · 自己写中间件时的第二个坑：不能用 `tool.SetClaims`

`tool.SetClaims`（`tool/gin.go:13-18`）返回的是一个**新的 `context.Context`**，对 `*gin.Context` 无效——后续 handler 拿到的还是原来那个 `c`。必须用 `c.Set(util.ClaimsKey, claims)`。

已核 `gin@v1.12.0/context.go` 的 `Context.Value`：对 string key 会先走 `c.Get(keyAsString)`，所以 `c.Set` 写进去的值，下游用 `tool.GetClaims(ctx)`（走 `ctx.Value`）能取到。这条链路成立。

**修复原型实测**（临时用例，已删除）：把 `validate` 换成 `tool.DeJwt` + `c.Set` 之后，同一套路由的四种输入：

```
[口令都对]   {"code":200,"msg":"","data":{"ip":"","sn":"jotcash","ts":...}}
[前端口令错] {"code":500,"msg":"连接数据库，口令错误或数据库文件损坏","data":{...}}
[后端口令错] {"code":500,"msg":"JWT解密异常: signature is invalid","data":null}
[没带jwt]   {"code":500,"msg":"JWT解密异常: token contains an invalid number of segments","data":null}
```

四种分支全部区分正确，A-4 的探针功能成立。

### 1.3 漏（6 条）

#### M1 · 没有任何地方签发 JWT——前端怎么拿到 token，是本轮最大的空白

`tool.EnJwt`（`tool/jwt.go:13`）全项目零生产调用方（grep 确认，只有 `tool/jwt_test.go` 在用）。按 A-3「无登录接口」+ 对话6，推断是**前端用后端口令在 JS 里自签 JWT**：用户从初始化日志（`db/db.go:142-143` 打印的 `clientToken` / `serverToken`）抄两个口令 → 前端 sessionStorage 存两个 → 每次请求用 serverToken 签一个带 `client_token` 的 JWT。

**这条属于「待确认」**，因为它决定前端要不要引 JS 的 JWT 库，也决定 `tool.EnJwt` 在后端还有没有生产用途。见 §四.1。

#### M2 · `GET /api/ping` 与 `POST /api/ping` 语义完全不同却共用一个路径

- `handler/handler.go:20`：`GET`，无鉴权，`util.Ping`，存活探针
- `handler/handler.go:21`：`POST`，过 `validate`，A-4 口令校验探针

能跑，但把「运维探活」和「业务口令校验」压在一个 URL 上。A-4 是业务接口，按 survive_monitor 的做法（`model.StatusPath`）业务路径应当由本项目自己定义常量。建议 A-4 独立成 `/api/token/check` 之类，`util.PathPing` 留给 GET 存活探针。

#### M3 · 响应语义不对：出错时照样返回 `PingData`，且错误文案违反 A-4「统一提示」

`handler/ping.go:17`：`util.NewHttpRespByErr(model.PingData{...}, err)`。`go_common/util/gin.go:35-39` 的约定是 msg 非空 → code 500，但 **data 仍然被填满**，前端必须先判 code 才知道 data 有没有意义。出错时 data 应为 nil。

更要紧的是文案。A-4 原文：「口令错与文件损坏不可区分，**统一提示**」。现在 `err.Error()` 原样透传，前端能看到至少四种不同文案：

| 来源 | 文案 |
| ---- | ---- |
| `db/db.go:39` `getToken` | 获取数据库口令，为空 |
| `db/db.go:169` `open` | 打开数据库，库文件不存在或为空 |
| `db/db.go:81` `connect` | 连接数据库，口令错误或数据库文件损坏 |
| `db/migrate.go:21` `AutoMigrate` | 自动建表，异常: … |

只有第三条符合 A-4。前两条既违反「统一提示」，也把服务端内部状态（库文件不存在 / ctx 里没口令）泄露给了调用方。

#### M4 · `service/db.CheckToken` 是纯转发，没有承担你给 `/service/db` 定义的职责

`service/db/db.go:9-11` 一行 `return db.CheckToken(ctx)`，零校验。而你对这一层的定义是「`/db` 没有业务逻辑，可能会缺少必要的参数校验；参数校验与业务逻辑有关，因此 `/service/db` 才会有足够的业务逻辑校验」。

这里至少缺两样，且**恰好都是「业务规则」而非「通用 DAO 规则」**，正好落在这一层：

1. **A-6 口令强度前置**：`tool.CheckToken`（`tool/token.go:41`）现成——长度 ≥ 12、不得纯数字或纯字母。明显不合规的口令直接挡回，不必走一次开库（开库要解密整库、还可能触发一次 `AutoMigrate`）。
   - 安全性已核：`tool.GenToken`（`tool/token.go:35-36`）循环到 `CheckToken` 通过才返回，所以系统生成的初始口令必然合规，前置不会误杀存量库。
2. **A-4 错误文案归一**：把 M3 那四种文案统一收敛成一句，比如「口令错误或数据库文件损坏」。这属于业务口径，`db` 包不该知道，`handler` 不该硬编码，正好归 `service/db`。

#### M5 · `handler/ping.go:15` 的日志用的是 `util.GetClaims`，修好 E1 后会变成永远 nil，且会绕开口令脱敏

`handler/ping.go:15` 用 `util.GetClaims(c)`（go_common 类型），`db/db.go:36` 用 `tool.GetClaims(ctx)`（jotcash 类型），**同一个 `ClaimsKey` 下并存两套类型**，本身就是混乱源。E1 修好之后 key 下存的是 jotcash 类型，`util.GetClaims` 就会恒为 nil，日志字段直接失效。

而且 `model/claims.go:11-14` 的 `String()` 是专门为 H-2 写的——序列化前把 `ClientToken` 抹掉。只有用 `tool.GetClaims` 打印才走得到这个保护。修 E1 时这一行必须一起换。

#### M6 · 中间件里必须砍掉「从 query 取 token」，否则前端口令会进日志文件（H-2 / §九不变式3）

`go_common/util/gin.go:76-78`：header 里没有 `Authorization` 时，回退到 `c.Query(AuthorizationKey)`。而 JWT 的 payload 里是**明文的前端口令**（`tool/jwt.go:26` `claims.ClientToken = clientToken`，未加密，只签名）。

`util.GinLog`（`go_common/util/log.go:110,113-117`）记录 `uri := c.Request.RequestURI`，**带 query string**。两者一叠加：只要有人用 `?Authorization=<jwt>` 调一次，前端口令就落进日志文件了。这直接违反 H-2「日志中只有初始化那一次出现口令」与 §九不变式3。

自己写中间件时**只从 `Authorization` header 取**，这是必须的，不是可选优化。
> 连带影响：B-1 数据库导出是个下载，浏览器 `<a href>` 没法带 header。要么前端 fetch + blob 下载，要么将来给导出单开一条短时效 query token 的口子。**留作 B-1 开工时的待确认**，本轮不处理。

### 1.4 可优化（不算错，列出备查）

- **A-4 这个「只读探针」会拿写锁**：`db.CheckToken`（`db/db.go:198`）→ `Open`（`db/db.go:147`）→ `autoMigrate`（`db/migrate.go:28`）。首个请求若是 ping，会 `dbLock.Lock()` 跑一次全表 `AutoMigrate`。功能上没错（migrate 之前照样要开库、口令照样被验），但探针的代价比预期重。`connect` 是私有的，要优化得在 `db` 包内部做，不在本轮范围。
- **`handler.Init` 建引擎与起服务耦合**（`handler/handler.go:16-32`：`gin.Default()` 到 `engine.Run` 一气呵成），外部拿不到 `*gin.Engine`，第二问的单测因此写不了。见 §二。
- **`gin.Default()` 自带的 Logger 与 `util.GinLog` 双份日志**：与 survive_monitor 一致，沿用即可，只是同一请求会打两行。
- **没有 `main.go`**：`handler.Init` 目前无调用方（find 确认全仓无 `main.go`）。属于预期内的进度，不是错。
- **`engine.Run` 是明文 HTTP**：§一前提3 / §十流程2 要求 HTTPS。H-1 是 docker 部署，通常由反向代理终结 TLS，但这一点文档没写死。见 §四.3。

## 二、第二个问题：能不能从发起 HTTP 的高层级写单测

### 2.1 结论：能，而且已经跑通了

**已实测通过**：`net/http/httptest` + `engine.ServeHTTP`，四种输入（口令都对 / 前端口令错 / 后端口令错 / 没带 JWT）全部得到预期响应，输出见 §1.2 E3。不需要真的监听端口、不需要起进程，`httptest.NewRequest` + `httptest.NewRecorder` 走的是 gin 完整的中间件链，**中间件、参数绑定、鉴权、业务、DB、响应体全在覆盖范围内**，对降低前端联通成本的价值是实打实的。

### 2.2 唯一的难点：测试怎么拿到「正确的前端口令」

初始前端口令是随机生成的（`db/db.go:98` → `tool.GenToken`），且按 A-2 只在建库那一次打进日志，任何地方都不持久化。而 `db` 包的 `init()`（`db/db.go:26-32`）在 **import 时**就把库建好了——测试代码根本没有机会在它之前挂日志钩子。

**解法：不去截 `init()` 那一次，而是在临时目录里重新建一次库。** `db/db_test.go` 已经有现成的范式（`catchLog` at `db/db_test.go:53`、`findLogField` at `:62`、`TestCreate` at `:80-96`），照搬即可：

```
t.Chdir(t.TempDir())            // config.DbPath/DbBackupPath 都是相对路径，chdir 即隔离
logrus.SetOutput(buffer)        // 挂缓冲
db.Create(ctx)                  // 导出的，且幂等（db/db.go:114-117 库已存在直接返回）
clientToken := findLogField(buffer.String(), "clientToken")
```

已验证的三个前提：

1. `config.DbPath = "resource/jotcash.db"`、`DbBackupPath = "resource/db_backup"` 都是相对路径（`config/config.go:17-19`），`t.Chdir` 能完整隔离；
2. `config` 的 init 在 chdir 之前就把 `ServerToken` 读进内存了（`config/config.go:26-33`），chdir 之后 `config.GetConfig().ServerToken` 照常可用，后端口令直接拿得到；
3. `migrated` 这个包级标志不会串味：`Create` → `create` 直接调 `AutoMigrate`（`db/db.go:126`）而不是 `migrate`，不置 `migrated`；新库在 `create` 里已经建过表，之后 `Open` 走不走 `autoMigrate` 都正确。

**所以：`db` 包一行生产代码都不用改。** 这一点是实测结论，不是推断。

### 2.3 生产代码只需要一处改动：把 `handler.Init` 拆成「建引擎」与「跑引擎」

```
func NewEngine(ctx context.Context) *gin.Engine   // 装中间件、注册路由，返回引擎
func Init(ctx context.Context) error              // NewEngine(ctx).Run(config.ListenAddress)
```

单测拿 `NewEngine(ctx)`，生产入口拿 `Init(ctx)`，路由表只有一份、不会测试跑通而线上漏注册。改动量约 5 行，不引入任何测试专用的导出 API（`export_test.go` 那套对跨包测试也无效，不考虑）。

### 2.4 建议的用例清单（`handler/ping_test.go`）

| 用例 | 断言 |
| ---- | ---- |
| 口令都对 | `code == 200`，`data.sn == "jotcash"` |
| 前端口令错 | `code == 500`，msg 为 A-4 的统一文案 |
| 后端口令错（签名不对） | `code == 500`，**msg 中不得出现任何口令** |
| 不带 Authorization | `code == 401`/`500`，不 panic |
| JWT 过期 | `code == 500`（`tool/jwt_test.go:55-60` 已证 `DeJwt` 会拒） |
| `?Authorization=<jwt>` | 被拒（把 M6 钉死，防回归） |
| 日志断言 | 全程 `catchLog` 缓冲里不得出现 clientToken 明文（把 H-2 钉死） |
| `GET /api/ping` | 不带任何凭据也返回 200（存活探针不被 validate 误伤） |

TestMain 沿用 `db/db_test.go:20-26` 的写法（`logrus.SetLevel(WarnLevel)` + 收尾 `os.RemoveAll("resource"/"log")`）——注意 `db` 的 `init()` 会在**测试二进制的原始工作目录**（也就是 `handler/`）里建一个库，这个残留必须清掉，否则 `handler/resource/` 会污染工作区（本轮实测踩到过，已清理）。

## 三、第三个问题：下一个功能选型与技术方案（只给方案，不写代码）

### 3.1 候选比较

| 候选 | 写操作 | 表数 | 要写审计 | 依赖汇率 | db 层现成度 | 评价 |
| ---- | ------ | ---- | -------- | -------- | ----------- | ---- |
| **C-3 审计查看** | 否 | 1 | 否（C-1：读操作除 B-1 外一律不记） | 否 | `SelectOperationLog` + `OperationLogInquiry` 全齐 | **推荐** |
| D-4 文件列表 | 否 | 1（下载才碰 2） | 否 | 否 | `SelectFileMeta` 齐 | 次选，但早期没数据可看 |
| A-5 更换口令 | 是 | — | 是 | 否 | `ChangeToken` 齐 | 第一个写链路的好人选，但不该第一个做（见 3.2） |
| B-1 数据库导出 | 否 | — | **是**（§8.4 第 8 类） | 否 | `Export` 齐 | 撞上 M6 的下载带 header 问题 |
| E-7 明细查询 | 否 | 1 | 否 | 否 | 齐 | 字段最多、筛选项最多，不适合第一个 |
| E-2 数据入库 | 是 | 4 | 是 | 是 | — | 最复杂，压轴 |

### 3.2 选定：**C-3 审计查看（操作日志只读列表）**

理由：

1. **纯读、单表、不落审计、不碰汇率、不碰事务语义**——链路里没有一个环节会把「接入层骨架该长什么样」这件事搅浑。
2. **`db` 层已经 100% 就绪**，本轮只需要往上长三层。`db/operation_log.go:104-111` 的 `SelectOperationLog` 已返回 `([]*model.OperationLog, int64, error)`，`model.OperationLogInquiry`（`model/operation_log.go:44-56`）的筛选字段（操作类型、时间区间、分页、排序）恰好就是 C-3 要的「按操作类型与时间区间筛选」。
3. **天然有数据可看**：系统初始化时已经写了一条「系统初始化」审计（`db/db.go:131-137`），接口一通就有真实返回，前端联调不用先造数据。
4. **一次性定型接入层的全部约定**（JWT 中间件、请求/响应体、分页、排序白名单、错误文案、HTTP 层单测范式），后面 D-4 / E-7 照抄即可。C-3 的返回结构（列表 + 总数）和 E-7 完全同构。
5. **不选 A-5 的原因**：`ChangeToken` 涉及整库改密 + 原子替换，且「老账」里还挂着两条未决（`ChangeToken` 不校验新口令强度、A-5 审计由谁写、写进新库还是旧库）。第一条完整链路不该同时背这些债——等骨架定了再做，成本反而更低。

### 3.3 分层设计

```
handler/operation_log.go   →  service/operation_log.go  →  service/db/operation_log.go  →  db/operation_log.go
    接口注册/参数绑定             业务编排/响应体组装            业务校验 + 调 DAO             无业务逻辑的 DAO（已有）
```

| 层 | 文件 | 职责 | 输入 | 输出 |
| -- | ---- | ---- | ---- | ---- |

## 三、修掉一个数据竞争（本轮最重要的发现）

### 3.1 现象

`go test -race ./handler/` 报 **7 处 DATA RACE**。按用例分组复现：

```
TestPing:                  0 races
TestSelectOperationLog:    4 races   ← 对话4 写的
TestSelectFileMeta:        3 races   ← 本轮写的
```

对话4 那轮我跑 `-race` 是过的——这个竞争窗口很窄，用例少的时候撞不上。**缺陷在对话4 就已经存在，不是本轮引入的**，只是本轮用例变多才稳定复现。

### 3.2 竞争双方

```
Write at 0x... by goroutine A:
  gin.(*Engine).ServeHTTP()          ← 从 sync.Pool 取出 *gin.Context 并 reset

Previous read at 0x... by goroutine B:
  gin.(*Context).hasRequestContext()
  gin.(*Context).Err()
  database/sql.(*Rows).awaitDone()
  database/sql.(*Rows).initContextClose.gowrap1()
```

### 3.3 机制

1. `util.NewGinPost` 把 `*gin.Context` 当 `context.Context` 直接传给 service（`go_common/util/gin.go:161` 的 `service(c, request)`），一路传到 `db.Transaction` → `gormDb.WithContext(ctx)` → `database/sql`。
2. `db.Transaction` 走的是 gorm 事务，`database/sql` 的 `BeginTx` 内部 `context.WithCancel` 出一个**可取消的 txctx**，于是 `Rows.initContextClose` 会起一个 `awaitDone` 后台协程。
3. `awaitDone` 在 select 返回后调 `rs.close(ctx.Err())`——**这一下读的是 `*gin.Context`**（`Err()` → `hasRequestContext()` → 读 `c.engine`、`c.Request`）。
4. 这个协程可能在 HTTP 请求结束之后才被调度到。而 gin 请求一结束就把 `*gin.Context` 放回 `sync.Pool`，下一个请求 `ServeHTTP` 直接把它 reset 掉。两边撞上就是数据竞争。

这不是测试假象：生产环境 `c.Request.Context()` 是 `http.Server` 的可取消 ctx，条件完全一样，并发请求下会读到撕裂的 `c.Request`/`c.engine`，`hasRequestContext()` 里还可能空指针 panic。

`TestPing` 之所以 0 races，是因为 `db.CheckToken` 只做 `QueryRowContext`（非事务）；但 `Open` 里的 `autoMigrate` 也是跑事务的，**ping 同样有暴露面，只是更难撞上**。

### 3.4 修法：在 `db` 包把 ctx 脱钩

```go
//gin会把*gin.Context放回sync.Pool给下个请求复用，而database/sql的awaitDone协程可能在请求结束后才去读ctx，交给gorm之前必须脱钩
func detachCtx(ctx context.Context) context.Context {
	return tool.SetClaims(util.CopyCtx(ctx), tool.GetClaims(ctx))
}
```

`util.CopyCtx`（`go_common/util/ctx.go`）本来就是干这个的：起一个 Background 根的新 ctx，把 LogId / ReqId / ignoreErr 抄过去，**日志串联不受影响**；再把 Claims 补上，`getToken` 照常工作。新 ctx 与 `*gin.Context` 再无引用关系，`awaitDone` 怎么读都读不到它。

加在 `db` 包所有接收外部 ctx 的导出入口，共 5 处、每处 1 行：`Open`、`Transaction`（`db/db.go:153,213`），`Export`、`Import`、`ChangeToken`（`db/backup.go:90,134,175`）。`ClearBackup` 不碰 `database/sql`，没加。

**为什么修在 `db` 而不是接入层**：接入层才是概念上的正确位置（不该把 `*gin.Context` 往下传），但那要改 `util.NewGinPost`，是 go_common 的事。修在 `db` 的两个导出入口，一次覆盖 ping、审计查看、文件列表和将来每一个接口，不用每写一个 handler 就提醒自己一次，也不动 go_common。**如果你更倾向在 go_common 的 `NewGinPost` 里改成传 `c` 的副本，这 5 行可以撤掉**——那是更根上的修法。

**修复后 `go test -race ./handler/ ./service/... ./db/` 零 DATA RACE。**

## 二、两个要紧的设计点

### 2.1 强度校验：这次用 `tool.CheckToken` 是对的

对话2 你纠正过「`CheckToken` 用于生成口令，不用来校验口令是否正确」——那次我把它当成开库前的廉价前置，用错了。这次不一样：**A-6「用户自定口令须满足最低强度（长度 ≥ 12，且不得为纯数字或纯字母）」管的就是新口令**，`tool.CheckToken`（`tool/token.go:41`）正是为这条写的，`tool.GenToken` 自己也调它。校验的是「新口令合不合规」，不是「旧口令对不对」。

放在 `service/db` 而不是 `db`：`db` 包不该知道 A-6 这条业务规则，而且 `db.ChangeToken` 也被测试直接调用。

### 2.2 审计必须落在新库里，而且要和改密同生共死

A-5 原文：「记一条「更换口令」审计（**写入新库**，不记口令值）」。难点在于换完之后库已经是新口令加密的了，而 ctx 里的 claims 装的是旧口令。

**没有采用**「`db.ChangeToken` 成功后再用新口令开一次库写审计」这种写法，三个问题：

1. `os.Rename` 已经发生了，这一步再失败就得在「报错（用户以为没换成，继续用旧口令 → 锁死自己）」和「报成功（审计缺一行）」之间二选一，两个都不好；
2. `ChangeToken` 的 `dbLock.Lock()` 已经释放，中间有并发窗口；
3. 多付一次开库的密钥派生（对话3 §3.1 实测 ~80ms）。

**采用的写法**：给 `db.ChangeToken` 加一个可选的 `handlers ...util.TransactionHandler`，在**副本改密之后、原子替换之前**把审计写进副本：

```
backup(原库, 旧口令 → 副本, 新口令)
  → transaction(副本, 新口令, handlers...)   //写不进去就删副本、整个放弃，原库一个字节没动
  → replace(副本 → 原库, 新口令)             //open校验能打开 + os.Rename
```

全程在 `ChangeToken` 那一把 `dbLock.Lock()` 里，且完全符合 A-5 的「任一步失败原库原封不动」。业务（写哪条审计、摘要写什么）留在 `service/db`，机制（何时开副本、何时 rename）留在 `db`——`handlers ...util.TransactionHandler` 是 `db.Transaction` 本来就在用的签名，不往 `db` 里塞业务。

顺带把 `Transaction` 尾部那段抽成私有的 `transaction(ctx, dbPath, token, handlers...)` 给两处复用，行为不变。

审计行按 §四.2 填：`OperationType=更换口令`、`Summary=数据库已用新口令重新加密`、`Result=成功`，**`Changes` 留空**（§四.2「变更内容……不记口令值」，更换口令也不是编辑类操作）。

## 三、新口令绝不能进日志——而且这不是想当然

`util.NewGinPost` 会把整个请求体打进日志（`go_common/util/gin.go:160`：`WithFields(logrus.Fields{"request": request}).Info(name)`）。请求体里就是新口令明文，直接违反 H-2 与 §九不变式3。

照 `model.Claims`（`model/claims.go:13-16`）的老办法，给 `ChangeTokenRequest` 加一个抹字段的 `String()`，logrus 走 `fmt.Stringer` 就打不到值了。

**这条做了反向验证**：把 `String()` 删掉后 `TestChangeTokenNotInLog` 立刻报「日志泄露口令」，加回去就过。用例不是空跑的，这个 `String()` 是真的在承重。

[SPACE] 旧口令还能用吗: code=200

## 二、审计写在快照之前——这是有意的取舍

C-1 明确「读操作**除数据库导出外**一律不记」，§8.4 第 8 类就是它。那么写在快照之前还是之后？B-1 原文只说「记一条」，没规定位置，两种都不违反文档。**选了之前**，理由是：

1. **导出是唯一一个会把整库搬出服务器的操作**，审计的意义正在于此。记录必须在数据可能离开之前落地——记不下来就不许导，而不是「先给你，记不记得上再说」。写在之后的话，审计写失败时字节已经在客户端手里了，无从补救。
2. **快照里带着自己这条记录**。B-3 说导出/导入一套覆盖「备份、迁移、换机、改密回滚」四场景，导回来的库里能看到「这份快照是什么时候导出的」，历史才是连续的。
3. **流式响应的约束**：一旦开始写 body 就改不回 JSON 错误。把所有可能失败的步骤（写审计、拍快照）都挪到第一个字节之前，错误处理才干净。

实现上复用了对话6 给 `ChangeToken` 加的那套：`db.Export` 也接 `handlers ...util.TransactionHandler`，在 `dbLock.RLock()` 里先跑事务再 `backup`：

```
transaction(原库, 口令, handlers...)   //写不进去直接返回，一个字节都不发
  → backup(原库 → 临时快照)            //sqlite online backup，一致性快照
  → io.Copy(临时快照 → writer)
  → defer RemoveFile(临时快照)
```

**代价要说清楚**：审计行的 `Result` 写的是 `成功`，但它落库时最后一步（把字节拷给客户端）还没发生。所以这条审计的语义准确说是「导出被发起且快照已生成」。客户端半路断线的话，库里仍会有一条 `成功`。对一个「只留痕、不承载业务」（§一前提8、C-2）的审计来说我认为可以接受——**宁可多记一次没拿全的导出，也不能漏记一次真的搬走了整库的导出**。如果你要求 `Result` 严格反映客户端是否收全，那就只能改成写在之后，同时接受第 1、2 条的损失。

## 三、二进制下载的两个实现细节

### 3.1 响应头懒设置

出错要能改回 JSON，但 `Content-Disposition: attachment` 一旦发出去就晚了。所以包了个 12 行的 `dbFileWriter`，**在真正写第一个字节时才设响应头**：

```go
func (this *dbFileWriter) Write(data []byte) (int, error) {
	if !this.written {
		this.written = true
		this.c.Header("Content-Type", "application/octet-stream")
		this.c.Header("Content-Disposition", ...)
	}
	return this.c.Writer.Write(data)
}
```

handler 据此三分支：没出错就结束；出错且还没开始写 → `c.JSON` 返回错误（`TestExportDbWrongToken` 断言此时**连 `Content-Disposition` 都没有**）；出错但已经开始写 → 只能打日志，HTTP 上无从补救。

**考虑过但没用的替代**：先 `bytes.Buffer` 缓冲整库再 `c.Data` 一把梭。代码更短，但要把整个数据库读进内存，docker 里不合适；而且 `export()` 本来就已经把快照落到临时文件了，再进内存是白抄一遍。

### 3.2 文件名

`jotcash-20260913231500.db`，东八区时间（`util.Time2Str` + `util.E8Loc`）。用时间不用 `util.GenId()`，是因为这个名字是给人看的、会落到用户的下载目录里。

### 3.3 前端得用 fetch + blob，不能用 `<a href>`

对话3 定了「jwt 只允许通过 header 传」，而浏览器的 `<a download>` 带不了自定义头。前端必须：

```
fetch(url, {method:'POST', headers:{Authorization:'Bearer '+jwt}})
  .then(r => r.blob()).then(b => { /* URL.createObjectURL 触发下载 */ })
```

这是对话3/对话5 里两次预告过的那个连带影响，现在真的碰上了。**没有为它开 query token 的口子**，与对话3 的结论一致。

## 二、补上 B-2 的两个缺口

### 2.1 「结构合法」校验（老账里挂了很久的一条）

B-2 原文：「上传的库文件须用本次请求口令校验能打开**且结构合法**，通过才原子替换」。口令校验本来就有（`replace` 里的 `open`），结构校验一直没有。

**为什么非有不可**：`AutoMigrate` 对着一个空库也能把 4 张表建全。所以如果没有这道闸，用户传错文件——只要那个文件恰好能用当前口令打开——系统会欣然接受，建一套空表，**把用户全部数据换成一个空库**。而 A-2 写得很清楚：口令丢了没有找回路径，数据同理。

实现放在 `db/migrate.go`，紧挨着 `AutoMigrate`：

```go
var migrateModels = []schema.Tabler{&model.Expense{}, &model.OperationLog{}, &model.FileMeta{}, &model.FileBlob{}}

func checkSchema(ctx context.Context, gormDb *gorm.DB) error {
	//逐个 migrator.HasTable(TableName())，缺哪张报哪张
}
```

模型清单从 `AutoMigrate` 的参数里提成了包级变量，两处共用，**避免以后加第 5 张表时只改一处**。用 `schema.Tabler`（gorm 自带的接口）是为了能直接拿到表名进错误信息，`AutoMigrate` 那边多了 3 行把它转回 `[]any`。

口径：**「结构合法」= 4 张表都在**。列的差异不算不合法——那正是 `AutoMigrate` 要补的（B-3 说导出/导入要覆盖「迁移、换机」，跨版本的库必须能导回来）。

### 2.2 「数据库导入」审计（落新库）

B-2：「替换后写一条「数据库导入」审计（**落新库**）」。与 A-5/B-1 用的是同一套 `handlers ...util.TransactionHandler`，写在**被替换进去的那个文件里**，替换成功它就是新库。

## 三、顺带修掉一个真实的顺序缺陷——这也是我改你已有用例的原因

### 3.1 原来的顺序有个洞

```go
err = replace(ctx, backupPath, dbPath, token)   // os.Rename，原库到这一步就没了
if err != nil { ... }
err = migrate(ctx, dbPath, token)               // 这里失败 → 原库已经被覆盖，还返回错误
```

`migrate` 失败（磁盘满、上传的库结构离谱到建不了表）时，**原库已经被 rename 掉了**，但 `Import` 返回 error。用户以为没导成，实际数据已经没了。这违反 B-2 的「**通过才**原子替换」。

### 3.2 改成全部在临时文件上做完再换

```
落临时文件
→ open(临时, 口令)        口令校验
→ checkSchema             结构校验
→ AutoMigrate             补齐旧版本的列差异
→ transaction(handlers)   落「数据库导入」审计
→ replace(临时 → 原库)     原子替换
→ setMigrated()
```

任一步失败都 `RemoveFile(临时)` 后返回，**原库一个字节没动**。和对话6 的 `ChangeToken`、对话7 的 `Export` 是同一个形状。

### 3.3 因此改了 `db/backup_test.go` 的一个夹具（请 review）

`TestImportOldDb` 原来造的「旧版本导出的库」是**一张表都没有**的库文件，靠 import 之后的 `migrate` 把表建出来。加了 §2.1 的结构校验之后，这种库会被拒——而这正是结构校验存在的意义（一张表都没有的库不是「旧版本的 jotcash 库」，是「不知道哪来的库」）。

**没有删弱这个用例，而是把夹具换成更真实的旧版本**：用 `create()` 建一个完整的库，再 `ALTER TABLE expense DROP COLUMN` 掉 `counterparty`、`remark` 两个无索引列。这样：

- 4 张表都在 → 过得了结构校验；
- 少两列 → 导入时 `AutoMigrate` 仍然有实活要干，用例原本要压的「并发读 + 反复导入」还在压。

用例的原始意图（内部注释：「建表标记要是在锁外从 true 翻回 false，这里就会撞上缺表」）**在新顺序下已经结构性地不可能发生**了——建表发生在 rename 之前，活着的库任何时刻都是表全的。用例照样保留着当回归。

### 3.4 `TestExport` 里 `migrated` 那条断言

它断言导入后 `migrated == true`（「导入后应在写锁内把表结构补齐」）。我一开始改成了 `resetMigrate()`，这条就红了。**这是我改错了，不是用例的问题**：新顺序下我们明确知道换进去的库已经在写锁内建过表，标记就该是 `true`。加了 `setMigrated()` 如实置位，用例一个字没改就回绿。

# 对话10 · 实现 E-5 明细批量软删除

> 依据来源：本轮「对话10」（参考 ping 链路实现明细删除）；功能口径取自 `记账系统功能与模型.md` E-5、§8.5「删除、复制与来源字段的稳定性」、§一前提7、§8.4 枚举4、§四.2 AuditLog。
> 范围：删除接口。E-5 的「删除前提示『本次将删除 N 笔』」是前端的二次确认，那个 N 直接用明细查询接口的 `count` 就有，不另开接口。

## 一、落地的链路

```
POST /api/expense/delete
  → validate → util.NewGinPost("明细删除", service.DeleteExpense)
  → service.DeleteExpense       返回 HttpData{Count}
  → service/db.DeleteExpense    区间校验 + 「删除与审计同事务」
  → db.NewExpenseDeleteHandler  已有，未改
```

**请求体就是 `model.ExpenseInquiry`**，一个形状同时覆盖 E-5 的两种入口：

- 勾选具体行 → `{"id":[...]}`
- 全选当前筛选结果全集 → 把列表页当前的筛选条件原样传上来（不用把跨页的 ID 一条条捞出来）

## 二、`service/db` 这层：两个 handler 组装进一个事务

```go
deleteHandler := db.NewExpenseDeleteHandler(inquiry)
operationLogHandler := db.NewOperationLogInsertHandler(&operationLog)
err = db.Transaction(ctx, deleteHandler, operationLogHandler)
...
return deleteHandler.Count, nil
```

这正是你给 `/service/db` 定的职责——「某个功能的多个表的在一个事务里的逻辑」。删不掉就不记审计，记不下审计就回滚删除，不会出现「删了但没留痕」。笔数从 `deleteHandler.Count` 取，事务跑完就拿得到。

审计行按 §四.2 填：批量操作的 `ObjectType`/`ObjectId` 留零值，删除不是编辑类操作所以 `Changes` 也留空，摘要写「批量软删除明细」。

**第一版我写错了，已按你的纠正重做**：原先自造了一个 `expenseDeleteHandler`，在它内部先跑删除再构造审计行，理由是「摘要要写『删除 N 笔』，而 N 只有删完才知道」。两个问题：

1. **那个理由不成立。** E-5 原文是「删除前提示『本次将删除 N 笔』；记一条「明细删除」审计」——N 出现在**前端的删除前确认提示**里，文档从没要求审计摘要带笔数。我把它当成了需求，再为了满足它去耦合。
2. **即便需要 N，也不该那样耦合。** 把 `operationLog` 塞进 `expenseDeleteHandler` 内部，等于让「删除」这个 handler 知道「删完要记什么审计」，两件事焊死在一起，换个调用场景就复用不了。`util.TransactionHandler` 本来就是为组装设计的，`db.Transaction(ctx, handlers...)` 按顺序跑，组装才是正确用法。

**校验只做区间倒挂**（日期、金额），把 `checkExpenseInquiry` 里那两条抽成 `checkExpenseRange` 与查询共用。**没有跑查询那套校验**——`PageSize` 兜底和排序默认值对批量删除毫无意义，`db.NewExpenseDeleteHandler`（`db/expense.go:140-145`）本来就会把 `Page`/`PageSize` 清零、把 `Deleted` 强制成 `DeletedNo`。

## 三、一处我改错又改回来的地方（记下来）

我一开始在 `handler/expense_test.go` 里把「不带任何条件的删除会被 gorm 的空条件保护挡下」注释成「别哪天默默变成清空全表」。**这个说法不对：expense 是软删除，无条件删除也不会清空任何东西，只是给所有未删除行打上删除时间**（行还在，`DeletedAll`/`DeletedOnly` 照样查得到，§8.5 还允许复制已删除行来恢复）。

# 对话11 · 实现 E-2 明细入库

> 依据来源：本轮「对话11」；功能口径取自 `记账系统功能与模型.md` E-1 CSV 契约、E-2、§8.1 折算联动「CSV 导入该行」、§8.2 摊分、§四.1 Expense 属性、§四.3 FileMeta、D-2 内容寻址、§8.4 枚举2、§九不变式1/6。
> 范围：入库接口。E-3 落库后的核实视图（按审计ID反查三要素）是另一个接口，不在本轮。
> **本轮有 5 处必须你拍板或知情的地方，集中在 §四，其中 2 处会影响数据正确性。**

## 一、落地的链路

```
POST /api/expense/insert   multipart：file=CSV，accounting_currency=记账币种
  → validate → handler.InsertExpense（显式 handler，multipart 套不进 NewGinPost）
  → service.InsertExpense        解析CSV → 派生字段 → 生成快照
  → service/db.InsertExpense     审计+原件+快照+明细，一个事务
  → db 各 InsertHandler          未改
```

E-2 的三个入口（单行新增 / 批量上传 / 复制已删除行）**共用这一个接口**：前端把内容组成一份符合 E-1 契约的 CSV 再上传，单行场景就是一份只有 1 行的 CSV。

## 二、CSV 契约（E-1）

`model/csv.go` 定义 `ExpenseCsv`——带 `csv` 标签的契约结构体，9 个全字符串字段；解析与生成在 `service/expense_csv.go`，因为 E-1 是业务规则。

- **列名匹配、不依赖顺序、可选列缺失按空**：交给 `util.CsvData2Struct`（gocsv 按 `csv` 标签匹配），不自己拼下标（`TestInsertExpenseColumnOrder` 用 `支出金额,支出币种,支出日期` 倒序只带必填列验证）
- **未知列 / 重复列 / 必填列缺失报错**：gocsv 对多余列是**静默忽略**的，所以先用 `util.CsvData2Strs` 取表头自己过一遍。必填 = 支出日期、支出币种、支出金额（§四.1 标必填的三项）
- **快照生成**用 `util.CsvStruct2Data`，同一个 `ExpenseCsv` 结构体反向序列化

### 4.4 文档自相矛盾：E-1 说「契约仅 8 个业务列」，紧接着列了 9 个

### 4.6 删掉快照文件名之后，原件与快照在库里分不出来

`用途` 字段在更早的轮次里被你删了，现在两条 `FileMeta` 只剩「同一个审计ID下的两条记录」这一点关联，**没有任何字段能区分哪条是原件、哪条是快照**。可以间接判断：明细的 `文件ID` 指向的那条就是快照。要不要有更直接的区分方式（比如把 `用途` 加回来），你定。

### 4.5 「快照」的定义是我定的

E-2 只说「存档 CSV（原件 + 快照）」，没定义快照是什么。我实现为：**按契约列顺序、由真正落库的明细重新生成的 CSV**，所以快照里的折算汇率是实际采用值（自动获取的也写进去了），金额是规范化形态（`100.50` 会写成 `100.5`）。

这带来一个可见后果：**原件与快照通常是两个不同的哈希**，会存两份 FileBlob。如果你希望「原件已经规范时不重复存」，那得改快照的生成口径（比如保留原始文本），说一声。

## 五、`service/db` 这层：一个事务四张表

按对话10 你纠正过的组装思路，把 handler 排好一起交给 `db.Transaction`：

```
OperationLogInsertHandler   →  FileBlobInsertHandler(只插库里还没有的)
  →  FileMetaInsertHandler(原件, 快照)  →  ExpenseInsertHandler(本批明细)
```

- **D-2 内容寻址去重**：`FileBlob` 以哈希为主键，重复插会撞主键。所以**先查一次库里已有哪些哈希，只把缺的组进事务**（同一请求内原件与快照同哈希时也只插一次）。这个查询在事务外，单用户单实例（§一前提1）下 TOCTOU 可忽略，真撞上了也是事务回滚，不会写坏。
