## 一、第一个问题：ping 的代码与调用链路，是否有错/有漏

### 1.1 结论先行：链路是断的，当前 100% 跑不通

实测（临时用例，已删除）：用 `tool.EnJwt(ctx, config.GetConfig().ServerToken, "<任意前端口令>", time.Hour)` 签一个完全合法的 JWT，打到 `POST /api/ping`：

```
[有jwt] status=200 body={"code":500,"msg":"获取数据库口令，为空","data":{"ip":"","sn":"jotcash","ts":...}}
[无jwt] status=200 body={"code":401,"msg":"Authorization非法","data":null}
```

也就是说：**无论前端口令对不对，这个接口永远返回「获取数据库口令，为空」**，A-4「口令校验（只读探针）」的功能为零。

### 1.2 错（3 条，都在同一个根因上）

#### E1 · Claims 类型对不上，前端口令根本进不了 ctx（致命）

| 位置 | 行为 |
| ---- | ---- |
| `handler/handler.go:40-42` `validate` | 调 `util.ValidateGin(ctx, config.GetConfig().ServerToken)` |
|  `go_common/util/gin.go:84` | `var claims model.Claims` —— 这是 **`go_common/model.Claims`** |
| `go_common/util/gin.go:126` | `c.Set(ClaimsKey, &claims)` —— 存进去的是 `*go_common/model.Claims` |
| `db/db.go:36` `getToken` | `tool.GetClaims(ctx)` |
| `tool/gin.go:11` | `util.GetCtxValue[*model.Claims](ctx, util.ClaimsKey)` —— 取的是 **`*jotcash/model.Claims`** |
| `go_common/util/ctx.go:8` | `object, _ := value.(T)` —— 类型断言失败，**吞掉 ok，返回零值 nil** |

`getToken`（`db/db.go:37-40`）拿到 nil 就直接 `errors.Errorf("获取数据库口令，为空")`，链路到此终止。

这个坑在 `260913-005452-answer.md`「对话17 §五.7」已经登记过原话——「`util.ValidateGin` 塞的是 `go_common/model.Claims`，类型对不上，必须自己写」——但 `handler` 包落地时没有按登记结论做。

#### E2 · 就算 key 的类型对上了，`client_token` 也已经在反序列化时被丢掉

`go_common/model/claims.go` 的 `Claims` 只有 `jwt.StandardClaims` + `Ip/ServerName/LogId/Uri/ReqId` 五个字段，**没有 `ClientToken`**。`util.ValidateGin` 第 85 行 `DeJwt(c, token, secret, &claims)` 反序列化到这个结构体上，JWT payload 里的 `client_token`（`model/claims.go:10` 定义的 `json:"client_token,omitempty"`）被直接丢弃。

所以 E1 不是「改个类型断言就行」，**必须换成 `tool.DeJwt`（`tool/jwt.go:30`）**——它反序列化到 `jotcash/model.Claims`，才留得住前端口令。结论：`util.ValidateGin` 在本项目不可用，中间件得自己写。

#### E3 · 自己写中间件时的第二个坑：不能用 `tool.SetClaims`

`tool.SetClaims`（`tool/gin.go:13-18`）返回的是一个**新的 `context.Context`**，对 `*gin.Context` 无效——后续 handler 拿到的还是原来那个 `c`。必须用 `c.Set(util.ClaimsKey, claims)`。

已核 `gin@v1.12.0/context.go` 的 `Context.Value`：对 string key 会先走 `c.Get(keyAsString)`，所以 `c.Set` 写进去的值，下游用 `tool.GetClaims(ctx)`（走 `ctx.Value`）能取到。这条链路成立。

**修复原型实测**（临时用例，已删除）：把 `validate` 换成 `tool.DeJwt` + `c.Set` 之后，同一套路由的四种输入：

```
[口令都对]   {"code":200,"msg":"","data":{"ip":"","sn":"jotcash","ts":...}}
[前端口令错] {"code":500,"msg":"连接数据库，口令错误或数据库文件损坏","data":{...}}
[后端口令错] {"code":500,"msg":"JWT解密异常: signature is invalid","data":null}
[没带jwt]   {"code":500,"msg":"JWT解密异常: token contains an invalid number of segments","data":null}
```

四种分支全部区分正确，A-4 的探针功能成立。

### 1.3 漏（6 条）

#### M1 · 没有任何地方签发 JWT——前端怎么拿到 token，是本轮最大的空白

`tool.EnJwt`（`tool/jwt.go:13`）全项目零生产调用方（grep 确认，只有 `tool/jwt_test.go` 在用）。按 A-3「无登录接口」+ 对话6，推断是**前端用后端口令在 JS 里自签 JWT**：用户从初始化日志（`db/db.go:142-143` 打印的 `clientToken` / `serverToken`）抄两个口令 → 前端 sessionStorage 存两个 → 每次请求用 serverToken 签一个带 `client_token` 的 JWT。

**这条属于「待确认」**，因为它决定前端要不要引 JS 的 JWT 库，也决定 `tool.EnJwt` 在后端还有没有生产用途。见 §四.1。

#### M2 · `GET /api/ping` 与 `POST /api/ping` 语义完全不同却共用一个路径

- `handler/handler.go:20`：`GET`，无鉴权，`util.Ping`，存活探针
- `handler/handler.go:21`：`POST`，过 `validate`，A-4 口令校验探针

能跑，但把「运维探活」和「业务口令校验」压在一个 URL 上。A-4 是业务接口，按 survive_monitor 的做法（`model.StatusPath`）业务路径应当由本项目自己定义常量。建议 A-4 独立成 `/api/token/check` 之类，`util.PathPing` 留给 GET 存活探针。

#### M3 · 响应语义不对：出错时照样返回 `PingData`，且错误文案违反 A-4「统一提示」

`handler/ping.go:17`：`util.NewHttpRespByErr(model.PingData{...}, err)`。`go_common/util/gin.go:35-39` 的约定是 msg 非空 → code 500，但 **data 仍然被填满**，前端必须先判 code 才知道 data 有没有意义。出错时 data 应为 nil。

更要紧的是文案。A-4 原文：「口令错与文件损坏不可区分，**统一提示**」。现在 `err.Error()` 原样透传，前端能看到至少四种不同文案：

| 来源 | 文案 |
| ---- | ---- |
| `db/db.go:39` `getToken` | 获取数据库口令，为空 |
| `db/db.go:169` `open` | 打开数据库，库文件不存在或为空 |
| `db/db.go:81` `connect` | 连接数据库，口令错误或数据库文件损坏 |
| `db/migrate.go:21` `AutoMigrate` | 自动建表，异常: … |

只有第三条符合 A-4。前两条既违反「统一提示」，也把服务端内部状态（库文件不存在 / ctx 里没口令）泄露给了调用方。

#### M4 · `service/db.CheckToken` 是纯转发，没有承担你给 `/service/db` 定义的职责

`service/db/db.go:9-11` 一行 `return db.CheckToken(ctx)`，零校验。而你对这一层的定义是「`/db` 没有业务逻辑，可能会缺少必要的参数校验；参数校验与业务逻辑有关，因此 `/service/db` 才会有足够的业务逻辑校验」。

这里至少缺两样，且**恰好都是「业务规则」而非「通用 DAO 规则」**，正好落在这一层：

1. **A-6 口令强度前置**：`tool.CheckToken`（`tool/token.go:41`）现成——长度 ≥ 12、不得纯数字或纯字母。明显不合规的口令直接挡回，不必走一次开库（开库要解密整库、还可能触发一次 `AutoMigrate`）。
   - 安全性已核：`tool.GenToken`（`tool/token.go:35-36`）循环到 `CheckToken` 通过才返回，所以系统生成的初始口令必然合规，前置不会误杀存量库。
2. **A-4 错误文案归一**：把 M3 那四种文案统一收敛成一句，比如「口令错误或数据库文件损坏」。这属于业务口径，`db` 包不该知道，`handler` 不该硬编码，正好归 `service/db`。

#### M5 · `handler/ping.go:15` 的日志用的是 `util.GetClaims`，修好 E1 后会变成永远 nil，且会绕开口令脱敏

`handler/ping.go:15` 用 `util.GetClaims(c)`（go_common 类型），`db/db.go:36` 用 `tool.GetClaims(ctx)`（jotcash 类型），**同一个 `ClaimsKey` 下并存两套类型**，本身就是混乱源。E1 修好之后 key 下存的是 jotcash 类型，`util.GetClaims` 就会恒为 nil，日志字段直接失效。

而且 `model/claims.go:11-14` 的 `String()` 是专门为 H-2 写的——序列化前把 `ClientToken` 抹掉。只有用 `tool.GetClaims` 打印才走得到这个保护。修 E1 时这一行必须一起换。

#### M6 · 中间件里必须砍掉「从 query 取 token」，否则前端口令会进日志文件（H-2 / §九不变式3）

`go_common/util/gin.go:76-78`：header 里没有 `Authorization` 时，回退到 `c.Query(AuthorizationKey)`。而 JWT 的 payload 里是**明文的前端口令**（`tool/jwt.go:26` `claims.ClientToken = clientToken`，未加密，只签名）。

`util.GinLog`（`go_common/util/log.go:110,113-117`）记录 `uri := c.Request.RequestURI`，**带 query string**。两者一叠加：只要有人用 `?Authorization=<jwt>` 调一次，前端口令就落进日志文件了。这直接违反 H-2「日志中只有初始化那一次出现口令」与 §九不变式3。

自己写中间件时**只从 `Authorization` header 取**，这是必须的，不是可选优化。
> 连带影响：B-1 数据库导出是个下载，浏览器 `<a href>` 没法带 header。要么前端 fetch + blob 下载，要么将来给导出单开一条短时效 query token 的口子。**留作 B-1 开工时的待确认**，本轮不处理。

### 1.4 可优化（不算错，列出备查）

- **A-4 这个「只读探针」会拿写锁**：`db.CheckToken`（`db/db.go:198`）→ `Open`（`db/db.go:147`）→ `autoMigrate`（`db/migrate.go:28`）。首个请求若是 ping，会 `dbLock.Lock()` 跑一次全表 `AutoMigrate`。功能上没错（migrate 之前照样要开库、口令照样被验），但探针的代价比预期重。`connect` 是私有的，要优化得在 `db` 包内部做，不在本轮范围。
- **`handler.Init` 建引擎与起服务耦合**（`handler/handler.go:16-32`：`gin.Default()` 到 `engine.Run` 一气呵成），外部拿不到 `*gin.Engine`，第二问的单测因此写不了。见 §二。
- **`gin.Default()` 自带的 Logger 与 `util.GinLog` 双份日志**：与 survive_monitor 一致，沿用即可，只是同一请求会打两行。
- **没有 `main.go`**：`handler.Init` 目前无调用方（find 确认全仓无 `main.go`）。属于预期内的进度，不是错。
- **`engine.Run` 是明文 HTTP**：§一前提3 / §十流程2 要求 HTTPS。H-1 是 docker 部署，通常由反向代理终结 TLS，但这一点文档没写死。见 §四.3。

## 二、第二个问题：能不能从发起 HTTP 的高层级写单测

### 2.1 结论：能，而且已经跑通了

**已实测通过**：`net/http/httptest` + `engine.ServeHTTP`，四种输入（口令都对 / 前端口令错 / 后端口令错 / 没带 JWT）全部得到预期响应，输出见 §1.2 E3。不需要真的监听端口、不需要起进程，`httptest.NewRequest` + `httptest.NewRecorder` 走的是 gin 完整的中间件链，**中间件、参数绑定、鉴权、业务、DB、响应体全在覆盖范围内**，对降低前端联通成本的价值是实打实的。

### 2.2 唯一的难点：测试怎么拿到「正确的前端口令」

初始前端口令是随机生成的（`db/db.go:98` → `tool.GenToken`），且按 A-2 只在建库那一次打进日志，任何地方都不持久化。而 `db` 包的 `init()`（`db/db.go:26-32`）在 **import 时**就把库建好了——测试代码根本没有机会在它之前挂日志钩子。

**解法：不去截 `init()` 那一次，而是在临时目录里重新建一次库。** `db/db_test.go` 已经有现成的范式（`catchLog` at `db/db_test.go:53`、`findLogField` at `:62`、`TestCreate` at `:80-96`），照搬即可：

```
t.Chdir(t.TempDir())            // config.DbPath/DbBackupPath 都是相对路径，chdir 即隔离
logrus.SetOutput(buffer)        // 挂缓冲
db.Create(ctx)                  // 导出的，且幂等（db/db.go:114-117 库已存在直接返回）
clientToken := findLogField(buffer.String(), "clientToken")
```

已验证的三个前提：

1. `config.DbPath = "resource/jotcash.db"`、`DbBackupPath = "resource/db_backup"` 都是相对路径（`config/config.go:17-19`），`t.Chdir` 能完整隔离；
2. `config` 的 init 在 chdir 之前就把 `ServerToken` 读进内存了（`config/config.go:26-33`），chdir 之后 `config.GetConfig().ServerToken` 照常可用，后端口令直接拿得到；
3. `migrated` 这个包级标志不会串味：`Create` → `create` 直接调 `AutoMigrate`（`db/db.go:126`）而不是 `migrate`，不置 `migrated`；新库在 `create` 里已经建过表，之后 `Open` 走不走 `autoMigrate` 都正确。

**所以：`db` 包一行生产代码都不用改。** 这一点是实测结论，不是推断。

### 2.3 生产代码只需要一处改动：把 `handler.Init` 拆成「建引擎」与「跑引擎」

```
func NewEngine(ctx context.Context) *gin.Engine   // 装中间件、注册路由，返回引擎
func Init(ctx context.Context) error              // NewEngine(ctx).Run(config.ListenAddress)
```

单测拿 `NewEngine(ctx)`，生产入口拿 `Init(ctx)`，路由表只有一份、不会测试跑通而线上漏注册。改动量约 5 行，不引入任何测试专用的导出 API（`export_test.go` 那套对跨包测试也无效，不考虑）。

### 2.4 建议的用例清单（`handler/ping_test.go`）

| 用例 | 断言 |
| ---- | ---- |
| 口令都对 | `code == 200`，`data.sn == "jotcash"` |
| 前端口令错 | `code == 500`，msg 为 A-4 的统一文案 |
| 后端口令错（签名不对） | `code == 500`，**msg 中不得出现任何口令** |
| 不带 Authorization | `code == 401`/`500`，不 panic |
| JWT 过期 | `code == 500`（`tool/jwt_test.go:55-60` 已证 `DeJwt` 会拒） |
| `?Authorization=<jwt>` | 被拒（把 M6 钉死，防回归） |
| 日志断言 | 全程 `catchLog` 缓冲里不得出现 clientToken 明文（把 H-2 钉死） |
| `GET /api/ping` | 不带任何凭据也返回 200（存活探针不被 validate 误伤） |

TestMain 沿用 `db/db_test.go:20-26` 的写法（`logrus.SetLevel(WarnLevel)` + 收尾 `os.RemoveAll("resource"/"log")`）——注意 `db` 的 `init()` 会在**测试二进制的原始工作目录**（也就是 `handler/`）里建一个库，这个残留必须清掉，否则 `handler/resource/` 会污染工作区（本轮实测踩到过，已清理）。

## 三、第三个问题：下一个功能选型与技术方案（只给方案，不写代码）

### 3.1 候选比较

| 候选 | 写操作 | 表数 | 要写审计 | 依赖汇率 | db 层现成度 | 评价 |
| ---- | ------ | ---- | -------- | -------- | ----------- | ---- |
| **C-3 审计查看** | 否 | 1 | 否（C-1：读操作除 B-1 外一律不记） | 否 | `SelectOperationLog` + `OperationLogInquiry` 全齐 | **推荐** |
| D-4 文件列表 | 否 | 1（下载才碰 2） | 否 | 否 | `SelectFileMeta` 齐 | 次选，但早期没数据可看 |
| A-5 更换口令 | 是 | — | 是 | 否 | `ChangeToken` 齐 | 第一个写链路的好人选，但不该第一个做（见 3.2） |
| B-1 数据库导出 | 否 | — | **是**（§8.4 第 8 类） | 否 | `Export` 齐 | 撞上 M6 的下载带 header 问题 |
| E-7 明细查询 | 否 | 1 | 否 | 否 | 齐 | 字段最多、筛选项最多，不适合第一个 |
| E-2 数据入库 | 是 | 4 | 是 | 是 | — | 最复杂，压轴 |

### 3.2 选定：**C-3 审计查看（操作日志只读列表）**

理由：

1. **纯读、单表、不落审计、不碰汇率、不碰事务语义**——链路里没有一个环节会把「接入层骨架该长什么样」这件事搅浑。
2. **`db` 层已经 100% 就绪**，本轮只需要往上长三层。`db/operation_log.go:104-111` 的 `SelectOperationLog` 已返回 `([]*model.OperationLog, int64, error)`，`model.OperationLogInquiry`（`model/operation_log.go:44-56`）的筛选字段（操作类型、时间区间、分页、排序）恰好就是 C-3 要的「按操作类型与时间区间筛选」。
3. **天然有数据可看**：系统初始化时已经写了一条「系统初始化」审计（`db/db.go:129-135`），接口一通就有真实返回，前端联调不用先造数据。
4. **一次性定型接入层的全部约定**（JWT 中间件、请求/响应体、分页、排序白名单、错误文案、HTTP 层单测范式），后面 D-4 / E-7 照抄即可。C-3 的返回结构（列表 + 总数）和 E-7 完全同构。
5. **不选 A-5 的原因**：`ChangeToken` 涉及整库改密 + 原子替换，且「老账」里还挂着两条未决（`ChangeToken` 不校验新口令强度、A-5 审计由谁写、写进新库还是旧库）。第一条完整链路不该同时背这些债——等骨架定了再做，成本反而更低。

### 3.3 分层设计

```
handler/operation_log.go   →  service/operation_log.go  →  service/db/operation_log.go  →  db/operation_log.go
    接口注册/参数绑定             业务编排/响应体组装            业务校验 + 调 DAO             无业务逻辑的 DAO（已有）
```

| 层 | 文件 | 职责 | 输入 | 输出 |
| -- | ---- | ---- | ---- | ---- |
| handler | `handler/operation_log.go` | 只注册路由，不写 body 解析样板 | — | `gin.HandlerFunc` |
| service | `service/operation_log.go` | 调 `service/db`，组装 `go_common/model.HttpData{Object, Count}` | `ctx, model.OperationLogInquiry` | `(any, error)` |

## 一、改了什么

### 1.1 `handler/handler.go` —— 自写 `validate` 中间件（修 E1/E2/E3/M6）

`validate` 原来 3 行委托给 `util.ValidateGin`，现在按 §1.2 的结论改为自己解 jwt，与 go_common 同型，三处差异：

| 差异 | 原因 |
| ---- | ---- |
| 用 `tool.DeJwt`（解到 `jotcash/model.Claims`） | go_common 解到自己的 `Claims`，没有 `ClientToken` 字段，前端口令在反序列化时就没了（E2） |
| 只从 `Authorization` header 取，**砍掉 query 回退** | jwt 载荷里是明文前端口令，走 query 会被 `GinLog` 连着 uri 写进日志（M6，违反 H-2 / §九不变式3） |
| `c.Set(util.ClaimsKey, claims)` | `tool.SetClaims` 返回的是新 ctx，对 `*gin.Context` 无效（E3） |

其余逻辑（logId、过期、`ReqId` 防重放、`Uri` 绑定、各分支的响应码与文案）与 `util.ValidateGin` 逐条对齐，保持行为一致。拆出 `setLogId`/`getJwt`/`getUri` 三个小函数，是因为 `go_common` 的 `setGinLogId` 不导出、`validate` 一坨 40 行读不下去。

留了两条注释，都是「不写就会被改回去」那类：query 回退为什么不能加、`tool.SetClaims` 为什么不能用。

### 1.2 `handler/handler.go` —— 拆出 `NewEngine`（§二.3）

`Init` 保留「建引擎 + `engine.Run`」的对外语义，路由注册挪到 `NewEngine(ctx) *gin.Engine`。路由表只有一份，单测拿 `NewEngine`，不会出现测试跑通而线上漏注册。

**未改路由本身**：`POST /api/ping` 维持现状，M2（A-4 要不要独立路径）等你拍板，见 §四.2。

### 1.3 `handler/ping.go`（修 M3/M5）

- `util.GetClaims` → `tool.GetClaims`。修完 E1 之后 key 下存的是 jotcash 类型，前者会恒为 nil；而且只有 jotcash 的 `Claims.String()`（`model/claims.go:13-16`）才会在序列化前抹掉 `ClientToken`，H-2 的脱敏靠的就是它。
- 出错时 `data` 传 nil，不再连错带 `PingData` 一起返回。

### 1.4 `service/db/db.go`（修 M4，以及 M3 的文案部分）

从 1 行透传变成三段，这一层的存在意义落到实处：

1. **Claims 兜底**：middleware 之外的调用方（比如将来的定时任务）没塞 claims 时，不往下走。
2. **A-6 强度前置**：`tool.CheckToken` 挡掉长度 < 12 / 纯数字 / 纯字母的口令，**不开库**。开库要解密整库、还可能触发一次 `AutoMigrate`，明显不合规的输入不该付这个代价。已核 `tool.GenToken`（`tool/token.go:35-36`）循环到强度通过才返回，系统生成的初始口令必然合规，前置不会误杀存量库。
3. **A-4 文案归一**：`db` 层四种文案（`获取数据库口令，为空` / `打开数据库，库文件不存在或为空` / `连接数据库，口令错误或数据库文件损坏` / `自动建表，异常`）统一收敛成常量 `tokenInvalid = "口令错误或数据库文件损坏"`。原始错误在 `db` 层已经各自打过日志，排查不受影响。

**一处口径说明**：强度校验失败时**原样返回强度文案**（如「校验口令，长度不足12位」），不归一。A-4 要求不可区分的是「口令错」与「文件损坏」这两件事，强度是第三类；强度规则本身是 A-6 公开的，不构成信息泄露，而且告诉用户「你这口令连格式都不对」比统一报「口令错误」对排障更有用。如果你认为探针接口应当一视同仁，改成也返回 `tokenInvalid` 即可，一行。

## 四、发现一条既存失败（不在本次范围，未修）

`db` 包 `TestTokenSpecialChar`（`db/backup_test.go:108`）**在我动手之前就是红的**——已用 `git stash` 退回改动前实跑确认，与本次修改无关。

- **现象**：`backup_test.go:126` 「导出的库用同一口令导不回来」，底层报 `sqlite3: file is not a database`。
- **原因**：`db/backup.go:53-56` 用 `url.Values.Encode()` 拼备份目标的 dsn。`Encode()` 走的是 `application/x-www-form-urlencoded`，**空格编码成 `+`**；而 SQLite 的 URI 只认 `%XX` 转义，`+` 被原样当字符。于是口令 `"pass word 1234"` 到了目标库变成 `"pass+word+1234"`，备份落在另一把口令上，再用原口令导回自然失败。
- **影响面**：B-1 导出、B-2 导入、A-5 更换口令三条链路，只要口令含空格（或任何 `Encode()` 与 URI 转义不一致的字符）就会静默用错口令。初始随机口令的字符集（`tool/token.go:15-16`，只有字母数字且剔除易混字符）不含这类字符，所以**当前默认路径不受影响**；一旦 A-5 允许用户自定口令就会踩到。
- **这条测试是对的**，它的注释（`db/backup_test.go:110`）把原因写得很清楚，说明写的时候就知道；红的是 `backup.go`，不是测试。要不要本轮一并修，你说。
