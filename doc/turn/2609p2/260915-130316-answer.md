## 一、直接回答：不会，一个外键都没有

`AutoMigrate` 现在生成的四条建表语句里，`FOREIGN KEY` 出现 0 次（探针实测，原样贴出）：

```sql
CREATE TABLE `expense` (`id` integer,...,`operation_id` integer,`file_id` integer,...,PRIMARY KEY (`id`))
CREATE TABLE `operation_log` (`id` integer,...,`object_id` integer,...,PRIMARY KEY (`id`))
CREATE TABLE `file_meta` (`id` integer,`file_hash` text,...,`operation_id` integer,...,PRIMARY KEY (`id`))
CREATE TABLE `file_blob` (`file_hash` text,`file_data` blob,PRIMARY KEY (`file_hash`))
```

根因是 GORM 的机制，不是配置漏了：`migrator.AutoMigrate` 只从 `stmt.Schema.Relationships.Relations` 取外键约束（`gorm@v1.31.2/migrator/migrator.go`，建表与补约束两处都是这个来源）。**关联关系只能由结构体里的关联字段声明**，而 `model` 包四个结构体里一个关联字段都没有——`Expense.OperationId`、`Expense.FileId`、`FileMeta.OperationId`、`FileMeta.FileHash` 全是裸 `int64`/`string`，GORM 眼里它们只是普通列，`Relations` 是空的。所以 `DisableForeignKeyConstraintWhenMigrating` 是不是默认值根本不重要，没有关系可解析，约束无从谈起。

顺带一个**与直觉相反、但对本项目是好消息**的事实：本项目这份 SQLite 的**外键开关默认是开的**。

```
PRAGMA foreign_keys = 1
```

标准 SQLite 默认 OFF，这里是 `ncruces/go-sqlite3-wasm/v2@v2.1.35300/build/sqlite_opt.h:23` 编译期写死了 `#define SQLITE_DEFAULT_FOREIGN_KEYS 1`。`db/db.go:145-158 open` 里没有任何 `PRAGMA foreign_keys` 语句，走的就是这个默认值。也就是说：**只要把约束建出来，它立刻就是生效的，不需要在 `open` 里补 pragma**。

## 二、加外键能不能成：能，但四张表只护得住三张

### 2.1 按文档该建哪几条

`doc/decisions/记账系统功能与模型.md` §七 列了 4 组关联，逐条核对到列上：

| # | 子表.列 | 父表.列 | 文档依据 | 建不建 |
| - | ------- | ------- | -------- | ------ |
| 1 | `expense.operation_id` | `operation_log.id` | §七 AuditLog→Expense 1:N；§四.1「审计ID 必填」 | 建 |
| 2 | `expense.file_id` | `file_meta.id` | §七 FileMeta→Expense 1:N；§四.1「文件ID 必填」 | 建 |
| 3 | `file_meta.operation_id` | `operation_log.id` | §四.3「审计ID：在哪次操作中落档」 | 建 |
| 4 | `file_meta.file_hash` | `file_blob.file_hash` | §七 FileBlob→FileMeta 1:N；D-2「`FileMeta` 以哈希为外键」 | 建 |
| — | `operation_log.object_id` | 多态（可能指 expense，也可能指 file_meta） | **C-2 与 §四.2 明写「历史指针，非外键」，且零值合法** | **不建** |

父列都是主键（`operation_log.id`、`file_meta.id`、`file_blob.file_hash`），满足 SQLite 对被引用列必须唯一的要求。

### 2.2 GORM 侧怎么写（有一个坑）

三条 belongs-to 直写就行：

```go
OperationLog *OperationLog `json:"-" gorm:"foreignKey:OperationId;references:Id;constraint:OnUpdate:RESTRICT,OnDelete:RESTRICT"`
```

**第 4 条不能照抄**。`FileMeta.FileHash` 和 `FileBlob.FileHash` 字段同名，`guessRelation`（`gorm@v1.31.2/schema/relationship.go:462-468`）对「字段类型是另一个 schema」的情况**默认先按 has-one 猜**，`foreignKey:FileHash` 在 `FileBlob` 上能查到，于是它就地认定 has-one，把外键建到了**反方向**：

```sql
-- 错的：约束长在 file_blob 上，指向非唯一的 file_meta.file_hash
CREATE TABLE `file_blob` (...,CONSTRAINT `fk_file_meta_file_blob` FOREIGN KEY (`file_hash`) REFERENCES `file_meta`(`file_hash`) ...)
```

运行期直接报 `foreign key mismatch - "file_blob" referencing "file_meta"`，插入全挂。正确写法是**反着声明 has-many，挂在 `FileBlob` 上**：

```go
type FileBlob struct {
    FileHash  string     `gorm:"column:file_hash;primaryKey"`
    FileData  []byte     `gorm:"column:file_data;type:blob"`
    FileMetas []FileMeta `json:"-" gorm:"foreignKey:FileHash;references:FileHash;constraint:OnUpdate:RESTRICT,OnDelete:RESTRICT"`
}
```

这样约束才落到 `file_meta` 上。实测四条一次建齐：

```sql
CREATE TABLE `expense` (...,CONSTRAINT `fk_expense_file_meta` FOREIGN KEY (`file_id`) REFERENCES `file_meta`(`id`) ON DELETE RESTRICT ON UPDATE RESTRICT,
                            CONSTRAINT `fk_expense_operation_log` FOREIGN KEY (`operation_id`) REFERENCES `operation_log`(`id`) ON DELETE RESTRICT ON UPDATE RESTRICT)
CREATE TABLE `file_meta` (...,CONSTRAINT `fk_file_blob_file_metas` FOREIGN KEY (`file_hash`) REFERENCES `file_blob`(`file_hash`) ON DELETE RESTRICT ON UPDATE RESTRICT,
                              CONSTRAINT `fk_file_meta_operation_log` FOREIGN KEY (`operation_id`) REFERENCES `operation_log`(`id`) ON DELETE RESTRICT ON UPDATE RESTRICT)
```

### 2.3 误删演练：**`expense` 自己一点都没被保护**

这是本轮最该先说的一条。造齐四张表的数据后逐条物理删：

| 操作 | 结果 |
| ---- | ---- |
| `DELETE FROM operation_log WHERE id=99`（被 expense/file_meta 引用） | ✅ 拦住：`FOREIGN KEY constraint failed` |
| `DELETE FROM file_meta WHERE id=11`（被 expense 引用） | ✅ 拦住 |
| `DELETE FROM file_blob WHERE file_hash='h1'`（被 file_meta 引用） | ✅ 拦住 |
| **`DELETE FROM expense WHERE id=1`** | ❌ **删成功，行数归 0** |
| **`DROP TABLE expense`** | ❌ **成功** |

原因是外键的语义：`ON DELETE RESTRICT` 保护的是**被引用的父行**。`expense` 是整个模型的叶子，**没有任何表引用它**（唯一可能指向它的 `operation_log.object_id` 按 C-2 明确不做外键），所以它拿不到任何保护。

而你担心的「日后迭代误删」，最可能的形态恰恰是 `DELETE FROM expense WHERE ...` ——`expense` 是 §三 里写的「唯一的事实实体」，也是唯一有软删语义、因而唯一会被写 `DELETE` 的表。**外键在这个场景上是脱靶的**：它护住了审计、文件元数据、文件内容这三张本来就「只增不删」、也没人会去删的表，唯独没护住最值钱的那张。

## 三、加外键的四个代价（全部实测）

### 3.1 现有入库顺序会直接崩

`service/db/expense.go:37`：

```go
return db.Transaction(ctx, fileBlobHandler, fileMetaHandler, expenseHandler, operationLogHandler)
```

顺序是 `file_blob → file_meta → expense → operation_log`，**审计行排在最后**。SQLite 外键是立即检查（非 DEFERRABLE），插 `file_meta` 时它的 `operation_id` 所指的审计行还不存在：

```
现网顺序 → file_meta: sqlite3: constraint failed: FOREIGN KEY constraint failed
改成 operation_log→file_blob→file_meta→expense → <nil>
```

修法很轻：把 `operationLogHandler` 提到链首。但要注意 `service/db/expense.go` 正是当前编译不过的文件之一（`db.Transaction` 未定义），改它会和你手上的重构撞车。

### 3.2 **和「建表链跑在事务里」硬冲突 —— 这条最重**

SQLite 规定 `PRAGMA foreign_keys` **在事务内是 no-op**，实测：

```
初始: 1
事务外执行 OFF 之后: 0
事务内执行 OFF 之后: 1   ← 没关掉
```

而 SQLite 不支持 `ALTER TABLE ADD CONSTRAINT`，gormlite 改表一律走 `recreateTable`（`gormlite@v0.34.0/migrator.go:376`）——新建临时表、拷数据、`DROP` 旧表、改名；为此它在 `AlterColumn`/`DropColumn`/`CreateConstraint` 外面套了 `RunWithoutForeignKey`（`migrator.go:18-27`）去关外键。**这个关闭动作在事务里失效**，于是拷完数据 `DROP` 旧父表时，子表的外键当场炸。

实测对照（外键已就位、库里有数据，对父表 `operation_log` 做一次列变更）：

```
事务内 AlterColumn(operation_log.summary) → sqlite3: constraint failed: FOREIGN KEY constraint failed
事务外 AlterColumn(operation_log.summary) → <nil>
```

本项目**所有**建表入口都在事务里：

- `db/db.go:94-105`：`db.Transaction(func(tx){ tx.AutoMigrate(...) })`
- `db/migrate.go:27`：`MigrateHandler.Exec(ctx, tx *gorm.DB)`，签名上就只收事务
- `db/backup.go:186-190`：导入链 `util.NewTransaction(gormDb).AddCommit(NewSchemaCheckHandler()).AddCommit(NewMigrateHandler())...`

也就是说：**加了外键之后，日后任何一次需要重建父表的迭代（改 `operation_log`/`file_meta`/`file_blob` 的列类型、删列），只要还从这三个入口走，就必然失败。** 纯加列不受影响（实测事务内给 `expense` 加 `note` 列通过，走的是 `ALTER TABLE ADD COLUMN`，不重建）。

这一条和你的出发点正好相反：外键是为了让日后迭代更安全，结果它给日后迭代埋的是另一个雷。要拆雷就得把建表从事务里挪出去，而这正是你上一轮刚理顺的那条链。

### 3.3 存量库有孤儿行就迁不动

干净数据的存量库，`AutoMigrate` 能就地补外键（走 `CreateConstraint` → `recreateTable`），事务内外都通过：

```
干净存量库，事务外 AutoMigrate 补外键 → <nil>，DDL 里 CONSTRAINT 出现，数据行数不变
干净存量库，事务内 AutoMigrate 补外键 → <nil>
```

但只要库里存在一条 `operation_id` 指不到审计行的 `expense`：

```
有孤儿行 → sqlite3: constraint failed: FOREIGN KEY constraint failed
（且 expense 表 DDL 原样不动，迁移整体回滚）
```

生产库按 `service/expense.go:54-58` 是同批生成 `operationId`/`fileId` 的，理论上没有孤儿。但 **B-2 导入数据库**允许外来库顶上来，那份库的干净程度不由本系统保证，导入链又恰好是「校验 → 建表 → 写审计」全在一个事务里（`db/backup.go:186-190`），届时是整笔导入失败。

### 3.4 测试要补父行

`grep` 出 7 处测试直接用 `util.GenId()` 造 `OperationId`/`FileId`，父行根本不存在；`db/file_blob_test.go:12` 的 `FileHash: "deadbeefcafebabe"`、`handler/file_meta_test.go:30-32` 的 `"hash-1"` 同理。加外键后这些用例会全红，得逐个补上对应的 `operation_log`/`file_meta`/`file_blob` 父行。

另外 `NewSchemaCheckHandler`（`db/backup.go:188`，本体还没写）将来要校验的「库结构合法」里，外键算不算结构的一部分、外来库缺外键要不要判不合法，也得一并定。

## 四、对症的替代：`BEFORE DELETE` 触发器

如果目标就是「本系统没有物理删除，别让日后迭代误删」，触发器比外键正对症。实测：

```sql
CREATE TRIGGER IF NOT EXISTS expense_no_delete BEFORE DELETE ON expense
BEGIN SELECT RAISE(ABORT, '明细表禁止物理删除'); END;
```

| 场景 | 结果 |
| ---- | ---- |
| `DELETE FROM expense WHERE id=1` | ✅ 拦住：`sqlite3: constraint failed: 明细表禁止物理删除`，行数不变 |
| `UPDATE expense SET ...`（软删就是 UPDATE） | ✅ 不受影响 |
| `AutoMigrate` | ✅ 不受影响 |
| 入库顺序 | ✅ 不受影响 |
| `DROP TABLE expense` | ❌ 拦不住（外键同样拦不住） |

对照 §二.3 和 §三，触发器**恰好补上了外键的空档**（护住 `expense` 自己），而且**避开了外键的全部四个代价**。四张表各挂一个即可，全覆盖 `doc/decisions/记账系统功能与模型.md` 前提 7「明细只有软删除…文件与审计不可删除」。

代价是 `AutoMigrate` 不管触发器，要在 `MigrateHandler.Exec` 里自己 `CREATE TRIGGER IF NOT EXISTS`；且 gormlite 的 `recreateTable` 会 `DROP` 旧表、触发器随之消失，所以建触发器这步必须每次跟在建表之后重跑——好在 `IF NOT EXISTS` 天然幂等。

## 六、实施结果

### 6.1 `db/migrate.go`：建表之后重挂四个防删触发器

`MigrateHandler.Exec` 收敛成一层壳，真身是新的包级 `migrate(ctx, tx)` = `AutoMigrate` + `migrateTrigger`。触发器表按 `migrateTriggers` 声明，四张表一一对应：

| 表 | 触发器名 | `RAISE(ABORT)` 文案 | 文档依据 |
| -- | -------- | ------------------- | -------- |
| `expense` | `expense_forbid_delete` | 明细只能软删除，禁止物理删除 | 前提 7、E-5 |
| `operation_log` | `operation_log_forbid_delete` | 审计不可删除，禁止物理删除 | 前提 7、C-2 |
| `file_meta` | `file_meta_forbid_delete` | 文件不可删除，禁止物理删除 | 前提 7、D-4 |
| `file_blob` | `file_blob_forbid_delete` | 文件不可删除，禁止物理删除 | 前提 7、D-4 |

一律 `CREATE TRIGGER IF NOT EXISTS`，因为 `AutoMigrate` 不管触发器，而 gormlite 改表走的是「建临时表 → 拷数据 → `DROP` 旧表 → 改名」，触发器会随旧表一起没掉——所以建表之后必须每次重挂，幂等由 `IF NOT EXISTS` 兜住。这条有专门的用例钉死（§七.2）。

### 6.2 `db/db.go`：建库路径改为复用 `migrate`

`create` 里原本内联了一份 `AutoMigrate`（旧 `../../../rdb`），跟 `MigrateHandler` 是两份实现。现在统一走 `migrate(ctx, tx)`：

```go
err = db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
    //建表与防删触发器统一走migrate，别在这儿再写一份AutoMigrate，否则新建的库会漏挂触发器
    err := migrate(ctx, tx)
    if err != nil {
        return err
    }
    err = tx.Create(&operationLog).Error
    ...
```

不这么收的话，**新建的库会一个触发器都没有**——`db/backup.go:186-190` 的导入链走 `MigrateHandler` 有触发器，`create` 走内联 `AutoMigrate` 没有，两条路会给出结构不同的库。

### 6.3 触发器上线当场拦到的违规：三个物理删接口

`TestOperationLogCrud` 立刻红了，报错是 `sqlite3: constraint failed: 审计不可删除，禁止物理删除`。查下来不是误报，是真漏洞：

| 位置 | 症状 |
| ---- | ---- |
| `db/operation_log.go` `DeleteOperationLog` + `NewOperationLogDeleteHandler` | `model.OperationLog` 没有 `gorm.DeletedAt`，`util.DeleteHandler` 的 `tx.Delete(...)` 发出去的是**真 `DELETE`** |
| `db/file_meta.go` `DeleteFileMeta` + `NewFileMetaDeleteHandler` | 同上 |
| `db/file_blob.go` `DeleteFileBlob` + `NewFileBlobDeleteHandler` | 同上 |

三个都与前提 7「文件与审计不可删除」、C-2、D-4「文件只留存不删除，无孤儿问题」直接矛盾，且**生产代码里一个调用点都没有**，唯一的使用者是 `db/operation_log_test.go:62` 那段删除断言。按你的选择全删：六个函数（三个 `DeleteXxx` + 三个 `NewXxxDeleteHandler`）连同那段断言一并移除。

`db/expense.go` 的 `DeleteExpense` **保留**：`model.Expense` 有 `gorm.DeletedAt`，`NewExpenseDeleteHandler` 又强制把 `inquiry.Deleted` 压成 `model.DeletedNo`（不加 `Unscoped()`），发出去的是 `UPDATE`，正是 E-5 要的软删。

> 顺带记一个还没拆的雷：`db/expense.go:83-87` 里 `Deleted` 取 `DeletedAll`/`DeletedOnly` 时会挂 `Unscoped()`，这个 inquiry 一旦被喂给 `util.DeleteHandler`，`Unscoped()` + `Delete` 就是物理删。目前 `NewExpenseDeleteHandler` 挡住了，`expense_forbid_delete` 是第二道。

### 7.1 与基线逐条对齐

基线 = 同一份带桩副本，只把 `db/migrate.go`、`db/db.go` 换回 `HEAD`。


## 二、四个函数的成品形状

统一骨架照 `db/db.go:35 Create` / `:59 create`：**导出层只做三件事**（取 `config` 里的路径、`tool.GetToken` 取口令、上锁），**小写函数先逐个校参、再平铺干活**，错误一律「`logrus.Error` + `errors.Errorf` 同文案」。

### 2.1 `Export` / `export`（`db/backup.go:104`、`:120`）

锁沿用 `RLock`（与 `Open`、`NewTransaction` 同级：读锁挡的是库文件被替换，不是行级并发）。校参三条：库文件在不在、口令空不空、`writer` 空不空。主流程：

```
open(原库) → 写「数据库导出」审计 → 关连接 → genBackupPath → backup(原库→备份, 同口令) → OpenReadFile → io.Copy(writer)
```

两个要点：

- **审计先写、再备份**（`db/backup.go:135` 注释）。顺序不能反：`backup` 是对库文件做整库快照，审计写在它后面就进不了导出的那份文件。这与换 handler 之前的行为一致（原来 `handlers` 也是在 `backup` 之前跑的）。
- **写完审计显式 `CloseDb`，不用 `defer`**（`db/backup.go:151`）。`backup` 内部会对同一个库文件另开一条连接，先关掉这条更干净；`defer` 会让它一直挂到 `export` 返回。

### 2.2 `Import` / `import_`（`db/backup.go:184`、`:200`）

`Lock`（整库覆盖）。校参三条后，主流程：

```
checkToken(原库,本次口令)          ← 拦越权：拿到后端口令也顶不掉别人的库
  → genBackupPath → WriteReader2File(上传流→副本)
  → open(副本,本次口令)             ← 上传的库自己必须能用这把口令打开
  → 一个事务里：结构校验 → migrate → 写「数据库导入」审计
  → 关连接 → backup(原库→originPath) ← 覆盖前留底
  → replace(副本, 口令, 原库)
```

结构校验平铺在事务里（`db/backup.go:243-251`），就是照 `fb6bf77` 的 `checkSchema` 逐张查 `migrateModels[i].TableName()`：

```go
migrator := tx.Migrator()
for i := range migrateModels {
    table := migrateModels[i].TableName()
    if migrator.HasTable(table) {
        continue
    }
    ...
    return errors.Errorf("导入数据库，缺表: %s", table)
}
```

**顺序仍然不能调**：校验必须排在 `migrate` 前面，否则建表先把缺的表补齐，外来库就混过去了（`TestImportWrongSchema` 钉的就是这条）。口径仍是「4 张表都在」，列的差异交给 `migrate` 补（B-3 要求旧版本导出的库能导回来），代码里留了注释。按对话1 §八.2 的建议，**触发器缺不缺不算结构不合法**——`migrate` 排在后面会补上，触发器不承载数据。

失败清理沿用原样：每个失败分支都 `util.RemoveFile(ctx, backupPath)`，所以被拒的导入不会在 `resource/db_backup` 留残骸（`TestImportWrongSchema`/`TestImportIllegal` 各有一条断言钉着）。`originPath` 是留底，成功后**故意保留**（`TestImportBackupOrigin` 断言目录里正好剩它这一份）。

多一步显式 `CloseDb`（`db/backup.go:271`）：副本马上要被 `os.Rename` 顶上去，连接不能还攥着旧路径。原来是 `defer`，关在 `replace` 之后。

### 2.3 `ChangeToken` / `changeToken`（`../../../rdb`、`:316`）

`Lock`。校参三条：库文件、旧口令、新口令（原来「新口令为空」是掉进 `backup` 的 `dstToken == ""` 才报的，现在在门口就报，文案是「更换口令，新口令为空」）。主流程：

```
genBackupPath → backup(原库,旧口令 → 副本,新口令)   ← 换口令 = 用新口令重新加密出一份
  → open(副本,新口令) → 写「更换口令」审计 → 关连接
  → replace(副本, 新口令, 原库)
```

审计落在**换好口令的副本**里，跟着副本一起顶上去——这正是原来 `handlers` 参数的语义（`TestChangeTokenHandlerFail` 的注释写的就是它），内联之后语义不变。任一步失败都 `RemoveFile(backupPath)` 且不走 `replace`，原库一个字节不动。

## 一、先把两个 API 的语义钉死

| API | 关的是什么 | 返回 | 幂等 |
| --- | ---------- | ---- | ---- |
| `util.CloseDb(ctx, gormDb)` | `gormDb.DB()` 取出的 `*sql.DB` | error | 幂等（`database/sql.DB.Close` 自带 `if db.closed { return nil }`） |
| `util.CloseIo(ctx, closer...)` | 任意 `io.Closer`，`nil` 自动跳过 | 无 | 取决于被关对象 |

关键一条：**`CloseDb(gormDb)` 和 `CloseIo(gormDb.DB())` 是同一件事**。探针实证（`db/backup.go` 那段的三个对象）：

```

conn.Close(): err=<nil>
第1次 sqlDb.Close(): err=<nil>
第2次 CloseDb(gormDb) 关的是同一个 *sql.DB: err=<nil>
```

而 `conn` 是**另一个对象**，且 `sqlDb.Close()` 关不掉它：

```
不关conn直接关DB: err=<nil>
关DB之后 sqlDb.Stats(): {OpenConnections:1 InUse:1 Idle:0}   ← 底层sqlite句柄还挂着
此时再关conn: err=<nil>
归还conn之后 sqlDb.Stats(): {OpenConnections:0 InUse:0 Idle:0}
```

`database/sql` 的规矩：`DB.Close()` 只关空闲连接并置位「已关闭」，**被 `Conn()` 借出去的连接要等归还时才真关**。所以你问的三行里，`conn` 那行是必需的，`sqlDb` 那行是多余的。

## 二、使用错的：`db/backup.go` 重复关同一个 `*sql.DB`

原文（`backup`，你手工调过的那个函数）：

```go
gormDb, err := open(ctx, srcPath, srcToken)
defer util.CloseDb(ctx, gormDb)   // ← 关 gormDb.DB()

sqlDb, err := gormDb.DB()
defer util.CloseIo(ctx, sqlDb)    // ← 关的是同一个对象
```

按 §一 的实证，这两行落到同一个 `*sql.DB` 上。`DB.Close()` 幂等，第二次直接返回 nil，所以**不出错、也不泄漏**，但「一个资源两个 owner」这件事本身是错的：以后谁改了其中一行的语义，另一行会静默地跟着变。

**改法**：删掉 `defer util.CloseIo(ctx, sqlDb)`，保留 `CloseDb(gormDb)`——全仓库另外 8 处 gorm 连接都是 `CloseDb` 收的，而且 `open` 交出来的本来就是 `gormDb`，`sqlDb` 只是为了 `sqlDb.Conn(ctx)` 顺手取的中间量。`sqlDb` 变量本身还要用，只删 defer 那一行。

> 这是本轮唯一一次动 `backup`——对话3 那条「三个函数不要改动」的约束在这里让位于你这轮点名要查的东西，改动是 1 行删除。

**同时给 `conn` 那行补了一句注释**，免得下次读到「上面已经关了 gormDb」就把它跟着一起删：

```go
//占出来的连接不归还，上面那句CloseDb关不掉它，库文件句柄会一直挂着
defer util.CloseIo(ctx, conn)
```

**验证没关漏**：20 轮 `Export` + `backup` 前后数 `/proc/self/fd`：

```
20轮 export+backup 前后 fd 数: before=10 after=9 差值=-1
```

没有增长。

## 三、关的时机不对：`db/db.go create` 先删文件后关连接

`create` 的事务失败分支（`db/db.go:106-110`）：

```go
db, err := open(ctx, dbPath, token)
...
defer util.CloseDb(ctx, db)      // ← 函数返回时才关
...
if err != nil {
    util.RemoveFile(ctx, dbPath) // ← 连接还开着就把库文件删了
    return err
}
```

等于把库文件从还开着的句柄底下抽走。Linux 上 unlink 一个已打开的文件是合法的，defer 再去关一个已经没有目录项的 fd 也无害，**所以现在不报错**；但 Windows 上 `os.Remove` 对已打开文件直接失败，`db/db_test.go:238 TestCreateRollback` 钉的「建库失败时应把已占位的库文件清掉」在那边就会破。

而且这与你自己在 `backup.go` 里立的规矩不一致：`export`/`import_`/`changeToken` 三处都是**先显式 `CloseDb` 再碰文件**（`db/backup.go:134`、`:247`、`:333`），只有 `create` 反着来。

**改法**（+1 行，删文件之前先断连接，defer 那次二次关闭幂等）：

```go
if err != nil {
    util.CloseDb(ctx, db) //先断连接再删文件，别把库文件从还开着的句柄底下抽走
    util.RemoveFile(ctx, dbPath)
    return err
}
```

> 这里的「二次关闭」和 §二 那处不是一回事：这是错误分支提前关 + defer 兜底，Go 里的常规写法；§二 是两个 API 各自声称拥有同一个对象。

## 六、记一笔、本轮不动

**`DbTransaction.Close` 不幂等**（`db/db.go:217-220`）：

```go
func (this *DbTransaction) Close(ctx context.Context) error {
	defer dbLock.RUnlock()
	return this.Transaction.Close(ctx)
}
```

`CloseDb` 自己幂等，`dbLock.RUnlock()` 不幂等——同一个 `DbTransaction` 被 `Close` 两次（比如调用方写了 `defer object.Close(ctx)` 又在中途手动关了一次），第二次会 `panic: sync: RUnlock of unlocked RWMutex`，而且是在读锁计数上打洞，后面所有写锁都别想拿到。目前所有调用点都只关一次，没有真实触发点，所以只记不动；真要收口就在结构体里加个 `closed bool`。
