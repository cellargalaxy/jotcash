## 步骤

- 背景调研
    - 研读prompt中提及的文档/代码/配置
    - 对齐背景，梳理核心逻辑/组件依赖/改动点
- 需求分析与方案
    - 提取核心目标/交付物/范围边界/关键约束
    - 制定方案：最小改动/复用优先/任务拆解；说明模块职责/输入输出/关键逻辑/异常处理
    - 评估对现有链路/性能/兼容性/下游的副作用
    - 写入`answer.md`：依据来源/方案取舍/实施步骤/验证说明
- 实施
    - 按方案执行，命名/注释/文案与项目风格一致
    - 中文注释与日志，处理边界与异常分支
    - 同步更新类型定义/关联配置/文档
    - 复杂任务使用主agent调度子agent的方式实施
- 验证与交付
    - 执行测试/逻辑校验/数据校验/文档校对
    - 重读`prompt.md`，检查与交付结果是否一致
    - 核心产出同步至`answer.md`
    - 清理临时文件/调试代码/冗余产物，但无须提交变更

## 约束

- 依据：结论只能来自文档/代码/表结构/日志/SQL等明确来源；严厉禁止猜测业务逻辑/捏造接口字段，不能断言的内容都询问用户
- 引用：关键事实引用到具体章节/字段名/代码路径或枚举值，禁止笼统援引
- 信息不足：区分「已确认/待确认/不可推断」并标注，不得脑补
- 历史资料：历史Prompt/answer/旧方案仅供参考，必须与代码交叉核对后才能使用
- 冲突：资料冲突时列出冲突点与采用依据，不得默默取一方
- 风格：命名/注释语言/代码组织与项目既有风格一致，优先复用现有实现

### 对话2

+ 代码包层级
    + 系统与外部对接的包，一般放在项目根部，越外部越靠近项目根部
    + 一般而言，越靠近系统边缘的代码包，越同样，越少业务逻辑
    + [config](../../../config)
    + [db](../../../db)
    + [exchange_rate](../../../exchange_rate)
    + [handler](../../../handler)
    + [model](../../../model)
    + [tool](../../../tool)
    + [db](../../../db)
    + [handler](../../../handler)
+ tool与util的区别
    + util在go_common，都是无业务逻辑的，一般性的同样函数
    + 如果需要包含一些业务规则，或者特殊一点的逻辑的工具类函数，就放在tool里
+ db由于没有业务逻辑，因此不允许上层代码直接调用根部的db
    + service/db包含业务逻辑与参数校验，上层代码与业务代码，只能调用service/db
+ for _, one := range 这不对
    + 例如`for _, one := range inquiry.OperationType {`
    + 应该是`for _, operationType := range inquiry.OperationType {`才对
    + 这样能直接就知道是什么变量
+ 文件与包内组织顺序
    + 其实并没有什么规范
+ 导出包装 + 非导出实现 分开实现，作为一对代码，之间不留空行视觉上是一个单元，这是好规范
+ 非导出函数可被测试直接构造任意环境调用，导出函数则要可靠安全
+ 函数的职责需要单一且明确
    + 创建归创建，打开归打开
+ 函数边界
    + 函数的功能与逻辑，在不少情况下，都有正向/反向或者左链路/右链路，之类的哲学概念上的一对
    + 这些一对的函数，内部实现会相似或者镜像
    + 如果一个函数边界的设定，能兼容一对多种多个有镜像关系的函数，才能说明函数边界的设计是有一定合理性的
    + 例如[db.go](../../../db/db.go)，Create与Open是一对的，Open与Close是一对的，getToken与GenToken是一对的
    + 避免过度拆分，适当平铺能提高代码可读性
    + 避免职责焊死，优先使用组合，代码更加解耦和灵活
+ 5.1 唯一句式：都认同
+ 日志级别
    + Error:代码逻辑无法兜底无法处理的错误情况
    + Warn：虽然奇怪，或者需要特别提醒，但是有相应的兜底或者处理逻辑
    + Info：预期之中的情况
+ 错误的传递
    + 只有接收到的err是从业务逻辑外部获得的才进行封装，否则直接传递
    + 例如从数据库/外部HTTP接口获得的err
+ 注释
    + 注释严禁『引用文档条款』只留『不看就会改错』，不写过程注释
+ 你需要重新梳理，输出完整的规范
    + **你输出的规范本身也需要准时本规范**
    + 规范的标准需要更加通用抽象，不要只针对本代码仓库来说
    + 因此不要列代码，不要『引用文档条款』
