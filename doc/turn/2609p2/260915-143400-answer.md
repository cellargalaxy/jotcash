+	//库没就绪就地建出来，上层只管拿事务做业务读写，不感知建库建表

- `Create` 的**双检写锁骨架、0 字节残骸判定（`info.Size() > 0`）、`create` 的平铺实现一个字没动**——`260915-102207-answer.md` 对话3 §1 那张「`create` 卡 `Size()>0` / `open` 只卡存在」的对照表继续成立。

### 3.2 13 处 DAO 包装函数：`Transaction(ctx, handler)` → `NewTransaction`

统一形状（以 `db/expense.go:152` 为例，其余 12 处逐字同构）：

```go
func InsertExpense(ctx context.Context, object ...*model.Expense) (int64, error) {
	transaction, err := NewTransaction(ctx)
	if err != nil {
		return 0, err
	}
	defer transaction.Close(ctx)

	handler := NewExpenseInsertHandler(object...)
	err = transaction.AddCommit(handler).Exec(ctx)
	if err != nil {
		return 0, err
	}
	return handler.Count, nil
}
```

**没有再抽一个 `execTransaction(ctx, handlers...)` 小函数**：那等于换个名字把删掉的 `Transaction` 捡回来，与你在对话7 里选甲弃乙的结论冲突。`defer transaction.Close(ctx)` 是这套形状里唯一的解锁点，13 处全部带上。

### 3.3 `service/db/expense.go`：2 处多 handler 事务（范围外，为了让仓库能 build）

`InsertExpense` / `DeleteExpense` 是 `db.Transaction` 仅剩的两个外部调用点，不改的话 `go build ./...` 一直红。改法与 §3.2 同构，多 handler 直接进同一个 `AddCommit`：

```go
	transaction, err := db.NewTransaction(ctx)
	if err != nil {
		return err
	}
	defer transaction.Close(ctx)
	...
	return transaction.AddCommit(fileBlobHandler, fileMetaHandler, expenseHandler, operationLogHandler).Exec(ctx)
```

**这是本轮唯一越出 config/db/model/tool 四包的改动**，共 16 行，事务语义（四个 handler 同生共死）不变。

### 3.4 6 处测试调用点

## 五、读代码读出来的问题（**只报不改**，等你定）

### 5.1 `Open` 的读锁在交出连接的那一刻就放掉了 —— 锁作用域错位

`db/db.go:114`：

```go
dbLock.RLock()
defer dbLock.RUnlock()      // ← 函数 return 就放，连接刚交出去
db, err := open(ctx, dbPath, token)
return db, nil              // ← 危险窗口从这里才开始
```

危险窗口是「连接活着的那一整段」，而这把锁只罩住了开库那几微秒。`DbTransaction`（`db/db.go:216`）当初就是为了把解锁点挪到 `Close` 才引入的，`Open` 还是老形状。

- **现在不出事**的原因：唯一的生产调用方是 `CheckToken`（`db/db.go:171`），下一行就 `util.CloseDb`，窗口以微秒计；`handler/ping.go` → `service/db.CheckToken` 走的就是它。
- **两条自洽的收尾**（对话6 §3 列过，仍未选）：① 干脆把这两行删掉——它现在提供的不是保护而是「看起来有保护」；② 让 `Open` 也返回一个带解锁的 closer，与 `DbTransaction` 对齐。
- 不动的理由：`Open` 是公开 API，`TestOpenWithoutDbFile`/`TestPageLimit`/`TestMigrateTrigger*` 都在用，改签名是设计决定不是修 bug。

### 5.2 同一协程里嵌套 `NewTransaction` 会死锁 —— 现在没人踩，但是个地雷

`sync.RWMutex` 的文档规则：**读锁持有期间若有写者在等，新的读锁必须排在写者后面**。所以

```go
transaction, _ := db.NewTransaction(ctx)   // 持读锁
defer transaction.Close(ctx)
db.SelectExpense(ctx, inquiry)             // ← 内部又要 RLock，此时若 Import 正在等写锁 → 死锁
```

**全仓库当前没有这种写法**（`service/db/expense.go` 的两个事务、`service/expense.go` 的三个入口都是平的，已逐个核对），所以不是现存 bug。但方案甲把「持锁」这件事藏进了 `NewTransaction`，调用方看不见，以后 `service` 层想在一个事务里顺手查一把就会撞上。建议在 `NewTransaction` 的注释里写一句「同一协程内不得嵌套」。

### 5.3 `import_` 失败时会在备份目录留下半个 `originPath`

`db/backup.go:257`：

```go
err = backup(ctx, dbPath, token, originPath, token)
if err != nil {
	util.RemoveFile(ctx, backupPath)   // ← 只清了上传的那份，originPath 没清
	return err
}
```

同一个文件里的 `changeToken`（`db/backup.go:308`）碰到 `backup` 失败是清自己 dst 的，两个兄弟函数口径不一致。**触发条件**：`backup` 在真正写 dst 的中途失败（磁盘满 / IO 错），实际概率很低，也因此 `TestImportWrongSchema`/`TestImportIllegal` 那两条「不应留下临时文件」断言碰不到它——它们在更早的守卫就返回了。修法是一行 `util.RemoveFile(ctx, originPath)`。没改是因为 `import_` 是你对话3/对话4 手写并 review 过的函数。

### 5.4 建库日志现在打的是「用户自带的口令」，不再是「系统生成的口令」

`db/db.go:106`：

```go
logrus...WithFields(logrus.Fields{"dbPath": ..., "serverToken": ..., "clientToken": token}).Info("创建数据库，口令")
```

`init()` + `GenToken` 时代，这行是**用户唯一能拿到随机口令的渠道**，非打不可。本轮口令来源换成 `tool.GetToken` 之后，`clientToken` 是请求自己带来的，用户本来就知道——这行等于把一个用户机密原样落进 `log/` 里的日志文件。`serverToken` 同理（它来自 `resource/jotcash.yaml`）。

**没动**，因为 `db/db_test.go:93`、`:96`、`:145` 三条断言正钉着它，是你重构之后写的，属于明确意图。要收的话是「保留 `serverToken`、去掉 `clientToken`」还是「整行降级到 Debug」，你定。

### 5.5 金额区间筛选与金额排序都过一遍 float64

`db/expense.go:69`：

```go
tx = tx.Where("cast(expense_amount as real) >= ?", this.ExpenseAmountMin.InexactFloat64())
```

列是 `varchar(32)` 存 `decimal`，两边都被压成 float64（约 15~16 位有效数字）。`db/expense_test.go:20` 那个 `-1234567890123456.7890` 已经在临界上，边界值上的 `>=` / `<=` 可能多一条少一条。排序同理（`expense_amount asc` → `cast(... as real)`，已有注释说明）。这是「金额存文本」这个设计的既定代价，不是实现 bug；真要精确只能改成定长补零的字符串比较或者拆整数分列，代价是迁移存量数据。**列在这里备案。**

### 5.6 扫过但确认没问题的几处

- **连接释放**：生产代码 18 个 close 点全部复核，与 `260915-130316-answer.md` 对话5 的结论一致——`backup` 里 `defer CloseDb(gormDb)` 先注册、`defer CloseIo(conn)` 后注册，LIFO 下先还连接再关 DB，顺序是对的；`create`/`export`/`import_`/`changeToken` 四处都是「先显式 `CloseDb` 再碰文件」。**新增的 13 个包装函数每一个都带 `defer transaction.Close(ctx)`**，没有漏网。
- **`clearBackup` 的 `sort.Strings`**：备份文件名是 `fmt.Sprintf("%d.db", util.GenId())`，`util.GenId` 走 `GenIdByTime`，恒为 16 位定宽数字，字典序与数值序一致，按名字排 = 按时间排。
- **`migrate` 的触发器 SQL 用 `fmt.Sprintf` 拼串**：`Table`/`Reason` 都是 `migrateTriggers` 里的编译期常量，没有注入面。
- **`DeleteHandler` 会把 `Order` 也套到 DELETE 上**：gorm 构建 DELETE 时只取 `Delete/From/Where` 三个 clause，`ORDER BY` 被丢弃，不影响语义；而非法排序仍然会在 `Order` 这一步报错，`TestExpenseSort` 最后三条断言钉的就是这个。
- **`model.Claims.String()` / `Config.String()` / `ChangeTokenReq.String()`** 全是值接收者，抹字段抹在副本上，不会污染原对象——新增用例已覆盖。
