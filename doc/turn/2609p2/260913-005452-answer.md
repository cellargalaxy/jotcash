## 一、背景调研

- **需求文档**：`doc/decisions/记账系统功能与模型.md` §四「逐实体属性（4 实体 38 项）」是唯一权威的字段清单：`Expense` 21 项、`AuditLog` 8 项、`FileMeta` 7 项、`FileBlob` 2 项；§8.4 给出 `AuditLog.操作类型` 的 8 类枚举；`FileMeta.用途`、`AuditLog.操作结果` 的枚举取值散见于 §四.2/§四.3 的属性说明列。
- **现状代码**：`jotcash` 仓库此前只有 `go.mod`（`module github.com/cellargalaxy/jotcash`，`go 1.27.0`），无任何 `.go` 源码，本轮是该仓库第一批代码。
- **代码风格参考**：`survive_monitor/model/config.go` 确立了本作者的既有约定——方法接收者用 `this`、提供 `String()` 做序列化输出、struct 字段用 `json` 标签；其依赖的 `go_common/model/gorm.go` 额外给出了 `gorm` 标签的写法示例（`gorm:"id;auto_increment;primary_key"`）。
- **关键发现（影响实施方案，记录在此避免重复踩坑）**：
  1. `go_common/model/gorm.go` 里的 `gorm:"id;auto_increment;primary_key"` 是 gorm v1 时代的写法。用 gorm v2（`gorm.io/gorm v1.31.2`，本仓库实际拉取版本）的 `schema.ParseTagSetting` 逐字核对（`gorm.io/gorm@v1.31.2/schema/field.go:126-127`）：`PrimaryKey` 同时识别 `PRIMARYKEY` 与 `PRIMARY_KEY` 两种写法（历史兼容），但 `AutoIncrement` **只识别 `AUTOINCREMENT`，不识别 `AUTO_INCREMENT`**。也就是说若照抄这段旧标签，`auto_increment` 这个 flag 在 gorm v2 下会被静默忽略。因此本次新写的标签一律使用 gorm v2 规范写法 `primaryKey;autoIncrement`（无下划线），不沿用 `go_common` 里那段旧标签的具体写法，只沿用其「`json` + `gorm` 双标签」的风格。已用 `gorm.io/gorm@v1.31.2` 的 `schema.Parse` 实测验证，见「四、验证」。
  2. `github.com/bojanz/currency`（`v1.5.0`）的 `Amount` 类型虽然实现了 `driver.Valuer`/`sql.Scanner`，但其官方 wiki（Database integration notes）明确写明该实现是为 **PostgreSQL 组合类型**设计的；到了 SQLite（本项目按 §一 前提1/2 使用 `github.com/ncruces/go-sqlite3` 整库加密）官方给出的建议是「SQLite 不支持组合类型，需拆成两列存储」。这一发现直接决定了下面的字段拆分方案（见「二、2.3」）。

## 二、需求分析与方案

### 2.1 目标与交付物

- 交付物：`model` 包，含 `Expense`/`AuditLog`/`FileMeta`/`FileBlob` 四个 struct，字段与数量与需求文档 §四 一一对应（21/8/7/2 = 38 项）。
- 范围边界：**不做**任何校验/派生计算/枚举匹配等业务逻辑；**不做** PO/BO/DTO 分层——全部代码层级（接口层、服务层、持久化层）复用同一份 struct，这是本次任务的硬约束，也是与常见分层实践的主动偏离，原因是需求 prompt 明确要求「全部代码层级都使用同一个 struct」。

### 2.2 关键约束落地方式

| 约束 | 落地方式 |
| ---- | -------- |
| 不划分 PO/BO | 每个实体只有一个 struct，定义在 `model` 包，无 `xxxPO`/`xxxDTO` 变体 |
| 不含业务逻辑，`String()` 类允许 | 每个 struct 仅有一个 `String()` 方法（`encoding/json` 序列化后转字符串），不含任何分支判断/计算/校验 |
| 字段标签需要 `json`/`gorm` 等 | 每个字段都带 `json:"xxx"` 与 `gorm:"column:xxx;..."` 双标签；`FileBlob.Content` 额外用 `json:"-"` 排除出 JSON（原始字节，避免日志/接口响应里出现整段二进制，是序列化层面的技术决策，不构成业务逻辑） |
| 金额用 `shopspring/decimal` | `Expense.ExpenseAmount`/`ExchangeRate`/`AccountingAmount` 三个金额/汇率字段均为 `decimal.Decimal` |
| 货币用 `bojanz/currency` | 见下方 2.3，本轮结论是**该库不直接出现在 `model` 层**，留给后续业务/校验层使用 |

### 2.3 取舍点：金额与币种字段如何拆分（已与你确认，采纳方案A）

需求文档 §四.1 把「支出金额」与「支出币种」列为两个独立属性（「记账金额」「记账币种」同理），但 `bojanz/currency` 的设计意图是把金额与币种绑定成一个 `Amount` 值对象。这里存在两种可选实现，已通过 `AskUserQuestion` 向你核实，**采纳「拆成两个字段」方案**：

- `ExpenseAmount decimal.Decimal` + `ExpenseCurrency string`（`AccountingAmount`/`AccountingCurrency` 同理）——两列独立存储。
- 理由（你确认的依据）：`bojanz/currency` 官方 wiki 明确 SQLite 下 `Amount.Value()/Scan()` 的组合列写法不适用，必须拆成两列；且需求文档 F-1「库中只存币种代码」、E-7「金额区间、支出币种」独立筛选，都要求币种与金额是可独立做 SQL 查询的两列，若合并成一个 `currency.Amount` 字段会把金额序列化成不透明字符串（如 `"(123.45,CNY)"`），金额区间查询在 SQL 层无法正确做数值比较。
- 被否决的方案（合并成单一 `currency.Amount` 字段）：写法更贴合该库设计意图，但会与已确认的 E-7 查询需求冲突，故不采纳。
- 连带结论：`bojanz/currency` 本轮不出现在 `model` 包的 import 中，`go.mod` 也不引入该依赖（避免出现未被使用的依赖）；等后续实现币种校验/格式化/汇率相关的业务层时再引入并使用该库，届时 `model` 层的 `ExpenseCurrency`/`AccountingCurrency` 仍是 `string`（与 F-1「库中只存币种代码」的口径一致），不需要回头改动 `model`。

### 2.4 其余技术默认值（未被 prompt 明确规定，按既有风格/文档措辞给出的默认选择，均为可逆的技术细节，非业务判断）

| ---- | ---- | ---- |

| 金额/汇率列的 `gorm:"type:..."` | 金额 `decimal(20,4)`，汇率 `decimal(20,8)` | 需求文档明确留给技术轮次决定精度，这里给出一个不过度设计的默认值，后续可在技术方案轮次调整而不影响 struct 结构 |

## 二、Id 类型改为 int64、改用 go_common.GenId 生成

- `Expense.Id`/`AuditLog.Id`/`FileMeta.Id`，以及全部引用它们的外键字段（`Expense.AuditId`/`Expense.FileId`/`FileMeta.AuditId`/`AuditLog.ObjectId`）统一从 `int` 改为 **`int64`**。
- 依据你给的优先级（go_common 优先 → 其次高星第三方库），核对了 `github.com/cellargalaxy/go_common/util/gen.go`：`GenId() int64`（第38行）用「进程内加锁 + 微秒时间戳」生成一个最长18位、按时间单调递增的整数，配套 `ParseId`/`ParseStrId` 可反解回时间。返回类型正是 `int64`，这也是本轮把 Id 定为 `int64` 而不是更大的字符串型 ID（如 UUID）的直接依据。
- **`model` 包本身不调用 `GenId()`**：生成 ID 是一次函数调用（依赖当前时间与进程内锁状态），按对话1 已确认的「`model` 不含业务逻辑」的约束，这类调用应发生在后续新增/写入的服务层，而不是写死在 struct 定义里。本轮只做了两件与之配套的结构性改动：
  1. 字段类型改为 `int64`，与 `GenId()` 的返回类型对齐；
  2. gorm 主键标签从 `primaryKey;autoIncrement` 去掉了 `autoIncrement`（`FileMeta`/`AuditLog`/`Expense` 三处），因为 ID 将由应用层在插入前赋值，不再依赖数据库自增；每个 `Id` 字段旁补充了中文注释说明取值来源，供后续实现新增逻辑的人直接抄依据，不用回头翻决策文档。
- `go.mod` 新增直接依赖 `github.com/cellargalaxy/go_common`（用于单测里实际调用 `util.GenId()` 生成测试数据，见下文「五」）。该模块自身的 `go.mod` 直接依赖较重（gin、excelize、mongo-driver 等，`go mod tidy` 已如实展开到 `go.sum`），但 `model` 包只 import 了 `go_common/util` 这一个子包，实际编译进制品的代码只includes `util` 包自身的依赖（`context`/`sync`/`time`/`github.com/pkg/errors`/`github.com/sirupsen/logrus`），其余重依赖只是 go.sum 里的校验和记录，不会被链接进最终产物。

## 三、`AuditLog.OperatedAt` → `CreatedAt`

**你的判断成立，已改**。核对 `gorm.io/gorm@v1.31.2` 源码（非猜测）：

- `schema/field.go:292`：`field.Name == "CreatedAt" && (field.DataType == Time || ...)` → 命中则 `AutoCreateTime` 生效，gorm 在 `Create` 时自动写入当前时间；
- `schema/field.go:304`：同理 `field.Name == "UpdatedAt"` 触发 `AutoUpdateTime`；
- `soft_delete.go:15`：`type DeletedAt sql.NullTime`，配合字段名/类型被 gorm 识别为软删除标记。

**结论：gorm 的“约定”确切地说是按 Go 字段名（`CreatedAt`/`UpdatedAt`）+ `DeletedAt` 类型识别，不是按列名**——列名可以通过 `gorm:"column:xxx"` 另起，不影响这个自动填充/软删除行为是否生效。因此把 `AuditLog.OperatedAt time.Time`（需要手工赋值）改成 `CreatedAt time.Time`（gorm 自动填充，写库时不用再显式设置），语义上两者等价（审计记录只写入不更新，创建时点即操作时点，§C-2/前提7/前提8），但更规范、也少一处手工赋值的遗漏风险。已用 `TestAuditLogRoundTrip` 验证：`Create` 后 `origin.CreatedAt` 被自动填充为非零值。

`AuditLog` 因此**只有 `CreatedAt` 一个时间字段**，不设 `UpdatedAt`/`DeletedAt`——因为审计记录本身不可更新、不可删除（前提7/8、C-2），加这两个字段没有语义基础。

### 6.2 「有些字段没有标明数据库字段类型，有影响吗」——实测结论

用 `PRAGMA table_info` 把 `AutoMigrate` 建出来的 4 张表全部列的实际类型 dump 出来核对（诊断脚本验证后已删除，不是仓库产物），结论分两部分：

**没有影响的部分**：纯 `string`/`int64` 字段即使没写 `gorm:"type:..."`，gormlite 驱动的默认规则（`sqlite.go:183` `DataTypeOf`）会按 Go 类型分别落到 `TEXT`/`INTEGER`——这两种 SQLite 类型亲和（type affinity）都不会做隐式数值转换，原样存取，经测试验证无精度/取值问题。这类字段本轮**不需要**补类型标注（`BankName`/`Counterparty`/`Remark`/`ExpenseType`/`FileName`/`Summary`/`AuditId`/`FileId`/`ObjectId`/`FileSize` 等）。

**发现了真实影响、已修复**：本轮把 Id 相关字段改造过程中，我复查了对话1 里给金额/汇率字段写的 `gorm:"type:decimal(20,4)"`/`type:decimal(20,8)`，用同一套 `PRAGMA table_info` + 实测发现了一个问题——**这个类型声明本身就是错的**：

- SQLite 按声明类型的字符串做「类型亲和」判定（官方规则：含 `INT`→INTEGER，含 `CHAR`/`CLOB`/`TEXT`→TEXT，含 `BLOB`或为空→BLOB，含 `REAL`/`FLOA`/`DOUB`→REAL，否则→NUMERIC）。`decimal(20,4)`/`numeric(20,4)` 都不命中前四条规则，落入第五条 **NUMERIC 亲和**。
- NUMERIC 亲和意味着 SQLite 会尝试把插入的文本自动转换成整数或浮点数存储。`decimal.Decimal` 的 `Value()` 输出是十进制数字字符串，看起来像合法数字，于是被 SQLite 转成了 **float64** 存储。
- 实测复现：写入 `"-1234567890123456.7890"`，读回后变成了 `-1234567890123456.8`——**小数部分全部精度丢失**（这个量级下 float64 只剩约15-17位有效数字，17位整数已经把小数部分挤没了）。`TestExpenseRoundTrip` 一开始就是因为这个断言失败才发现的。
- **修复**：把三个 `decimal.Decimal` 字段（`ExpenseAmount`/`ExchangeRate`/`AccountingAmount`）的 gorm 类型统一改成 `varchar(32)`（含 `CHAR` → TEXT 亲和，原样存字符串，精度不丢）。改完后 `TestExpenseRoundTrip` 通过。已在 `expense.go` 的 `Expense` struct 注释里把这条根因和实测结论写清楚，避免以后又有人「好心」把它改回 `decimal(20,4)`。

**结论对齐你的问题**：没写类型的字段本身没问题；反而是本轮写了一个「看起来很合理但在 SQLite 下是错的」类型声明，已经在这一轮里找到并修复，同时补上了能在未来重构中持续守住这个结论的回归测试。

## 二、需求分析与方案取舍

### 2.1 `model`：只补结构体本身缺的东西，不加任何行为

- **表名**：`expense` / `operation_log` / `file_meta` / `file_blob`，单数蛇形，与 `mmm/db/db.go:31` 的 `schema.NamingStrategy{SingularTable: true}` 口径一致；接收者互换的问题一并修正。
- **gorm 标签**：对话1 的诉求原文是「字段标签需要有 json/grom 等」，你手改版只剩 json 标签，本轮补回。取舍是**每一个标签都要有理由**，不铺无用信息：
  - 全字段 `column:xxx`——`db` 层的 `Where` 是手写 SQL 片段（`"file_hash in (?)"`），列名显式写死才能一眼核对，不依赖命名策略。
  - `Id`：`primaryKey;autoIncrement:false`。**必须显式关自增**：gorm 对「单个整型主键且没写 autoIncrement 标签」会自动置 `AutoIncrement=true`，而 gormlite 的 `DataTypeOf`（`sqlite.go:187-194`）看到 `AutoIncrement` 就会建成 `integer PRIMARY KEY AUTOINCREMENT`；本项目 ID 由 `util.GenId()` 生成，不该走库自增。实测建表 DDL 现在是 `` `id` integer, ... PRIMARY KEY(`id`) ``，无 AUTOINCREMENT。
  - 三个 `decimal.Decimal`：`type:varchar(32)`。**这里更正一个对话2 的说法**：对话2 写的是「不写类型就会丢精度」，本轮实测**不成立**——`decimal.Decimal` 实现了 `driver.Valuer` 且 `Value()` 返回字符串，gorm 会把它判成 `schema.String`，gormlite 默认落 `text`，实测写入 `-1234567890123456.7890` 读回完全一致。真正会丢精度的是**写成 `decimal(20,4)`/`numeric(20,4)`**（NUMERIC 亲和 → 转 float64，对话2 已实测复现）。所以 `varchar(32)` 现在的作用不是「救精度」，而是把「这一列必须是 TEXT 亲和」这件事显式钉死，防止后来人再改成 `decimal(20,4)`。struct 上保留的唯一一行注释就是说这件事。
  - `index`：只加在 `db` 层 `Inquiry` 真的能筛的列上（含 `deleted_at`），规则是「能被 `Where` 命中的列才建索引」，不按需求文档的筛选清单预埋——文档里的日期区间/模糊匹配本轮 `Inquiry` 还不支持（见 2.5）。
  - 字符串/整型/时间列不写 `type`，用 gormlite 默认的 `text`/`integer`/`datetime`（`sqlite.go:183-211`），实测读写无损，写死长度在 SQLite 里也不生效。
- **`Inquiry` 补 `Page`/`PageSize`**：你只在 `FileBlobInquiry` 里写了这两个字段，而 `db` 层的 `Limit()` 必须靠它们；其余三个 `Inquiry` 补齐，实现与你 `FileBlobInquiry` 的 `Limit()` 完全一致（`PageSize<=0` 即不分页）。

### 2.2 `db`：以你的 `file_blob.go` 为唯一模板，横向复制到四个实体

每个实体文件的结构与你写的一模一样，顺序也一致：`type XxxInquiry model.XxxInquiry` → `Where`/`Order`/`Limit` → 四个 `NewXxx*Handler` → 四个包级函数 `InsertXxx`/`UpdateXxx`/`DeleteXxx`/`SelectXxx`。

- `Where`：全部是 `in (?)` 等值集合，与你的写法一致；空切片即不加条件。
- `Order`：有自增性 ID 的三张表按 `id`（`util.GenId()` 是时间有序 ID，等价于按时间正序，且能保证分页稳定）；`file_blob` 沿用你写的按 `file_hash`。

### 2.3 连接从哪里来——本轮唯一一处对你 `db.go` 注释的偏离（重点）

你在 `db/db.go` 的 todo 写的是「在 `init()` 里初始化数据库连接 + 自动建表，参考 `mmm/db/db.go`」。**这条在 jotcash 上做不到，我没有照做**，理由是硬约束而不是我的偏好：

- `mmm/db/db.go:54` 的 `config.Config.MysqlDsn` 在 jotcash 不存在（本仓库还没有 `config` 包），照抄会凭空发明一个配置项。

**采用的方案**：`db` 包不持有全局连接，连接由上层（未来的 controller/service）开好后放进 `ctx`，`db` 包从 `ctx` 取——这正好是 go_common 现成的 `util.SetCtxValue`/`GetCtxValue[T]`（`util/ctx.go:7-14`）的用法，与 `ignoreErrKey` 的写法同构。`db/db.go` 因此提供五个东西，全部无业务逻辑：

| 函数 | 职责 |
| ---- | ---- |
| `SetDb(ctx, *gorm.DB) context.Context` / `GetDb(ctx) *gorm.DB` | 连接在 ctx 里的存取，key 为 `db` |
| `Open(ctx, dsn) (*gorm.DB, error)` | `gormlite.Open(dsn)` + `SingularTable` + `util.NewDefaultGormLog()`（即你说的「用 go_common `util/gorm.go` 做初始化」），**dsn 由调用方拼**，加密参数/口令派生不进 `db` 包 |

| `AutoMigrate(ctx, *gorm.DB) error` | 建 4 张表，接你删掉的 `migrate.go` 的班；与 `Open` 分开，避免每个请求都跑一次建表 |

`Open`/`Close`/`AutoMigrate` 都是连接性代码，不是增删查改，但你原来的 `db.go` todo 就把它们放在这里，`model` 又明确不许放连接性代码，所以仍留在 `db` 包。**如果你更希望 `Open`/`Close` 挪去未来的 `service`/`config` 包、`db` 包只剩 CRUD 与 `Transaction`，说一声就搬。**

## 二、方案与取舍

### 2.1 连接链路：`Claims.ClientToken` → 加密库，全程封在 db 包内

```
上层(未来的gin/service)           db 包内部
  ctx 里有 *model.Claims   ──►  Transaction(ctx, handlers...)
                                  ├ GetClaims(ctx) 取 ClientToken，空则直接报错
                                  ├ Open(ctx, clientToken)
                                  │   ├ configs 里的 DbPath，必要时建目录
                                  │   ├ driver.Open("file:<path>?vfs=adiantum", init)
                                  │   │     init: PRAGMA textkey=<口令>; PRAGMA temp_store=memory;
                                  │   ├ PRAGMA user_version 探一次库头 → 口令错/文件损坏在这里就暴露
                                  │   └ gorm.Open(gormlite.OpenDB(sqlDb))
                                  ├ util.Transaction(ctx, db, handlers...)
                                  └ defer Close(ctx, db)
```

四个实体的 `InsertXxx/UpdateXxx/DeleteXxx/SelectXxx` 全部只调 `Transaction`，所以**上层调用签名没有任何变化**（还是 `SelectExpense(ctx, inquiry)`），也没有任何一处需要上层去开库、传 `*gorm.DB` 或知道加密的存在。对话5 里那对 `SetDb/GetDb(ctx) *gorm.DB` 已删除。

几个关键取舍：

- **口令只走 PRAGMA，不进 DSN**：DSN 只有 `file:<path>?vfs=adiantum`，出现在日志里也不含口令；`PRAGMA textkey` 是通过 `driver.Open` 的连接初始化回调直接打给底层 `*sqlite3.Conn` 的，**不经过 gorm 的 Logger**，所以 `util.NewDefaultGormLog()` 打的 SQL 日志里也不会有它（H-2）。口令值用 `sqlite3.Quote()` 转义后拼进 PRAGMA，不做手工拼字符串。
- **必须自己探一次库头**：实测（临时探针，跑完即删）`sqlDb.Ping()` 对**错误口令返回 nil**——因为 `driver.Open` 是懒连接，Ping 建连时只跑到 `PRAGMA textkey`，没读文件，所以验不出来；`PRAGMA user_version` 会读库头，错误口令直接报 `sqlite3: file is not a database`。故 `Open` 里加了这一次探测，让错误在开库处就暴露，而不是拖到第一条业务 SQL。返回的提示统一为「口令错误或数据库文件损坏」，对齐 A-4「口令错与文件损坏不可区分，统一提示」。
- **逐请求（逐次调用）开关库，不做连接缓存**：对齐前提 2「不跨请求缓存、不落盘」与流程 2「派生密钥 → 打开库 → 读写 → 关库」。代价实测：一次 `Open` 约 **70~95ms**（Argon2id 64MiB/3 轮/4 线程是大头），单测里一次完整 CRUD 用例（8 次开库）约 0.7s。如果将来嫌慢，正确的省法不是缓存密钥，而是让 service 层把多个 handler 合进**一次** `db.Transaction(ctx, h1, h2, ...)`（本轮已有用例覆盖：一次事务里同时插明细与操作日志，且第二步失败会整体回滚）。
- **没做的**：连接池调参（SQLite 逐次开关库场景无依据）、WAL（`.gitignore` 提到 WAL 副产品，但本轮不改 journal 模式，默认 rollback journal 更简单；要改是一行 PRAGMA，等你定）。

三个实现细节：

- **金额区间用 `*decimal.Decimal` 而不是值类型**：金额允许 0 与负数（前提 5），值类型的零值没法区分「不限」和「限定为 0」。

## 二、第二问：「AutoMigrate 不需要被调用，就能自动建表吗」

**直接回答**：Go 里没有「不被调用就执行」的函数，`AutoMigrate` 必须有人调；但可以做到**上层一行都不用写**——把它塞进 db 包自己的开库路径里。本轮就是这么改的：

- `AutoMigrate` 仍然导出：B-2 导入外部数据库文件后，那个库可能是旧结构，需要显式补一次（守卫认路径，导入后路径没变、不会自动重跑）。这一条登记在「四、仍然缺的」里。

# 对话9 · 两个设计问题：建表为什么不在 Init 里、migratePaths 干什么用

> 依据来源：本轮 prompt「对话9」2 问；需求文档 §一 前提 2/3（口令即密钥、逐请求携带）、A-1；`go_common@2d06a61` `util/config.go:50-68`（配置每分钟热加载）；本轮实测数据。
> 本轮是答疑，**没有改行为**，只把这两问的答案压成两行注释写回 `db/db.go:74-75`（你上一轮删掉了我在 `Init` 上写的长注释，这次只留最短的「为什么」，不再复述做了什么）。

---

## 一、AutoMigrate 为什么不在 Init 里调

### 1.1 根因：启动时手里没有口令，打不开已经存在的库

`Init` 只在**库文件不存在**时才往下走（A-1：数据卷里没有库文件即首次启动）。库已经存在时它直接 return——不是不想建表，而是**建不了**：

- 前提 2/3 规定「口令即密钥，逐请求携带，服务端不存储、不跨请求缓存」。服务启动的那一刻，进程里根本没有任何一把能打开已有库的口令。
- 没有口令 → 开不了库 → 拿不到 `*gorm.DB` → `AutoMigrate` 无从谈起。

所以「已存在的库」这条路上，**唯一能拿到口令的时机是某个带 jwt 的请求进来**。建表就只能挂在那个时机上，也就是 `Open` 之后。

### 1.2 如果按你说的放进 Init，会坏在哪

具体的失败场景：v1 已经在跑、库里有数据 → v2 给 `Expense` 加了一个字段 → 部署 v2 重启 → `Init` 看到库文件存在，直接 return，什么都不做 → 第一个请求进来，gorm 按新 struct 拼 SQL，SQLite 报 `no such column: xxx`。**而且它不会在启动时暴露，要等第一个请求才炸**。

`Init` 里那次建库之所以看起来「没调 AutoMigrate 也建出了表」，正是因为它内部调的 `Open` 已经把表建好了——首次启动这条路本来就被 `Open` 覆盖着，在 `Init` 里再调一次是重复的。

### 1.3 现在的分工

| 时机 | 谁触发 | 建表由谁完成 |
| ---- | ------ | ------------ |
| 首次启动（无库文件） | `db.init()` → `Init` → `Open` | `Open` 内的 `autoMigrate` |
| 老库 + 新版本代码 | 第一个带口令的请求 → `Transaction` → `Open` | 同上 |
| 口令探针 A-4 | `CheckClientToken` → `Open` | 同上 |

一句话：**`Init` 管「库要不要从零建出来」，`Open` 管「表结构是不是最新的」**，两件事的触发条件不同，不能合并。

---

## 二、migratePaths 干什么用

### 2.1 作用：每个进程对每张库文件只建一次表

`Open` 是每个请求都要走的路径。`gorm.AutoMigrate` 即使在结构完全一致、什么都不用改的情况下，也要把每张表、每个索引挨个探一遍。**实测**（临时探针，跑完即删）：

- 结构已经最新时，跑一次 `AutoMigrate` = **32 条 SQL**（`SELECT count(*) FROM sqlite_master WHERE ... name="expense"`、`SELECT sql FROM sqlite_master ...`、`SELECT * FROM expense LIMIT 1`、以及 17 个索引各一条存在性查询……），耗时约 **3ms**。
- 而一次开库总耗时约 **107ms**，其中约 100ms 是 Adiantum 的 Argon2id 派生密钥。

所以守卫省下的不是那 3ms（占比 3%，无所谓），**真正的收益是每个请求少 32 条毫无意义的 SQL 日志**——`util.NewDefaultGormLog()` 默认是打 SELECT 的，不拦住的话日志里全是建表探测，真正的业务 SQL 会被淹掉。

### 2.2 为什么是 map[路径]，不是一个 bool

两个理由，都是真实场景不是假设：

1. **`config.Config.DbPath` 会在运行期变**。你在 `9c74f1f` 里用的 `util.ConfigService` 每分钟重新加载一次配置（`util/config.go:50-68` 的 `flushConfig`），改了 `resource/jotcash.yaml` 的 `db_path` 之后，进程不用重启就会指向新文件。用单个 bool 的话，换过去的新库永远不会建表。
2. **测试里每个用例一个独立的临时库**（`newTestCtx` 把 `DbPath` 指到 `t.TempDir()`）。单个 bool 会让第一个用例之后的所有用例都跳过建表，全部查不到表。

`migrateLock` 就是保护这张 map 的：`Open` 会被并发请求同时调用，map 并发读写会直接 panic。

### 2.3 它**不**负责的事（一个已知缺口，登记在案）

B-2 导入数据库：外部库文件替换到同一个路径上，路径没变、守卫认为「已建过」，于是不会给这个新文件补结构。所以未来实现 B-2 时，导入完成后必须显式调一次已经导出的 `db.AutoMigrate`（或者顺手把该路径从 `migratePaths` 里去掉）。这条在对话8 §四.1 已登记，这里再说明一次它和守卫的关系。

## 一、改了什么

### 1.1 `migratePaths` → 一个 bool

```go
var migrateLock sync.Mutex
var migrated bool

func autoMigrate(ctx context.Context, db *gorm.DB) error {   // 去掉了 dbPath 入参
	...
	if migrated { return nil }
	...
	migrated = true
}
```

路径成了常量，一个进程只可能对着一个库文件，按路径分桶就没有意义了。**`migrateLock` 保留**：`Open` 会被并发请求同时调用，`migrated` 的读改写必须互斥（读写一个 bool 在 Go 里同样是数据竞争，不是「反正只会从 false 变 true 就无所谓」）。没有换成 `sync.Once`，因为 `Once` 在回调返回 error 时也算「已执行」，建表失败就永远不会再试了；现在的写法只有成功才置位。

### 1.2 测试改成包内测试（`package db`）

原来的隔离手段是每个用例把 `config.Config.DbPath` 指到 `t.TempDir()`，字段没了就没法这么干了。换成两步：

```go
func newTestDb(t *testing.T) {
	t.Chdir(t.TempDir())        // 路径是相对常量，切工作目录就等于换了个库
	migrateLock.Lock()
	defer migrateLock.Unlock()
	migrated = false            // 不重置的话，第二个用例开出来的新库不会建表
}
```

**为什么必须改成包内测试**：路径是常量、`migrated` 是包内私有变量，外部测试包（`package db_test`）没有任何合法手段让每个用例拿到一个干净的库——要么所有用例共用同一个库互相污染，要么第二个用例开始就查不到表。包内测试可以直接把标记复位。这也和 `go_common` 自己的测试风格一致（`util/gorm_test.go` 就是 `package util`）。代价是这组测试不再顺带验证「导出的 API 够不够用」，考虑到 `db` 包的调用方还没写，这个代价可以接受。

## 二、逐条

### 2.1 【P0，已修】`AutoMigrate` 的空连接校验被短路挡住了

你把守卫合并进导出函数时，顺序是「先判 `migrated` 再判 `db == nil`」：

```go
func AutoMigrate(ctx context.Context, db *gorm.DB) error {
	migrateLock.Lock(); defer migrateLock.Unlock()
	if migrated { return nil }        // ← 先短路
	if db == nil { ...return err }    // ← 永远轮不到
```

进程里只要成功建过一次表，`AutoMigrate(ctx, nil)` 就会安静地返回 nil。`db/db_test.go` 里 `TestAutoMigrate` 最后一行断言的正是「连接为空时自动建表应报错」，所以 `aed0459` 这个 commit 上 `go test ./db/` 是 **FAIL** 的（`--- FAIL: TestAutoMigrate`）。

**已修**：把 `db == nil` 提到加锁之前。参数校验本来就该在拿锁和读共享状态之前做，顺手也少持一次锁：

```go
func AutoMigrate(ctx context.Context, db *gorm.DB) error {
	if db == nil { ...return err }
	migrateLock.Lock(); defer migrateLock.Unlock()
	if migrated { return nil }
	...
}
```

改完 `go test ./... -count=1` 全绿。这是本轮唯一动的生产代码。

### 2.2 【P1，待定】导出的 `AutoMigrate` 现在是一次性的

守卫在导出函数里，意味着**整个进程只有第一次调用真的建表**，之后无论谁调、传什么连接，都是空操作。带来两个后果：

1. **B-2 导入数据库的逃生口没了**。对话8 §四.1、对话9 §二.3 两次登记过：导入的外部库文件可能是旧结构，路径又没变，所以导入完成后必须显式补一次建表。之前那版守卫在包内私有的 `autoMigrate` 上、导出的 `AutoMigrate` 是干净可重入的，正好能干这件事；现在两个入口合成一个，**没有任何办法在不重启进程的情况下再建一次表**。
2. **导出 API 的语义变了**：调用方看到一个叫 `AutoMigrate` 的导出函数，合理预期是「幂等地把表补齐」，实际是「进程内只生效一次」。将来 service 层的人踩这个坑，症状会是「我明明调了建表，怎么没建」。

**两个方案，你选**：
- (a) 恢复两层：导出的 `AutoMigrate` 不带守卫（谁调谁建），包内加回一个带守卫的 `autoMigrate` 给 `Open` 用——就是 `aed0459` 之前的形态，只是不再按路径分桶。
- (b) 保持现在的合并形态，另外加一个导出的复位函数（比如 `ResetMigrate(ctx)`），B-2 导入后先复位再开库。

我倾向 (a)：守卫是「`Open` 每个请求都会调，别每次都跑 32 条 DDL 探测」这个性能诉求带来的，本质上属于 `Open` 的实现细节，不该改变导出 API 的语义。

### 2.3 【P1，待定，已实测】库文件运行期丢失 → 空库 + 不建表 + 全线 `no such table`

写了个临时探针复现（跑完已删），场景是「服务在跑，库文件被删掉/被移走」：

```
插入1条 → 查得到1条
删掉 resource/jotcash.db
用另一个完全不同的口令查询 → err = 查询expense，异常: sqlite3: SQL logic error: no such table: expense
                              并且 resource/jotcash.db 被重新创建了
用原来的正确口令再查询   → err = 同样的 no such table
```

三件事叠在一起造成的：① `Open` 在文件不存在时会让 SQLite 直接建一个新库（这是 `Init` 建库依赖的行为）；② 新库是用**这次请求带来的那个口令**加密的，等于谁先来谁定密钥；③ `migrated` 还是 true，新库不会建表，于是**所有人**（包括拿着正确原口令的）都只能收到 `no such table`，而不是「库文件不见了」这种能看懂的错误。

按 A-2，「删库文件重新初始化」本来就是文档认可的恢复路径，但它的前提是**重启服务**（重启才会走 `Init`、才会打印新口令）。现在的代码在「删了但没重启」这个中间态里表现得既不安全也不可诊断。

**最小补丁**（约 6 行，供你决定）：只让 `Init` 允许创建库文件，其余入口文件不存在就直接报错。

```go
func Open(ctx context.Context, clientToken string) (*gorm.DB, error) { return open(ctx, clientToken, false) }

func open(ctx context.Context, clientToken string, create bool) (*gorm.DB, error) {
	...
	if !create && util.GetPathInfo(ctx, config.DbPath) == nil {
		return nil, errors.Errorf("打开数据库，库文件不存在")
	}
	...
}
```
`Init` 改调 `open(ctx, clientToken, true)`。这样删了文件不重启时，请求会明确报「库文件不存在」，而不是悄悄建一个谁都用不了的空库。

### 2.4 【P2】`Init` 失败删文件时没有复位 `migrated`

`Init` 里 `Open` 成功（此时 `migrated` 已被置 true）之后，如果写「系统初始化」审计失败，会把刚建的库文件删掉再返回错误，但 `migrated` 留在 true。现在 `db.init()` 拿到错误直接 panic、进程退出，所以不致命；但只要将来 `main.go` 里有人调 `Init` 并容错继续跑，后面新建出来的库就不会建表，症状同 2.3。跟 2.3 一起定方案时顺手处理（(a) 方案下把这行改成调用包内 `autoMigrate` 之外，再在删文件时复位标记即可）。

### 3.1 §六.1 `Claims.ClientToken` 的 `json:"-"`——到底影响什么

**这条的意思**：`db.Transaction` 是从 `ctx` 里的 `Claims.ClientToken` 取口令开库的（`db/db.go`）。口令怎么进到 `Claims` 里？按你在对话6 定的设计，是前端放进 jwt、后端验签后解出来。而 `json:"-"` 的作用正是「这个字段不参与 json 序列化」，jwt 的载荷就是 json，所以**打了 `json:"-"` 的口令根本不会被写进 jwt、也解不出来**，整条链路是断的。

**代码**（`tool/jwt.go`，新增）：

```go
func EnJwt(ctx, serverToken, clientToken string, expire time.Duration) (string, error)  //后端口令当密钥签名，前端口令放载荷
func DeJwt(ctx, serverToken, token string) (*model.Claims, error)                       //验签+过期校验，返回带口令的Claims
```

`model/claims.go` 改了一个字段标签：`json:"-"` → `json:"client_token,omitempty"`，同时给 `Claims` 加了 `String()`，**在 String() 里把口令抹掉**——这样「口令能进 jwt」和「口令不进日志」两件事同时成立（`logrus.WithFields{"claims": claims}` 打出来的是抹过的版本，H-2 保住）。

**怎么验**：`tool/jwt_test.go` 四个用例——口令能跟着 jwt 往返回来、换一把后端口令验不过、过期的验不过、`String()` 里搜不到口令。你要是想回到 `json:"-"`，把标签改回去 `TestJwtClientToken` 立刻会红，红的地方就是链路断掉的位置。

### 3.2 §六.2 `util.Init` 与「初始口令会不会被写进磁盘」

**这条的意思**：`go_common` 的日志初始化（落盘 `log/<服务名>/log.log`、轮转、格式、服务名）要靠 `util.Init(serverName)` 触发，全项目一直没人调，所以日志只在 stderr 裸奔。但它和 A-1 有冲突：A-1 要求把初始口令**打进日志**，一旦日志落盘，数据库口令就明文躺在磁盘上了。

**代码**（两处）：

1. `model/config.go` 按 `survive_monitor/model/config.go:13` 的写法补上调用点：`const DefaultServerName = "jotcash"` + `func init() { util.Init(DefaultServerName) }`。`model` 是所有包的最底层依赖，放这里能保证任何入口（服务、测试、将来的 cmd）都初始化过日志。
2. `db.Init` 里那两行口令**不再走 logrus**，改成直接写 stdout：

```go
var tokenWriter io.Writer = os.Stdout
...
fmt.Fprintf(tokenWriter, "系统初始化，前端口令: %s\n", clientToken)
fmt.Fprintf(tokenWriter, "系统初始化，后端口令: %s\n", config.Config.ServerToken)
```

这样 A-1「打印到日志（仅此一次）」照做（docker logs 看得到），前提 2「口令不落盘」也守住了（`log/jotcash/log.log` 里搜不到口令）。`TestInit` 把 `tokenWriter` 接到 buffer 上验证两个口令都打出来了、重复 `Init` 不再打。

### 3.3 §六.3 A-5 / B-1 / B-2 三个库文件级能力

**这条的意思**：换口令、导出、导入都不是改某几行数据，而是**整个库文件级别的操作**，需要「拷贝一份 → 校验 → 原子替换」。之前没做是因为接口长什么样没定。现在按文档算法实现在 `db/file.go`（新增）：

```go
func Export(ctx, clientToken string, writer io.Writer) error              // B-1
func ChangeClientToken(ctx, oldToken, newToken string) error             // A-5
func Import(ctx, clientToken string, reader io.Reader) error             // B-2
```

关键实现选择：

| 点 | 做法 | 理由 |
| -- | ---- | ---- |
| 怎么拷贝 | SQLite **在线备份 API**（`conn.Raw().Backup("main", dsn)`），不是 `io.Copy` 文件 | 直接拷文件会拷到写到一半的状态；备份 API 给的是一致性快照（B-1 原话「一致性快照」） |
| 目标库怎么给密钥 | 备份目标只能通过 URI 参数给钥：`file:<path>?vfs=adiantum&textkey=<口令>`，口令用 `url.Values.Encode()` 转义 | 目标库是 SQLite 内部打开的，没机会执行 `PRAGMA textkey`。这个串**不进日志**，`genDsn` 的返回值只传给备份调用 |
| 怎么替换 | 临时文件写在库文件同目录（`<库>.<id>.tmp`），最后 `os.Rename` | 同目录 rename 是原子的；跨目录/跨盘不是。失败一律删临时文件，原库一个字节都不动 |
| 校验什么 | `checkDb`：能用给定口令打开 + 四张表齐全 | B-2 原话「须用本次请求口令校验能打开且结构合法」 |
| 并发 | 三个操作共用一把 `fileLock` | 避免两个请求同时往同一个路径搬文件 |
| 审计 | **没写** | 「更换口令」「数据库导入/导出」三条审计是业务留痕，按 db 包不含业务逻辑的原则留给 service 层；如果你希望 db 层就写，说一声 |

**用 `Export` 的输出直接喂 `Import` 能跑通**（`TestExport` 就是这么验的：导出 → 导回 → 数据一条不差），所以「备份/迁移/换机/改密回滚共用一套」（B-3）在这一层是成立的。

**怎么验**（`db/file_test.go`，6 个用例）：导出的内容不是明文（搜不到 `SQLite format 3`、搜不到交易对手方）、错误口令导不出、换口令后旧口令失效新口令能用且数据齐全、弱口令与错旧口令被拒且原库不动、导入口令不匹配/非数据库文件/缺表三种非法输入都被拒且原库不动、导入成功后建表标记被复位。

### 3.4 §六.4 E-4 乐观锁更新

**这条的意思**：E-4 要求单行编辑带版本号乐观锁（「数据已落后，请刷新页面重新加载」），而 `go_common` 的 `UpdateHandler` 是按主键更新、不支持附加条件，所以这个能力一直没有落点。

**代码**（`db/expense.go`）：

```go
func NewExpenseUpdateByVersionHandler(object *model.Expense) *ExpenseUpdateByVersionHandler
func UpdateExpenseByVersion(ctx, object *model.Expense) (int64, error)
```

语义：`WHERE id = ? AND version = ?` → 更新成功把 `version + 1` 并回填到入参。**影响行数为 0 就是版本冲突，不返回错误**——提示文案是业务口径，留给 service 层根据 0/1 决定，db 层不判业务。

**怎么验**（`TestUpdateExpenseByVersion`）：两个人读同一行 → 先提交的成功、版本号变 2 并回填 → 后提交的返回 0 行、不回填、库里还是先提交那份、`CreatedAt` 与未改字段没被抹掉。
