## 步骤

- 背景调研
    - 研读prompt中提及的文档/代码/配置
    - 对齐背景，梳理核心逻辑/组件依赖/改动点
- 需求分析与方案
    - 提取核心目标/交付物/范围边界/关键约束
    - 制定方案：最小改动/复用优先/任务拆解；说明模块职责/输入输出/关键逻辑/异常处理
    - 评估对现有链路/性能/兼容性/下游的副作用
    - 写入`answer.md`：依据来源/方案取舍/实施步骤/验证说明
- 实施
    - 按方案执行，命名/注释/文案与项目风格一致
    - 中文注释与日志，处理边界与异常分支
    - 同步更新类型定义/关联配置/文档
    - 复杂任务使用主agent调度子agent的方式实施
- 验证与交付
    - 执行测试/逻辑校验/数据校验/文档校对
    - 重读`prompt.md`，检查与交付结果是否一致
    - 核心产出同步至`answer.md`
    - 清理临时文件/调试代码/冗余产物，但无须提交变更

## 约束

- 依据：结论只能来自文档/代码/表结构/日志/SQL等明确来源；严厉禁止猜测业务逻辑/捏造接口字段，不能断言的内容都询问用户
- 引用：关键事实引用到具体章节/字段名/代码路径或枚举值，禁止笼统援引
- 信息不足：区分「已确认/待确认/不可推断」并标注，不得脑补
- 历史资料：历史Prompt/answer/旧方案仅供参考，必须与代码交叉核对后才能使用
- 冲突：资料冲突时列出冲突点与采用依据，不得默默取一方
- 风格：命名/注释语言/代码组织与项目既有风格一致，优先复用现有实现

+ 当前后端代码的大体架构已经搭建起来，实现里一部分功能的接口
+ 现在需要开始写前端
+ 前端代码放在[static](../../../static)下面，通过StaticFile暴露出去
+ 你需要将本系统预期的全部功能的页面都写出来
+ 先不需要跟服务端联调，只需要在前端代码里先mock一些测试代码用于数据展示，给我验收

+ 可以使用各种开源的html/js/css库，这些库需要下载到本地，也通过StaticFile暴露出去，避免走CDN
+ 系统在本地启动的时候，路径使用的是/static，但是到生产环境，会可能有caddy反代，路径变成/xxx/static
    + 因此需要使用相对路径，避免使用绝对路径
