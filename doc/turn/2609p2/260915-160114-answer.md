## 三、生产代码改了什么（1 行）

### 3.1 `rdb/backup.go` `import_`：备份原库失败时漏清半个 `originPath`

`260915-143400-answer.md` §6.3 列过、当轮指令范围外没动，本轮指令明写「修复不对的代码」，改掉：

```diff
 	err = backup(ctx, dbPath, token, originPath, token)
 	if err != nil {
+		util.RemoveFile(ctx, originPath)
 		util.RemoveFile(ctx, backupPath)
 		return err
 	}
```

依据是**兄弟函数的口径**：`changeToken`（`rdb/backup.go:308`）在同一个 `backup(...)` 失败分支上是 `util.RemoveFile(ctx, backupPath)`，`export`（`rdb/backup.go:142`）用的是 `defer util.RemoveFile(ctx, backupPath)`——`backup()` 自己不清目标文件，**清目标文件的责任在调用方**，三个调用方里只有 `import_` 漏了。这正是 `编码规范` §二 第五层「副作用镜像」点名的那类失衡：接收方向必须在每个失败分支显式删。

## 四、单测：改正 1 条、补齐 6 组

### 4.1 case 思路从哪儿来

按四个来源找，不是凭空想：

1. **覆盖率的空白块**：`go test -coverprofile -coverpkg=./...` 之后逐块看哪些 `count=0`，再判断「是真够不到（磁盘 IO 出错、`rand.Int` 失败）还是没人写」。
2. **`doc/decisions/记账系统功能与模型.md`**：§二 A~H、§八 业务规则、§九 六条不变式，逐条对着找有没有钉住的用例。
3. **`doc/decisions/编码规范.md` §七 必测清单**：边界与异常分支、并发路径、镜像对的往返恒等、敏感信息不外泄、「无条件」的批量操作不会误伤全量、每一条写进规范的不变式。
4. **依赖本体的实际行为**：`util/csv.go` 里 `read.FieldsPerRecord = -1`——CSV 读的是**不定长行**，短行不报错，这条直接指出 `csvValue` 的下标越界分支是真能走到的。

### 4.2 改正：`TestCreateRollback` 的前提与代码对不上

原用例与注释：

```go

if util.GetFileInfo(ctx, dbPath) != nil {
	t.Errorf("建库失败时应把已占位的库文件清掉")
```

`git show 3395bcf` 显示这条注释写的时候是**对的**：当时 `create` 没有口令守卫，库文件是 `connect()` 顺手建出来的，所以确实「占位文件已经建出来了」。后来 `e7e9c1b` 把 `token == ""` 的守卫加到了函数最前面（`rdb/rdb.go:66`），**排在 `util.WriteData2File` 占位之前**——从那天起这条用例就再也走不到回滚分支，`GetFileInfo` 恒为 `nil`，断言恒真。

**代码是对的**（守卫在碰盘之前拦下，比建了再删更好），**用例的前提过期了**。改法：注释改成实际口径，再补一段真能走到写盘失败的：

依据是 `util/io.go:75 GetFileInfo` 对目录返回 `nil`（`GetPathInfo` 才返回）。覆盖率核对：`rdb/rdb.go:80.3,81.1` 由 `0` 变 `1`。

## 五、读代码读出来的问题（**只报不改**，等你定）

### 5.1 `rdb.ClearBackup` 全仓没有生产调用点 —— `db_backup_limit` 是死配置

```
grep -rn "ClearBackup\|clearBackup" --include=*.go .
rdb/backup.go:349   func ClearBackup
rdb/backup.go:362   func clearBackup
rdb/backup_test.go  （4 处，全是测试）
```

**没有任何生产代码调它**。后果是 `import_` 每成功一次就在 `resource/db_backup/` 里留一份原库快照（`rdb/backup.go:252` 的 `originPath`，设计上就是要留的），而 `config.DbBackupLimit`（默认 5）从来没有机会生效——备份目录**无上限增长**。`export` 自己 `defer util.RemoveFile` 清临时文件，`changeToken` 的备份被 `os.Rename` 消费掉，所以只有导入这条路会堆。

**接的时候有个坑**：`ClearBackup` 取的是 `dbLock.Lock()` 写锁（这是对的——它要挡住 `export` 在读锁下正在用的临时文件），所以**不能从 `Import`/`ChangeToken` 内部调**，那里已经持有写锁，会自己锁死自己。要接得接在 `service/repo` 层、`rdb.Import` 返回之后；或者按 `编码规范` §3.2 第2点复用非导出的 `clearBackup` 在锁内组合。**没擅自接。**

### 5.2 `rdb.Open` 的读锁在交出连接那一刻就放掉 —— 锁作用域错位

```go
func Open(ctx context.Context) (*gorm.DB, error) {
	dbLock.RLock()
	defer dbLock.RUnlock()      // ← Open 一返回就放了，调用方拿着连接在锁外用
	db, err := open(ctx, dbPath, token)
	...
}
```

对照 `NewTransaction`：读锁一直持到 `DbTransaction.Close`，`TestChangeTokenDuringTransaction` 专门钉这件事。`Open` 少的正是那半截。**现在不是 bug**：唯一的生产调用方是 `rdb.CheckToken`（`rdb/rdb.go:178`），拿到连接下一行就关，中间不读不写，窗口以微秒计，被 `os.Rename` 顶掉也没东西可丢。但这是个**形状陷阱**——将来谁用 `Open` 拿连接干正事，就完全裸奔。第三轮报同一处（`260915-143400-answer.md` §6.3）。

### 5.3 `Export` 在读锁里做 `io.Copy` 到 HTTP 响应 —— 慢客户端能饿死写锁

`rdb.Export` 全程持读锁，其中 `export`（`rdb/backup.go:154`）最后一步 `io.Copy(writer, file)` 写的是 `handler.dbFileWriter` → `gin.Context.Writer` → **客户端的 socket**。一个卡住的下载会把读锁扣住任意久；而 Go 的 `RWMutex` 在有写者等待时**新读者也要排在写者后面**，于是 `Import`/`ChangeToken` 一等，所有业务请求跟着一起堵。

真要治，得把「产出快照」和「把快照流出去」拆开——`backupPath` 那份副本本来就是独立文件，`io.Copy` 阶段不碰 `dbPath`，锁到 `backup()` 结束就够了。但这会破掉 `编码规范` §3.3 那套「导出包装取锁 → 非导出纯逻辑」的统一骨架，**不是一行改动，没动**。

### 5.4 同一协程里嵌套 `NewTransaction` 会死锁

`260915-143400-answer.md` §6.1 已写清。复核过，**当前 5 个调用点仍然都是平的**（`service/repo` 的五个门面都在开事务之前把校验做完）。建议在 `NewTransaction` 上补一句「同一协程内不得嵌套」的注释把规矩写进代码，**没擅自加**。

### 5.5 `DbTransaction.Close` 重复调用会 panic

```go
func (this *DbTransaction) Close(ctx context.Context) error {
	defer dbLock.RUnlock()
	return this.Transaction.Close(ctx)
}
```

`util.Transaction.Close` → `CloseDb` → `sql.DB.Close()` 是幂等的，但 `dbLock.RUnlock()` 不是：调两次会 `sync: RUnlock of unlocked RWMutex`。**当前所有调用点都是 `defer transaction.Close(ctx)` 恰好一次**，不是现存 bug。

### 5.6 `service.InsertExpense` 的 `filename == ""` 兜底从 HTTP 入口够不到

```go
if filename == "" {
	filename = fmt.Sprintf("%d.csv", util.GetLogId(ctx))
```

### 5.7 `config.ConfigService` 每分钟按**相对工作目录**重载 —— 与 `t.Chdir` 组合有 flaky 隐患

`util/config.go:64 flushConfig` 是常驻协程，每分钟 `loadConfig` 一次，路径是 `config.ConfigPath = "resource/jotcash.yaml"`（相对路径）。测试用 `t.Chdir(t.TempDir())` 改的是**进程级**工作目录，于是重载会在临时目录里发现没有配置 → 写一份**新的默认配置（ServerToken 随机重生成）**。`rdb`（`-race` 下 74s）与 `handler`（47s）都可能跨过那个 60s 的点。签 jwt 与 `validate` 读 ServerToken 之间的窗口很窄，本轮 `-race` 连跑没有复现，但这是**真实存在的 flaky 源**。病根在 `go_common`，**不在本仓库改**。

## 一、指令②：`rdb.Open` 的读锁提前释放 —— 已修

### 1.1 按你给的口径对照全部入口

> 对库文件的写操作（导入/创建等）拿写锁；对库文件的读操作、以及对业务数据的读写操作拿读锁；**操作完成之后才能释放**。

| 入口 | 动作 | 该拿的锁 | 修之前 | 修之后 |
| ---- | ---- | -------- | ------ | ------ |
| `Create` | 建库文件 | 写 | 全程持有 ✓ | 未动 |
| `Import` | `os.Rename` 顶替库文件 | 写 | 全程持有 ✓ | 未动 |
| `ChangeToken` | `os.Rename` 顶替库文件 | 写 | 全程持有 ✓ | 未动 |
| `ClearBackup` | 删备份文件 | 写 | 全程持有 ✓ | 未动 |
| `NewTransaction` | 业务数据读写 | 读 | 持到 `DbTransaction.Close` ✓ | 未动 |
| `Export` | 读库文件产副本 | 读 | 全程持有，**连流出也罩着** | 见 §二 |
| **`Open`** | **交出连接给上层读写** | **读** | **交出连接那一刻就放掉 ✗** | **持到 `DbConn.Close`** |

### 1.2 改法：照着 `DbTransaction` 的形状再做一个 `DbConn`

包里本来就有一对完全合规的实现——`NewTransaction` 取读锁、`DbTransaction.Close` 还锁。`Open` 缺的就是那后半截，所以按同一个形状补齐，不新造思路：

```go
func Open(ctx context.Context) (*DbConn, error) {
	...
	//读锁得攥到连接关掉那一刻：交出连接就放锁的话，导入/换口令的os.Rename会把连接指向的库文件顶掉，读写落进被替换掉的旧文件
	dbLock.RLock()
	object, err := open(ctx, dbPath, token)
	if err != nil {
		dbLock.RUnlock()      // 开连接失败，锁在原地还回去
		return nil, err
	}
	return &DbConn{DB: object}, nil
}

type DbConn struct {
	*gorm.DB
}

func (this *DbConn) Close(ctx context.Context) error {
	defer dbLock.RUnlock()
	return util.CloseDb(ctx, this.DB)
}
```

`DbConn` 内嵌 `*gorm.DB`，所以 `gormDb.Migrator()`、`gormDb.WithContext(...)`、`gormDb.Session(...)` 这些调用点一个字都不用改；`*gorm.DB` 本身没有 `Close` 方法（gorm v2 已经收进 `DB()`），不存在方法遮蔽。

生产代码只有 `CheckToken` 一个调用方，改一行：

```diff
-	return util.CloseDb(ctx, db)
+	return db.Close(ctx)
```

测试里 13 处 `Open` 调用点同样把 `util.CloseDb(ctx, gormDb)` 换成 `gormDb.Close(ctx)`（`rdb/rdb_test.go` 8 处、`rdb/inquiry_test.go` 2 处、`rdb/migrate_test.go` 2 处、`rdb/backup_test.go` 1 处）。`open`（非导出）返回的仍是 `*gorm.DB`，那些调用点继续走 `util.CloseDb`，没动。

## 二、指令③：`Export` 在读锁里 `io.Copy` —— 先把问题说清楚，再改

### 2.1 "没看懂"的那件事

`handler.Export` 把 `gin` 的响应写出器交给 `rdb.Export`：

```go
writer := &dbFileWriter{c: c}      // handler/rdb.go:33，Write 最终写到 c.Writer
err := repo.Export(ctx, writer)
```

`rdb.Export` 全程持读锁，末尾的 `io.Copy(writer, file)` 写的就是**客户端的 socket**。客户端要是不读（网断了、下载卡住、浏览器挂起），TCP 发送缓冲区一满，`Write` 就**阻塞在那儿不返回**——这段时间读锁一直攥着。

关键在 Go `sync.RWMutex` 的写者优先：**只要有一个写者在等，后来的读者也要排在写者后面**。所以连锁反应是：

```
慢客户端下载卡住 → Export 攥着读锁不放
        ↓
换口令/导入 在 dbLock.Lock() 上排队
        ↓
后面每一个业务请求的 NewTransaction 要读锁，也得排在那个写者后面
        ↓
整个服务停摆，直到那个下载超时或断开
```

一个卡住的下载能把整个服务堵死，这就是原来的问题。

### 2.2 改法：读锁只罩住「活库 → 副本」

按你自己定的口径推：`io.Copy` 读的是 `resource/db_backup/<id>.db` 这份**私有临时副本**，不是 `resource/jotcash.db`——它根本不是「对库文件的读操作」，本来就不该占着读锁。真正碰库文件的是前半段（开库写导出审计 + `backup(dbPath → backupPath)`），读锁罩住那一段就够，而且必须罩满。

于是按 `编码规范` §二第二层说的「中转形态（临时副本）是两条链路共同的原子」在副本这个点上切开：

```go
func Export(ctx context.Context, writer io.Writer) error {
	...
	//读锁只罩到副本落盘为止：副本之后就与库文件无关了，再攥着读锁把它流给客户端，
	//一个卡在半路的下载能把导入/换口令的写锁饿死，而写者一排队，后面所有业务请求的读锁也跟着堵住
	dbLock.RLock()
	backupPath, err := export(ctx, dbPath, token)   // 活库 → 副本
	dbLock.RUnlock()
	if err != nil {
		return err
	}
	defer util.RemoveFile(ctx, backupPath)

	err = exportWrite(ctx, backupPath, writer)      // 副本 → 流出，锁外
	...
}
```

三处配套：

1. **`writer == nil` 的守卫挪到公开入口 `Export`**。`编码规范` §3.2 把「兜底校验」派给导出包装，正合适；更要紧的是这样被它拦下时**连副本都不会产、也不会写导出审计**（原来它排在 `export` 第一位，效果一样，挪上去只是跟着拆分走）。
2. **`defer util.RemoveFile(backupPath)` 从 `export` 移到 `Export`**。§二第五层：产出方向用延迟清理无条件删。成功路径由 `Export` 的 defer 兜；`export` 内部 `backup` 失败那一步改成**显式删**（跟上一轮给 `import_` 补 `originPath` 是同一条口径——`backup()` 自己不清目标文件，责任在调用方）。
3. **日志分成两条**：`导出数据库，副本完成`（锁内）与 `导出数据库，完成`（锁外），出问题时一眼能看出卡在哪一段。

`Import` / `ChangeToken` **没有跟着拆**，这是刻意的不对称：它们的 `os.Rename` 在链路**最后一步**，写锁必须罩满全程；导出碰库文件的部分在链路**前半段**，所以锁只罩前半段。这正是 §二第五层说的「呼应不等于照抄」。

### 2.3 新增单测

**`TestExportNotBlockWriteLock`** —— 用一个卡在第一次写出上的 `blockWriter` 把「副本正在流出」的窗口拉开，此时换口令必须还能拿到写锁：

```

--- FAIL: TestExportNotBlockWriteLock (10.34s)
    backup_test.go:246: 导出把副本流出去时还攥着读锁，换口令被挡住
```

`TestBackupGuard` 跟着新签名改了：两处 `export` 调用改成收两个返回值，`writer == nil` 与错误口令这两条守卫改从公开入口 `Export` 打，并且仍然断言「被守卫拦下时一个字节都不该写出去」。

### 2.4 这次拆分带进来的一个权衡（**已确认影响可忽略，但写在这儿**）

读锁提前放掉之后，`resource/db_backup/` 里那份副本在流出期间不再被读锁保护，理论上会被并发的 `ClearBackup` 删掉。实际不会出事，两个原因：① `clearBackup` 删的是**排序最靠前（最旧）的那几份**，而 `genBackupPath` 用的 `util.GenId()` 单调递增、定长 16 位，导出的副本永远是最新那份；② `ClearBackup` 目前**全仓没有生产调用点**（指令①：维持现状）。将来真要把 `ClearBackup` 接起来，这一条值得重新看一眼。

## 五、指令⑥：「够不到」是什么意思 —— 是的，从 HTTP 入口永远进不去，维持现状

「够不到」指的是：**这段代码从 HTTP 接口那条路走过来，条件永远不成立**。

```go
// service/expense.go:44
if filename == "" {
	filename = fmt.Sprintf("%d.csv", util.GetLogId(ctx))
}
```

`filename` 的唯一来源是 `handler.InsertExpense` 里的 `fileHeader.Filename`（`handler/expense.go:31`）。而 `fileHeader` 是 `c.FormFile(config.ExpenseFileKey)` 取出来的——**Go 的 multipart 解析把 `filename=""` 的分段当成普通表单字段、不当文件**，所以文件名为空时 `c.FormFile` 根本不返回 `fileHeader`，而是直接报错：

```
实测：构造 writer.CreateFormFile("file", "") 打到 /api/expense/insert
响应：{"code":500,"msg":"明细入库，取上传文件异常: http: no such file"}
```

请求在进 `service` 之前就被 `handler` 挡掉了，所以 `filename == ""` 这个分支只有**直接调 `service.InsertExpense`** 才进得去。它不是死代码——功能模型 E-2 的「列表页新增一行 = 一份仅 1 行的 CSV」那条入口接上之后就会走到（那时没有真实文件名，正需要系统生成一个）。

按你的判断口径「如果永远不会进入就维持现状」：**从当前 HTTP 入口确实永远不会进入，维持现状，没动**。

```go
func CheckToken(ctx context.Context) error {
	dbPath := config.DbPath
	token, err := tool.GetToken(ctx)

		return err
	}
```

# 对话4 · 评审你手动重写的 `Export` / `export`

> 依据来源：`rdb/backup.go`（`a17f524` 你的改动）、`rdb/backup_test.go`、`rdb/rdb.go` 全部 `dbLock` 调用点；`doc/decisions/编码规范.md` §二第四/五层、§4.2、§5.1
>
> 结论：**这版比我那版好**，`export` 的边界切得更准。但有 **1 处编译红灯**（测试调用点没跟上新签名，已修）、**1 处值得你定夺的风险**（`Export` 是全包唯一没用 `defer` 还锁的地方，`export` 一旦 panic 整个服务会永久卡死），另有 1 条命名上的小建议。

## 一、先说改得好的地方

### 1.1 `export` 的签名与 `backup` 对齐了

```go
func export(ctx context.Context, srcPath, token, dstPath string) error
func backup(ctx context.Context, srcPath, srcToken, dstPath, dstToken string) error
```

我那版让 `export` 自己 `genBackupPath` 再把路径 `return` 出来，是「函数自己决定产物放哪儿、再告诉调用方」；你这版把目标路径变成**入参**，`export` 退回成一个纯粹的「把 srcPath 按 token 导成 dstPath，顺带记一条审计」。依赖全由参数传入、产物位置由调用方决定，这才是 `编码规范` §3.2 说的非导出纯逻辑，也让它和 `backup` 成了同一个形状。

### 1.2 新加的「目标文件已存在」守卫，位置是对的

```go
	if util.GetFileInfo(ctx, dstPath) != nil {
		logrus...Error("导出数据库，目标文件已存在")
		return errors.Errorf("导出数据库，目标文件已存在")
	}
```

`backup` 里本来就有一条同样的守卫，看着重复，但这条**有独立价值**：`export` 在调 `backup` 之前会先写一条「数据库导出」审计，守卫要是只留在 `backup` 里，撞上同名目标时就会**留下一条「导出成功」的审计、却什么都没导出**。提前拦掉正好堵住这个。这也正是 §二第四层「执行侧不得假设判定侧已经跑过」的正例。

已补一条断言钉住它（见 §三）。

### 1.3 `defer util.RemoveFile(ctx, backupPath)` 压在错误判断之后，是对的

```go
	err = export(ctx, dbPath, token, backupPath)
	dbLock.RUnlock()
	if err != nil {
		return err                              // 这条路径上没有 defer
	}
	defer util.RemoveFile(ctx, backupPath)
```

第一眼像是漏了清理，逐条走完 `export` 的失败分支之后确认**没有泄漏，而且这个位置比放在 `genBackupPath` 之后更安全**：

| `export` 的失败分支 | dstPath 状态 | 谁负责清 |
| ------------------- | ------------ | -------- |
| srcPath 不存在 / token 为空 | 没建 | 无需清 |
| **dstPath 已存在** | **存在，但不是我们建的** | **谁都不该清** |
| open / 写审计 / CloseDb 失败 | 还没到 `backup`，没建 | 无需清 |
| `backup` 失败 | 可能半个 | `export` 自己 `util.RemoveFile(dstPath)` |

关键是第二行：`defer` 要是提到 `genBackupPath` 之后，撞上「目标文件已存在」时就会**把别人的文件删掉**。现在的位置正好躲开。（`genBackupPath` 只建目录、不建文件，所以提前返回也不留东西。）

### 1.4 读锁的修复保住了

```go
	dbLock.RLock()
	err = export(ctx, dbPath, token, backupPath)
	dbLock.RUnlock()
	...
	_, err = io.Copy(writer, file)      // 锁外
```

碰库文件的全在锁内，流给客户端在锁外。变异验证过：把 `RUnlock` 改回 `defer`，`TestExportNotBlockWriteLock` 立刻以「导出把副本流出去时还攥着读锁，换口令被挡住」失败（10s 超时）。

`genBackupPath` 挪到锁外也没问题——它只 `os.MkdirAll` 备份目录、算个文件名，不碰库文件。

## 四、一处要你定夺的风险：`Export` 是全包唯一没用 `defer` 还锁的地方

把 `rdb` 包所有 `dbLock` 调用点排出来：

```
rdb/rdb.go:46,47     Create           Lock  + defer Unlock      ✓
rdb/rdb.go:170,171   CheckToken       RLock + defer RUnlock     ✓
rdb/rdb.go:195,198   NewTransaction   RLock，错误分支显式 RUnlock
rdb/rdb.go:217       DbTransaction.Close      defer RUnlock     ✓（调用方都是 defer Close，panic 也会走到）
rdb/backup.go:174,175 Import          Lock  + defer Unlock      ✓
rdb/backup.go:285,286 ChangeToken     Lock  + defer Unlock      ✓
rdb/backup.go:357,358 ClearBackup     Lock  + defer Unlock      ✓
rdb/backup.go:102,104 Export          RLock +       RUnlock     ← 只有这一处不是 defer
```

**这是对话2 我改出来的**（为了提前放锁而把 `defer` 去掉），你这版沿用了，所以现在一并提出来。

后果不是小事：`export` 内部一旦 panic（`ncruces/go-sqlite3` 是 wasm 运行时，内部错误有 panic 路径），`gin.Default()` 自带的 `Recovery` 会接住、请求返 500、**进程活着，但那把读锁再也放不掉**。之后所有导入/换口令卡在写锁上，而 `RWMutex` 写者优先，后面每一个业务请求的读锁也排在那个写者后面——**整个服务永久卡死，只能重启**。

对比 `NewTransaction` 那条路：读锁由 `DbTransaction.Close` 释放，调用方一律 `defer transaction.Close(ctx)`，panic 时 defer 照样跑，所以是安全的。只有 `Export` 这条路径上，panic 会把锁带走。

要同时保住「提前放锁」和「panic 也能放锁」，只能用一个立即执行的闭包：

```go
	err = func() error {
		dbLock.RLock()
		defer dbLock.RUnlock()
		return export(ctx, dbPath, token, backupPath)
	}()
	if err != nil {
		return err
	}
```

但对话3 你刚定了「导出只允许两个函数」，匿名闭包算不算「新建函数」得你说了算，**所以我没动**。三个选择：① 上面这个闭包；② 维持现状，认为 `export` 不会 panic；③ 放弃提前放锁、改回 `defer dbLock.RUnlock()`（那就退回对话2 之前的慢客户端饿死写锁问题）。等你定。

## 五、一条命名上的小建议（低优先级）

`export` 现在用 `srcPath`，但它的镜像 `import_` 和 `changeToken` 用的都是 `dbPath`：

```go
func import_(ctx context.Context, dbPath, token string, reader io.Reader) error
```

三个函数第二个参数指的是同一样东西——**活的库文件**。`编码规范` §4.2 是「同一概念全仓只有一个名字」。改成 `export(ctx, dbPath, token, dstPath)` 就齐了；不改也说得通（它现在和 `backup(srcPath…dstPath)` 同形）。**没动，你定。**
