## 一、分层与包职责：函数该落在哪一层

实测依赖图（`go list -deps`，无环）：

```
model   ← 谁都可以依赖，它谁都不依赖
tool    → model
config  → model tool
db      → model tool config
exchange_rate → （无内部依赖）
service/expense        → model exchange_rate
service/expense/base_csv → model exchange_rate service/expense
service/db → model tool config db
service    → model tool config service/db service/expense service/expense/base_csv
handler    → model tool config service service/db static
```

| 包 | 职责 | 硬约束 |
| --- | --- | --- |
| `model` | 只放 struct、常量枚举、`String()`、`TableName()` | **不得包含任何业务逻辑或连接性代码**（`260913-005452` 对话1/5）。唯一例外是 `model/config.go` 的 `init()` 调 `util.Init(DefaultServerName)`，这是 go_common 的日志初始化契约 |
| `tool` | 无业务语义的工具：JWT 收发、口令生成/强度校验、ctx 里的 Claims 存取 | 不碰数据库，不碰 HTTP |
| `config` | 配置文件加载与热更 | 路径类常量（`ListenAddress`/`ConfigPath`/`DbPath`/`DbBackupPath`）是**不变常量，不允许可配**（`260913-005452` 对话10） |
| `db` | 数据库连接 + **无业务逻辑**的增删查改 | 连接性代码必须在包内完成，上层不感知（`260913-005452` 对话6）。不做参数校验 |
| `exchange_rate` | 汇率获取 | 外部接口对接**挂起中**，现写死返回 1（`exchange_rate.go:11` 的 `//todo`） |
| `service/expense` | 解析器注册表 + 派生字段填充 | 解析器接口与派生逻辑在此，具体格式在子包 |
| `service/expense/<格式>` | 单一格式的解析器实现 | 只填文件里给了的字段，派生字段留给上层 |
| `service/db` | **带业务逻辑**的数据库读写：多表同事务、参数校验、默认值兜底 | 上层**只能**调 `service/db`，不能直接调 `/db`（`260913-215504` 对话1）。理由：`/db` 没有业务逻辑，会缺必要的参数校验 |
| `service` | 业务编排，出参统一 `(any, error)` 以喂 `util.NewGinPost` | |
| `handler` | 路由注册、多段表单/二进制流这类 gin 专属的活 | 能用 `util.NewGinPost` 的绝不手写 handler |
| `static` | `embed.FS` | 6 行，不要长大 |

**当前生产代码 100% 遵守"上层不直接调 `/db`"**：只有 `service/db/{db,expense,file_meta,operation_log}.go` 四个文件 import 了 `jotcash/db`。测试可以越层（`handler/*_test.go` 直接调 `db.Create` 建库），这是允许的例外。

## 二、命名

### 2.1 接收器

**一律 `this`**，36 个方法零例外。值接收器还是指针接收器按是否改字段决定：

- 值接收器：`func (this Expense) String() string`、`func (this ExpenseInquiry) Where(...)`
- 指针接收器：`func (this *ExpenseUpdateHandler) Transaction(...)`（要写 `this.Count`）

`String()` 用值接收器还有一个刻意的用途，见 §8.3。

### 2.2 变量名（全仓通用词表）

| 名字 | 含义 | 出现次数 |
| --- | --- | --- |
| `object` / `objects` | 实体单个 / 列表 | 107 / 141 |
| `inquiry` | 查询条件 | 162 |
| `handler` | 事务 Handler | 106 |
| `one` | `for _, one := range` 的元素 | — |
| `i` | `for i := range` 的下标 | — |
| `tx` | `*gorm.DB` 事务句柄 | — |
| `gormDb` / `sqlDb` | gorm 连接 / database/sql 连接 | — |
| `ctx` | `context.Context`，**永远是第一个参数** | — |

新代码需要给"某个实体的一条记录"命名时，用 `object`，不要用 `item`、`record`、`row`、`e`、`exp`。

### 2.3 中英文边界

- **标识符一律英文**，且不做死板直译：`CardLast4` 而不是 `CardLastFour`（`260913-005452` 对话2 明文点名）
- **注释、日志、错误文案一律中文**
- 领域名词用中文文档里的标准名：「记账币种/记账金额」不是「本位币」（`260911-220830` 对话3 采纳）；「支出类型」不是「标签」（同上）；「口令」不是「密码」（`260911-220830` 对话2 采纳）；前端动作叫「解锁」，服务端只有「口令校验」
- 私有函数与 Go 关键字冲突时加下划线后缀：`import_`（`db/backup.go:157`）

### 2.4 文件名

`snake_case.go`，与主类型同名：`model/operation_log.go` 放 `OperationLog`。枚举常量与它修饰的实体放**同一个文件**（`260913-005452` 对话6 明文），例如 `OperationTypeXxx` 和 `ResultXxx` 都在 `model/operation_log.go`。

## 三、文件与包内组织顺序

固定顺序，不要打乱：

```go
package xxx

import (
    // 标准库
    ""
    // 空行
    // 第三方 + 本仓库（同一组，按路径字母序，gofmt 自动排）
)

// 1. 排序白名单 var + 默认排序 const
// 2. 类型别名 / Inquiry 定义
// 3. Where / Order / Limit
// 4. NewXxxHandler 构造 + Handler struct + Transaction 方法
// 5. 对外的 Insert/Update/Delete/Select 函数
```

`db/expense.go`、`db/operation_log.go`、`db/file_meta.go`、`db/file_blob.go` 四个文件是这个顺序的样板，新增实体照抄。

### 3.1 import 分组

只有两组：标准库 / 其余，中间一个空行。本仓库包和第三方包**混在同一组**（gofmt 默认行为），不要人为再分第三组。重名 import 才起别名，且用下划线风格：`common_model "github.com/cellargalaxy/go_common/model"`。

### 3.2 空行：成对函数要贴在一起

**导出包装 + 非导出实现** 这一对之间**不留空行**，视觉上是一个单元：

```go
func Create(ctx context.Context) error {
    ...
}
func create(ctx context.Context, dbPath, token string) error {
    ...
}
```

已成对的：`Create/create`、`Open/open`、`Transaction/transaction`、`Export/export`、`Import/import_`、`ChangeToken/changeToken`、`ClearBackup/clearBackup`。

同样贴紧的还有：`String()` 与 `TableName()`、`Order()` 与 `Limit()`、`GetClaims()` 与 `SetClaims()`、`ConfigHandler` 的三个方法。

其余函数之间留一个空行。函数体内用空行分段，段与段之间是"取参数 / 加锁 / 干活"这种粗粒度，不要每两行就空一行。

## 四、函数边界（被点名次数最多的一条）

### 4.1 量化基线

| 指标 | 现值 | 新代码应落在 |
| --- | --- | --- |
| 函数长度中位数 | **8 行** | 10 行上下 |
| p90 | **24 行** | 不超过 30 行 |
| 最长 | **63 行**（`db/expense.go:28` `ExpenseInquiry.Where`） | 只有"平铺的 if 列表"允许这么长 |

`ExpenseInquiry.Where` 63 行不是反例，是**正例**：它是 18 个平级的 `if` 拼 where 条件，拆成子函数只会更难读。判据不是行数，是**分支深度与职责数**。

### 4.2 两条对称的红线

**红线 A —— 严禁过度拆分**（`260913-215504` 对话11/12）

原话：「`newCsvFile` 这种函数的逻辑太过单薄，属于过度拆分，去除该函数」。

判据：一个函数如果只是把 2~4 行原地代码换个名字包起来、且只有一个调用方、且不含分支，就是薄封装，内联掉。

反面样本（历史上被删掉的）：`newCsvFile`、`genExpenseCsv`、`parseCsvColumns`、`fillExpenseDerived`、`tokenWriter` 那套。

**红线 B —— 严禁职责焊死**（`260913-215504` 对话10）

原话：「正确的做法是分别创建 `deleteHandler` 与 `operationLogInsertHandler`，然后将两个 Handler 一起放进一个 `db.Transaction`，是组装的思路；而不是像你写的，在 `expenseDeleteHandler` 里耦合 `operationLog`」。

判据：一个函数/Handler 只干一件事，多件事靠**组装**（把多个 Handler 塞进一个 `db.Transaction`）完成。

`service/db/expense.go:36-42` 是这条的标准落地：

```go
fileBlobHandler := db.NewFileBlobInsertHandler(fileBlob)
fileMetaHandler := db.NewFileMetaInsertHandler(fileMeta)
expenseHandler := db.NewExpenseInsertHandler(expenses...)
operationLogHandler := db.NewOperationLogInsertHandler(&operationLog)
return db.Transaction(ctx, fileBlobHandler, fileMetaHandler, expenseHandler, operationLogHandler)
```

### 4.3 导出/非导出的切分法则

`db` 包把"环境"和"逻辑"切开，是全仓最该照抄的边界形态：

| 层 | 干什么 | 例 |
| --- | --- | --- |
| **导出函数** | 读 `config` 常量、从 ctx 取口令、**加锁**、调非导出函数 | `db.Open`（`db/db.go:150-170`） |
| **非导出函数** | 参数**全部显式传入**（`dbPath`、`token`），不碰锁、不读全局 | `db.open`（`db/db.go:172-182`） |

好处是非导出函数可被测试直接构造任意环境调用（`db/db_test.go:46` 的 `create(ctx, config.DbPath, testClientToken)`），且锁的持有范围一眼可见。新增需要加锁或读全局配置的能力，照这个切。

### 4.4 创建归创建，打开归打开

`260913-005452` 对话14 明文：「数据库文件，创建归创建，打开归打开，不要打开的函数又通过 create 耦合创建；打开的时候，没有文件或者文件损坏或者口令错误就报错，不要 create」。

现状 `db/open()` 首行就是 `if !existDb(...) { 报错 }`，不兜底建库。**任何"读路径顺手补写"的诱惑都要拒绝。**

## 五、错误与日志

### 5.1 唯一句式

错误产生点，**先 logrus 后 errors.Errorf，两条文案保持一致**：

```go
logrus.WithContext(ctx).WithFields(logrus.Fields{"err": err}).Error("连接数据库，异常")
return nil, errors.Errorf("连接数据库，异常: %+v", err)
```

要点：

- `logrus.WithContext(ctx)` 一定要带 ctx，logId 靠它串联
- **`WithFields(logrus.Fields{})` 即使为空也要写**，不要退化成 `logrus.WithContext(ctx).Error(...)`
- 文案格式：**`动作，问题`** / **`动作，完成`**，中间是**全角逗号**。带上下文时 `动作，问题: %+v`（冒号后一个半角空格）
- 只用 `github.com/pkg/errors` 的 `errors.Errorf`。全仓 **0 处** `fmt.Errorf`、`errors.New`、`errors.Wrap`、`errors.WithStack`
- 动作名用中文业务词或表名：「连接数据库」「插入file_blob」「解析CSV」「校验口令」

### 5.2 日志级别

| 级别 | 用于 | 样本 |
| --- | --- | --- |
| `Error` | 系统/IO/连接/配置层面的异常，或"不该发生"的状态 | 「连接数据库，异常」「自动建表，连接为空」「排序，不在白名单内」 |
| `Warn` | **用户输入或业务校验不过**；以及"入参为空所以什么都没干" | 「解析CSV，支出金额非法」「查询，时间区间倒挂」「插入file_blob，为空」 |
| `Info` | 成功完成、启动期事实 | 「导出数据库，完成」「加载配置」 |

另有一处刻意的 `Warn`：初始前后端口令 `db/db.go:147-148`，用 Warn 是为了在默认级别下必定可见，且**允许写进日志文件**（`260913-005452` 对话14 明文否决了此前的 `tokenWriter` 方案）。

### 5.3 错误的传递：不重复包装

下层返回的 err **原样 `return err`**（全仓 46 处），不再加一层文案。理由见 `260913-215504` 对话2：「err 在 CheckToken 内部已经封装过，err 是什么就给前端返回什么，不要加工」。

唯一允许"不在原地记日志"的情形：错误文案是个**片段**，由调用方拼前缀并在那里记日志。例如 `base_csv.go:81` 返回 `支出日期非法: %+v`，由 `base_csv.go:70` 记「解析CSV，行非法」并拼成 `解析CSV，第%d行，%s`。

**位置决定有没有空格**，这条全仓零例外：

| 位置 | 写法 | 样本 |

## 七、并发与资源

1. **全局并发收敛到一把读写锁**：`db/db.go:23` 的 `var dbLock sync.RWMutex`。`260913-005452` 对话15 明文：「db 包里的并发控制要不收敛到一个读写锁中，并发性能低一点可以接受」。
   - `RLock`：读写数据（`Open`/`Transaction`/`Export`）
   - `Lock`：动库文件本身（`Create`/`Import`/`ChangeToken`/`ClearBackup`/`autoMigrate` 的建表分支）
2. **ctx 脱钩**：交给 gorm 之前必须 `detachCtx`（`db/db.go:45`），否则 gin 复用 `*gin.Context` 会串请求。
3. **双检锁**：`autoMigrate`（`db/migrate.go:50-65`）先 `RLock` 读标记，再 `Lock` 复检，标准形态。
4. **关闭资源用 `defer`**，且走 go_common：`defer util.CloseIo(ctx, file)`、`defer Close(ctx, gormDb)`。
5. **临时文件失败即删**：`db/backup.go` 的 `import_`/`changeToken` 每个错误分支都 `util.RemoveFile(ctx, backupPath)`，成功路径靠 rename 消费掉。这是刻意不用 `defer` 的地方——成功时文件要被 rename 走，defer 会误删。

## 八、`model` 包专项

1. **只有 struct、常量、`String()`、`TableName()`**。零业务逻辑、零连接代码。
2. **字段标签成对**：`json:"snake_case"` + `gorm:"column:snake_case;..."`，列名显式写出不靠推导。
3. **敏感字段两种遮蔽法，按用途选**：

| 手法 | 用于 | 样本 |
| --- | --- | --- |
| `json:"-"` | 这个字段**根本不该出现在任何 JSON 里** | `Config.ServerToken`、`FileBlob.FileData` |
| `String()` 值接收器里置空后再 marshal | 字段**必须能序列化**（要进 JWT / 要收请求体），但**不能进日志** | `Claims.ClientToken`、`ChangeTokenRequest.NewToken` |

第二种能成立，靠的正是 §2.1 的值接收器——`this.ClientToken = ""` 只改副本。`model/claims_test.go` 同时断言了"JWT 载荷要带上 ClientToken"和"`String()` 里不能有"，两条一起锁住这个设计。

4. **`decimal.Decimal` 必须声明 `type:varchar(32)`**。原因写在 `model/expense.go:32`：SQLite 按声明类型做亲和判定，`decimal`/`numeric` 落到 NUMERIC 亲和会把数字文本转成浮点丢精度。新增金额/汇率字段照抄。
5. **Id 一律 `int64` + `primaryKey;autoIncrement:false`**，值由 `util.GenId()` 生成（`260913-005452` 对话2）。
6. **时间字段沿用 gorm 约定**：`CreatedAt`/`UpdatedAt`/`DeletedAt gorm.DeletedAt`（`260913-005452` 对话2）。
7. **每个实体配一个 `XxxInquiry`**，字段形态固定：切片 = `in`，`XxxStart`/`XxxEnd` = 区间，`XxxLike` = 模糊，外加 `Sort`/`Page`/`PageSize`。允许为将来的业务需要提前加查询字段（`260913-005452` 对话6）。
8. **路径常量集中在 `model/path.go`**，含表单字段名（`ImportFileKey`/`ExpenseFileKey`）。

## 九、`db` 包专项

1. **`XxxInquiry` 是 `model.XxxInquiry` 的类型别名**（`type ExpenseInquiry model.ExpenseInquiry`），只为挂 `Where`/`Order`/`Limit` 三个方法，不新增字段。
2. **排序走字符串白名单**。`260913-005452` 对话7 改判：不用 `map[int]string`，让上层直接传字符串更直观，`Inquiry` 里查白名单，**不在白名单就 `Error` + 报错**，不是静默降级。
   ```go
   var expenseSortMap = map[string]string{
       "expense_amount asc": "cast(expense_amount as real) asc", //金额列是文本，按文本排序会串位
       ...
   }
   const expenseSortDefault = "id asc"
   ```
   key 是给上层看的语义，value 是真正拼进 SQL 的表达式，两者可以不同——这就是防注入的落点。
3. **`like` 必须转义**：统一走 `db/inquiry.go` 的 `likeValue()`（转义 `\` `%` `_`），SQL 侧写 `like ? escape '\'`。
4. **Handler 优先复用 go_common 泛型**：`util.NewInsertHandler[T]`、`NewUpdateHandler[T]`、`NewDeleteHandler[T]`、`NewSelectHandler[T]`。只有泛型满足不了才自己写，现有两个自定义 Handler 各有明确理由：
   - `ExpenseUpdateHandler`（`db/expense.go:104`）：需要 version 乐观锁 + `Omit("id","created_at","deleted_at")`
   - `FileBlobInsertHandler`（`db/file_blob.go:41`）：需要 `clause.OnConflict{DoNothing: true}` 做按 hash 去重
5. **自定义 Handler 的固定骨架**：`New...` 构造 → `struct{ Object; Count int64 }` → `Transaction(ctx, tx) error`；空入参 `Warn` 后 `return nil`；结束 `Info("...，完成")` 带 `count`。
6. **`db` 包不做业务校验**。`NewExpenseDeleteHandler` 里那两行（强制 `DeletedNo`、清掉 `Page/PageSize`）是**安全兜底不是业务校验**，业务校验在 `service/db`。

## 十、`service/db` 专项

这一层的存在理由就是"参数校验与业务逻辑有关，所以要有足够业务语义的地方来做"（`260913-215504` 对话1）。固定形态：

```go
const expenseSortDefault = "expense_date desc"      // 业务默认排序，覆盖 db 层的 id asc

var expenseDeleteds = map[int]bool{...}             // 枚举白名单

func SelectExpense(ctx, inquiry) (...) {
    inquiry, err := checkExpenseInquiry(ctx, inquiry)   // 先校验+补默认
    if err != nil { return nil, 0, err }
    return db.SelectExpense(ctx, inquiry)               // 再下沉
}

func checkExpenseInquiry(ctx, inquiry) (model.ExpenseInquiry, error) { ... }
```

必做的四件事：

1. **枚举白名单校验**，非法值 `Warn` + 报错，**不静默降级**（`service/db/expense.go:58` 的注释把理由写死了：「db 层对没见过的取值会按『只查未删除』处理，静默少查数据不如直接报错」）
2. **区间倒挂校验**：`checkTimeRange`、`checkAmountRange`（`service/db/inquiry.go`）
3. **分页兜底**：`checkPageSize`，`<=0 → 20`，`>200 → 200`。理由在注释里：db 层 `pageSize<=0` 是不加 limit，上层不兜底会整表拉出来
4. **业务默认排序**：`Sort == ""` 时补上，因为 db 层默认 `id asc` 不符合列表页「最新在前」的预期

写操作在这一层组装审计日志（`model.OperationLog`）与业务 Handler，放进同一个 `db.Transaction`（见 §4.2 红线 B）。

## 十一、`handler` 专项

1. **能用 `util.NewGinPost` 就不手写**：`NewGinPost("明细查询", service.SelectExpense)`。它已经包了参数绑定、入参日志、`NewHttpRespByErr`。
2. **只有 gin 专属的活才手写 handler**：多段表单取文件（`InsertExpense`、`Import`）、二进制流响应（`Export`）。
3. 手写 handler 的骨架：
   ```go
   func Xxx(c *gin.Context) {
       logrus.WithContext(c).WithFields(logrus.Fields{"claims": tool.GetClaims(c)}).Info("动作")
       ...
       c.JSON(http.StatusOK, util.NewHttpRespByErr(service.Xxx(c, ...)))
   }
   ```
   **HTTP 状态码永远 200**，业务码在 body 的 `code` 里（go_common `HttpResp` 契约）。
4. **`*gin.Context` 直接当 `context.Context` 传**，不额外包。
5. **中间件链**：`engine.POST(path, validate, 业务)`，`validate` 校验后端口令，业务侧再校验前端口令。
6. **报错也要返回基础信息**：`Ping` 即使 `err != nil` 也把 `PingData{Ip, ServerName, Timestamp}` 带回去（`260913-215504` 对话2 明文确认）。
7. **JWT 只从 header 取**，不支持 query（`260913-215504` 对话3：「如果前端不遵守约定、非要通过这种暴露的方式传，为什么不直接将口令发布到报纸上」）。

## 十二、可扩展点用注册式，不用 if-else

`260913-215504` 对话12：「前端上传的文件未来会有多种不同的格式，需要使用不同的解析器……需要使用设计模式，收纳规范不同格式的解析器」「**不能使用文件扩展名来判断解析器**，同样的 CSV/PDF 内容格式可能完全不同」。

落地形态（`service/expense/expense.go` + `base_csv/base_csv.go`）：

```go
type Parser interface {
    Support(ctx context.Context, data []byte) bool
    Parse(ctx context.Context, data []byte) ([]*model.Expense, error)
}

var parsers []Parser
func Register(parser Parser) { parsers = append(parsers, parser) }
```

- 子包在 `init()` 里 `expense.Register(new(Parser))`
- 上层用**空白 import** 触发注册：`_ "github.com/cellargalaxy/jotcash/service/expense/base_csv"`（`service/expense.go:13`）
- **`Support` 认内容不认后缀**，且要严格：`base_csv` 要求表头与 `columns` **完全相等**（顺序、数量都要对，`slices.Equal`），`260913-215504` 对话12 明文要求
- 解析器**只填文件里给的字段**，`Id`/`AccountingAmount`/`Version`/摊分起止月这些派生字段由 `fillExpense` 统一填

新增格式时只加子包 + 一行空白 import，不动 `Parse` 的分发逻辑。

## 一、包的层级：按"距外部的远近"排布

**唯一的排布轴是"离外部系统有多远"，不是"抽象程度"，也不是"调用先后"。**

- 与外部对接的包（配置文件、数据库、第三方接口、HTTP 入口、数据契约、工具）放在项目根部，**越外部越靠近根部**。
- 业务逻辑往内层目录收，按业务域再分子包。
- **越靠近边缘的包越通用、业务逻辑越少**；越靠内的包越专用、业务规则越密。

这条轴同时决定了依赖方向：内层可以依赖外层的适配能力，外层不得反向依赖内层的业务。依赖图必须无环，且每个包都能被单独实现与单独测试。

判断一个新包该放哪里，只问一句：**它知道多少业务规则？** 一条都不知道的，放根部；离不开业务规则的，往里放。

---

## 二、三组必须守住的包边界

这三组是同一条原则的三个切面：**通用与专用之间必须有边界，且边界要单向。**

### 2.1 通用工具 与 带规则的工具

- 完全无业务逻辑、换个项目照样能用的函数，沉到**跨项目共享库**里。
- 携带了本系统业务规则、或逻辑有本系统特殊性的工具函数，留在**项目内的工具包**。

判据是"能否原样搬到下一个项目"，不是"看起来像不像工具"。这条守住了，共享库才不会被业务污染，项目内工具包也不会膨胀成第二个共享库。

### 2.2 无校验的底层能力 与 有校验的业务门面

底层数据访问包只做无业务逻辑的增删查改，因此它**必然缺少充分的参数校验**——参数什么算合法，是业务问题，底层没有资格判断。

于是：

- 底层包**不允许被上层直接调用**。
- 由一个业务门面包做参数校验、默认值兜底、多表同事务的编排，**上层只能调门面**。
- 门面对非法输入要报错，不得静默降级。底层对没见过的取值往往有兜底行为，静默降级会让"少查了数据"或"多删了数据"变成无声故障。

底层包里也可以有安全兜底（比如强制清掉对批量删除无意义的分页参数），但那是**防呆不是校验**，不能替代门面的职责。

### 2.3 数据契约 与 行为

承载数据契约的包只放结构定义、常量枚举、以及序列化/表名这类纯声明性的方法，**不含任何业务逻辑与连接性代码**。

枚举常量与它所修饰的实体放在一起，不另设枚举包——常量脱离了它描述的实体就失去了含义。

---

## 三、命名

### 3.1 循环变量与局部变量：名字必须直接说明它是什么

用实际含义命名，不用 `one`、`it`、`v`、`e` 这类占位词。遍历操作类型的集合，变量就叫操作类型；遍历文件的集合，变量就叫文件。读代码的人不该为了知道一个变量是什么而回头去看它从哪个集合里来。

只有下标 `i`、事务句柄 `tx`、上下文 `ctx` 这类**含义由类型唯一确定**的短名例外。

### 3.2 同一概念在全仓只有一个名字

实体的一条记录、查询条件、事务处理器——每个概念在整个代码库里固定一个词，不允许同义词并存。新代码要给东西命名时，先找现有词表里有没有，有就用，没有才新造。

### 3.3 成对的功能用成对的词根

编码/解码、生成/解析、读取/写入、获取/设置、判定/设置、启动/停止、加锁/解锁、创建/打开、打开/关闭、导入/导出——成对的能力必须用**互为镜像的词根**，且参数顺序、返回形态也对称。

转换类函数用「源 2 目标」的形式命名，源和目标都是明确的形态名词。同一族转换要把形态矩阵铺满：如果支持了"从 A 读成中间形态"，就该同样支持"从中间形态写成 A"。

### 3.4 语言分工

标识符一律英文，且按语义翻译不做逐字直译；注释、日志、错误文案一律中文。领域名词以业务方认定的标准中文名为准，不允许在代码里另起一套叫法。

与语言关键字冲突时加后缀区分，不为了避让而扭曲语义。

## 四、函数边界

这是整套规范里最难也最重要的一节。

### 4.1 职责单一且明确

一个函数只干一件事。创建归创建，打开归打开——打开的路径上绝不能"顺手补写"，读的路径上绝不能"顺手创建"。资源不存在、已损坏、凭据不对，就是报错，不是兜底重建。

**一旦一个函数在失败时会改变外部状态，调用方就永远无法安全地重试它。**

### 4.2 边界的好坏，只能在镜像函数上检验

函数的功能与逻辑，在不少情况下都存在哲学意义上的一对：正向与反向、左链路与右链路。成对的函数内部实现会相似甚至完全镜像。

**单看一个函数看不出边界切得好不好。只有当同一套边界能同时容纳多组互为镜像的函数时，这个边界才算合理。**

具体怎么用：

- 设计一个函数时，先问"它的镜像是什么"。
- 再问"镜像函数能不能用同样形态的参数、同样的层级、同样的错误语义写出来"。
- 如果正向函数只需要少量参数、反向函数却要一大堆；或者正向留在这一层、反向被迫下沉到另一层；或者两者对同一种失败给出不同语义——**说明边界切在了错的地方，该改的是边界，不是给反向函数打补丁**。
- 一套边界如果能同时支撑三组以上的镜像关系，基本可以认定是对的。

这条也是重构的信号灯：当你发现某个反向操作"写起来特别别扭"，不要去优化那个反向函数，回头看正向函数的边界。

### 4.3 导出包装 与 非导出实现

成对出现，**中间不留空行，视觉上是一个单元**。

- **导出的那个负责可靠与安全**：加锁、读全局配置与环境、做兜底校验，对外提供无论怎么调都不会出事的入口。
- **非导出的那个负责纯逻辑**：所有依赖都由参数显式传入，不碰锁、不读全局。

这样切有两个收益，缺一不可：

1. 测试可以直接构造任意环境调用非导出实现，不必为了测一段逻辑去搭一整套全局状态。
2. **更高层的内部操作可以复用非导出实现来组合，而不会重入锁**。如果只有加锁的导出版本，任何"读了再写"的复合操作都会死锁或被迫把逻辑抄一遍。

第 2 点比第 1 点更根本。一个包里如果出现了复合操作，却没有对应的非导出纯逻辑层，那个包迟早会长出重复代码或死锁。

### 4.4 两条对称的红线

这两条本身就是一对镜像，**必须一起看**，只守一条会掉进另一条：

| 红线 | 症状 | 判据 | 处置 |
| --- | --- | --- | --- |
| **避免过度拆分** | 函数只是把几行原地代码换个名字包起来，单一调用方，内部无分支 | 内联回去之后，可读性不降反升 | 内联掉。适当平铺能提高可读性，平级的条件罗列不必强行拆 |
| **避免职责焊死** | 一个函数/处理器内部偷偷做了第二件事（典型如在业务写入里塞审计） | 想单独使用其中一件事时做不到 | 拆成各自独立的单元，由调用方**组合**成完整流程 |

两者的共同判据是**职责数**，不是行数。一个很长但只做一件事、且是平级罗列的函数是好函数；一个很短却做了两件事的函数是坏函数。

优先用组合而不是内嵌：把多个独立单元交给一个统一的执行器（事务、管道、中间件链）串起来，比把它们焊进彼此内部更解耦、更灵活，也更容易在下一个场景里换掉其中一个。

### 4.5 可扩展点用注册，不用条件分支

同一类能力会有多种实现时（多种文件格式、多种外部渠道），定义能力接口，各实现自行注册，由注册表统一分发。新增一种实现只加一个子包和一行引入，不改分发逻辑。

**识别用内容不用外壳**：文件格式不靠扩展名判断，协议不靠端口判断——外壳相同而内容不同的情况一定会出现。识别条件要严格到不会误认领，宁可不认领也不能认错。

## 五、错误与日志

### 5.1 唯一句式

在错误的产生点，**先记日志、再返回错误，两处文案保持一致**。

- 日志必须携带上下文对象，全链路才串得起来。
- 字段容器即使为空也保留，形态统一。
- 文案格式固定为「动作，问题」与「动作，完成」，需要携带原始错误时在其后附加。
- 全仓统一一种错误构造方式，不混用多种错误库。

动作名用中文业务词或资源名，让人不看堆栈也知道是哪一步出的事。

### 5.2 级别的判据是"代码能不能处理"，不是"事情有多严重"

| 级别 | 含义 |
| --- | --- |
| **Error** | 代码逻辑**无法兜底、无法处理**的错误情况 |
| **Warn** | 情况虽然奇怪、或需要特别提醒，但**有相应的兜底或处理逻辑** |
| **Info** | 预期之中的情况 |

所以同一件事在不同函数里可以是不同级别：一个查询在"目标不存在时返回空列表"的函数里是 Warn，在"目标不存在就没法继续"的函数里是 Error。判据永远是**这段代码接下来还能不能正常走下去**。

### 5.3 只封装来自业务逻辑外部的错误

- 错误来自**业务逻辑外部**——数据库、外部接口、文件系统、第三方库——**才封装**，加上本层的动作描述。
- 错误来自本系统内部的其他函数，**直接透传**，不再包一层。

内部函数在产生错误时已经按 5.1 记过日志、写过文案了，再包一层只会让最终呈现给调用方的信息变成一串套娃，且同一次故障会在日志里重复出现多遍。

例外只有一种：本层返回的是一个**片段式文案**，需要由调用方补上位置或批次信息才完整。这种情况下日志记在调用方，由它拼出完整文案。

## 六、注释

**严禁引用文档条款，只留"不看就会改错"的，不写过程注释。**

允许写的只有两类：

- **踩过的坑**：为什么必须这样写，不这样写会出什么事。这类注释保护的是下一个改这段代码的人。
- **非显然的取值语义**：某个值的特殊含义无法从类型和名字推出来时。

禁止写的：

- 文档条款号、需求编号、设计文档章节的引用——文档会变、会被重构、会改名，代码里的引用只会变成误导。要说就直接说清楚约束本身。
- 过程注释——代码自己说得清的事不重复说一遍。
- 仅为满足"导出符号要有注释"而写的门面注释。

密度上限由内容决定而不是比例决定，但一个健康的代码库里注释是**稀疏**的：几十行才有一条，且每一条都能回答"为什么"而不是"是什么"。

注释的形态在一个仓库内保持统一即可，重要的是统一，不是选了哪种。

## 七、测试

- **黑盒优先**：默认从包外测公开行为。只有需要触达内部状态时才用白盒。
- **非导出实现是测试的主要抓手**：按 4.3 切好边界之后，绝大部分逻辑都能在不搭建全局环境的前提下被直接调用验证。
- 每个会落盘的测试单元负责清理自己产生的残留，不污染源码树。测试之间用临时目录隔离，不共用固定路径。
- 辅助函数要声明自己是辅助函数，失败时才能报到真正的调用处。
- **失败信息要带实际值与期望值**，只说"不符"的断言在排查时等于没写。
- 必测的几类：边界与异常分支、并发路径、敏感信息不外泄、"无条件"的批量操作不会误伤全量数据、以及每一条被写进规范的不变式。
- 能从最外层入口发起的测试就从最外层发起——它顺带验证了整条链路的装配，也降低了对接方的联调成本。
