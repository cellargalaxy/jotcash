### 对话1

+ 首先需要从第一步，从功能与模型开始重新分析设计
    + 之前设计了很多功能与表，但是感觉还是太多了，搭建与维护成本太多，因此需要往简洁的方向去设计
+ 服务使用docker部署
+ 系统只支持单用户，登录无须用户名，只需要输入密码即可
+ 数据库采用sqlite，需要对整个数据库加密
    + github.com/ncruces/go-sqlite3
+ 数据库加密的私钥，代码不写死，服务端也不存储，私钥由用户的密码生成
    + 每次用户登录，输入密码，服务端通过密码在内存里生成私钥，通过私钥读写数据库
+ 系统定位只记录支出，支出金额为正数，但也允许负数的记录
+ 系统初始化，会生成一个随机密码，会将密码打印到日志中，并且使用该密码生成私钥加密数据库
+ 用户在日志获取到初始密码之后，就可以操作了
    + 可以通过是否有数据库文件来判断是否是第一次启动？
    + 如果用户在第一次没能获取到初始密码，之后日志也不会再次打印密码，因为服务不持久化密码与私钥
    + 这时用户可以通过重装服务，或者直接删除数据库文件，来重新进入初始化
+ 系统没有登录的概念，也没有登录的接口，全部操作都带着密码，服务端再通过密码转为私钥来读写数据库
    + 服务端的内存中也不缓存密码与私钥
+ 需要支持直接导入和导出经过加密的数据库文件
+ 需要支持更换密码（本质是更换数据库的私钥）
    + 先导出旧密码的数据库
    + 调用接口，更换数据库的加密私钥
    + 如果更换私钥过程中有什么以外，则上传旧密码的数据库，来达到回滚的效果
    + 更换密码前，页面需要前置让用户下载旧密码的数据库，避免无备份状态下更换私钥失败
+ 审计
    + 对于全部的写操作都需要有操作记录
    + 操作记录本身仅仅做记录，不能耦合任何的业务功能（例如回滚）
+ 文件管理
    + 文件管理需要有两个实体
    + 实体A是存储文件的元数据，用户绝大部分场景的查询
    + 实体B是存储文件本身，只在下载之类的场景才使用该表
    + 实体B的唯一ID可以采用hash，作为实体A的外键，避免相同文件重复存储，也能用于校验文件数据本身是否有损坏
    + 但是实体A依然允许同一个文件有多行记录，例如文件名称不一样，在不同的时间做了不同的操作
+ 数据录入
    + 本次先实现的CSV表头，并不采用任何银行的CSV表头，而是直接适配本系统CSV表头
    + 合并手动录入与CSV上传两者模式，其合并的思路，会认为用户在页面所手动填写的支出明细，其实就是在填写一份CSV文件数据
    + 因此无论是真实上传CSV文件来进行数据录入，还是手动填写支出明细，都会有一个CSV文件在文件表中
+ 支出明细的字段
    + 前端需要让用户选择入账币种，全部的请求除了带上密码，还需要带上入账币种
    + 允许这种情况
        + 数据库中的数据，入账币种都是人民币，但是用户本次操作，选择的入账币种是美元，操作了数据录入
        + 此时数据库中同时有人民币与美元的入账币种与入账金额数据，金额的统计确实是由于混合了多种币种而有问题
        + 此时用户可以发起入账币种切换的功能，例如切换到人民币，系统会筛选出入账币种!=人民币的数据，重算折算汇率与入账金额
        + 如果某次入账币种切换失败或者中断了，用户继续重试入账币种切换功能即可
    + 在前端页面中，支出明细表格的表头，在入账币种的表头中，需要提示当前存在哪些入账币种
    + 如果有多种入账币种，如果提示用户执行入账币种切换

+ 去重
    + 「支出日期 + 支出金额 + 支出币种」作为疑似重复判定字段
    + 疑似重复的数据，有人工核查手动删除
+ 支出明细的查询，与上传CSV/手动录入，是两个不同页面，但是页面中展示支出明细的表格与样式是复用的
+ 支出明细的表格与样式
    + 表格的表头可选，默认展示的字段和顺序：
        + 支出日期
        + 支出币种
        + 支出金额
        + 折算汇率
        + 入账币种
        + 入账金额
        + 交易对手方
        + 交易备注
        + 支出类型ID
        + 摊分月数
    + 表格完整状态的全字段展示，按照上面支出明细的字段的顺序，平铺展示即可
    + 对于「支出日期 + 支出金额 + 支出币种」相同的行，需要使用一个方框框起来，并且高亮上颜色，便于人工进行重复性检查
+ 在查询的列表页中，页面顶部有筛选框支持筛选所需要的明显，但是在列表页中不支持编辑
+ 如果需要编辑，前端会将列表页当前查询到的明细，转为CSV格式，当作一个CSV文件传到编辑页面里进行编辑
+ 无论是查询转编辑，还是全新的手动创建，还是上传真实的CSV文件，都需要与数据库已有数据进行合并展示，方便用户进行重复性判断
+ 对于查询转编辑或者明细ID有值的CSV文件数据的情况，保留原有的明细ID
    + 对于已删除的数据，复制一行来编辑，这种情况需要生成新的明细ID
+ 对于全新手动创建，或者明细ID为空的CSV文件数据，则生成新的ID以赋值
+ 然后与数据库的数据使用明细ID进行去重，即可达到预期的效果
