## 二、需求分析与方案设计

### 2.1 支出类型查空（前后端）

1. **后端**：`ExpenseType []string` 走 `expense_type in (?)`，SQL 层面天然支持在集合里放入空字符串来命中 `expense_type = ''` 的行，**无需修改 `Where()` 中该分支**。唯一需要的后端改动是删除 `ExpenseTypeLike` 字段与其查询分支（见 2.2）。
2. **前端**：`expense_type` 筛选框改造为与 `bank_name` 等字段一致的"逗号分隔多选组合框"，另加一枚"未填写"复选框；提交时把复选框状态追加为数组里的一个 `''` 元素：
   ```js
   expense_type: [...compact(controls.expense_type.value.split(',')), ...(controls.expense_type_empty.checked ? [''] : [])]
   ```
   拆成"真实类型多选"与"是否查空"两个独立控件，而不是把 `''` 塞进逗号分隔文本里，是因为组合框的 `appendValue`/`compact` 两处逻辑都会把空字符串当噪声清掉（[`static/js/component.js:43`](file:///home/ms/document/code/jotcash/static/js/component.js#L43)、[`static/js/util.js:359-361`](file:///home/ms/document/code/jotcash/static/js/util.js#L359-L361)），这两个函数是多个字段共用的公共逻辑，不能只为支出类型一个字段改语义；复选框方案零touch这两处公共代码。

### 2.2 去除支出类型模糊搜索

- 删除 `model.ExpenseInquiry.ExpenseTypeLike` 字段；
- 删除 `rdb/expense.go` 中 `expense_type like ... escape '\'` 查询分支；
- 前端删除单值模糊组合框 `singleComboField('expense_type_like', ...)`，改为 2.1 所述多选+查空方案；
- 同步清理 `static/js/mock.js` 里 `likeMatch(inquiry.expense_type_like, ...)` 分支，以及不再被引用的英文词条 `'模糊匹配，也可下拉选已有'`。

### 2.3 明细按更新时间排序

- `rdb/expense.go` 的 `expenseSortMap` 白名单新增 `"updated_at asc": "updated_at asc"`、`"updated_at desc": "updated_at desc"`，与既有 `created_at`/`expense_date` 写法完全一致（`updated_at` 是普通时间列，无需像 `expense_amount` 那样转型）；
- 前端 `static/js/config.js` 的 `EXPENSE_SORTS` 白名单同步补两项，命名沿用"创建时间 · 新→旧"的措辞风格；
- `static/js/mock.js` 的 `EXPENSE_SORT_WHITELIST`/`EXPENSE_COMPARATORS` 同步补齐，`updated_at` 用已有的 `compareTime` 比较器。

# 对话2 · 线上部署 `exec /jotcash: no such file or directory` 排障与容器化编译脚本

## 一、依据来源

| 事实 / 契约 | 出处 / 规范 | 采用依据 |
| ----------- | ----------- | -------- |
| 报错现象 | 任务 Prompt 对话2：「线上部署会先编译好jotcash，与install-docker.sh同文件夹……启动报错了：exec /jotcash: no such file or directory」 | 用户在自己的部署机上本地编译好 `jotcash` 二进制，放进 build context 根目录，再跑 `install-docker.sh` |
| Dockerfile 对"预编译二进制"分支的处理 | [`Dockerfile:6-13`](file:///home/ms/document/code/jotcash/Dockerfile#L6-L13)：`if [ -s jotcash ]; then chmod +x jotcash; else CGO_ENABLED=0 GOOS=linux go build -o /jotcash; fi` | 只要 build context 根目录已有非空 `jotcash` 文件，就直接复用、不会重新编译，也**不校验**这个文件是否与最终运行镜像兼容 |
| 最终运行镜像 | [`Dockerfile:15`](file:///home/ms/document/code/jotcash/Dockerfile#L15)：`FROM golang:1.27-alpine` | Alpine 用 musl libc，没有 glibc 的动态链接器路径 `/lib64/ld-linux-x86-64.so.2` |
| 本地复现实测 | 在本沙箱内对本仓库执行一次不带任何 `CGO_ENABLED`/`GOOS` 覆盖的普通 `go build`，`file`/`ldd` 结果：`ELF 64-bit ... dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2`，依赖 `libc.so.6`、`libresolv.so.2`（复现完直接删除，未留存于仓库） | 证实：在一台默认开着 CGO 的类 glibc 宿主机上跑不带 `CGO_ENABLED=0` 的 `go build`，产物是动态链接 glibc 的二进制；这种二进制放进 Alpine 容器，内核找不到它指定的动态链接器路径，`execve` 返回 `ENOENT`，Docker 把这个 `ENOENT` 原样报成"`exec /jotcash: no such file or directory`"——文件确实存在，"不存在"的是它依赖的动态链接器 |
| 项目无需 CGO | 全仓 `grep` 未见任何 `.go` 文件 import `mattn/go-sqlite3`（`go.sum` 里那条是未被引用的历史遗留间接依赖）；sqlite 驱动走的是纯 Go 的 [`github.com/ncruces/go-sqlite3`](file:///home/ms/document/code/jotcash/go.mod#L10)（wazero 编译 wasm 实现，不需要 cgo） | 确认 `CGO_ENABLED=0` 编译不会因为缺 cgo 支持而编译失败或运行异常，Dockerfile 自身的自动编译分支（[`Dockerfile:12`](file:///home/ms/document/code/jotcash/Dockerfile#L12)）走的正是这条路径 |

## 二、结论

`exec /jotcash: no such file or directory` 的根因：**部署机上手工编译 `jotcash` 时没有关闭 CGO（未指定 `CGO_ENABLED=0 GOOS=linux`），产出的是动态链接 glibc 的二进制；这个二进制被 `Dockerfile` 的"预编译二进制"分支原样复用进了 `golang:1.27-alpine`（musl libc）运行镜像，容器里找不到其依赖的 glibc 动态链接器，导致进程起不来。**

**修复**：部署机重新编译，显式加上：

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o jotcash   # GOARCH按部署服务器架构改，服务器上`uname -m`是aarch64就填arm64
```

替换掉原来那份 `jotcash`，再跑 `install-docker.sh` 即可。

按用户确认（AskUserQuestion）：**不改 `Dockerfile`**，只给编译命令。

## 三、方案取舍与变更说明

| 文件路径 | 变更类型 | 变更内容 |
| -------- | -------- | -------- |
| [`build-docker.sh`](file:///home/ms/document/code/jotcash/build-docker.sh)（新增） | 新增运维脚本 | 不重新拼一套编译参数，直接 `docker build --target builder` 复用 `Dockerfile` 自己的 builder 阶段（挂载路径、`WORKDIR`、`COPY . .`、`CGO_ENABLED=0 GOOS=linux`、`GOPROXY` 全部沿用 `Dockerfile` 原文件，一处修改两边自动同步），编译产物再用 `docker create` + `docker cp` 从这个 builder 镜像里拷到宿主机目录（默认与脚本同目录，即 `install-docker.sh`/`Dockerfile` 所在目录）；`--arch`/`--output` 可传参覆盖，交互确认风格与 `install-docker.sh` 保持一致 |

**关键设计点**：
1. **完全复用 `Dockerfile` 的 builder 阶段，不重新发明一套编译命令**：一开始的方案是用 `docker run` 挂载源码到容器内 `/src` 再跑 `go build`，但这样编译环境是脚本自己拼出来的一份"等价复刻"，跟 `Dockerfile` 实际的 `WORKDIR /`、`COPY . .` 不是同一份东西，以后 `Dockerfile` 一改这里就可能悄悄跑偏。改为直接 `docker build --target builder -t jotcash-builder "$repo_root"`，编译发生在 `Dockerfile` 本来就有的那个 builder 镜像里，`Dockerfile` 改了编译参数这边自动跟着变，不用维护两份；
2. **构建产物落地路径必须先清场**：`Dockerfile` 的 builder 阶段有一条"build context 根目录已有非空 `jotcash` 就直接复用、不重新编译"的分支（[`Dockerfile:6-9`](file:///home/ms/document/code/jotcash/Dockerfile#L6-L9)），而这个脚本的目的恰恰是产出一份新的编译结果——如果不清场，脚本会在"复用旧二进制"这条分支上直接躺平，等于什么都没编译。脚本在 `docker build` 之前把仓库根目录下已有的 `jotcash`（如果有）临时挪到 `.jotcash.bak.$$`，构建成功且产物目录就是仓库根目录时丢弃这份备份，其余情况（构建失败、或产物落到了别的目录）都把它原样放回去，用 `trap ... EXIT` 兜底，不会因为构建失败就把用户原来能跑的二进制搞丢；
3. **目标架构必须匹配部署服务器而非编译所在机器**：`Dockerfile` 本身没有 `GOARCH` 相关的 `ARG`/`ENV`，实际编译目标架构是由 `docker build` 用的基础镜像平台决定的，所以脚本用 `docker build --platform linux/$goarch` 控制，而不是自己给 `go build` 传 `GOARCH` 环境变量（那样跟 `Dockerfile` 实际编译方式不是同一套逻辑）；跨架构（比如本机 amd64、服务器是 arm64）需要显式传 `--arch` 且依赖 `docker buildx`/`QEMU` 支持；
4. **不改动 `Dockerfile`/`install-docker.sh` 本身的文件内容**：这条编译路径与"`install-docker.sh` 触发的 `docker build` 全量构建（含最终运行阶段）"是两次独立的 `docker build` 调用，互不影响，用户可以先用这个脚本编好 `jotcash` 再跑 `install-docker.sh`（走"预编译二进制"分支），也可以完全不管这个新脚本，让 `install-docker.sh` 触发的构建自己在容器内联编译。

## 四、验证说明

1. **根因复现**：在本沙箱（Linux glibc 环境）对仓库执行一次不带 `CGO_ENABLED=0`/`GOOS` 的普通 `go build`，`file`/`ldd` 输出证实产物是动态链接 glibc、依赖 `/lib64/ld-linux-x86-64.so.2` 的二进制——与用户报错现象完全吻合的成因，验证完毕后已删除该二进制，未提交仓库。
2. **`build-docker.sh` 静态校验**：`bash -n build-docker.sh` 语法检查通过；本沙箱环境未安装 Docker（`which docker` 未找到），**无法在此环境实际跑一遍容器化编译**，脚本直接调用 `Dockerfile` 现有的 `builder` 阶段（`docker build --target builder`），编译命令本身就是 `Dockerfile` 里那一份，逻辑经过人工逐行走查（含"已有旧二进制时先挪开再还原"这条分支的成功/失败/输出目录不同三种路径），但**未做端到端实机验证**，建议用户在有 Docker 的机器上先跑一遍 `sh build-docker.sh -h` 看参数说明、再跑一遍实际编译确认产物可用（`file` 一下产物应为 `statically linked`）。
3. `go vet ./...`、`gofmt -l .`：本轮未改动任何 `.go` 文件，两项检查按对话1状态保持通过。

## 五、已确认与待确认事项

   - 项目当前不依赖任何需要 cgo 的库，`CGO_ENABLED=0` 编译不影响功能；
   - 按用户选择，本轮不修改 `Dockerfile`/`install-docker.sh`。
2. **待确认**：
   - `build-docker.sh` 因沙箱内无 Docker 环境，只做了语法与逻辑走查，未做实机端到端验证，请用户在真实部署机上跑一遍确认；
   - 部署服务器的 CPU 架构（`amd64`/`arm64`）未经用户明确告知，脚本按编译所在机器的 `uname -m` 猜测，跨架构部署场景需要用户显式传 `--arch` 覆盖。
