## 二、Review 结论与 Bug 清单

用户的业务编排与分层逻辑方向是正确的，但在调整过程中引入了 **1 个致命运行时 Panic**、**2 处测试编译失败** 以及 **2 处可靠性/可观测性隐患**。详细分析如下：

### 1. 【致命 Bug · 运行时 Panic】`robfig/cron/v3` 默认 5 段解析器与配置的 6 段表达式冲突
- **代码位置**：[`corn/corn.go:15-18`](file:///home/ms/document/code/jotcash/corn/corn.go#L15-L18)、[`config/config.go:20`](file:///home/ms/document/code/jotcash/config/config.go#L20)、[`main.go:11-14`](file:///home/ms/document/code/jotcash/main.go#L11-L14)
- **现象**：服务启动即 panic 崩溃。
- **根因分析**：
  - `config/config.go:20` 定义的 `dbBackupCron` 为 `"0 0 4 * * *"`（共 6 段：`秒 分 时 日 月 周`）。
  - `github.com/robfig/cron` (v1) 默认支持 6 段表达式。但升级到 `github.com/robfig/cron/v3` 后，`cron.New()` 默认使用的是标准 5 段 crontab 解析器（`分 时 日 月 周`）。
  - 执行 `object.AddJob("0 0 4 * * *", ...)` 时，解析器直接返回错误：`expected 5 fields, got 6: 0 0 4 * * *`。
  - `corn.Init(ctx)` 返回该 error，`main.go:13` 执行 `panic(err)`，导致服务完全无法启动。
- **修复方案（不破坏现有结构）**：
  保持在 `Init` 中集中注册不变，初始化调度器时开启秒级支持：
  ```go
  object := cron.New(cron.WithSeconds())
  ```

### 2. 【可靠性隐患】`defer object.Start()` 在注册失败时依然启动空调度器
- **代码位置**：[`corn/corn.go:16`](file:///home/ms/document/code/jotcash/corn/corn.go#L16)
- **现象**：若后续 `AddJob` 返回错误（例如表达式配置错误），`defer object.Start()` 依然会在 `Init` 函数退出前触发执行，在后台启动一个空无一物的 cron 协程。
- **规范依据**：`doc/decisions/编码规范.md` §3.1「一旦一个函数在失败时会改变外部状态，调用方就永远无法安全地重试它」。
- **建议**：取消 `defer`，在所有 `AddJob` 成功注册后，显式调用 `object.Start()`。

### 3. 【可观测性缺失】`BackupDbJob.Run()` 静默吞噬错误
- **代码位置**：[`corn/corn.go:30-34`](file:///home/ms/document/code/jotcash/corn/corn.go#L30-L34)
- **现象**：
  ```go
  func (this *BackupDbJob) Run() {
      ctx := util.GenCtx()
      service.Backup(ctx)
  }
  ```
  `service.Backup(ctx)` 会返回 error。定时任务是由 cron 独立协程触发的异步动作，如果磁盘写满、文件权限受阻导致备份失败，当前写法直接丢弃了返回值，也没有任何日志记录。线上发生备份失败时将完全处于静默盲区。
- **建议**：检查 error 并记录 `logrus.WithContext(ctx).WithFields(...).Error("定时任务，备份数据库异常")`。

### 4. 【编译失败】`corn/corn_test.go` 遗留对已删除函数 `start` 的调用
- **代码位置**：[`corn/corn_test.go:37`](file:///home/ms/document/code/jotcash/corn/corn_test.go#L37)
- **现象**：`corn/corn_test.go:37:13: undefined: start`，导致 `go test ./corn` 无法编译。
- **根因分析**：
  先前对话 1 生成的测试用例 `TestInitIllegalCron` 中调用了 `start(ctx, dbBackupCron)`。由于用户将 `start` 删除、统一由 `Init` 负责，该测试用例未同步更新。
- **建议**：将该测试用例适配为直接测试标准解析或测试 `Init`。

### 5. 【编译失败】`rdb/backup.go` 与 `rdb/backup_test.go` 命名断层
- **代码位置**：[`rdb/backup.go:32,353,369`](file:///home/ms/document/code/jotcash/rdb/backup.go#L32)、[`rdb/backup_test.go:456,681,781`](file:///home/ms/document/code/jotcash/rdb/backup_test.go#L456)
- **现象**：`go test ./rdb` 报 9 处编译错误：
  - `too many arguments in call to backup (have 5, want 2)` (行 456, 459, 462, 473)
  - `undefined: BackupDb` (行 681, 753, 801)
  - `undefined: backupDb` (行 781, 791)
- **根因分析**：
  1. `rdb/backup.go` 原有 5 参数函数为 `backup(ctx, srcPath, srcToken, dstPath, dstToken)`，既有测试 `TestBackupIllegalArgument` 直接对其进行边界验证。用户将其重命名为 `copyDb`，而新加的 2 参数纯文件复制函数命名为 `backup(ctx, srcPath, dstPath)`，导致既有单测实参个数不匹配。
  2. 既有用例 `TestBackupDb` 与 `TestBackupDbGuard` 编写时使用的是 `BackupDb` 与 `backupDb`。用户在手动调整时将其重命名为 `Backup` 与 `backup`，未同步更新测试文件。
- **建议**：在保持用户统一的 `Backup` 命名同时，可更新测试中的调用名，或在 `rdb` 层提供向下兼容别名。

## 三、业务逻辑评价（`service/rdb.go`）

```go
func Backup(ctx context.Context) error {
	err := repo.Backup(ctx)
	//备份失败多半是盘满，清理照样要做，正好给下一轮腾地方
	eee := repo.ClearBackup(ctx)
	if err != nil {
		return err
	}
	return eee
}
```

1. **执行顺序**：先执行全量备份 `repo.Backup`，后执行保留上限清理 `repo.ClearBackup`。此顺序确保备份成功后，目录内备份总数严格受控在 `DbBackupLimit` 之内，不会出现提前多删一份旧备份的风险。
2. **失败兜底逻辑**：备份失败时依然执行清理（释放磁盘空间为后续轮次腾挪空间），且优先返回核心错误 `err`（备份失败本身）。逻辑清晰且契合实际运维场景。
3. **并发安全**：底层 `rdb.Backup` 加了写锁 `dbLock.Lock()`，全量复制期间所有 `NewTransaction`（持有读锁 `dbLock.RLock()`）均被互斥等待，能够保障复制到的一定是静止状态的完整密文数据库文件。

# 对话3 · 免费免登录汇率接口调研与实现方案

## 一、需求与约束梳理

1. **调用方特征**：
   - 接口签名：[`GetExchangeRate(ctx context.Context, expenseCurrency, accountingCurrency string, expenseDate time.Time) (decimal.Decimal, error)`](file:///home/ms/document/code/jotcash/exchange_rate/exchange_rate.go#L10)；
   - 核心参数：消费币种、记账币种、**明细日期（`expenseDate`）**。
   - 场景特征：记账软件存在大量**历史账单导入**与**跨期对账**场景，接口**必须支持指定历史日期查询**，而不能仅提供最新汇率快照。
   - 日期边界：消费往往发生在周末或法定节假日（银行休市），接口必须能智能对齐或回退至最近一个有效交易日。
2. **硬性指标**：
   - **完全免费**；
   - **免登录 / 无须申请 API Key / 无须绑定鉴权 Token**；
   - 格式标准友好（JSON）、支持交叉汇率（如 USD->CNY、EUR->CNY、HKD->CNY、JPY->CNY 等主流币种）。

## 三、首选方案深度解析：Frankfurter API

### 1. 数据权威性与可靠性
- 数据源：**欧洲中央银行（European Central Bank, ECB）** 官方发布的每日基准汇率（每天欧洲中部时间 16:00 左右更新）。
- 架构属性：完全开源（支持本地自建 Docker 部署）、无商业强制绑定、已持续稳定运行多年。

### 2. 接口协议与实测报文
- **最新汇率**：`GET https://api.frankfurter.dev/v1/latest?base={FROM}&symbols={TO}`
  ```json
  {"amount":1.0,"base":"USD","date":"2026-09-15","rates":{"CNY":6.7115}}
  ```
- **指定历史日期汇率**：`GET https://api.frankfurter.dev/v1/{YYYY-MM-DD}?base={FROM}&symbols={TO}`
  - 实测历史日期 `2026-01-15`（周四）：
    ```json
    {"amount":1.0,"base":"USD","date":"2026-01-15","rates":{"CNY":6.9673}}
    ```
  - 实测非交易日 `2026-01-17`（周六）：
    ```json
    {"amount":1.0,"base":"USD","date":"2026-01-16","rates":{"CNY":6.9697}}
    ```
    *自动向前顺延至周五 1 月 16 日，无需客户端复杂的重试兜底逻辑。*

### 3. 支持的币种矩阵
涵盖绝大部分高频出境/海淘消费币种：
`USD` (美元), `EUR` (欧元), `CNY` (人民币), `JPY` (日元), `GBP` (英镑), `HKD` (港币), `SGD` (新加坡元), `AUD` (澳元), `CAD` (加元), `CHF` (瑞士法郎), `KRW` (韩元), `THB` (泰铢), `NZD` (新西兰元), `SEK` (瑞典克朗), `MYR` (林吉特) 等 31 种。

## 四、落地实现方案设计（`exchange_rate.go`）

1. **入口逻辑与边界保护**：
   - 相同币种（如 `USD -> USD`）直接返回 `decimal.NewFromInt(1)`（调用层 `service/expense` 已前置过滤，但在 `exchange_rate` 包做自检兜底，符合 `编码规范.md` §2.1 第四层要求）；
   - 日期格式化：`expenseDate.Format("2006-01-02")`。若日期晚于今天，则直接请求 `/v1/latest`。
2. **HTTP 客户端与健壮性**：
   - 使用带超时控制的 `http.Client`（5 秒超时，避免阻塞外部调用）；
   - 绑定请求上下文 `http.NewRequestWithContext(ctx, ...)`，支持调用方主动取消或超时级联。
3. **本地进程内二级缓存（优化网络与频控）**：
   - **理论依据**：历史某天的基准汇率是**不可变事实**（Immutable）。例如查询 `2026-01-15 USD->CNY`，无论查询多少次结果均相同。
   - **缓存设计**：使用带读写锁的内存映射 `sync.Map` 或 `map[string]decimal.Decimal`（Key: `FROM_TO_YYYY-MM-DD`）。
   - 命中缓存直接返回，未命中发起 HTTP，成功后写入缓存。批量导入几十笔账单时只会有 1~2 次外部网络调用，零延迟响应。
4. **小众币种兜底（可扩展性）**：
   - 当 Frankfurter 报 404（表明币种未被 ECB 纳入，如 TWD 或 MOP）时，可退避至 jsDelivr `@fawazahmed0/currency-api` 获取汇率；若仍不支持则明确返回错误。
