## 二、结论

**空跑时几十 M 的内存，绝大部分不是"业务数据"或"泄漏"，而是这个 Go 二进制本身体积大、依赖多，启动时把自己的代码段/只读数据段大量"翻页"进了物理内存，叠加 Go runtime 的堆 arena 保留；数据库连接不常驻，只在有请求时短暂占用，这解释了"有时几十、有时上百 M"这种随负载波动的现象。**

### 1. 空跑 RSS 的构成拆解（实测，生产等价构建）

沙箱内按生产同款命令 `CGO_ENABLED=0 GOOS=linux go build` 编译出的二进制（`file` 确认为 `statically linked`），冷启动、不发任何请求，稳定后：

```
VmRSS: 28204 kB   (~27.5 MB)
```

`pmap -x` 按 RSS 从大到小排列，前几项已覆盖 RSS 总量的 97% 以上：

| 映射 | RSS | 占比 | 是什么 |
| ---- | --- | ---- | ------ |
| 二进制 `r-x`（代码段 .text） | ~9.05 MB | 33% | 进程启动时被**实际执行过**的机器码页面 |
| 二进制 `r---`（只读数据段 .rodata 等） | ~8.35 MB | 30% | 字符串常量、反射类型元数据、`static/` 前端资源（`go:embed`）等 |
| 匿名 `rw`（Go heap arena 主段） | ~6.24 MB | 22% | Go runtime 堆区，已经过 GC（`GODEBUG=gctrace=1` 实测首次 GC 后**存活对象仅 ~1MB**，见下） |
| 匿名 `rw`（另一保留段） | ~2.06 MB | 7% | Go runtime 调度器/GC 辅助结构 |
| 其余（栈、少量小映射） | ~2.5 MB | 8% | 线程栈等零碎项 |

`GODEBUG=gctrace=1` 输出的第一行：

```
gc 1 @0.007s 2%: ... 3->4->1 MB, 4 MB goal, 0 MB stacks, 0 MB globals, 12 P
```

`1 MB` 是 GC 后**堆里存活对象的大小**——业务真正"活着"的数据不到 1MB，跟 27.5MB 的 RSS 差了一个数量级。这说明瓶颈根本不在"业务对象常驻内存"，而在二进制自身的代码/数据页面 + Go runtime 的固定开销。

**为什么代码段这么大**：本项目依赖较重——尤其是 [`github.com/ncruces/go-sqlite3`](file:///home/ms/document/code/jotcash/go.mod#L10) 把整个 SQLite C 源码离线转译成了一份 `/home/ms/go/pkg/mod/github.com/ncruces/go-sqlite3-wasm/v2@v2.1.35300/sqlite3.go`（5.9MB 纯 Go 源码，全部是 SQLite 的等价实现），加上 `gorm`、`gin`、`go-playground/validator`（大量反射）、`gabriel-vasile/mimetype`（内置文件类型特征库）等，整个二进制未 strip 时 57.7MB；`gin.Default()` 在默认 debug 模式下启动时会遍历打印全部路由、执行较多初始化路径，这些初始化过程会把相当一部分 `.text`/`.rodata` 页面提前"翻页"进物理内存，即使后续用不到也不会自动退回。这是**结构性代价**，不是 bug。

### 2. 排除的可能性（已代码交叉核对，排除）

- **不是 sonic JIT 占用**：gin 只有编译时显式加 `-tags=sonic` 才会启用 `bytedance/sonic`（[`gin@v1.12.0/codec/json/json.go`](file:///home/ms/go/pkg/mod/github.com/gin-gonic/gin@v1.12.0/codec/json/json.go) 的 `go:build` 约束是 `!jsoniter && !go_json && !(sonic && ...)`），项目的 `Dockerfile`/`build-docker.sh` 均未加此 tag；`go list -deps .` 对当前 `go.mod` 实际依赖图确认 `sonic` 包根本不在最终二进制里。
- **不是 wazero 虚拟机常驻**：当前锁定的 `go-sqlite3` v0.34.0 已经不依赖 wazero（见"依据来源"表的冲突说明），SQLite 是被转译成纯 Go 代码直接编译进二进制执行，没有额外的 wasm 运行时对象常驻。
- **不是数据库连接池常驻**：`rdb.go` 每次业务调用都新开、用完关闭一条连接（见"依据来源"表），空跑时没有任何活跃连接。
- **不是短期内存泄漏**：同一进程连续 100 次 `GET /api/ping`（走 gin 默认中间件链，不触发数据库），RSS 从 28.9MB 涨到 29.9MB，涨幅 1MB 左右且不再继续攀升，符合正常的运行时元数据/连接缓冲增长，没有持续爬升的迹象。

### 3. "有时上百 M"的合理解释（推断，标注为待确认）

结合代码结构，能让 RSS 明显高于这个 ~28MB 基线的场景大概率是：

- **并发请求叠加**：每个并发中的业务请求都会各自开一条新 SQLite 连接（[`rdb/rdb.go:187`](file:///home/ms/document/code/jotcash/rdb/rdb.go#L187) `NewTransaction`），且各自独立最多可以长到 256MB（`wrap.go:34`）；如果某几个请求恰好带较大结果集/排序（`PRAGMA temp_store=memory` 让排序临时数据也吃这块内存），瞬时堆占用会显著上升；
- **Go 的 GC 不会让 RSS 立刻跟着回落**：即使这些连接很快关闭、堆对象被回收，Go runtime 的 scavenger 把空闲的堆 arena 页面还给操作系统（`madvise`）有一定延迟，短时间内 `ps`/`top` 看到的 RSS 会停留在这次峰值附近，过一段时间才慢慢降回基线。

这两点能解释"同一个服务，有时看到几十M，有时看到上百M"——是**峰值残留**，不是稳定的高基线，也不是持续泄漏。**待确认**：具体是哪类请求/哪个时间点触发了上百M，需要用户在真实环境里配合 `date` 时间点回忆一下当时有没有做过大批量查询/导入导出（[`config.PathExportDb`](file:///home/ms/document/code/jotcash/config/handler.go)/`PathImportDb`，导入上限 1GB，导出/导入这类接口最可能瞬时吃内存），本沙箱无法访问生产真实流量，不能断言。

# 对话2 · 数据库文件会不会被整个加载进内存

## 一、依据来源

| 事实 | 出处 | 采用依据 |
| ---- | ---- | -------- |
| 加密文件的读写实现按 4KB 定长块、逐块走 | `/home/ms/go/pkg/mod/github.com/ncruces/go-sqlite3@v0.34.0/vfs/adiantum/hbsh.go:70-73`（`blockSize = 4096`，注释"Use the default SQLite page size"）、`hbsh.go:115-149`（`ReadAt`：`for ; min < max; min += blockSize { h.File.ReadAt(h.block[:], min); ... }`）、`hbsh.go:151-199`（`WriteAt` 同样逐块 read-decrypt/encrypt-write） | jotcash 打开数据库时用的是 `vfs=adiantum`（[`rdb/rdb.go:23`](file:///home/ms/document/code/jotcash/rdb/rdb.go#L23) `vfsName = "adiantum"`、[`rdb/rdb.go:131`](file:///home/ms/document/code/jotcash/rdb/rdb.go#L131)），这层就是负责加解密的 VFS，实测其 I/O 单位是单个 4KB 块，而不是整个文件 |
| 每次块读写只占一块 4096 字节的临时缓冲区 | `hbsh.go:91` `block [blockSize]byte`（`hbshFile` 结构体里只有这一个固定大小数组，不是按文件大小分配的切片） | 每个打开的文件对象自带的缓冲区大小固定为 4KB，跟数据库文件多大无关 |
| 加密层下面的操作系统文件访问，用的是标准 `pread`/`pwrite`，不是 `mmap` | `/home/ms/go/pkg/mod/github.com/ncruces/go-sqlite3@v0.34.0/vfs/os_unix.go:28-40`（`osReadAt`：`file.ReadAt(p, off)`）、`os_unix.go:42-48`（`osWriteAt`：`file.WriteAt(p, off)`），`os` 参数是标准库 `*os.File` | Go 标准库 `os.File.ReadAt/WriteAt` 在 Linux 上对应内核的 `pread64`/`pwrite64`，按偏移量读取指定长度，不会把文件映射进地址空间或整份读入 |
| 全仓 `grep` 未发现任何 `mmap_size`/`cache_size` 相关 PRAGMA 覆写 | `grep -rn "cache_size\|mmap_size" --include=*.go .` 只匹配到 `rdb/rdb.go:132/136/144` 的 `textkey`/`temp_store`/`user_version` 三条 PRAGMA，均与整份加载无关 | jotcash 从未调大 SQLite 的页缓存或开启内存映射 I/O，用的都是 SQLite 编译期默认值（一个较小、有上限的页缓存） |
| 全仓 `grep` 未发现 `vfs/memdb`（该驱动自带的"纯内存数据库"VFS）被引用 | `grep -rn "memdb" --include=*.go .` 无结果；`rdb/rdb.go:16` 只 `import _ "github.com/ncruces/go-sqlite3/vfs/adiantum"` | 排除了"用内存 VFS 打开数据库"这种会导致整份数据都在内存里的用法 |

## 二、结论

**不会。** jotcash 这套 SQLite 驱动栈的 I/O 路径是"按 SQLite 页大小（4KB）逐块读写磁盘文件"，不是把整个 `.db` 文件读进内存：

1. 最底层（`vfs/os_unix.go`）直接调用 Go 标准库 `*os.File` 的 `ReadAt`/`WriteAt`，对应 Linux 的 `pread`/`pwrite`——只读写调用方指定偏移量和长度的那一段字节，跟文件总大小无关，读 1.6MB 的库文件和读 1.6GB 的库文件走的是同一条代码路径，内存开销不随文件大小变化。
2. 上面包一层 `adiantum`（jotcash 用的加密 VFS）对每次读写按 4096 字节的块边界切开，每块单独解密/加密后再拷给调用方，这一层自己只维护一个 4KB 的临时缓冲区（`hbshFile.block`），不会攒下整份文件的明文或密文。
3. 再上面是 SQLite 自身的页缓存（page cache）——这是所有 SQLite 使用场景（不只是这个 Go 实现）都有的机制，缓存"最近用到的页"，有上限（未被 jotcash 用 `PRAGMA cache_size` 调大，走 SQLite 编译期默认值，量级在几 MB），跟数据库文件总大小无关，缓存满了会按 LRU 淘汰旧页，不是无限增长到把整个文件吃进去。

所以对话1里测到的空跑内存（~28MB）和数据库文件大小（当前 `resource/jotcash.db` 约 1.6MB）之间没有对应关系——即使这个库文件涨到几百 MB，只要不是单次查询要扫描/排序全表，连接的内存占用也不会跟着线性涨到那个量级；真正会让内存明显升高的是"一次查询要处理的数据量"（比如无索引的全表扫描、大结果集排序，这些临时数据会被 `PRAGMA temp_store=memory`（[`rdb/rdb.go:136`](file:///home/ms/document/code/jotcash/rdb/rdb.go#L136)）放进连接自己的内存而不是磁盘临时文件），而不是"数据库文件本身有多大"。

## 三、已确认与待确认事项

1. **已确认**：
   - 数据库文件的读写按 SQLite 标准 4KB 页粒度走 `pread`/`pwrite`，没有 `mmap`，也没有把整份文件读入内存的代码路径；
   - jotcash 未覆写 `cache_size`/`mmap_size`，页缓存大小走 SQLite 默认值，有上限；
   - 内存占用量级与数据库文件大小无直接关系，与单次查询/排序需要处理的数据量、并发连接数关系更大（呼应对话1的结论）。
2. **待确认**：
   - SQLite 编译期默认 `cache_size` 的确切字节数未在本仓库或其依赖中显式配置到具体数值，本轮未做进一步实测（如需精确数值可执行 `PRAGMA cache_size;` 查询当前生效值，本轮未改代码/未在生产环境操作，未做此项）。

# 对话3 · 纠正后的现象（刚启动30M，刷新页面暴涨到300M）—— 定位到未分页的明细查询

## 一、依据来源

## 二、复现实验（沙箱内，未改动仓库任何交付代码）

在沙箱里拷贝一份仓库副本，往 `rdb` 包里加了一个**临时测试文件**（只存在于沙箱副本，未写入本仓库，跑完已连同临时数据库一起删除），直接调用 jotcash 现有的 `create`/`open`/`NewExpenseSelectHandler`（一个字都没改），流程：

1. 建一个全新的加密 SQLite 库；
2. 批量插入 5 万条合成的 `model.Expense` 记录（字段内容是随手编的示例值，不是真实数据）；
3. 用**跟线上完全同一个** `NewExpenseSelectHandler`（`Page`/`PageSize` 缺省为 0）跑一次查询——即复现前端刷新首页时后端实际执行的那条不分页查询；
4. 对查询结果做一次 `json.Marshal`——模拟 `gin` 的 `c.JSON()` 序列化响应体这一步；
5. 每一步之间读 `/proc/self/status` 的 `VmRSS`。

实测结果：

| 步骤 | VmRSS | 相对上一步 |
| ---- | ----- | -------- |
| 插入 5 万行后（基线） | 43.6 MB | — |
| 查出 5 万行（不加 LIMIT，全部 `Find()` 进 Go 对象） | 102.0 MB | +58 MB |
| 对这 5 万行 `json.Marshal`（序列化出 33.2 MB 的 JSON 字节流） | 280.9 MB | **+178 MB** |
| 把切片/字节流引用置空，但不主动 `runtime.GC()` | 280.9 MB | 0（没有自动回落）|

## 三、结论

**"刷新一次页面内存直接从 30M 冲到 300M"这个现象，跟对话1里"进程有没有泄漏"是两件不同的事，根因是首页默认查询没有分页、没有行数上限。**

1. 首页刷新会立刻重新触发 `SelectExpense`——前端按设计"筛选拉全集"（[`expense_inquiry.js:15-18`](file:///home/ms/document/code/jotcash/static/js/expense_inquiry.js#L15-L18)），请求体里没有 `page_size`；后端 `pageLimit` 在 `pageSize<=0` 时直接跳过 `LIMIT`（[`rdb/inquiry.go:20-22`](file:///home/ms/document/code/jotcash/rdb/inquiry.go#L20-L22)），把所有满足"最近一年"筛选条件的明细一次性 `Find()` 进内存，再整体 `json.Marshal` 成一个大响应体。
2. 复现实验证明：仅 5 万行明细，走这条链路就能让进程 RSS 从 43.6MB 冲到 280.9MB，涨幅 +237MB——**跟用户描述的 30M→300M（约 +270MB）在同一个量级**。真实触发这个量级需要用户库里"最近一年"范围内的明细行数达到类似规模（几万行上下），具体是不是这个原因、真实命中了多少行，需要用户确认（见下方待确确认）。
3. `json.Marshal` 这一步比"查出 Go 对象"本身还贵（+178MB vs +58MB）：`encoding/json` 用反射逐字段编码，每个字段都要过一遍 `decimal.Decimal`/`time.Time` 各自的 `MarshalJSON`，加上转义、缓冲区增长，成本远高于原始数据量（33MB 的 JSON 文本背后是 178MB 的临时分配）。
4. "释放引用后 RSS 没有自动回落"这一点跟对话1的结论完全一致——**这次峰值会在 `ps`/`top` 里挂一段时间**，不是内存泄漏，但用户体感上就是"刷新一下，内存再也没降下来"。如果短时间内多次刷新，或者多个浏览器标签/多个人同时刷新，会有多个这样的峰值叠加（各自新开一条 SQLite 连接，见对话1），峰值互相不共享、按次数累加，比单次刷新更容易把内存推得更高。

## 四、已确认与待确认事项

1. **已确认**：
   - "刚启动 30M"与对话1实测的生产等价基线（~28MB）一致，启动阶段的结论不变；
   - 首页刷新会重新执行 `SelectExpense`，该查询在 `page_size` 缺省时不加 `LIMIT`，服务端也没有任何最大跨度/最大行数的兜底校验（`checkTimeRange`/`checkAmountRange` 只查起止顺序，不查跨度）；
   - 用沙箱内复现实验证实：同一条真实代码链路（不分页 `Find()` + `json.Marshal`），5 万行明细就能把进程内存推高 200+MB 且释放引用后不自动回落，量级上能解释用户观察到的"刷新一下涨 270M"这个现象；
   - 候选取值接口（`selectExpenseDistinct`）走的是 SQL `DISTINCT`，不是这次内存暴涨的主因，已排除。
2. **待确认（不可推断，需用户提供信息，本轮未接触用户真实数据库）**：
   - 用户库里"最近一年"筛选范围内的明细实际行数是多少——这是决定"刷新一次到底会涨多少"的关键变量，本沙箱只能用合成数据证明机制成立，不能代表用户真实数据量；
   - 用户刷新时页面停留在哪个筛选条件/哪个路由（默认是 `/expense` 最近一年，但如果之前手动把筛选放宽过、或停在核实视图 `loadVerify` 反查全库，实际拉取的范围可能更大）；

# 对话4 · 优化方案（仅方案与可行性分析，未改代码）

## 一、方案制定前发现的关键约束（与历史资料/既有测试交叉核对）

在着手设计优化方案前，先核对了一遍现有测试，发现一条**明确锁定当前"不封顶"行为**的既有测试，这条约束会直接否掉最直观的那种"优化"思路：

| 事实 | 出处 | 含义 |
| ---- | ---- | ---- |
| 不传分页字段应原样留空，不能被兜底成有限值 | [`service/repo/expense_test.go:19-21`](file:///home/ms/document/code/jotcash/service/repo/expense_test.go#L19-L21)：`if inquiry.PageSize != 0 { t.Errorf("不传分页应原样留空，前端导出csv靠它拉全量"...) }` | 断言的名字和报错文案已经把"为什么不能兜底"写死了：**前端"导出查询结果"这个功能，靠的就是后端不加LIMIT返回全集** |
| 传了很大的 `page_size` 也不应该被服务端封顶 | [`service/repo/expense_test.go:29-31`](file:///home/ms/document/code/jotcash/service/repo/expense_test.go#L29-L31)：`if inquiry, _ = checkExpenseInquiry(ctx, model.ExpenseInquiry{PageSize: 100000}); inquiry.PageSize != 100000 { t.Errorf("分页不应再封顶"...) }` | 明确禁止"服务端悄悄设一个上限、超过就砍掉多余的行"这类做法 |

**结论**：对话3里"要不要给这条查询加一个硬性行数上限"这个最直接的优化思路，会跟这两条已经写进测试、且测试文案已经说明了业务理由（导出全量）的约束**正面冲突**。任何方案如果要引入"结果集超过阈值就拒绝/裁剪"，都必须先让用户明确知道这会打破"导出查询结果"在大数据量下的可用性，不能默默选一边。

## 二、三个可选方向及可行性分析

### 方案A：服务端硬性行数上限（拒绝过大查询）
- **做法**：在 `service/repo/inquiry.go` 或 `SelectExpense` 里先做一次 `Count()`，超过阈值（比如5万/10万行，可配置）直接报错"筛选结果过多，请缩小范围"，不再 `Find()`。
- **冲突**：与上面两条测试锁定的"不封顶，前端导出csv靠它拉全量"直接矛盾——一旦数据量超过阈值，"导出查询结果"这个功能就会失效。
- **改动量**：小（一两处代码 + 改写/删除那两条测试断言）。
- **可行性结论**：**不推荐单独采用**，除非用户明确愿意接受"数据量大了之后，明细列表/导出会直接报错、拿不到全量"这个产品取舍，并同意同步改掉那两条现有测试。

### 方案B：服务端流式分批查询 + 流式JSON编码（推荐）
- **做法**：不改变"能查/能导出全量、不封顶"这个已经被测试锁定的语义，只改**服务端怎么把这份全量数据吐给客户端**——用 GORM 的 `FindInBatches` 按批（比如500行/批）读，每批读完立刻对每一行 `json.Marshal`，直接写一段到 HTTP 响应流后就丢弃这批对象，不再像现在这样先 `Find()` 整批进一个大切片、再对整个切片一次性 `json.Marshal`。
- **已有先例，风格可复用**：项目里 [`handler/rdb.go`](file:///home/ms/document/code/jotcash/handler/rdb.go) 的 `Export`/`dbFileWriter` 已经在解决同一类问题（流式导出整个加密数据库文件）：自定义一个 `io.Writer` 包一层 `gin.Context`，首次 `Write()` 时才落响应头；如果流已经开始写、后面又出错，就只能记日志、断开连接，**回不去** `c.JSON()` 的干净错误响应——`handler/rdb.go:38-40` 的注释原文就是"数据库导出，已开始写出，改不回错误响应"。这套模式可以原样复用到"明细查询"这个接口上。
- **量化收益**：对话3里用真实代码复现过的实验——5万行合成数据，"不分页 `Find()`"和"整体 `json.Marshal`"两步合计把进程 RSS 从 43.6MB 推到 280.9MB（+237MB）。换成分批流式后，任意时刻内存里最多只有一个批次（约500行）的对象和它们的JSON片段，峰值不再随命中行数线性增长，理论上能把这条路径的峰值内存压到几MB量级的常数级别，而不是几百MB。
- **代价/风险（明确列出，不回避）**：
  1. 响应体的 JSON 结构（`{"code":200,"msg":"","data":{"object":[...],"count":N}}`）保持不变，**前端不用改一行代码**；
  2. 但服务端这一路要绕开通用的 `util.NewGinPost`，改动会落在三处：`rdb/expense.go`（新增一个流式版本的 select handler）、`service/repo/expense.go`（新增一个流式版本的 `SelectExpense`）、`handler/expense.go`+`handler/handler.go`（新增自定义 handler、改路由注册）；`service/expense.go` 里现有的 `SelectExpense` 包装函数会因此失去唯一调用点，需要一并清理，避免留下死代码；
  3. **error-handling 的天然限制**：一旦响应流已经开始写（也就是写完 JSON 前缀之后），这次 HTTP 请求就"回不了头"——如果后续批次查询中途出错（比如磁盘故障），没法再改写成一个干净的 `{code:500,msg:...}` 错误响应，只能记日志后断开连接，前端拿到的是一段不完整/不合法的 JSON，会被当成网络错误处理。这不是新增的风险类型（`Export` 接口已经是这个约定），而且全程都在同一个已经成功打开的本地 SQLite 事务内读数据，中途失败概率本身很低；
  4. `FindInBatches` 会在已有的 `Order()` 后面追加一个按主键（`id`）的次级排序做稳定分页——不影响返回哪些行，只是让原来"同一排序键值的行之间谁先谁后"从"不保证"变成"确定"，算是让行为更可预测，不算功能回归。
- **改动量**：中（预计一轮改动、跑通现有单测、补一条新场景单测即可完成）。
- **可行性结论**：**推荐**。不触碰已被测试锁定的"不封顶"产品语义，不改前端、不改 API 契约，风格上完全复用项目里 `Export` 这个已有的流式响应先例，能把对话3实测出的"+237MB"峰值大部分削掉。

### 方案C：真正的服务端分页（彻底改造，本轮不建议直接动手）
- **做法**：后端强制加 `LIMIT`/`OFFSET`，前端 `page_expense.js` 改成真正翻页回后端查；但"疑似重复分组"（跨页去重，[`page_expense.js:88-103`](file:///home/ms/document/code/jotcash/static/js/page_expense.js#L88-L103)）和 `page_statistic.js` 的统计图表聚合，现在都是在浏览器端拿着全集算的，分页后这两块逻辑都得挪到后端做聚合；"导出查询结果"现在直接用 `state.rows`（已经是全集）拼CSV，分页后也得单独做一个流式导出接口。
- **可行性结论**：这是产品级改造，正面推翻 `expense_test.go` 里"不封顶，前端导出csv靠它拉全量"这条被测试锁定的设计意图，改动面覆盖前后端契约、统计聚合、去重分组三块逻辑，需要专门立项、单独评估，**本轮不建议直接动手**。

## 三、根因分析

### 1. 主因：内存峰值由「这一刷打了几个请求」决定，不由「查了多少行」决定

链路是这样接起来的：

```
一个业务请求
  → repo.XxxYyy → rdb.NewTransaction(rdb/rdb.go:187)
    → rdb.open(rdb/rdb.go:121)
      → driver.Open(... vfs=adiantum ...) 的初始化回调
        → conn.Exec("PRAGMA textkey=<口令>")   (rdb/rdb.go:132)
          → adiantum 的 hbshFile.Pragma       (hbsh.go:101-104)
            → adiantumCreator.KDF             (adiantum.go:26-32)
              → argon2.IDKey(口令, pepper, 3, 64*1024, 4, 32)
                → 一次性 make 出 64 MiB 的 Go 堆块，跑3轮内存硬化
```

用 `-memprofilerate=1` 抓的分配剖面直接把这条路径钉死了（`go tool pprof -sample_index=alloc_space`）：

```
      flat  flat%   sum%        cum   cum%
 3407872kB 91.78% 91.78%  3408025kB 91.78%  golang.org/x/crypto/argon2.initBlocks
   ...
    15.35kB                    3410972kB 91.86%  github.com/cellargalaxy/jotcash/rdb.open
     0.39kB                    3279843kB 88.33%  github.com/cellargalaxy/jotcash/rdb.NewTransaction
```

**全进程 91.78% 的堆分配都来自 Argon2 的 `initBlocks`，且百分之百经由 `rdb.open`。** 3.4GB ÷ 64MiB = 52 次，正好等于那一轮测试里 `open()` 的调用次数——**一次 `open()` 恰好一次 64 MiB，没有别的分配源能跟它同一个数量级**。

刷新首页打6个请求，其中5个候选取值是 `Promise.all` 并发发出的（[`expense_inquiry.js:83-87`](file:///home/ms/document/code/jotcash/static/js/expense_inquiry.js#L83-L87)），于是 5×64 MiB **同时**存活在堆上，峰值 ≈ 384MB —— 与用户看到的「一下子上升到300M」量级完全吻合。

### 2. 为什么「内存也没有被释放」

这不是泄漏。看上面表格第3行：`runtime.GC()` 之后 `HeapAlloc` 立刻从 405.8MB 掉回 **2.5MB**——对象全回收了，**一个字节都没泄漏**；但同一时刻 `HeapIdle` 是 413.4MB 而 `HeapReleased` 只有 9.0MB，也就是这 400 多MB 以「空闲但仍属于本进程」的形式挂在堆区里，RSS 自然还是 423.3MB。

Go 运行时的后台 scavenger 归还空闲页是**按堆目标缓慢进行**的：堆一旦被 400MB 的瞬时峰值撑大，堆目标就跟着抬高，运行时会把这些页面留着等下一次分配复用，短时间内不还给操作系统（本轮实测等10秒只降了 1.5MB）。另一轮实验里手动调 `debug.FreeOSMemory()` 立刻把 RSS 从 166.8MB 压回 **37.1MB**，反向印证了「RSS 里那一大坨是没归还的空闲堆页，不是活着的业务数据」。

### 3. 为什么对话5的方案B「没有效果」

方案B削的是**跟行数线性相关**的那部分开销（把「整表 `Find()` 进切片 + 整体 `json.Marshal`」换成分批），这一刀本身是有效的：本轮实测同样5万行，用游标流式读时 RSS 只从 36.6MB 涨到 44.6MB，而对话3实测的旧链路是 43.6MB → 280.9MB。

但用户实际看到的那 300MB **压根不是行数带来的**——它是 `open()` 的固定开销 × 请求数。**只要请求数不变，这部分一分钱都省不下来**，所以从用户视角看「改成流式之后依然没有效果」，完全说得通。方案B 没做错，只是治的不是这个病。

### 4. 附带查出的缺陷：`FindInBatches` 的主键游标跟排序键错位，会静默漏行/重复行

**这条比内存问题更严重，属于数据正确性问题。**

[`rdb/expense.go:234`](file:///home/ms/document/code/jotcash/rdb/expense.go#L234) 的 `tx.FindInBatches(&rows, util.DbBatchSize, ...)`：gorm 在入口处**追加**一个主键排序（于是最终 SQL 是 `ORDER BY expense_date desc, expense.id`），批与批之间用 `WHERE expense.id > 上一批最后一行的id` 接力。

前端默认排序是 `expense_date desc`，明细是按时间顺序录进去的，主键（雪花ID）与支出日期基本同向递增，于是 `expense_date desc` ≈ **主键倒序**：第一批100行拿到的是**id最大的那100行**，末行的id是这100个里最小的；下一批的接力条件 `id > 那个值` 圈住的恰恰是**刚刚已经吐过的那99行**，于是第二批把它们原样再吐一遍，第三批因为不足100行就停了。结果就是上表里的 205行 → 吐出199行、其中99行重复、**105行永远拿不到**，而响应体里的 `count` 字段仍然诚实地写着 205。

前端 `page_expense.js` 拿这份 `rows` 去做表格分页、疑似重复分组、统计图表和「导出查询结果」的CSV——**这些全都会静默地少一半数据、还带着重复行**。

为什么对话5跑的既有用例没发现：[`handler/expense_test.go:177-192`](file:///home/ms/document/code/jotcash/handler/expense_test.go#L177-L192) `TestSelectExpenseWithoutPage` 铺的205行**支出日期全都一样**（都是 `2026-01-02`），排序键没有区分度，`ORDER BY expense_date desc, id` 退化成纯主键升序，主键游标恰好成立，于是一路绿灯。本轮新加的 `TestSelectExpenseWithoutPageSort` 只把日期改成两两不同，问题立刻暴露。

## 四、优化方案

### 方案一（主因，推荐）：把 Argon2 派生出来的密钥缓存起来，只算一次

**做法**：`rdb` 包自己实现一个 `adiantum.HBSHCreator`（上游公开接口，见 `vfs/adiantum/api.go:44-70` 的 `Wrap` 与 `HBSHCreator`），`KDF` 里加一层「口令 → 32字节密钥」的进程内缓存，命中就直接返回，不命中才跑 Argon2；`HBSH` 原样调 `lukechampine.com/adiantum` 的 `adiantum.New(key)`。然后 `vfs.Register("jotcash", adiantum.Wrap(vfs.Find(""), 自己的creator))`，把 [`rdb/rdb.go:23`](file:///home/ms/document/code/jotcash/rdb/rdb.go#L23) 的 `vfsName` 指向它。

**关键前提：派生出来的密钥必须与现在完全一致，否则存量库文件全部打不开。** 本轮写了临时探针（跑完已删除）实测验证过：

- 用**标准 `adiantum` VFS** 建库写数据 → 换用**缓存KDF的自定义VFS**去读，**读得出来**，说明只要沿用同一套参数（`argon2.IDKey(口令, "github.com/ncruces/go-sqlite3/vfs/adiantum", 3, 64*1024, 4, 32)`）派生结果逐字节一致，**磁盘格式不变、零迁移、存量库文件直接可用**；
- 错口令依然打不开，未削弱鉴权；
- 开5条连接的分配量对照：

| | 5条连接的 `TotalAlloc` 增量 |
| ---- | ---- |
| 现状（标准 adiantum） | **335.8 MB** |
| 缓存KDF（第1/2/3轮） | **0.2 MB / 0.2 MB / 0.2 MB** |

即 **单条连接从 67.2MB 降到 0.04MB 量级（约1700倍）**，刷新首页那 384MB 的峰值直接消失；顺带每个请求还省掉约70ms的 Argon2 计算（6个请求就是几百毫秒的首屏延迟）。

**必须一并处理的安全权衡（重要）**：Argon2 是内存硬化KDF，它那 64MiB+70ms 的成本本来就是**给暴力猜口令用的门槛**。如果不加区分地把任意口令的派生结果都缓存起来，在线猜口令的第二次尝试起就变成近乎免费。因此缓存的写入时机必须收口：[`rdb/rdb.go:139-146`](file:///home/ms/document/code/jotcash/rdb/rdb.go#L139-L146) 已经有一次 `PRAGMA user_version` 探针来判定口令对不对，**只有这一步成功才把该口令的密钥留在缓存里，失败就把它从缓存剔除**，这样错口令每次都要重新付全额 Argon2 成本，暴破门槛一点不降；再叠加已有的 `tokenBan`（[`handler/token_ban.go`](file:///home/ms/document/code/jotcash/handler/token_ban.go)）失败封禁，风险可控。另外缓存里留的是派生密钥，属于敏感材料常驻内存——但该进程本来每个请求都要拿明文口令（JWT claims 里的 `ClientToken`）去开库，敏感度没有实质变化。换口令/导入这类会重写库文件的操作（`ChangeToken`/`Import`）走的是新口令、新缓存键，**不影响正确性**，但建议顺手清掉旧条目，别让废弃密钥无限期驻留。

**改动量**：小，集中在 [`rdb/rdb.go`](file:///home/ms/document/code/jotcash/rdb/rdb.go) 一个文件（新增一个 creator 类型 + `init` 里注册 + `vfsName` 改名 + `open` 失败路径剔除缓存），`go.mod` 里把 `golang.org/x/crypto`、`lukechampine.com/adiantum` 两条从 indirect 提为直接依赖（两者已在依赖图里，不引入新模块）。不动API契约、不动前端、不动表结构。

### 方案二（加固，可与方案一叠加）：给进程加软内存上限

在 `main.go` 里 `debug.SetMemoryLimit(...)`（配合 `GOGC`），让运行时在逼近上限时主动做GC与归还页面。这治的是「峰值过后RSS赖着不走」这个症状，**不减少分配总量**，所以只能当兜底；单独用它，请求一多照样会被真实的 Argon2 分配顶上去。**待用户确认**：是否愿意为进程设一个固定内存上限、设成多少（取决于部署机器规格，本轮不掌握生产配置，不能替用户定）。

### 方案三（更彻底，但改动面大）：复用连接，不再每请求现开现关

维持一个进程级的 `*sql.DB` 连接池，`Import`/`ChangeToken` 这类持写锁的操作负责把池关掉重建。这样 Argon2 一个进程只跑几次，连接建立、`gorm.Open` 的元数据初始化等开销也一并省掉。但它会推翻 [`rdb/rdb.go`](file:///home/ms/document/code/jotcash/rdb/rdb.go) 现在「读锁罩住整条连接生命周期」这套设计（`TestChangeTokenDuringTransaction`、`TestTransactionUnlockOnFail` 等用例都锁着这套语义），**属于结构性改造，本轮不建议**。方案一能用十分之一的改动量拿到同一条曲线上绝大部分收益。

### 方案四（必须做，修第4条缺陷）：把 `FindInBatches` 换成 `Rows()` 游标

`FindInBatches` 的主键游标语义与「任意排序键」天然不兼容，**没有配置能绕开**（gorm 硬编码用 `clause.PrimaryKey` 做接力条件）。正确的流式原语是 `tx.Rows()` + `tx.ScanRows(rows, &row)`：**一条 SQL、一个游标，读一行吐一行**，`ORDER BY` 原样交给 SQLite，不存在批与批之间的接力假设，也不会像现在这样每批都重跑一次全表排序。

本轮用临时探针（已删除）在5万行上验证过这个替代方案：

| 排序 | `count` | 实际吐出 | 写出 | 耗时 | 请求后 RSS |
| ---- | ------- | ------- | ---- | ---- | --------- |
| `expense_date desc` | 50000 | **50000** | 31.8 MB | 1.91s | **40.8 MB** |
| `id asc` | 50000 | **50000** | 31.8 MB | 1.94s | **41.6 MB** |

即：**不漏行、不重复、内存平坦**（对照对话3旧链路的 43.6MB → 280.9MB），同时保住了对话5「流式、不封顶、前端零改动」的全部目标。`ExpenseSelectStreamHandler` 里 `PageSize>0` 走 `Find()`、`PageSize<=0` 走批处理这个分叉也可以一并收掉——游标对两种情况都成立，代码反而更短。

### 建议的实施顺序

1. **方案四**（数据正确性，最紧急——现在线上「导出查询结果」拿到的CSV是缺行且带重复的）；
2. **方案一**（内存主因，收益最大、改动最小）；
3. 方案二按需（等方案一落地后再看实测曲线决定要不要加）；
4. 方案三不做。

## 三、方案一答疑

### 1. map 里存的是什么？——存的是 Argon2 的**输出**，不是 Argon2 本身

「复用的Argon2」这个说法要纠一下：Argon2 是个**纯函数**，同样的（口令 + pepper + 参数）永远算出同样的结果，它没有可以留下来复用的对象或状态。可以复用的是**它算出来的那 32 字节密钥**。所以：

```
map[string][]byte     // key = 口令(明文)，value = argon2.IDKey(...) 算出的 32 字节派生密钥
```

派生参数必须逐字照抄现在的（`argon2.IDKey([]byte(口令), []byte("github.com/ncruces/go-sqlite3/vfs/adiantum"), 3, 64*1024, 4, 32)`，见 `vfs/adiantum/adiantum.go:32`），否则算出来的密钥不一样，**存量库文件全部打不开**。对话6已用探针实测验证过：参数照抄之后，**标准 `adiantum` VFS 建的库能被缓存版原样读出，磁盘格式不变、零迁移，错口令依然打不开**。

### 2. 锁该怎么加？——担心的那个问题真实存在，实测如下

本轮把两种加锁写法都实现出来、在**冷缓存 + 6个并发请求**（就是刷新首页那一刷）下实测（探针已删除）：

| 加锁设计 | Argon2 **实际算了几次** | `TotalAlloc` 增量 | 耗时 |
| ---- | ---- | ---- | ---- |
| **设计A**：`RWMutex` 只罩住 map 读写，算 Argon2 在锁外 | **6 次** | **403.0 MB** | 258 ms |
| **设计B**：`Mutex` 罩住「查表 → 算 → 写回」整段 | **1 次** | **67.4 MB** | 57 ms |

**担心的是对的，而且就是设计A**：6 个请求同时查表全部落空，于是各自在锁外算一遍 Argon2，6×64MiB 照样上去，缓存等于白加。

不过有个细节要纠正：**问题不是"只有最后一个 set 到 map 里"导致值不对**。Argon2 是确定性的，6 个协程算出来的是**同一个值**，谁最后写进 map 都一样，map 里的内容始终是正确的。真正的损失是**白算了 6 次、白分配了 6×64MiB**——是浪费，不是错误。

**结论：用最普通的 `sync.Mutex`，`Lock()` 之后把「查表 → 没有就算 → 写回」全做完再 `Unlock()`（`defer` 即可），不要用 `RWMutex` 只罩 map。** 代价是冷路径被串行化：第一个请求算 57ms，其余 5 个排队等它，等完直接命中缓存——从上表看，**总耗时反而从 258ms 降到 57ms**（本来 6 个并行跑 Argon2 就在互相抢 CPU），没有付出任何延迟代价。缓存热了以后每次只是一次 map 查表，锁的持有时间是纳秒级，不会成为瓶颈。

### 3. 什么时候该把条目从 map 里删掉？——这是个安全问题，必须处理

Argon2 那 64MiB + 57ms 本来就是**故意设给暴力猜口令的门槛**。如果不加区分地把任何口令的派生结果都留在 map 里，猜口令的第二次尝试起就变成免费查表，门槛没了。

收口办法：[`rdb/rdb.go:139-146`](file:///home/ms/document/code/jotcash/rdb/rdb.go#L139-L146) 已经有一次 `PRAGMA user_version` 探针在判定口令对不对（错了就报「口令错误或数据库文件损坏」）。**在那条失败分支里把这个口令从 map 里剔掉**即可：对的口令算一次、长期命中；错的口令每次都要重付全额 Argon2 成本，门槛一点没降。再叠上已有的 `tokenBan`（[`handler/token_ban.go`](file:///home/ms/document/code/jotcash/handler/token_ban.go)，失败5次封5分钟），风险可控。

**这也是为什么要用 map、而不是只缓存一条**：如果只留单条，一个错口令请求会把正确口令那条顶掉，下一个正常请求就得重算——等于给了一个白送的骚扰手段。用 map 按口令分槽，错口令只影响它自己那一格，加上失败即删，map 不会无限涨。

换口令/导入（`ChangeToken`/`Import`）走的是新口令、新的 map key，**不影响正确性**；顺手把旧条目清掉即可，属于卫生问题不是正确性问题。

### 4. 敏感性

map 里留的是派生密钥，属于敏感材料常驻内存。但该进程本来每个请求都要拿**明文口令**（JWT claims 里的 `ClientToken`）去开库，敏感度没有实质变化。

## 四、方案三跟方案一到底差在哪

一句话：**方案一改的是「开一条连接有多贵」，方案三改的是「还要不要开连接」。**

## 五、`TestSelectExpenseWithoutPageSort` 那个缺陷到底是什么

### 手算一遍就清楚了

假设库里 5 行，批大小 2（真实是 100，`util.DbBatchSize`）。明细是按时间顺序录进去的，所以**越新的行 id 越大**：

| id | 支出日期 |
| -- | ------- |
| 1 | 1月1日 |
| 2 | 1月2日 |
| 3 | 1月3日 |
| 4 | 1月4日 |
| 5 | 1月5日 |

前端要的是「支出日期最新在前」，即 `ORDER BY 支出日期 desc` → 期望顺序 **5,4,3,2,1**。

gorm 的 `FindInBatches` 是这么翻批的：**在你的排序后面追加一个主键排序，然后用「主键大于上一批最后一行的主键」当接力条件**。于是：

- **第1批**：`ORDER BY 支出日期 desc, id LIMIT 2` → 拿到 **id=5, id=4**，这一批最后一行是 id=4；
- **第2批**：`WHERE id > 4 ORDER BY 支出日期 desc, id LIMIT 2` → `id > 4` 只圈得住 id=5，而 id=5 **第1批已经吐过了** → **把 id=5 又吐了一遍**；只返回 1 行 < 批大小 2，循环判定"到底了"，结束。

最终吐出 **5, 4, 5** ——id=5 重复，**id=1、2、3 永远拿不到**，而响应体里的 `count` 仍然诚实地写着 5。

### 根子在哪

`FindInBatches` 的游标假设是「**按主键升序一路往后走**」：走过的 id 一定比没走的小，所以 `id > 上一批末行` 正好圈住"还没走的"。这个假设**只有在排序键就是主键升序时才成立**。

而前端默认排序是 `expense_date desc`（[`expense_inquiry.js:36`](file:///home/ms/document/code/jotcash/static/js/expense_inquiry.js#L36)、[`service/repo/expense.go:15`](file:///home/ms/document/code/jotcash/service/repo/expense.go#L15)），明细按时间顺序录入使得日期倒序 ≈ **主键倒序**，方向正好相反：第一批先把 id 最大的那批吃掉，游标 `id >` 反而把剩下的行**全挡在外面**。

真实跑出来的 SQL（本轮实测打印，非推断）：

```sql
SELECT * FROM `expense` WHERE `expense`.`deleted_at` IS NULL
  ORDER BY expense_date desc,`expense`.`id` LIMIT 100
SELECT * FROM `expense` WHERE `expense`.`id` > 2609171504445950 AND `expense`.`deleted_at` IS NULL
  ORDER BY expense_date desc,`expense`.`id` LIMIT 100
SELECT * FROM `expense` WHERE `expense`.`id` > 2609171504446250 AND `expense`.`deleted_at` IS NULL
  ORDER BY expense_date desc,`expense`.`id` LIMIT 100
```

205 行的实测结果就是这么来的：吐出 199 行 = 第1批100行 + 第2批把其中99行**重吐一遍**，去重后只剩 100 行，**105 行丢失**。

### 影响面

前端 `page_expense.js` 拿这份 `rows` 去做表格分页、疑似重复分组、统计图表和**「导出查询结果」的CSV**——全都会静默少一半数据、还带重复行。

### 为什么既有用例没抓到

[`handler/expense_test.go`](file:///home/ms/document/code/jotcash/handler/expense_test.go) 的 `TestSelectExpenseWithoutPage` 铺的 205 行**支出日期全都一样**（都是 `2026-01-02`），排序键没有区分度，`ORDER BY expense_date desc, id` 退化成纯主键升序，游标假设恰好成立，于是一路绿灯。对话6新加的 `TestSelectExpenseWithoutPageSort` 只是把日期改成两两不同，问题立刻暴露。**这条用例在回滚后应当自动转绿，可以直接留着当回归护栏。**

## 三、效果实测

改动后重测「刷新一次首页 = 1条明细查询 + 5条候选取值并发」（临时探针，跑完已删除）：

| 库里行数 | 刷新一次(6个请求) `TotalAlloc` | 明细响应体 | 耗时 |
| ---- | ---- | ---- | ---- |
| 3 行 | **0.9 MB** | 0.00 MB | 11 ms |
| 1000 行 | **6.7 MB** | 0.64 MB | 37 ms |
| 2000 行 | **6.0 ~ 12.7 MB** | 1.29 MB | 70~94 ms |

对照改动前（对话6实测，3行小库）：**403.6 MB / RSS 36.2MB→423.3MB 且不回落**。

单条连接的开销（对话6实测 → 本轮）：**67.2 MB / 约70ms → 0.042 MB / 约0.2ms**。

**冷启动第一次要说明**：进程重启后，第一个带用户口令的请求仍要实打实算一次 Argon2（约64MiB、几十毫秒），之后才一路命中缓存。启动时的 `init()→Create` 在库文件已存在时直接返回、不开库，所以这一次落在第一个业务请求上。这是设计使然——把这个成本去掉就等于去掉暴破门槛。

**旁证**：全量单测总耗时明显下降（`rdb` 39.7s→4.7s、`handler` 56.3s→17.4s、`service/repo` 11.3s→2.1s），因为测试里每开一条连接就少跑一次 Argon2。

## 四、验证说明

1. `gofmt -l .` 无输出、`go build ./...`、`go vet ./...` 均通过；
2. `go test ./... -count=1` **全部 `ok`**，包括对话6那三条原本是红的复现用例（`rdb.TestOpenMemory`、`handler.TestSelectExpenseWithoutPageSort`、`handler.TestSelectExpenseRefreshMemory`）与本轮新增的三条；
3. `go test ./rdb/ -race` 通过——KDF 缓存是新引入的共享可变状态，专门过了一遍竞态检测；
4. 期间 `service/expense` 的 `TestParseAccountingCurrency` 偶发失败过一次。已排查：该包 `go list -deps` 里**不含** `jotcash/rdb`，与本轮改动无依赖关系；失败原因是它断言 `AccountingAmount == ExpenseAmount × ExchangeRate` 的精确相等，而记账金额会按 `AmountScale=2` 四舍五入——当实时查到的 JPY 汇率小数位较多时（实测那次是 `156.60668752`，100×它=15660.668752，落库成 15660.67）这条断言就挂。**是依赖实时汇率的既有用例缺陷，本轮未动**，当前树上连跑3次均通过；
5. 临时探针文件已全部删除，工作区没有残留。

## 五、已确认与待确认事项
