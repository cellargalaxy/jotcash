## 二、需求分析与方案设计

### 2.1 账单结构解析与逆向分析

通过对账单 PDF 进行页面文本与版面结构逆向提取分析：
1. **页眉与特征标识**：
   - 包含主标题 `中国工商银行信用卡历史明细（电子版）`；
   - 包含卡号及账期元数据：`卡号: ************XXXX 户名：*某某 起止日期：YYYY-MM-DD — YYYY-MM-DD`；
   - 表头固定 10 个字段列：`入账日期`、`交易卡号`、`收支`、`交易币种`、`交易金额`、`入账币种`、`入账金额`、`账户余额`、`摘要`、`交易场所`。
2. **页脚标识**：
   - 包含汇总行：`本页支出算术合计：...`、`本页交易笔数：...`、`本页收入算术合计：...`、`下单时间：...`、`共X页 第 X 页`；
   - 包含防伪流水水印：`中国工商银行 流水号...`。
3. **明细区域特征**：
   - 每笔明细固定以 `YYYY-MM-DD` 日期起始；
   - 支持多页连续明细提取与单卡/多张关联卡（如主副卡不同卡号后四位）；
   - 币种支持多币种（如 `人民币`、`美元` 等）；
   - 金额支持千分位逗号（如 `1,xxx.xx`、`-1,xxx.xx`）；
   - 支持多行或由于版面宽度换行的交易场所拼接（如长商户名、带括号分店名称）。

### 2.3 核心业务逻辑与方案取舍

1. **贷方转帐还款行的过滤处置（核心决议）**：
   - 账单中的「贷方转帐/还款」通常为定期信用卡还款记录（涵盖人民币与外币还款）；
   - 在个人支出记账体系下，信用卡还款为资产账户间内部划转。若将还款记为负支出，将导致当月生活消费被还款金额完全冲销（报表金额严重失真）；若记为正支出，则导致先消费后还款被双重记账；
   - 依据项目权威定稿 `记账系统功能与模型.md` §一 5（「只记支出、丢弃还款行，负金额仅代表退款/冲正」）及用户明确确认，解析器判定 `direction == "贷" && (summary == "转帐" || summary == "转账" || summary == "还款")` 时直接跳过该笔记录。
2. **退货与退款的负金额映射**：
   - 账单中的贷方退款/退货记录（摘要为 `退货` 或非还款贷方项目），精准冲抵前置消费；
   - 解析器将其准确解析为负数金额（`amount.Abs().Neg()`），完整符合支出抵扣契约。
3. **多行与断行商户名拼接**：
   - 表格中部分单元格内容因列宽限制产生折行（如带括号的长商户名称）；
   - 解析器采用状态机按 `^\d{4}-\d{2}-\d{2}` 划分每笔交易 Chunk，将 `摘要` 字段之后的所有文本行拼接合并为完整的 `Counterparty`。
4. **纯 Go PDF 库选型**：
   - 引入 [`github.com/ledongthuc/pdf`](https://github.com/ledongthuc/pdf)，纯 Go 编写、无 CGO 依赖、BSD 开源协议；
   - 经实测，`GetPlainText` 对中文字符集与表格结构保留良好，满足静态编译与极速导入要求。

## 二、需求分析与架构设计

### 2.1 保守过滤规则设计

1. **业务背景与痛点**：
   - 信用卡账单中的「贷」方向表示银行卡资金增加（即欠款减少），包含两类性质截然不同的流水：
     - **信用卡还款 / 转账**：属于个人多账户之间的资金内部划转，并非消费逆操作，不应记入支出（若记为负支出将虚减消费，若记为正支出将双重记账）；
     - **消费退货 / 商户退款 / 冲正**：属于原有支出的抵扣，必须作为负数金额记入支出系统（如 `model.Expense{ExpenseAmount: -20.00}`）。
2. **保守性（Conservative）决策准则**：
   - 若过滤规则过于宽松（例如过滤所有 `贷` 或匹配包含 `转` 字），极易将合法的消费退款（如部分商户退款摘要包含特殊文本）误删，导致支出数据丢失且不可恢复；
   - 因此系统采取**最小集严格丢弃**策略：
     ```go
     func isRepayment(direction, summary string) bool {
         return direction == "贷" && (summary == "转帐" || summary == "转账" || summary == "还款")
     }
     ```
   - 任何未精准命中上述三项摘要的明细（无论是 `借` 还是 `贷`），一律保留在输出明细中；对于 `贷` 方记录，统一做绝对值取负 `expenseAmount = expenseAmount.Abs().Neg()`，保障支出抵扣逻辑的正确性与安全性。

### 2.2 严格 Support 认领机制

1. **同行不同版式与可选字段的风险**：
   - 商业银行不同卡种（如多币种卡、单币种卡、联名借贷合一卡、商务卡）导出的明细列可能存在差异（例如缺少 `账户余额` 列，或者增设 `交易国家`、`清算汇率`、`原始交易金额`、`授权码` 等可选列）；
   - 导出渠道（网银网页端 vs 手机银行 App vs 柜面打印版）生成的 PDF 排版与表头结构也可能存在变种；
   - 若采用宽松的 `strings.Contains` 判断单列，极易导致其他未知版式被误认领，后续解析由于列偏移引发字段错位或运行时恐慌。
2. **严格比对实现方案**：
   - 定义静态常量预期表头列：
     ```go
     expectedColumns = []string{
         "入账日期", "交易卡号", "收支", "交易币种", "交易金额",
         "入账币种", "入账金额", "账户余额", "摘要", "交易场所",
     }
     ```
   - 在 `Support` 中定位第 1 页从 `入账日期` 起始至 `交易场所` 结束的子串块，切分为列片段数组 `cols`；
   - 采用 `slices.Equal(cols, expectedColumns)` 进行全元素同序精确比对；
