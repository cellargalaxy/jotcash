## 二、需求分析与方案

### 2.1 任务一：解锁页面支持密码自动填充工具识别

#### 2.1.1 核心痛点与历史成因分析
在原实现中（`static/js/page_unlock.js`），两把口令输入框的定义为：
```javascript
const input = el('input', { class: 'form-control', type: 'password', placeholder, autocomplete: 'off' });
```
此设计导致主流密码管理器（Bitwarden、1Password、Chrome Autofill、Safari 钥匙串等）完全无法正常工作的根源在于：
1. **显式禁用了自动填充**：`autocomplete: 'off'` 明确指示浏览器/插件不要对该输入框进行历史记录和自动填充建议。
2. **缺乏表单语义标记**：两个 `<input>` 均无 `name` 与 `id` 属性，且外层 `<label>` 缺少 `for` 属性关联。
3. **多密码框启发式冲突（Password Heuristics Collision）**：表单中同时存在两个匿名的 `type="password"` 输入框。在现代密码管理器的表单分类器中，双密码框且无用户名字段的标准模式会被判定为「修改密码/用户注册（新密码 + 确认新密码）」流程，从而导致：
   - 错误触发“生成强密码”提示；
   - 自动填充时将同一密码重复填入两个输入框；
   - 或者判定为未知表单而完全忽略，无法保存或填充。

#### 2.1.2 架构评估：将「后端口令作为账户名、前端口令作为密码」是否合适？
**结论：高度合适，且是目前主流密码生态下最优雅、兼容性最佳的工程解法。**

从跨学科与系统安全工程视角进行深度剖析：
1. **规范与标准适配（Standards Alignment）**：
   - WHATWG HTML 规范中，`autocomplete="username"` 的定义即用于表示“该字段为账户标识符”。规范并未强制该字段必须是邮箱或公开 ID，其本质是区分不同凭证空间的命名键（Key Name）。
   - 将后端口令标记为 `autocomplete="username"`，前端口令标记为 `autocomplete="current-password"`，完全符合 WHATWG 对身份认证表单（Authentication Form）的标准契约。
2. **密码管理器数据模型拟合（Data Model Fit）**：
   - 绝大多数主流密码管理器（Bitwarden, 1Password, Chrome, Safari, KeepassXC 等）的基础条目数据模型均为 `(URI, Username, Password)`。
   - 在 jotcash 的架构中，后端口令是服务实例级别的访问密钥（在宿主机配置文件 `jotcash.yaml` 中持久化，服务生命周期内不变）；前端口令则是用户个人的加密主密钥（永不落盘）。
   - 用户在密码管理器中只需维护一条标准的站点条目：
     - **URI**：`http://your-host:7678/`
     - **用户名 (Username)**：`<后端口令>`
     - **密码 (Password)**：`<前端口令>`
   - 解锁时，无论是 Bitwarden 的快捷键（`Ctrl+Shift+L`）、右键填充，还是浏览器的原生凭据浮窗，均可**一键同时将两把口令准确填入对应的输入框**；解锁成功后，浏览器也能精准感知表单提交并弹出“保存/更新密码”提示。
3. **安全与隐私权衡（Security & Privacy Trade-offs）**：
   - **防窥保护**：后端口令输入框依然保留默认 `type="password"` 遮罩，并保留「显示/隐藏」切换按钮。所有现代密码管理器均完全支持在 `type="password"` 元素上解析 `autocomplete="username"`。
   - **凭证暴露面**：后端口令作为密码管理器中的 Username 字段存储。在密码管理器客户端查看条目时，Username 通常默认明文显示，但这与后端口令在服务端落盘（`jotcash.yaml` 为明文）的安全级别是完全对等的，没有扩大攻击面。
4. **更换口令注意事项**：
   - 用户在设置页更换口令时更换的是前端口令（数据库加密密钥），此时密码管理器提示更新凭据时只需更新 Password 字段，Username（后端口令）保持不变；若运维在后端修改了 `jotcash.yaml` 中的 `server_token`，则在密码管理器中更新 Username 字段。心智模型清晰直观。

### 2.2 任务二：编写 Docker 构建与部署脚本

#### 2.2.1 镜像构建方案（`Dockerfile`）
参考 `/home/ms/document/code/survive_monitor/Dockerfile`，结合 jotcash 的服务特性进行适配：
1. **两阶段构建与二进制复用**：
   - 延续 `builder` 阶段的二进制检测机制：若当前工作目录下已有编译好的 `jotcash` 二进制文件（如宿主机预编译产物），直接跳过源码编译，提升构建速度；若无二进制，则通过 `go mod download && CGO_ENABLED=0 GOOS=linux go build -o /jotcash` 进行全静态无 CGO 编译。
2. **时区参数化支持（核心要求）**：
   - 原 `survive_monitor/Dockerfile` 采用硬编码 `Asia/Shanghai` 且执行了 `apk del tzdata`。一旦删除 `tzdata`，容器在运行期无法再查找其他时区的 zoneinfo 数据。
   - 优化方案：
     - 引入 `ARG TZ="Asia/Shanghai"` 与 `ENV TZ=${TZ}`，支持构建阶段通过 `--build-arg TZ=...` 指定默认时区。
     - **保留 `tzdata` 数据包**（仅 ~3MB），既确保在构建期正确链接 `/etc/localtime` 与 `/etc/timezone`，又允许在运行期通过 `docker run -e TZ=...` 动态指定任意全球时区，Go 运行时与 Alpine 均能即时生效。
3. **卷与工作目录**：
   - 声明 `VOLUME /log` 与 `VOLUME /resource`，分别承载 go_common 日志与应用持久化数据（`jotcash.yaml`、`jotcash.db`、`db_backup`）。
   - 工作目录保持 `WORKDIR /`，与 jotcash 代码中硬编码的相对路径 `resource/...` 与 `log/...` 保持基准一致。
4. **健康检查机制**：
   - 容器内监听端口为 `7678`。
   - 基于 jotcash 的公开探活探针 `GET /api/ping`，配置健康检查命令：
     `HEALTHCHECK --interval=30s --timeout=5s --retries=3 CMD wget --spider -q http://127.0.0.1:7678/api/ping || exit 1`

#### 2.2.2 安装部署脚本方案（`install-docker.sh`）
参考 `/home/ms/document/code/survive_monitor/install-docker.sh`，并针对需求进行增强：
1. **参数化与交互式兼备（核心要求）**：
   - 支持通过 CLI 命令行选项传参：
     - `-s, --server_name`：容器与镜像名称，默认 `jotcash`。
     - `-p, --listen_port`：宿主机映射端口，默认 `127.0.0.1:7678`。
     - `-r, --resource`：支持参数指定 resource 挂载路径（命名卷或宿主机物理目录）。
     - `-t, -z, --timezone`：支持参数传入 docker 内时区，缺省自动探测宿主机时区，兜底 `Asia/Shanghai`。
   - 若未通过参数传入，则无缝回退至交互式输入（带缺省提示与回车默认值），与 `survive_monitor` 的操作心智完全一致。
2. **挂载路径智能识别**：
   - 若 `resource` 为相对路径（如 `./resource` 或 `data`），自动转为绝对路径以适配 Docker bind mount；
   - 若 `resource` 为目录路径，提前创建宿主机目录；若为纯卷名（如 `jotcash_resource`），则调用 `docker volume create`。
3. **全流程自动化闭环**：
   - 打印配置汇总并等待用户确认。
   - 优雅停用、移除同名老容器与老镜像。
   - 调用 `docker build --build-arg TZ="$timezone" -t $server_name .`。
   - 调用 `docker run -d --restart=always -v log:/log -v "$resource":/resource -p $listen_port:7678 -e server_name=$server_name -e TZ="$timezone" $server_name`。

### 4.2 Docker 脚本产出
- `Dockerfile` 完整内容：
  ```dockerfile
  FROM golang:1.24-alpine AS builder
  ENV GOPROXY="https://goproxy.cn,direct"
  ENV GO111MODULE=on
  WORKDIR /
  COPY . .
  RUN if [ -s jotcash ]; then \
          echo "Binary already exists, skipping build"; \
          chmod +x jotcash; \
      else \
          echo "Binary not found, building from source"; \
          go mod download && \
          CGO_ENABLED=0 GOOS=linux go build -o /jotcash; \
      fi

  FROM golang:1.24-alpine
  COPY --from=builder /jotcash /jotcash
  ARG TZ="Asia/Shanghai"
  ENV TZ=${TZ}
  RUN sed -i 's/dl-cdn.alpinelinux.org/mirrors.tuna.tsinghua.edu.cn/g' /etc/apk/repositories
  RUN apk update
  RUN apk --no-cache add ca-certificates
  RUN apk --no-cache add tzdata && cp /usr/share/zoneinfo/${TZ} /etc/localtime && echo "${TZ}" > /etc/timezone
  VOLUME /log
  VOLUME /resource
  WORKDIR /
  HEALTHCHECK --interval=30s --timeout=5s --retries=3 CMD wget --spider -q http://127.0.0.1:7678/api/ping || exit 1
  CMD ["/jotcash"]
  ```

# 对话2 · 基础镜像版本订正与分析（对齐 go.mod 1.27）

## 一、依据来源

| 事实 | 出处 |
| ---- | ---- |
| jotcash 声明的 Go 模块版本为 `go 1.27.0` | `go.mod:3` `go 1.27.0` |
| 宿主机实际安装与使用的 Go 版本为 `go1.27.1` | `go version` -> `go version go1.27.1 linux/amd64` |
| 参考工程 `survive_monitor` 声明的 Go 模块版本为 `go 1.24` | `/home/ms/document/code/survive_monitor/go.mod:3` `go 1.24` |
| 参考工程 `survive_monitor` 的 Dockerfile 采用 `golang:1.24-alpine` | `/home/ms/document/code/survive_monitor/Dockerfile:1,15` |

## 二、原因剖析与冲突根源

在对话1初版实现中，Dockerfile 采用了 `golang:1.24-alpine`，其核心原因如下：
1. **参考源的机械继承**：
   - 任务 Prompt 指定参考 `/home/ms/document/code/survive_monitor/Dockerfile`；
   - 在 `survive_monitor` 中，其 `go.mod` 定义为 `go 1.24`，故其 Dockerfile 第一行与第十五行均直接写死 `FROM golang:1.24-alpine`；
   - 初版在对齐参考项目结构时，过于机械地直接沿用了其 `1.24` 的镜像标签，未优先与本项目自身的 `go.mod` 进行版本参数映射。
2. **Go 1.21+ Toolchain 自动下载机制带来的遮蔽**：
   - 从 Go 1.21 起，Go 引入了 `GOTOOLCHAIN=auto` 机制。当编译器发现本地是 Go 1.24 但 `go.mod` 声明了 `go 1.27.0` 时，如果配置了 `GOPROXY`，`go build` 会在容器构建期自动静默下载 `go1.27.0` 工具链并继续编译；
   - 尽管依靠 Toolchain 自动升级机制在有网络时能够完成构建，但这带来了两项明显的副作用：
     - **构建耗时增加**：每次无缓存构建都需要动态拉取 ~100MB 的新编译器工具链；
     - **依赖外部网络稳定性**：在离线或内网构建环境下可能因无法自动下载 toolchain 而导致构建失败。

## 三、方案取舍与订正实施

**结论：基础镜像必须严格对齐本项目 `go.mod` 中的 `1.27` 版本，采用 `golang:1.27-alpine`。**

### 3.1 实施改动
在 `Dockerfile` 中同步修改两处基础镜像声明：
1. **Stage 1 (Builder)**：`FROM golang:1.24-alpine AS builder` -> `FROM golang:1.27-alpine AS builder`
   - 与 `go.mod:3` 的 `go 1.27.0` 原生对齐；
   - 消除镜像构建期因跨大版本而触发的额外 toolchain 下载开销；
   - 与本地开发调试环境（`go1.27.1`）保持一致的语言特性与编译行为。
