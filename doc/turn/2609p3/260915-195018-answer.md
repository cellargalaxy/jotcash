## 二、目标与边界

- **交付物**：两处后端改动。① 去掉分页参数限制，使不传 `page_size` 即返回全量（前端据此导出 csv）；② 口令校验加失败封禁，挡字典爆破。
- **不做**：前端代码（本轮明确只做后端，csv 导出由前端消费这条能力）；前端口令（开库口令）失败的计数——理由与缺口见 §五。
- **硬约束**：只改必要的点，复用现有骨架；标识符英文、注释与日志中文；日志不得出现任何口令值。

## 三、方案与实施

### 3.1 去掉分页参数限制

**做法是删掉限制本身，而不是加开关。** db 层 `pageLimit` 早就把 `pageSize <= 0` 定义为「不加 limit」，限制完全是门面那一层 `checkPageSize` 加出来的，删掉它，「不限」这个语义自然透到上层。

| 改动 | 文件 |
| ---- | ---- |
| 删 `pageSizeDefault`/`pageSizeMax` 两个常量与 `checkPageSize` 整个函数 | `service/repo/inquiry.go` |
| 删三处 `inquiry.PageSize = checkPageSize(inquiry.PageSize)` 调用 | `service/repo/expense.go`、`file_meta.go`、`operation_log.go` |

- 排序兜底（`expenseSortDefault` 等）原样保留——那是「db 层默认 id asc、列表要最新在前」的业务选择，与分页无关。
- **不碰 db 层**：`pageLimit` 的三个分支（不限 / page 归一 / offset-limit）本来就对，没有改的理由。
- 兼容性：`page` + `page_size` 照常分页，`count` 一直是筛选全集不受分页影响，前端三个列表页都显式传 `page_size`，**行为零变化**；新增的只是「不传就是全量」这条路。

### 3.2 口令校验失败封禁（新建 `handler/token_ban.go`）

**新增能力整个落在新文件 `handler/token_ban.go`，`handler.go` 只动 `validate` 函数体的 4 行**，import 与 `NewEngine` 一行未改：

```go
func validate(ctx *gin.Context) {
	if checkTokenBan(ctx) {
		return
	}
	util.ValidateGin(ctx, config.GetConfig(ctx).ServerToken, new(model.Claims))
	checkTokenFail(ctx)
}
```

一前一后两个钩子互为镜像：`checkTokenBan` 在校验**之前**看封禁并决定挡不挡，`checkTokenFail` 在校验**之后**看这次算不算失败并计数。

**判定失败的信号**：`ValidateGin` 只在**放行**时把 claims 写进请求上下文（`gin.go:144`），所以 `checkTokenFail` 用 `util.GetClaims[*model.Claims](ctx) != nil` 判定「这次口令对不对」。**没有用 `c.IsAborted()`**：校验通过时 `ValidateGin` 内部已经把整条链跑完，业务 handler 自己的中断（典型如 panic 被 `gin.Recovery` 兜住）会把 `IsAborted` 染成 true，那不是口令失败。

**滑动窗口**（`handler/token_ban.go`）：

| 成员 | 含义 |
| ---- | ---- |
| `tokenFailWindow = 5m` | 失败次数的统计窗口 |
| `tokenFailMax = 5` | 窗口内失败到这个次数就封禁 |
| `tokenBanDuration = 5m` | 封禁时长 |
| `tokenBan.check(now) time.Duration` | 返回剩余封禁时长，0 表示没被封 |
| `tokenBan.fail(now) bool` | 记一次失败并返回是否触发封禁 |

`fail` 每次先按窗口把过期失败剔掉再追加，攒满 `tokenFailMax` 就设 `banUntil = now + 5m` 并把计数清零——封禁期内请求根本进不到校验、不会再累加，清零保证解封后从头数，不会一解封就被上一轮旧账再封一次。`now` 由参数传入而非函数内部取，纯逻辑可直接构造时间点测试（`编码规范` §3.2）。

**状态存放**：`var validateBan = new(tokenBan)`，包级一份，对应「一个进程一道闸」。没有做成随 engine 走的闭包——那要动 `NewEngine`，不如包级变量改得少；测试里的串味用 `ResetValidateBan()` 解决（只定义在 `token_ban_test.go` 里，编译进测试二进制，不进生产代码），由 `newTestEngine` 每次建 engine 时归零。

流程：

```
checkTokenBan → 被封：Warn「口令校验，封禁中」+ 429 + 剩余秒数，Abort
              → 没封：ValidateGin → checkTokenFail → 放行则直接返回
                                                  → 没放行则 fail()，触发封禁时 Warn「口令校验，失败过多已封禁」
```

- **响应形态沿用全仓约定**：HTTP 状态恒 200，体内 `code = 429`、`msg = "口令校验失败过多，请N秒后重试"`，前端 `unwrap` 原样弹给用户，不需要改前端。
- **封禁不分来源（全局计数）**：反代之后 `c.ClientIP()` 取自可伪造的转发头（`gin.Default()` 默认信任全部代理），按地址分桶等于给爆破者留一条换头就绕开的旁路。代价是攻击者能顺带把本机用户也挡 5 分钟；单用户单实例的定位下，这个代价换「爆破真的被挡住」是划算的。已写进代码注释与 A-6。
- **封禁挡的是整道闸**，不是单个接口：9 个 POST 路由共用同一个 `validate`，封禁期内一律 429。爆破者换 `/api/expense/select` 试口令绕不开。
- 计数只在进程内存里，不落库、不写审计——保住「审计只留痕、认证失败不落库」这条不变式。重启即清零。

## 五、待确认（不可推断，留给你定）

**前端口令（开库口令）连错不计入封禁。** 这是本轮唯一的能力缺口，我没有自作主张补，因为补法不止一种且都超出「在 handler.go 里参考 validate」的范围：

- 它**不是在 `validate` 这道闸上失败的**。jwt 是用后端口令签的，前端口令只是 jwt 的一个 claim，闸照样放行；真正失败发生在后面开库那一步（`rdb/rdb.go:121-158` `open`，报「连接数据库，口令错误或数据库文件损坏」）。
- 而且它**不止 `/api/ping` 一个入口**：任何走 `rdb.NewTransaction` 的接口都会在同一处失败，只堵探针等于没堵。要覆盖得把埋点下沉到 `open` 或 `service/repo`，那是另一层的改动。
- 威胁模型上这条缺口不算大：两把口令是建库时**同一条日志一起打出来的**（`rdb/rdb.go:113-117`），能拿到后端口令的人通常已经能读到库文件，转去离线爆破比在线试更快。

**问**：要不要把「前端口令错」也计进同一个封禁窗口？要的话请确认埋点下沉到 `open` 一层（覆盖全部接口）可以接受。
