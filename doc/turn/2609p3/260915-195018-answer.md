## 二、目标与边界

- **交付物**：两处后端改动。① 去掉分页参数限制，使不传 `page_size` 即返回全量（前端据此导出 csv）；② 口令校验加失败封禁，挡字典爆破。
- **不做**：前端代码（本轮明确只做后端，csv 导出由前端消费这条能力）；前端口令（开库口令）失败的计数——理由与缺口见 §五。

## 三、方案与实施

### 3.1 去掉分页参数限制

**做法是删掉限制本身，而不是加开关。** db 层 `pageLimit` 早就把 `pageSize <= 0` 定义为「不加 limit」，限制完全是门面那一层 `checkPageSize` 加出来的，删掉它，「不限」这个语义自然透到上层。

| 改动 | 文件 |
| ---- | ---- |
| 删 `pageSizeDefault`/`pageSizeMax` 两个常量与 `checkPageSize` 整个函数 | `service/repo/inquiry.go` |
| 删三处 `inquiry.PageSize = checkPageSize(inquiry.PageSize)` 调用 | `service/repo/expense.go`、`file_meta.go`、`operation_log.go` |

- 排序兜底（`expenseSortDefault` 等）原样保留——那是「db 层默认 id asc、列表要最新在前」的业务选择，与分页无关。
- **不碰 db 层**：`pageLimit` 的三个分支（不限 / page 归一 / offset-limit）本来就对，没有改的理由。
- 兼容性：`page` + `page_size` 照常分页，`count` 一直是筛选全集不受分页影响，前端三个列表页都显式传 `page_size`，**行为零变化**；新增的只是「不传就是全量」这条路。

### 3.2 口令校验失败封禁（新建 `handler/token_ban.go`）

**新增能力整个落在新文件 `handler/token_ban.go`，`handler.go` 只动 `validate` 函数体的 4 行**，import 与 `NewEngine` 一行未改：

```go
func validate(ctx *gin.Context) {
	if checkTokenBan(ctx) {
		return
	}
	util.ValidateGin(ctx, config.GetConfig(ctx).ServerToken, new(model.Claims))
	checkTokenFail(ctx)
}
```

一前一后两个钩子互为镜像：`checkTokenBan` 在校验**之前**看封禁并决定挡不挡，`checkTokenFail` 在校验**之后**看这次算不算失败并计数。

**判定失败的信号**：`ValidateGin` 只在**放行**时把 claims 写进请求上下文（`gin.go:144`），所以 `checkTokenFail` 用 `util.GetClaims[*model.Claims](ctx) != nil` 判定「这次口令对不对」。**没有用 `c.IsAborted()`**：校验通过时 `ValidateGin` 内部已经把整条链跑完，业务 handler 自己的中断（典型如 panic 被 `gin.Recovery` 兜住）会把 `IsAborted` 染成 true，那不是口令失败。

**滑动窗口**（`handler/token_ban.go`）：

| 成员 | 含义 |
| ---- | ---- |
| `tokenFailWindow = 5m` | 失败次数的统计窗口 |
| `tokenFailMax = 5` | 窗口内失败到这个次数就封禁 |
| `tokenBanDuration = 5m` | 封禁时长 |
| `tokenBan.check(now) time.Duration` | 返回剩余封禁时长，0 表示没被封 |
| `tokenBan.fail(now) bool` | 记一次失败并返回是否触发封禁 |

`fail` 每次先按窗口把过期失败剔掉再追加，攒满 `tokenFailMax` 就设 `banUntil = now + 5m` 并把计数清零——封禁期内请求根本进不到校验、不会再累加，清零保证解封后从头数，不会一解封就被上一轮旧账再封一次。`now` 由参数传入而非函数内部取，纯逻辑可直接构造时间点测试（`编码规范` §3.2）。

**状态存放**：`var validateBan = new(tokenBan)`，包级一份，对应「一个进程一道闸」。没有做成随 engine 走的闭包——那要动 `NewEngine`，不如包级变量改得少；测试里的串味用 `ResetValidateBan()` 解决（只定义在 `token_ban_test.go` 里，编译进测试二进制，不进生产代码），由 `newTestEngine` 每次建 engine 时归零。

流程：

```
checkTokenBan → 被封：Warn「口令校验，封禁中」+ 429 + 剩余秒数，Abort
              → 没封：ValidateGin → checkTokenFail → 放行则直接返回
                                                  → 没放行则 fail()，触发封禁时 Warn「口令校验，失败过多已封禁」
```

- **响应形态沿用全仓约定**：HTTP 状态恒 200，体内 `code = 429`、`msg = "口令校验失败过多，请N秒后重试"`，前端 `unwrap` 原样弹给用户，不需要改前端。
- **封禁不分来源（全局计数）**：反代之后 `c.ClientIP()` 取自可伪造的转发头（`gin.Default()` 默认信任全部代理），按地址分桶等于给爆破者留一条换头就绕开的旁路。代价是攻击者能顺带把本机用户也挡 5 分钟；单用户单实例的定位下，这个代价换「爆破真的被挡住」是划算的。已写进代码注释与 A-6。
- **封禁挡的是整道闸**，不是单个接口：9 个 POST 路由共用同一个 `validate`，封禁期内一律 429。爆破者换 `/api/expense/select` 试口令绕不开。
- 计数只在进程内存里，不落库、不写审计——保住「审计只留痕、认证失败不落库」这条不变式。重启即清零。

# 对话2 · 封禁参数配置化 + 规则与代码简化

## 一、依据来源

| 事实 | 出处 |
| ---- | ---- |
| 配置项的三处落点：结构体字段、`GetDefault` 写默认、`Parse` 兜底 | `model/config.go` `Config`、`config/config.go:45-85` |
| 现有配置项的兜底形状一律是 `if config.X <= 0 { config.X = x }` | `config/config.go` `Parse` 里 `DbBackupLimit`/`ExpenseFileLimit`/`ImportFileLimit` 三处 |
| 默认值一律是 `config` 包里的非导出常量，带中文单位注释 | `config/config.go:19-24` |
| 配置热更由 `util.ConfigService` 托管，`GetConfig` 每次取当前值 | `config/config.go:27-39` |
| 缺字段的老配置文件会被 `Parse` 补上默认值 | 同上兜底分支；`config_test.go` `TestConfigParse` 的「缺省项未兜底」用例 |
| 金额精度的兜底判据是 `< 0` 而非 `<= 0`（0 是合法口径） | `config/config.go` `AmountScale` 分支 |

## 二、简化后的规则

原规则三个参数（统计窗口、次数、封禁时长），实现要维护一个失败时刻切片 + 一个封禁截止时刻，每次失败遍历并重建切片。

**新规则只有两个参数，且窗口与封禁时长合并成同一个值：**

> 连续失败攒够 **N** 次即封禁 **T** 分钟；T 同时是失败计数的有效期——连续 T 分钟没有新失败，计数归零。

- 「过去五分钟里≥五次失败 → 禁止五分钟」这条任务原话**依然成立**：封禁期内请求被挡在校验之前、不会再累加，所以解封时刻就是「第 N 次失败 + T 分钟」。
- 与严格滑动窗口的唯一差别：慢速试探（每次间隔小于 T 但总跨度大于 T）也会被累计。对爆破防护**只会更严不会更松**，而这种慢速试探本来就该挡。
- 参数从 3 个减到 2 个，正好对上「五分钟/五次是默认值」这两个可配项。

## 三、方案与实施

### 3.1 配置化（三处落点，形状照抄现有项）

| 位置 | 改动 |
| ---- | ---- |
| `model/config.go` | 新增 `TokenFailLimit int`（口令失败次数上限）、`TokenBanMinute int`（封禁时长，分钟；同时是计数有效期），json/yaml tag 与注释形态与既有字段一致 |
| `config/config.go` | 新增常量 `tokenFailLimit = 5`、`tokenBanMinute = 5`；`GetDefault` 里各写一行；`Parse` 里各加一个 `<= 0` 兜底分支 |

- **时长用「分钟数的 int」而不是 `time.Duration`**：yaml/json 反序列化 `time.Duration` 只认纳秒整数、不认 `5m`，配出来反而不可读；仓里既有配置项也全是带单位语义的整数（`ExpenseFileLimit` 是字节数）。字段名自带单位。
- **兜底判据取 `<= 0`**：次数为 0 等于「一次失败就封」、时长为 0 等于「封了立刻解」，两者都不是合法口径，与 `DbBackupLimit` 同族；不取 `AmountScale` 那种 `< 0`，因为 0 在这里没有意义。
- **老配置文件兼容**：缺这两个键的 `resource/jotcash.yaml` 会被 `Parse` 补上默认值，不需要手工迁移，也不会因为缺键报错。
- 生成的默认配置已实测确认多出 `token_fail_limit: 5` / `token_ban_minute: 5` 两行。

### 3.2 代码简化（`handler/token_ban.go`）

| | 简化前 | 简化后 |
| ---- | ------ | ------ |
| 字段 | `lock` + `failTimes []time.Time` + `banUntil` | `lock` + `count int` + `expireAt time.Time` |
| `fail` | 分配新切片、遍历剔除过期、追加、判阈值、清零、设封禁截止 | 过期则计数归零 → 计数加一 → 失效时刻后推，返回累计次数 |
| `check` | 比较 `banUntil` 算剩余时长 | `limit <= count && now.Before(expireAt)`，一行 |
| 每次失败的开销 | 一次切片分配 + 一次遍历 | 两个字段赋值 |
| 常量 | 3 个写死 | 0 个，全部从 `config.GetConfig(ctx)` 取 |

- `check`/`fail` 的阈值与时长**由参数传入**而不是函数内部读配置：纯逻辑与配置解耦，白盒用例可以直接构造任意参数与时间点（`编码规范` §3.2）。
- 响应文案改成 `"口令校验失败过多，请%d分钟后重试"`，直接用配置的分钟数。封禁从最后一次失败起算，所以这个值是等待时间的**上界**，不再单独算剩余秒数——少一次减法、少一个分支，代价只是最多多等一会儿，已在代码注释里写明。
- `handler/handler.go` 的 `validate` **本轮一行未动**，仍是对话1 那 4 行。

### 3.2 db 层的关键逻辑

```
白名单取列名（取不到直接报错）
  → 复用 ExpenseInquiry.Where 处理 Deleted 三态
  → Where(列 != '') → Distinct() → Order(列) → Pluck(列)
```

- **删除三态复用既有实现**，不另写：`ExpenseInquiry.Where` 里 `DeletedAll` 走 `Unscoped()`、`DeletedOnly` 走 `Unscoped()+deleted_at is not null`、`DeletedNo` 走 gorm 默认软删除作用域。这里只构造一个「只带 Deleted」的 `ExpenseInquiry` 借它的分支，不复制一份判断。
- **空值不进候选**：`列 != ''` 一条比较同时筛掉空串与 NULL（SQL 里 `NULL != ''` 为 NULL，行被排除），不需要再写一个 `is not null`。与 mock 的 `if (row[field])` 口径一致。
- **升序**由 `Order(列)` 给出，对应文档「建议已排序」。SQLite 的 BINARY 排序与 Go 的 `sort.Strings` 一致，前端不必再排。
- `Count` 取 `len(Object)`，即去重后的候选个数——不是命中行数。
- 分页/排序参数在这条链路上没有意义，**请求体里根本没有这两个字段**，不需要像 `NewExpenseDeleteHandler` 那样做防呆清理。

### 3.3 白名单为什么只放在 db 层

与既有的排序白名单**完全同构**：`checkExpenseInquiry` 不校验 `Sort`，非法排序由 `rdb/inquiry.go` `sortOrder` 直接报错。字段白名单照此办理，门面只管它该管的删除筛选。两处都报错、都不静默降级，符合 §1.4「门面对非法输入报错，不得静默降级」，也避免把同一份白名单抄到两层。

## 二、关键设计决定

### 2.1 两次查询必须合进一个 handler

`FileBlob` 要按 `FileMeta.FileHash` 取，**两次查询有先后依赖**。三种写法只有一种成立：

| 写法 | 判定 |
| ---- | ---- |
| 开两次 `rdb.NewTransaction` | ❌ **会死锁**。`NewTransaction` 持 `dbLock.RLock()`，`defer Close` 让两把读锁在同一协程里重叠，而 `rdb/rdb.go` 明确写了「同一协程内不得嵌套：有写者排队时新读者也要排在写者后面」 |
| 同一个 transaction 调两次 `Exec` | ❌ `Transaction.Exec` 跑的是**累积的** `commitHook`，第二次会把第一个 handler 再跑一遍 |
| 合成一个 `FileDownloadHandler`，内部串起两个既有 select handler | ✅ 采用 |

`FileDownloadHandler` 内部复用 `NewFileMetaSelectHandler` / `NewFileBlobSelectHandler`，不重写查询；元数据取不到就直接返回，让门面去判「不存在」还是「内容缺失」。

### 2.2 D-3 的哈希校验放在门面，不放 db 层

db 层只做无业务逻辑的增删查改，「取回来的内容对不对」是业务判断，落在 `service/repo/file_meta.go` 的 `DownloadFile`。三种失败分别给不同文案与日志级别：

| 情况 | 级别 | 文案 |
| ---- | ---- | ---- |
| 元数据不存在（ID 填错） | Warn | `文件下载，文件不存在: <id>` |
| 元数据在、内容行丢了 | Error | `文件下载，文件内容缺失: <id>` |
| 内容在、重算哈希对不上 | Error | `文件下载，文件数据已损坏: <id>` |

级别判据照 `编码规范.md` §5.2：ID 填错是调用方的问题、本层能正常返回错误（Warn）；内容缺失与内容损坏是库自身坏了、代码兜不住（Error）。

### 2.3 不经 `service` 包

响应是二进制流不是 `HttpData`，`service` 那层的职责（把结果装进 `HttpData`）在这里不存在。照 `Export`/`Import` 的既有做法，handler 直接调 `repo.DownloadFile`——**不为了层次整齐加一个什么都不做的中转函数**（对话3 那条教训）。

### 2.4 `Content-Disposition` 多给一份 `filename*`

```
attachment; filename="2609账单.csv"; filename*=UTF-8''2609%E8%B4%A6%E5%8D%95.csv
```

上传的文件名基本都是中文。只给 `filename="..."` 那一份，原始字节是非 ASCII，浏览器与 `fetch` 按 latin-1 读header，存下来就是乱码。加的这份 `filename*=UTF-8''`（RFC 6266）是浏览器优先采用的，编码方式与 gin 自己的 `c.FileAttachment` 一致（`url.QueryEscape`）。

**对文档契约与现有前端都是兼容的**：`filename="..."` 那份原样保留，前端 `postDownload` 的正则 `filename="?([^";]+)"?` 照旧能匹配到。
