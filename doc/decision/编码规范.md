## 一、包：层级、名称、职责、实现顺序

### 1.1 排布轴：距外部的远近

**唯一的排布轴是"离外部系统有多远"**，不是抽象程度，也不是调用先后。

与外部对接的包放在项目根部，越外部越靠近根部；业务逻辑往内层目录收，按业务域再分子包。**越靠边缘越通用、业务逻辑越少；越靠内越专用、业务规则越密。**

依赖方向随之确定：内层可以依赖外层的适配能力，外层不得反向依赖内层的业务。依赖图无环，每个包能被单独实现、单独测试。

判断新包该放哪，只问一句：**它知道多少业务规则？** 一条都不知道的放根部，离不开业务规则的往里放。

### 1.2 同一条轴也是实现顺序

这条轴不只是空间布局，**也是动工顺序**：

- 边缘包是调用链的基础，且不含业务逻辑，所以**先实现**——它们的正确性不依赖对业务的理解，写完就能独立测试，后面的所有代码都站在它们上面。
- 深层的业务包**后设计**。等边缘铺好、对整个代码库有了把握，业务该怎么切分才看得清楚。过早设计深层包，切出来的边界大概率要推倒。

推论：如果一个项目刚起步就冒出了目录很深的业务包，通常说明设计跑在了理解前面。

### 1.3 通用包名与职责

这套包名与业务领域无关，任何项目都适用：

| 包 | 位置 | 承载 | 业务逻辑 | 动工顺序 |
| --- | --- | --- | --- | --- |
| `model` | 根部 | 数据契约：结构定义、常量枚举、序列化与表名这类声明性方法 | 无 | 最先 |
| `config` | 根部 | 配置文件的加载、解析、热更；不变的路径与地址常量 | 无 | 最先 |
| `tool` | 根部 | 带本系统规则的工具函数 | 少量规则 | 早 |
| `db` / `store` | 根部 | 数据库连接与无业务逻辑的增删查改 | 无 | 早 |
| 外部适配包（按外部系统命名，如汇率、消息、对象存储） | 根部 | 单个外部系统的对接与容错 | 无 | 早，可先留桩 |
| `handler` / `api` | 根部 | 协议入口：路由、参数绑定、响应封装、鉴权中间件 | 无 | 中 |
| `service` | 内层 | 业务编排 | 全部 | 后 |
| `service/db` | 内层 | 带业务逻辑与参数校验的数据访问：多表同事务、默认值兜底 | 全部 | 后 |
| `service/<能力>/<实现>` | 内层 | 同一能力的多种实现（多格式解析、多渠道推送） | 全部 | 最后 |

`handler` 虽在根部，却是边缘包里最晚动工的：它要等被它调用的东西都存在了才有得接。**"放在根部"说的是位置与业务浓度，不是动工的先后。**

### 1.4 三组必须单向的包边界

同一条原则的三个切面：**通用与专用之间必须有边界，且边界单向。**

**其一，通用工具 与 带规则的工具。** 完全无业务逻辑、换个项目照样能用的，沉到跨项目共享库；携带本系统规则或逻辑有本系统特殊性的，留在项目内的工具包。判据是"能否原样搬到下一个项目"，不是"看起来像不像工具"。守住这条，共享库才不会被业务污染，项目工具包也不会膨胀成第二个共享库。

**其二，无校验的底层能力 与 有校验的业务门面。** 底层数据访问包只做无业务逻辑的增删查改，因此**必然缺少充分的参数校验**——什么算合法是业务问题，底层没有资格判断。所以底层包**不允许被上层直接调用**，由业务门面做参数校验、默认值兜底、多表同事务的编排，上层只能调门面。门面对非法输入报错，不得静默降级；底层对没见过的取值往往有兜底行为，静默降级会让"少查了数据"或"多删了数据"变成无声故障。底层可以有防呆（比如强制清掉对批量删除无意义的分页参数），但防呆不是校验，替代不了门面。

**其三，数据契约 与 行为。** 契约包只放结构、枚举、声明性方法，不含业务逻辑与连接性代码。枚举常量与它所修饰的实体放在一起，不另设枚举包——常量脱离了它描述的实体就失去含义。

## 二、镜像：判断设计是否合理的核心方法

功能与逻辑在不少情况下都存在哲学意义上的一对：正向与反向、左链路与右链路。**名字对称只是最表层的一层；真正成对的是内部结构、契约、失败收尾与并发语义。**

**一个边界好不好，单看一个函数看不出来。只有当同一套边界能同时容纳多组互为镜像的能力时，这个边界才算合理。**

### 2.1 六个层次，由浅入深

**第一层·名称镜像。** 成对的能力用互为镜像的词根：编码/解码、生成/解析、读取/写入、获取/设置、判定/设置、启动/停止、加锁/解锁、创建/打开、打开/关闭、导入/导出。参数顺序与返回形态一并对称。这是最容易做到也最表面的一层。

**第二层·结构镜像。** 成对能力的内部步骤序列互为倒转。导出是"活资源 → 临时副本 → 流出"，导入是"流入 → 临时副本 → 活资源"——把其中一条的步骤反过来就是另一条。**中间那个共用的中转形态（临时副本）本身就是边界切对了的证据**：它是两条链路共同的原子，也让第三条链路（换凭据 = 以新凭据产出副本 + 副本顶替活资源）不用另起炉灶就能拼出来。

**第三层·契约镜像。** 一方的输出必须是另一方的合法输入。因此**验收标准是往返恒等**：导出的产物必须能被导入吃回去且内容不变，序列化的结果必须能反序列化回等价对象。往返测试是镜像对唯一充分的测试——分别测两侧都通过、合起来却对不上的情况真实存在（编码差异、转义差异、精度差异都会在往返处暴露）。

**第四层·判据镜像。** 成对的生产侧与校验侧**共用同一个判据，且由生产侧主动服从校验侧**：生成凭据的函数应当循环生成直到校验函数通过，而不是各自实现一套规则。这样两者永远不会漂移——改了校验规则，生成侧自动跟上。

同族的还有"判定能否处理"与"实际处理"：两者共用同一个判定函数，**且执行侧不得假设判定侧已经跑过**。执行侧可能被单独调用，一旦它省掉自检，调用顺序的约定就成了隐形前提，迟早被人踩破。

**第五层·副作用镜像。** 失败收尾必须互相呼应，但**呼应不等于照抄**：

- 读方向失败没有副作用可退，直接返回。
- 写方向失败必须退回调用前的状态：删掉半成品、复位标记，让重试是安全的。
- 同一个临时资源在两个方向上的**释放策略相反**：产出方向用延迟清理无条件删（产物已经流出，副本再无用处）；接收方向必须在每个失败分支显式删（成功时副本会被顶替动作消费掉，无条件的延迟清理反而会误删刚生效的资源）。

**能不能正确说出"这个方向上临时资源该怎么释放"，是检验有没有真正理解这对镜像的试金石。** 照抄另一侧的写法，正是这里出事。

**第六层·并发语义镜像。** 不改变共享资源的方向取读锁，改变的取写锁。在统一的入口骨架下，**锁的选择常常是唯一随方向变化的参数**——如果一对能力在锁上没有呈现出这种对称，通常是其中一方的副作用被低估了。

### 2.2 业务逻辑层面的镜像

镜像不止于工具函数，业务链路同样成对：

- **写与写的镜像**：录入与删除在业务上相反，在结构上却完全一致——都是"业务单元 + 审计单元放进同一个事务"。结构一致恰恰证明"业务动作 + 伴生记录"这个边界切对了。
- **读与写的镜像**：差别不在步骤而在校验对象与失败语义——写路径校验**内容**、失败要回滚；读路径校验**条件**、失败只需报错。
- **定义与取用的镜像**：列契约的定义顺序与按顺序取值的函数是一对，取用方以定义方为唯一事实源，不另行硬编码位置。
- **对外呈现与对内落库的镜像**：同一个实体面向接口的形态与面向存储的形态各有一套声明，两者都挂在契约上，不散落到使用处。
- **共用判据与专有判据的分界**：跨实体重复的判据抽出来共用，每个实体独有的判据留在各自文件里。抽多了是过度拆分，不抽是重复——**分界线是"这条判据是否依赖具体实体的语义"**。

### 2.3 怎么用这套方法

设计一个函数或一条链路时：

1. 先问"它的镜像是什么"。
2. 再问"镜像能不能用同样形态的参数、同一层级、同一错误语义写出来"。
3. 如果正向只需要少量参数而反向要一大堆；或者正向留在这一层而反向被迫下沉；或者两者对同一种失败给出不同语义——**说明边界切在了错的地方，该改的是边界，不是给反向打补丁**。
4. 一套边界如果能同时支撑三组以上的镜像关系，基本可以认定是对的。

这也是重构的信号灯：当某个反向操作"写起来特别别扭"，不要去优化那个反向函数，回头看正向函数的边界。

**反过来同样成立**：如果新增一种能力必须绕开既有骨架另起一套，先别急着承认这个能力特殊——更常见的情况是骨架的边界切错了。

## 三、函数边界

### 3.1 职责单一且明确

一个函数只干一件事。创建归创建，打开归打开——打开的路径上绝不"顺手补写"，读的路径上绝不"顺手创建"。资源不存在、已损坏、凭据不对，就报错，不兜底重建。

**一旦一个函数在失败时会改变外部状态，调用方就永远无法安全地重试它。**

### 3.2 导出包装 与 非导出实现

成对出现，**中间不留空行，视觉上是一个单元**。

- **导出的负责可靠与安全**：加锁、读全局配置与环境、做兜底校验，对外提供无论怎么调都不会出事的入口。
- **非导出的负责纯逻辑**：所有依赖由参数显式传入，不碰锁、不读全局。

两个收益缺一不可：

1. 测试可以直接构造任意环境调用非导出实现，不必为测一段逻辑去搭一整套全局状态。
2. **更高层的内部操作可以复用非导出实现来组合，而不重入锁**。只有加锁的导出版本时，任何"读了再写"的复合操作要么死锁，要么被迫把逻辑抄一遍。

第 2 点比第 1 点更根本。一个包里出现了复合操作却没有对应的非导出纯逻辑层，迟早会长出重复代码或死锁。

### 3.3 统一的入口骨架

同一个包里所有对外能力应当共享一套入口骨架：**脱钩上下文 → 读不变配置 → 取凭据 → 按需预热 → 按方向取锁 → 调纯逻辑实现**。骨架之间的差异只应出现在方向相关的那几个参数上（取锁类型、是否需要预热、消费凭据还是生产凭据）。

骨架统一了，新增能力就是填空；骨架一旦被绕开，说明边界需要重切。

### 3.4 两条对称的红线

这两条本身就是一对镜像，**必须一起看**，只守一条会掉进另一条：

| 红线 | 症状 | 判据 | 处置 |
| --- | --- | --- | --- |
| **避免过度拆分** | 函数只是把几行原地代码换个名字包起来，单一调用方，内部无分支 | 内联回去之后可读性不降反升 | 内联掉。适当平铺能提高可读性，平级的条件罗列不必强行拆 |
| **避免职责焊死** | 一个函数内部偷偷做了第二件事（典型如在业务写入里塞审计） | 想单独使用其中一件事时做不到 | 拆成各自独立的单元，由调用方**组合**成完整流程 |

共同判据是**职责数**，不是行数。很长但只做一件事、且是平级罗列的函数是好函数；很短却做了两件事的函数是坏函数。

优先组合而非内嵌：把多个独立单元交给统一的执行器（事务、管道、中间件链）串起来，比焊进彼此内部更解耦、更灵活，也更容易在下一个场景里换掉其中一个。

### 3.5 可扩展点用注册，不用条件分支

同一类能力有多种实现时，定义能力接口，各实现自行注册，由注册表分发。新增实现只加一个子包和一行引入，不改分发逻辑。

**识别用内容不用外壳**：文件格式不靠扩展名判断，协议不靠端口判断——外壳相同而内容不同的情况一定会出现。识别条件要严格到不会误认领，宁可不认领也不能认错。

## 四、命名与代码组织

### 4.1 名字必须直接说明它是什么

循环变量与局部变量用实际含义命名，不用 `one`、`it`、`v`、`e` 这类占位词。遍历操作类型的集合，变量就叫操作类型。读代码的人不该为了知道一个变量是什么而回头去看它从哪个集合里来。

只有下标、事务句柄、上下文这类**含义由类型唯一确定**的短名例外。

### 4.2 同一概念全仓只有一个名字

实体的一条记录、查询条件、事务处理器——每个概念固定一个词，不允许同义词并存。新代码命名时先查现有词表，有就用，没有才新造。

### 4.3 其余固定约定

- 转换类函数用「源 2 目标」的形式，源与目标都是明确的形态名词；同一族转换要把形态矩阵铺满。
- 方法接收器在全仓统一一个名字，不随类型变化。
- 标识符英文且按语义翻译，不逐字直译；注释、日志、错误文案中文。领域名词以业务方认定的标准中文名为准，不在代码里另起一套叫法。
- 与语言关键字冲突时加后缀区分，不为避让而扭曲语义。
- 依赖引入分标准库与其余两组，组内由格式化工具排序，不人为再分组。
- 上下文永远是第一个参数。
- 文件名与其主类型对应，枚举与实体同文件。
- 不变的路径与地址做成常量，**不开放为配置**——可配意味着要处理所有取值，而这类值根本不需要变。

文件内部的成员排列顺序不作强制要求，成对函数贴紧是唯一的硬约定。

### 4.4 并发与资源

- 一个包内的并发控制收敛到尽量少的锁上；宁可牺牲一点并发度，也不要让锁的持有关系需要推理才能看懂。
- 跨请求生命周期的上下文在交给异步组件之前必须脱钩，否则会串到下一个请求。
- 延迟初始化用双检：先在读锁下看标记，再在写锁下复检。
- 资源关闭统一走延迟释放；例外见镜像那节的第五层。

## 五、错误与日志

### 5.1 唯一句式

在错误的产生点，**先记日志、再返回错误，两处文案保持一致**。

- 日志必须携带上下文对象，全链路才串得起来。
- 字段容器即使为空也保留，形态统一。
- 文案固定为「动作，问题」与「动作，完成」，需要携带原始错误时在其后附加。
- 全仓统一一种错误构造方式，不混用多种错误库。

动作名用中文业务词或资源名，让人不看堆栈也知道是哪一步出的事。

### 5.2 级别的判据是"代码能不能处理"

| 级别 | 含义 |
| --- | --- |
| **Error** | 代码逻辑**无法兜底、无法处理**的错误情况 |
| **Warn** | 情况虽然奇怪、或需要特别提醒，但**有相应的兜底或处理逻辑** |
| **Info** | 预期之中的情况 |

同一件事在不同函数里可以是不同级别：一个查询在"目标不存在时返回空列表"的函数里是 Warn，在"目标不存在就没法继续"的函数里是 Error。判据永远是**这段代码接下来还能不能正常走下去**，与故障所在层级、与输入来自谁都无关。

### 5.3 只封装来自业务逻辑外部的错误

- 错误来自**业务逻辑外部**——数据库、外部接口、文件系统、第三方库——**才封装**，加上本层的动作描述。
- 错误来自本系统内部的其他函数，**直接透传**。

内部函数在产生错误时已经记过日志、写过文案，再包一层只会让最终信息变成套娃，同一次故障还会在日志里重复出现多遍。

唯一例外：本层返回的是**片段式文案**，需要调用方补上位置或批次信息才完整。这种情况下日志记在调用方，由它拼出完整文案。

### 5.4 对外的错误呈现

协议层把业务结果统一装进响应体，**传输层状态码保持成功**，业务码与文案放在体内。失败时该返回的基础信息照常返回，不因为出错就吐一个空壳。

内部错误原样透出给调用方，不二次加工——加工过的文案往往丢掉了真正有用的那一段。

## 六、注释

**严禁引用文档条款，只留"不看就会改错"的，不写过程注释。**

允许写的只有两类：**踩过的坑**（为什么必须这样写、不这样写会出什么事），与**非显然的取值语义**（某个值的特殊含义无法从类型和名字推出来时）。

禁止写的：

- 文档条款号、需求编号、设计文档章节的引用——文档会变、会改名，代码里的引用只会变成误导。要说就直接说清楚约束本身。
- 过程注释——代码自己说得清的不重复说一遍。
- 仅为满足"导出符号要有注释"而写的门面注释。

一个健康的代码库里注释是**稀疏**的：几十行才有一条，且每条都回答"为什么"而非"是什么"。形态（缩进、空格、位置）在一个仓库内统一即可，重要的是统一。

## 七、测试

- **黑盒优先**：默认从包外测公开行为，只有需要触达内部状态时才用白盒。
- **非导出实现是主要抓手**：边界切好之后，绝大部分逻辑都能在不搭建全局环境的前提下被直接调用验证。
- 每个测试单元清理自己产生的残留，不污染源码树；测试之间用临时目录隔离，不共用固定路径。
- 辅助函数要声明自己是辅助函数，失败才能报到真正的调用处。
- **失败信息带实际值与期望值**，只说"不符"的断言等于没写。
- 断言直接手写，不引入断言库；少量场景用映射描述、以场景名作键，不为几个用例套上表驱动的骨架。
- 必测：边界与异常分支、并发路径、**镜像对的往返恒等**、敏感信息不外泄、"无条件"的批量操作不会误伤全量数据，以及每一条被写进规范的不变式。
- 能从最外层入口发起的测试就从最外层发起——它顺带验证整条链路的装配，也降低对接方的联调成本。

## 八、选型与精度

- 轮子选型顺序硬性：**自家共享库 → 有积极维护且使用面广的成熟三方库 → 真的没有方案才自造**。ID 生成、编解码、时间格式化、序列化、通用文件与表格处理，一律不自己写。
- 标识符类型选择要考虑全链路，包括前端的数值安全范围。
- **精度敏感的字段必须显式声明存储类型**，不依赖存储引擎的类型推导——推导规则会把数值文本转成浮点而悄悄丢精度，且这种故障只在数据变大之后才显形。
- 敏感字段按"是否需要过线"选遮蔽方式：**根本不该出现在任何序列化结果里的**，在契约上直接标记为不序列化；**必须能序列化但不能进日志的**，在对外呈现方法里置空后再输出——这依赖呈现方法作用于副本而非原值。
- 排序、筛选这类会拼进查询语句的输入走**白名单映射**：对外暴露语义化的键，内部映射为真正的表达式，不在白名单内直接报错。模糊匹配必须转义通配符并声明转义符。分页参数由调用方决定，业务门面不兜底缺省值也不封顶——全量导出这类消费方要的正是底层"不限"这个语义，门面替它兜底等于把能力封死。

## 十、对前两轮的订正

| 前两轮的说法 | 本轮订正 |
| --- | --- |
| 包层级只是空间布局 | **补全**。同一条轴也是动工顺序：边缘先行，深层等对代码库有把握之后再设计 |
| 规范要抽象，故不提包名 | **订正**。通用包名与职责本身与业务无关，应当讲清楚（1.3） |
| 成对主要体现在函数命名 | **推翻**。命名只是最表层；结构、契约、判据、副作用、并发语义五层才是实质（二） |
| 镜像只存在于工具函数 | **扩展**。业务链路同样成对，写与写、读与写、定义与取用都有镜像关系（2.2） |
| 循环变量用占位词 | **错**。用实际含义命名 |
| 文件内成员排列顺序是规范 | **撤销**。不作要求，只保留成对函数贴紧这一条 |
| Warn 用于"用户输入非法"、Error 用于"系统层异常" | **改判**。判据是代码能否处理，与输入来源、故障层级都无关 |
| 下层错误一律透传 | **收窄**。外部来源的要封装，内部来源的才透传 |
| 导出/非导出切分是"为了可测" | **补全**。更根本的收益是让复合操作复用纯逻辑而不重入锁 |
| 函数边界以行数与分支深度为判据 | **深化**。真正的判据是能否容纳成对的镜像；行数与职责数只是表象 |
