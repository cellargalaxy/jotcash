## 三、两次实测

**探针A —— `CreateDbHandler` 到底在盘上留下什么**

```
建库后库文件大小: 0
existDb=false
```

根因：SQLite 在第一次写页之前一个字节都不落盘，而 `connect` 只跑了 `PRAGMA user_version` 这条读（`db/db.go:53-59`）。老的 `create` 没撞上，是因为它把 `connect` 出来的连接直接拿去跑 `AutoMigrate`，写了页。这条直接推出了岔路口 5。

**探针B —— `connect` 版与 touch 版是否等价**

把 `CreateDbHandler.Exec` 的 `connect` 段整个换成 `util.WriteData2File(ctx, nil, this.dbPath)`，全量测试 **8 个包依旧全绿**。进一步确认：

- 放宽 `existDb` 之后，`CreateDbHandler` 只在**文件压根不存在**时才走到 `connect`；对不存在的路径，`PRAGMA user_version` 在全新空库上恒成功，**校验不到任何东西**。
- 真正把加密库做出来的是后面那条链：`db.NewTransaction` → `open` → `connect(dbPath, token)` + `MigrateHandler` 写页，**真正生效的 textkey 是那一次传进去的**。
- 所以旧写法里 `CreateDbHandler` 的 `token` 一个字节都没落到盘上，它唯一的持久效果就是「让 `existDb` 变 true」。`util.WriteData2File` 内部走 `OpenWriteFile` → `createFile`（`util/io.go:140`、`:94-101`），父目录照样建，这点也不丢。

这条推出了岔路口 6。

## 四、落地结果

### 4.1 `service/db/db.go`：建库链 + 锁

```go
var dbLock sync.RWMutex          //整库级互斥统一压在这一层：顶库文件的走写锁，其余走读锁

func init() { ... Create(ctx) ... }

func Create(ctx context.Context) error {
	dbPath := config.DbPath
	token, err := tool.GenToken(ctx, tool.TokenLen)
	...
	createDbHandler := db.NewCreateDbHandler(dbPath)
	dbRemoveHandler := db.NewDbRemoveHandler(dbPath)
	tokenLogHandler := db.NewTokenLogHandler(dbPath, token)
	operationLogHandler := db.NewOperationLogInsertHandler(&operationLog)

	dbLock.Lock()
	defer dbLock.Unlock()

	//库文件已在就收工；0字节是上次建库的残骸，得当没建过
	info := util.GetFileInfo(ctx, dbPath)
	if info != nil && info.Size() > 0 { ...; return nil }

	//建库handler不吃tx，必须排在开事务之前
	err = createDbHandler.Exec(ctx, nil)
	if err != nil { dbRemoveHandler.Exec(ctx, nil); return err }

	//新库的口令还没进ctx，NewTransaction要靠它开库
	ctx = util.SetClaims(ctx, &model.Claims{ClientToken: token})
	transaction, err := db.NewTransaction(ctx)
	if err != nil { dbRemoveHandler.Exec(ctx, nil); return err }
	defer transaction.Close(ctx)

	return transaction.
		AddCommit(db.NewMigrateHandler(), operationLogHandler, tokenLogHandler).
		AddRollback(dbRemoveHandler).
		Exec(ctx)
}
```

`DbRemoveHandler` 被用在两处：**事务外**兜住「库文件已建、事务还没开起来」的残骸，**回滚链**兜住「事务开了但提交失败」。

**幂等性要单独说一句**：`Create` 里那道 `Size() > 0` 的守卫与放宽后的 `existDb` **故意不一致**——
- `existDb`（`open` 用）：文件在就认，0 字节按「还没写过页的空库」处理，否则整条建库链走不通；
- `Create` 的守卫：0 字节按残骸处理，必须重新初始化，否则进程起来会拿到一个没表没口令的库。

两条规则各自钉在用例上：`TestOpenWithoutDbFile`（0 字节应能开库）与 `TestCreateEmptyDbFile`（0 字节应重新初始化）。

# 对话2 · 把 touch 塞进 `NewTransaction` 合不合理

> 依据来源：
> - **本仓库代码**：`db/db.go`（`existDb :23`、`connect :27`、`open :145`、`CheckToken :158`、`NewTransaction :172`、`newTransaction :185`）、`db/db_test.go` `TestOpenWithoutDbFile`、`db/backup.go:105/238`、`service/db/db.go:65`、`handler/ping.go:17`
> - **历史**：`325dbd5` 把 `autoMigrate` 预热从 `Open`/`Transaction`/`Export`/`Import`/`ChangeToken` 五处删掉
> - **实测**：两个一次性探针（探针C、探针D），已删除，结果见 §2
>
> 本轮**只做分析，未改动任何生产代码与测试**——结论是不建议做，所以没有落地。

## 1. 第一句已经是现状

「connect 只留给 open 用，建库不再走 connect」——对话1 已经落地。`connect` 现在**生产代码里只有一个调用点**：`db/db.go:151`，在 `open` 里面（另外两处在 `db/backup_test.go:64/104`）。`CreateDbHandler.Exec` 已经是纯 touch（`util.WriteData2File(ctx, nil, this.dbPath)`）。这半句没有分歧。

## 2. 第二句：不建议做。两个探针

**探针C —— 0 字节库文件对口令还有没有鉴别力**

```
口令 "token-aaa"   开库: 成功
口令 "token-bbb"   开库: 成功
口令 "完全不相干的口令" 开库: 成功
空库上查询明细: err=查询expense，异常: sqlite3: SQL logic error: no such table: expense
反复开库之后库文件大小: 0
```

0 字节文件在 SQLite 眼里是「一个还没写过页的新库」，`PRAGMA textkey` 爱是什么是什么，`PRAGMA user_version` 一律放行。**0 字节库 = 零鉴别力。**

**探针D —— 按你的方案改一版，看哪些用例会红**

在 `NewTransaction` 里加 `NewCreateDbHandler(dbPath).Exec(ctx, nil)`，`service/db.Create` 去掉那一步。全量测试结果：

```
--- FAIL: TestOpenWithoutDbFile
    db_test.go:111: 库文件不应被请求重新建出来
    db_test.go:114: 库文件不存在时口令探针应报错
```

这两条是**你自己写的断言**，而且第二条是被第一条带塌的：

1. `SelectExpense` 这条**普通查询请求**走 `Transaction` → `NewTransaction`，把库文件 touch 出来了（第 111 行红）；
2. 于是接下来的 `CheckToken` 面对的是一个 0 字节库，按探针C，**任何口令都开得起来**（第 114 行红）。

`CheckToken` 就是 `handler/ping.go:17` 那条口令探针，前端拿它判断口令对不对。也就是说：**库文件一旦丢失，随便来一次查询请求就会把它 touch 回来，此后口令探针对任何口令都返回成功**，用户会以为自己登录成功，面对的却是个空库。

## 3. 为什么会这样：`NewTransaction` 服务的是两类调用方

| 调用方 | 频次 | 口令来源 | 库文件不存在时应该怎样 |
| --- | --- | --- | --- |
| `service/db.Create` | 进程启动一次 | `tool.GenToken` 现生成 | **建出来**——这正是它的职责 |
| 全部请求链路（`db/expense.go` 等 16 处 + `service/db/expense.go` 2 处，迁移后都走 `NewTransaction`） | 每个请求 | jwt claims | **报错**——库没了是事故，不是常态 |

把 touch 塞进 `NewTransaction`，等于用第一类调用方的需求覆盖了第二类。省下来的是 `service/db.Create` 里的 5 行；代价是请求链路失去「库文件不存在」这条告警，换成一句 `no such table: expense`，盘上还留一个 0 字节残骸——下次进程启动时 `Create` 的 `Size() > 0` 守卫会把它判成残骸、用**新口令**重新初始化，**用户的口令就这么被悄悄换掉了**。

`newTransaction`（私有那个）也不能放：`db/backup.go:105/238` 用它开的是 `dbPath` 与 `backupPath`。`changeToken` 那处，`backupPath` 不存在就意味着前面的 `backup()` 失败了，touch 出一个空库只会把这个事故盖掉。

## 4. 这条路你自己走过一次

`325dbd5` 之前，`Open`/`Transaction`/`Export`/`Import`/`ChangeToken` 五处开头都有一句 `autoMigrate(ctx, dbPath, token)`——请求链路自我修复库结构。你在那一轮把五处全删了。这次提案是同一类东西：**请求链路自我修复库文件**。上次删掉的理由（进程级标记与库文件之间要手工同步、`Import` 会把整个库顶掉）在这里同样成立，而且这次连口令校验一起赔进去。

## 5. 我的建议

**不做。** 现状那一步并不是「上层多感知了一步」，而是「建库这件事写在了唯一职责就是建库的函数里」——`service/db.Create` 的 5 行，出现在它该出现的地方。`NewTransaction` 的边界现在是干净的：**开已有的库**；跨过这条线，它就同时是「开库」和「建库」，而两个调用方对同一个分支要的是相反的行为。

如果你仍然要藏这一步，唯一安全的藏法是**藏进一个只给建库用的入口**（例如 `db` 包里一个建库专用的事务入口），而不是所有请求都走的 `NewTransaction`——但那属于你已经禁掉的「新编造函数」，要你先松口。

## 6. 顺带发现的一处小冗余（与本题无关，未改）

`service/db.Create` 现在对同一个路径 stat 了两次：守卫里的 `util.GetFileInfo`（看 `Size() > 0`），以及 `CreateDbHandler.Exec` 内部的 `existDb`（只看在不在）。两次语义不同、各有各的用处（§4.1 已说明），合并会牺牲其中一条规则，所以没动，只记一笔。

		AddCommit(NewMigrateHandler(), NewOperationLogInsertHandler(&operationLog), NewTokenLogHandler(dbPath, token)).

## 1. 一个真 bug：建库没有并发控制，会把刚建好的库删掉

`NewTransaction` 不带锁地调 `create`，而 `create` 里有两处破坏性动作：

- `util.WriteData2File(ctx, nil, dbPath)`——`util/io.go:132` 的 `openWriteFile` 用的是 `os.O_RDWR|os.O_TRUNC`，**对已存在的文件是截断**；
- 失败分支的 `util.RemoveFile(ctx, dbPath)`——**直接删库文件**。

两者都靠函数开头那道 `info.Size() > 0` 守卫拦着。守卫和动作之间没有互斥，于是：

1. A、B 同时进来，都看到「库文件不存在」，都过了守卫；
2. A 建好库、写入页、库文件变成 110KB；
3. B 接着跑 `WriteData2File`，**把 A 的库截断成 0 字节**；
4. B 再 `open`，如果 B 的口令与 A 不同，连库失败 → 走 `util.RemoveFile` → **把库文件删掉**。

**探针E**（6 个并发请求，库文件不存在时同时开事务），跑 3 遍：

| | 修复前（你提交的那版） | 修复后 |
| --- | --- | --- |
| 三个不同口令并发 | **3/3 「并发建库之后库文件没了」** | 3/3 库文件 110592 字节，建库审计 1 条 |
| 同一口令并发 | **3/3 建库审计 6 条**（每个协程都截断重建了一遍） | 1 条 |

**修法**（已落地，`db/db.go` 的 `create`）：双检锁，复用现有的 `dbLock`。

```go
func create(ctx context.Context, dbPath, token string) error {
	info := util.GetFileInfo(ctx, dbPath)
	if info != nil && info.Size() > 0 { return nil }     //先无锁探一次，库已就绪就不抢锁

	//建库必须独占：占位用的WriteData2File带O_TRUNC，失败分支还要删库文件
	dbLock.Lock()
	defer dbLock.Unlock()

	//等锁的这段时间里别人可能已经把库建好了，抢到锁得再看一遍
	info = util.GetFileInfo(ctx, dbPath)
	if info != nil && info.Size() > 0 { return nil }
	...
}
```

先探后锁，所以库建好之后每次 `NewTransaction` 只多一次 `stat`，不会让请求在锁上排队。没有嵌套加锁：`Open`/`Export` 持读锁、`Import`/`ChangeToken`/`ClearBackup` 持写锁，它们内部走的都是私有的 `open`/`newTransaction`，不会再进 `create`。

## 2. 你的问题：`create` 放 `NewTransaction` 还是 `newTransaction`

**放 `NewTransaction`，也就是你现在的位置，是对的。**

分野在于两者服务的路径不同：

| | 绑定的库 | 调用方 |
| --- | --- | --- |
| `NewTransaction(ctx)` | 固定 `config.DbPath` | 业务读写 |
| `newTransaction(ctx, dbPath, token)` | **调用方给什么路径就开什么** | `export`（`db/backup.go:105`，主库）、`changeToken`（`:238`，**备份文件**） |

「库不在就建出来」是**主库**的策略，不是任意路径的策略。放进 `newTransaction` 的话，`changeToken` 那处传的是 `backupPath`——这个文件是上一步 `backup()` 产出的，它不存在只意味着备份失败了；此时 `create` 会就地造一个空库出来，**把备份失败伪装成成功**，接着 `replace` 把这个空库 rename 成主库，原库就没了。

`export` 那处同理。所以 `create` 必须待在 `NewTransaction` 这一层。

## 3. 你的问题：并发

分三种，结论不一样。

**① 普通业务读写之间：不需要应用层加锁。**

每个请求各自 `connect` 出一条连接，互斥由 SQLite 自己做：
- `_txlock=immediate`（`db/db.go:39`）——事务一开就拿写锁，避免「先读后写」在升级锁时死锁，这是 SQLite 最典型的 `SQLITE_BUSY` 来源；
- `busy_timeout=10000`（`db/db.go:44`）——拿不到锁时等 10 秒而不是立刻报错。

`TestConcurrentTransaction`（`db/db_test.go`）钉的就是这条：6 个协程 × 8 轮「先查后插」的混合事务，全绿。所以这一层不要再加应用锁——加了只会把 SQLite 本来能并行的读请求串起来。

**② 建库：需要，而且现在才刚补上。** 见 §1。原因不是 SQLite 扛不住并发，而是 `create` 里那两步（截断、删文件）是**文件级**操作，SQLite 根本不知道它们存在。

**③ 业务读写 vs 整库覆盖：需要，而且缺口还在。**

`Import`/`ChangeToken` 结尾是 `os.Rename`（`db/backup.go:82` 的 `replace`），这同样是文件级操作，SQLite 不知情。Linux 上 rename 不会让已打开的 fd 失效——在途的业务事务会提交进那个刚被顶掉的旧 inode，**静默丢数据**。

`dbLock` 本来就是干这个的，但 `NewTransaction` 这条路上拿不到读锁：它返回 `*util.Transaction`、调用方稍后自己 `Exec`，读锁**没有释放点**（`util.Transaction.Close` 在 go_common 里，db 包挂不上钩）。这一条在对话3 §3 已经记过，本轮没有变化，三条补法（db 包自己包一层 Transaction / 恢复一个带锁的 `Transaction` 入口 / 上游给 `util.Transaction` 加收尾钩子）都要动你禁掉的东西，仍然等你发话。

一句话概括：**SQLite 管得了的（行/页级并发）不用你管，SQLite 管不了的（截断、删除、rename 这些文件级动作）必须你管。**

## 4. 你的 todo：为什么要遍历一遍 `migrateModels` 转到 `models` 里

因为 Go 不允许把 `[]schema.Tabler` 直接当 `...any` 展开——`AutoMigrate(dst ...interface{})` 要的是 `[]interface{}`，而 `[]T` 到 `[]any` 没有隐式转换（每个元素的内存布局都要重新装箱），只能自己建一个 `[]any` 再 `...` 展开。

想彻底消掉这 4 行只有一条路：把 `migrateModels` 拆成 `[]any`（给 AutoMigrate）+ 表名 `[]string`（给结构校验），两份数据手工保持同步——不划算。建议保留现状，把 todo 换成一行说明。**本轮没动它**，等你确认。

# 对话6 · 既然普通读写不用加锁，`Open` 里那把读锁是干什么的

> 依据来源：`db/db.go`（`open :70`、`Open :81`、`CheckToken :95`、`create :113` 的 `dbLock.Lock()`、`newTransaction :181`）、`db/backup.go`（`Export :90` RLock、`Import :145` Lock、`ChangeToken :218` Lock、`ClearBackup :269` Lock、`replace :72` 的 `os.Rename :82`）
>
> 本轮只回答问题，**未改动任何代码**。

## 1. 不矛盾，因为这两句话防的不是同一个对手

先看 `dbLock` 的**写者**是谁——四处，全是**文件级**动作：

| 写者 | 它对库文件做了什么 |
| --- | --- |
| `Import`（`db/backup.go:152`） | `replace` → `os.Rename`（`db/backup.go:82`） |
| `ChangeToken`（`:225`） | 同上 |
| `ClearBackup`（`:273`） | `os.Remove` 备份文件 |
| `create`（`../../../rdb`） | `WriteData2File` 的 `O_TRUNC` + 失败分支 `os.Remove` |

**rename / truncate / remove，SQLite 对这三件事一无所知**。它的文件锁、`busy_timeout`、WAL/journal，管的是「谁能读页、谁能写页」，管不了「有人把整个文件从你脚下换掉」。

所以 `dbLock` 从来就不是「读写互斥锁」，它是「**文件级动作 vs 正在用这个文件的人**」的互斥锁。`Open` 里那个 `RLock` 是后者的读侧，意思是：**我正在打开这个库文件，别在这会儿 rename/truncate/删掉它。**

对话5 §3① 说的「普通业务读写之间不需要应用层加锁」，指的是**读写彼此之间**——那一层由 `_txlock=immediate`（`db/db.go:39`）+ `busy_timeout=10000`（`:44`）兜住，`TestConcurrentTransaction` 钉着。两句话管的是两件事，不冲突。

## 2. 但这把锁在当前形态下几乎没用，而且位置是反的

三条都能直接从代码读出来：

**(a) 覆盖范围只有「开库那一瞬」。** `Open` 用的是 `defer dbLock.RUnlock()`，锁在 `Open` **返回时就放了**，而返回的 `*gorm.DB` 还活着、还要被调用方拿去跑查询。真正危险的窗口是「连接存活期间库文件被 rename」，这把锁挡不住——它只挡住了 `connect` 那几微秒。

**(b) 保护的是最不需要保护的那条路。** `Open` 在生产代码里唯一的调用方是 `CheckToken`（`db/db.go:99`），开完下一行就 `util.CloseDb`，持有连接的时间以微秒计。

**(c) 真正需要保护的那条路一把锁都没有。** 业务读写走的是 `NewTransaction` → `newTransaction`（`db/db.go:181`）→ **私有的 `open`**，绕开了 `Open`，也就绕开了这把读锁。而它恰恰是长时间持有连接、最怕被 rename 抽走的那条。

净效果：**口令探针拿了锁，业务事务没拿。** 这就是对话3 §3、对话5 §3③ 记的那个缺口——`NewTransaction` 返回对象、调用方稍后自己 `Exec`，读锁没有释放点（`util.Transaction.Close` 在 go_common 里，db 包挂不上钩）。

## 3. 两个自洽的收尾

| | 做法 | 代价 |
| --- | --- | --- |
| **甲（倾向这个）** | 删掉 `Open` 里的 `RLock`/`RUnlock`，1 行 | 承认「文件级互斥目前只在写者之间生效」，缺口集中在一处，不留「已经保护好了」的错觉。丢掉的保护接近于零（见 §2a/2b） |
| **乙** | 把读锁做全：业务事务也拿读锁 | 需要一个释放点，三条补法（db 包自己包一层 Transaction / 恢复一个带锁的 `Transaction` 入口 / 上游给 `util.Transaction` 加收尾钩子）都要动你禁掉的东西 |

建议先甲，把乙当独立的一轮做。**本轮没动，等你发话。**

## 4. 顺带：`Open` 不建库，和 `NewTransaction` 不一致

`NewTransaction` 在库不存在时会建库，`Open` 不会——`open`（`db/db.go:70`）直接报「打开数据库，库文件不存在」。

去掉 `init` 之后的后果：全新部署上，`POST /api/ping` → `service/db.CheckToken` → `db.CheckToken` → `Open` 会**一直失败**，直到第一个业务读写请求把库建出来。

这未必是 bug——「库还没建、口令还没定」时探针报错是说得通的，而且如果让探针也触发建库，那随便 ping 一下就能用任意口令把库占了，比现在更糟。但它确实意味着**口令探针在建库之前不可用**，前端首次进入的交互得按这个来。要不要动，是产品决定，本轮只记一笔。

# 对话7 · 「读写用读锁、建库/导入导出用写锁」能修好吗

> 依据来源：`db/db.go`（`open :71`、`Open :82`、`CheckToken :98`、`create :113` 的 `dbLock.Lock()`、`NewTransaction :172`、`newTransaction :188`）、`db/backup.go`（`replace :72` 的 `os.Rename :82`、`Export :90`、`export` 里的 `io.Copy :135`、`Import :145`、`ChangeToken :218`、`ClearBackup :269`）、`go_common util/gorm.go` 的 `Transaction.Close :170`
>
> 本轮跑了三个一次性探针（F/G/H），**已删除**；**未改动仓库代码**，原型只在 scratchpad 副本里验证。

## 1. 先确认要修的是真问题

**探针F**：小红拿到连接、开事务插一笔，这时小明 `os.Rename` 把另一个库文件顶成主库，小红再提交。跑 2 遍：

```
小红提交: err=<nil>
重新开库后，小红那笔明细的条数=0
```

**提交返回成功，数据没了，全程无报错。** Linux 上 rename 只换名字，小红手里那条连接还指着旧 inode，写进去的东西随着连接关闭被系统回收。

**探针G**：换成真实入口——小红走 `Transaction(ctx, handler)`（事务里停 300ms 把窗口拉开），小明并发走 `ChangeToken`。跑 3 遍：

```
小明换口令: err=<nil>
小红事务:   err=<nil>
换口令之后，小红那笔明细的条数=0     ← 3/3 全丢
```

## 2. 你的模型是对的，探针也证明它有效

**探针H**：把读锁按「覆盖整个事务生命周期」加上，同一个探针G 跑 3 遍——**3/3 通过，小红的数据都在**。全量测试 8 个包也全绿。

原型（只在副本里，没进仓库）：

```go
type DbTransaction struct {
	*util.Transaction
}

func (this *DbTransaction) Close(ctx context.Context) error {
	defer dbLock.RUnlock()
	return this.Transaction.Close(ctx)
}

func NewTransaction(ctx context.Context) (*DbTransaction, error) {
	...
	//建库自己拿写锁，必须排在读锁之前
	err = create(ctx, dbPath, token)
	if err != nil { return nil, err }

	dbLock.RLock()
	object, err := newTransaction(ctx, dbPath, token)
	if err != nil { dbLock.RUnlock(); return nil, err }
	return &DbTransaction{Transaction: object}, nil
}
```

**注意读锁是共享的**：多个业务请求可以同时持有，彼此不排队，SQLite 那层（`_txlock=immediate` + `busy_timeout=10000`）照常干活。所以「普通读写都用读锁」不会把并发度压没——它只挡写者（建库/导入/换口令）。

## 3. 但有三个前提，缺一个就修不好或者引新 bug

### 前提一：解锁点必须落在 `Close` 上，不能只包住开库

`NewTransaction` 把事务对象交给调用方，调用方稍后自己 `Exec`、自己 `Close`。危险窗口是「连接活着的那一整段」，所以 `dbLock.RUnlock()` 必须跟着 `Close` 走。而 `util.Transaction.Close`（`util/gorm.go:170`）在 go_common 里，db 包插不进解锁代码——**只能在 db 包里包一层类型把 `Close` 接管过来**（上面的原型），或者换方案乙（见 §5）。

这也是 `Open`（`db/db.go:82`）那把读锁的老毛病：`defer dbLock.RUnlock()` 在函数 return 时就放了，连接刚交出去。只不过 `Open` 唯一的调用方 `CheckToken` 下一行就 `CloseDb`，窗口以微秒计，实际影响可以忽略。

### 前提二：读锁必须排在建库写锁**之后**，顺序反了会自锁

朴素写法是「`dbLock.RLock()` 包住整个 `NewTransaction`」。但 `NewTransaction` 里要调 `create`，而 `create`（`db/db.go:118`）自己要拿 `dbLock.Lock()`。同一条协程先读后写，Go 的 `sync.RWMutex` 不可重入 → **自锁**。

**反面样本实测**：把 `RLock()` 挪到 `create` 之前，库还不存在时跑 `TestConcurrentCreate`：

```
panic: test timed out after 30s
```

而且这是个**潜伏**的死锁——库已经建好时 `create` 在第一道守卫就返回了，根本走不到 `Lock()`，一切正常；只有全新部署的第一个请求会撞上。

### 前提三：导出**不能**改成写锁

`export` 是在锁里面把快照 `io.Copy` 给客户端的（`db/backup.go:135`），一次导出的持锁时间 = 整库复制 + **客户端把文件下载完**。

- 现在（读锁）：慢下载挡住 Import / ChangeToken / 建库，不挡查询；
- 改成写锁：慢下载把**所有业务查询一起挡死**，等于给自己开了个 DoS 口子——一个客户端点了导出然后不收数据，整个应用就停了。

导出只是读源库做快照，不 rename / 不截断 / 不删主库，**读锁在语义上就是对的**。建议你那条规则改成「**导入 / 换口令 / 建库用写锁，导出用读锁**」。

顺带：`ClearBackup`（`db/backup.go:269`）只动 `resource/db_backup/` 下的备份文件，从不碰主库，现在拿的是写锁——偏严，但它很少调、很快，留着也行。

## 5. 两个落地方案

| | 做法 | 代价 |
| --- | --- | --- |
| **甲** | db 包包一层事务类型（上面的原型），`Close` 里解读锁 | 新增一个类型——你在对话1 禁过「新编造函数」。另外这个类型若叫 `Transaction`，会和 `db/expense.go` 等 18 处待适配的 `Transaction(ctx, handler)` 调用点撞名，得先把那 18 处迁到 `NewTransaction` |
| **乙** | 恢复一个「一进一出」的 `Transaction(ctx, handlers...)` 入口，`dbLock.RLock()` / `defer RUnlock()` 天然罩住整个函数体 | 零新类型、零泄漏风险，而且那 18 处调用点本来就长这样、一行都不用改。代价是与「别把删掉的代码捡回来」冲突 |

## 6. 你的选择与落地

你选了**甲**（db 包包一层事务类型）与**导出保持读锁**，已落地。

`db/db.go`：

```go
// 读锁要罩住整条连接的生命周期，而util.Transaction的Close在go_common里，只能在这儿包一层把Close接管过来
type DbTransaction struct {
	*util.Transaction
}

func (this *DbTransaction) Close(ctx context.Context) error {
	defer dbLock.RUnlock()
	return this.Transaction.Close(ctx)
}

func NewTransaction(ctx context.Context) (*DbTransaction, error) {
	...
	//建库自己要拿写锁，必须排在读锁之前；顺序反了同一条协程先读后写，RWMutex不可重入会自锁
	err = create(ctx, dbPath, token)
	if err != nil { return nil, err }

	//读锁挡的是导入/换口令的os.Rename与建库的截断删除，读锁之间共享，业务请求彼此不排队
	dbLock.RLock()
	object, err := newTransaction(ctx, dbPath, token)
	if err != nil { dbLock.RUnlock(); return nil, err }
	return &DbTransaction{Transaction: object}, nil
}
```

类型名用 `DbTransaction` 而不是 `Transaction`，是为了不和 `db/expense.go` 等 18 处待适配的 `Transaction(ctx, handler)` 调用点撞名。`AddCommit`/`AddRollback`/`Exec` 都由内嵌的 `*util.Transaction` 提升上来，调用方写法不变；`Close` 被外层方法遮蔽，`defer object.Close(ctx)` 自然带上解锁。

**导出、ClearBackup 的锁一个字没动**，维持读锁 / 写锁现状。

**固化为用例 `TestChangeTokenDuringTransaction`**（`db/db_test.go`）：小红走 `Transaction` 插一笔、事务里停 300ms，小明并发 `ChangeToken`，断言那笔明细在换完口令的库里还在。把读锁摘掉这条用例立刻红（3/3 `count=0 want=1`）。

**剩下的一条风险照旧**：调用方忘了 `defer object.Close(ctx)`，读锁就永久泄漏，之后任何导入/换口令/建库会一直卡住。甲方案靠约定保证，没有编译期兜底。
