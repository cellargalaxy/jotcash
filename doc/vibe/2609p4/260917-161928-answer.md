# 对话1 · 统计页摊销口径漏算「跨期分期」的复核与修复

## 一、结论先说

**确实有逻辑问题，而且描述的那条正是根因。** 补上之后还牵出一处连带缺陷（月轴会长出统计不全的月份），一并修了。

## 三、问题复核

### 缺陷一（描述的那条）：摊销口径漏掉跨期分期的明细

筛选区间 2025-01~2025-12、柱高口径「摊销金额」时：

- 前端发出的条件是 `expense_date >= 2025-01-01 AND expense_date <= 2025-12-31`；
- 一笔 **2024-07** 买的、摊 12 个月的分期，摊销区间是 2024-07~2025-06，它在 2025-01~2025-06 这六个月每个月都有钱；
- 但它的支出日期是 2024-07，**后端根本不会把这一行返回**，前端拿不到它，于是 2025-01 到 2025-06 这六根柱子全都少算了这一笔。

**该算进来的判据不是「支出日期落在区间内」，而是「摊销区间与筛选区间有交集」**，即：

```
amortization_end_month >= 区间起月  AND  amortization_start_month <= 区间止月
```

### 缺陷二（补第一条时必然带出来的）：月轴会长出统计不全的月份

把上面的筛选换成交集判据之后，捞回来的行摊销区间会往区间两头溢出（2024-07 那笔在窗口左边还留着半年，2025-12 买的分期在窗口右边还留着大半年）。`monthAxis(monthType.keys())`（`expense_statistic.js`）取的是所有份额月的最小值到最大值，于是月轴会从 2024-07 一直画到 2026-11——**而这些窗口外的月份只有"恰好与窗口有交集"的那部分明细在贡献，数字系统性偏小**，放在正确的那几根柱子旁边比不画更误导。

所以窗口外的份额必须裁掉。

### 连带：裁剪之后「与口径无关」的那几张图必须跟着走

`aggregate` 原本把每行的 `accounting_amount` 整笔计进 `total`/`typeTotal`/`counterpartyTotal`，注释写着「与口径无关：一笔明细各月份额之和恒等于它的记账金额」。一旦按窗口裁剪份额，这条恒等式在摊销口径下就不成立了：若仍按整笔计，**概览的「合计」会大于柱状图各月之和**，同一屏上两个数字对不上。因此这几项一并改成「该行落在窗口内的份额之和」——

- 记账口径下，每行只有一个份额且必落在窗口内（拉数仍按支出日期筛），**结果与改动前逐字一致**，已用单测锁住；
- 摊销口径下，它们表达的是「这段区间里实际摊掉了多少钱」，与柱图口径统一。

## 四、方案取舍

| 取舍点 | 采用 | 理由 |
| ---- | ---- | ---- |
| 后端要不要做统计 | **不做** | 任务明确要求，且现有架构就是「后端只吐原始明细」。本轮后端只增加了两个筛选字段，`SelectExpense` 的函数签名、事务边界、handler 边界一律未动 |
| 交集条件怎么表达 | **新增两个筛选字段，跟现有区间字段同一形态** | `ExpenseInquiry` 加 `AmortizationMonthStart`/`AmortizationMonthEnd`，`Where` 里加两个 `if`，与 `ExpenseDateStart/End` 完全对称。没有新增 handler、没有新增 OR 条件、没有改 SQL 生成方式 |
| 两个字段怎么比 | **交叉比**：`起` 比 `amortization_end_month`，`止` 比 `amortization_start_month` | 这才是区间相交的判据。同名列对比（`amortization_start_month >= 起`）等价于「摊销起月落在区间内」，会重新漏掉跨期那批。已写变异用例钉死这一点 |
| 摊销口径下还带不带支出日期区间 | **不带，换成摊销区间** | 两者是 AND，同时带上等于回到原来的漏算。因为「支出日期在区间内 ⟹ 摊销起月在区间内 ⟹ 与区间有交集」，换过去只会多捞，不会少捞 |
| 换口径要不要重新拉数 | **要** | 两种口径拉的是不同的行集合。原来换口径只重绘（`renderBody`），现在改成 `reload()`。代价是多一次请求，但不这样就没法既保证记账口径行为不变、又让摊销口径拿到跨期的行 |
| 窗口裁剪放在哪 | **`aggregate`/`monthTotalOf` 加一个可选的 `window` 参数** | 不传 `window` 时行为与改动前完全一致（既有 12 条聚合单测一字未改、全绿）。`monthShares` 这个被穷举测试锁着的纯函数一行没动 |
| 整笔都摊在窗口之外的行 | **整行跳过，不进任何合计** | 否则它的支出类型会以恒为 0 的分段出现在堆叠柱和占比图里，表里多一整列「—」 |

## 七、已确认与待确认事项

1. **已确认**：
   - 描述的漏算真实存在，根因是「拉数按支出日期筛，算份额按摊销起止月铺」这两个判据不一致；
   - 补上交集筛选后月轴会溢出到统计不全的月份，所以窗口裁剪是这次修复的必需组成部分，不是额外功能；
   - 记账口径的所有数字与改动前逐字一致（已用「不给月窗时与改动前逐字一致」这条单测锁住）；
   - 后端只增加了两个筛选字段，`SelectExpense` 的函数签名、事务边界、handler 注册、表结构均未改动；后端仍然不做任何统计。
2. **待确认 / 需要知悉**：
   - **摊销口径下「支出类型占比」「交易对手方 Top」「合计金额」「月均」「最大单笔」的含义变了**——从「整笔记账金额」变成「摊进筛选区间的份额」。这是为了让同一屏上的数字互相对得上（否则概览合计会大于柱状图各月之和）。如果更希望这几项继续按整笔金额算、宁可与柱图对不上，请说一声，改回去只需要在 `aggregate` 里把 `amount` 换回 `row.accounting_amount`；
   - **换柱高口径现在会多打一次接口**。因为两种口径拉的确实不是同一批明细，没有别的办法既让摊销口径拿到跨期的行、又让记账口径的行集合保持不变；
   - **「最大单笔」在摊销口径下现在是「窗口内份额最大的一笔」**，不是「记账金额最大的一笔」。文案没改，如果觉得容易误读可以再调；
   - **时区**：新字段与既有的 `expense_date` 区间走同一套 RFC3339 比较，前端按浏览器本地时区拼串、后端按 `ExpenseDate.Location()` 落库。跨时区访问同一份数据时，月份边界理论上可能差一个月——这是既有设计的固有性质，本轮沿用未动，未做额外处理；
   - **历史数据**：`amortization_start_month`/`amortization_end_month` 由 `service/expense/expense.go` 的 `Derive` 在入库/编辑/币种切换时统一写入，正常路径上不会为空。如果库里存在早于这两列的历史行（值为零时间），摊销区间筛会把它们筛掉。本轮未在仓库或历史迁移里找到这样的证据，**不能断言是否存在**，如需兜底请告知，可在 `Where` 里补一条「零值放行」的判据。
