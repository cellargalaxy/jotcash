### 二、发现并修复的缺陷（2 个，均为实测确认，非推测）

#### 缺陷 1：`errs` 的 typed-nil 导致提取函数空指针 panic —— 且崩在成功路径

**触发形态**（`internal/base/errs/errs.go:From`）：

构造函数 `NewConflict` 等返回的是具体类型 `*Error`，于是 service 层很自然会写成 `func Svc() *Error`，而 handler / middleware 侧接的是 `error` 接口。成功路径返回的 nil 指针一旦装进接口，**接口值就非 nil**（携带类型信息），`err != nil` 判空拦不住；随后 `errors.As` **匹配成功并把 nil 写进 target**，原实现照直返回 `(nil, true)`，调用方解引用即 panic。

**实测结果**（修复前，独立 main 程序复现真实调用链路）：

```
失败路径: kind=唯一冲突 panic=<nil>
成功路径: kind=unknown panic=runtime error: invalid memory address or nil pointer dereference
```

后果的方向与直觉相反：**崩的不是出错的那条路，而是没有错误的成功路径**，且崩在 middleware 入口。逐个提取函数实测：`KindOf` / `MsgKeyOf` / `IsKind` 三个 panic，`ParamsOf`（因内部先判 nil）与 `Error()` / `Format` 正常。同时 `From` 返回 `(nil, true)` 违反了自身文档「未找到返回 nil, false」的承诺。

**为何既有 32 个用例没抓到**：`TestExtractFromNil` 测的是**字面 nil**（`KindOf(nil)`），`TestNilReceiverSafe` 测的是**nil 接收者直接调方法**（`err.Kind()`，不经接口）。二者都绕过了「nil 指针装进接口后再经 `errors.As`」这条真实路径。

**修复**：`From` 增加 `&& target != nil` 判定，把 typed-nil 按「未找到」处理，并在注释中写明成因与后果。修复后 typed-nil 归入既有的「未分档错误」规则得 `KindInternal` / `KeyInternal`——把一个编程错误响亮呈现，既不 panic，也不静默当成「无错误」放过去。

**回归用例**：新增 `TestTypedNilInInterface`（5 个提取函数逐个断言不 panic + From 返回值契约）与 `TestTypedNilConsumerShape`（回放 service→handler 两条路径）。

#### 缺陷 2：`decimal` 的量级设界被绕过，`Scale()` 呈 O(n²) —— 设界本身成了 DoS 入口

**触发形态**（`internal/base/decimal/round.go:Scale` + `decimal.go:Parse`）：

`Parse` 的量级校验（`checkMagnitude`）第一步就调 `Scale()`，而原 `Scale()` 用「逐位做 `big.Int` 除法」剥尾随零：n 位系数要做 n 次大整数除法，整体 **O(n²)**。此时值尚未设界，于是「`0.1` 后接 12 万个 0」这类文本——**有效位数只有 1 位，能合法通过校验**——在校验这一步就耗掉约 1.85 秒。

更关键的是放行之后：该值内部留下 12 万位系数，此后**每一次** `Scale` / `FitsScale` / `Units` / `StringFixed` 都要重新为这些零付一遍代价，实测单次 0.42~0.54 秒。这是一条不需要任何权限的拒绝服务路径，且经 `UnmarshalJSON`（dto 外部入口）同样可达。

**实测数据**（修复前 → 修复后）：

| 场景 | 修复前 | 修复后 | 改善 |
|---|---|---|---|
| `Parse` 12 万位输入 | 1.851 s | 15.6 ms | **119x** |
| 放行后单次 `Scale()` | 424 ms | 125 ns | **3.4M x** |
| 放行后 `Units(2)` | 541 ms | 583 ns | **928K x** |
| `UnmarshalJSON` 同形态 | 1.847 s | 13.3 ms | **139x** |

包注释原本声称量级校验拦住了「1e1000000 这类值」——该说法对**指数形态**成立（`Scale()` 在 `exp>=0` 时立即返回），但对**系数形态**（长串尾随零）不成立。这是注释与实际行为的偏差，已在修复中一并订正。

**修复（两处，缺一不可）**：

1. `Scale()` 改为按十进制文本一次数完尾随零（`big.Int.String()` 后线性扫描）。与除法版本结果完全相同——已在 20 个用例上逐一对照验证语义一致；实测提速 226~1374 倍，输入越长差距越大。同时移除因此不再使用的 `math/big` 导入。
2. 新增 `normalize()`，在 `Parse` 与 `FromUnits` 两个**外部输入**入口把系数压回有效位数。这样「通过校验」才真正等价于「后续运算都在量级内」。规范化是纯表示层整理：数值、`String`、`StringFixed`、最小单位整数输出全部不变（已由用例逐项锁死）。运算结果不必再规范化——参与运算的值都已规范化，其结果系数长度天然有界。

`FromUnits` 一并规范化还消除了一处潜在不一致：`scale` 由列口径决定（金额固定 2 位），`units` 末位常是零（10050 → 100.50），若不规范化，从库里读出的 `100.50` 与从账单解析的 `100.5` 数值相等而内部表示不同。

**回归用例**：新增 `TestParseNormalizesRepresentation`、`TestParseNormalizeIsLossless`、`TestFromUnitsNormalizesRepresentation`。判据取「底层小数位数 == 有效位数」而非计时——性能断言在慢机器或并行跑测试时会假失败，而表示是否压到有效位数是确定的。

### 三、逐包核查结论（未发现需修改的问题）

以下结论均来自探针实测，不是只读代码的推断。

**`calendar`**（44 例，全部通过）
- 前提 7 时区无关性：UTC / Asia-Shanghai / America-New_York / Pacific-Kiritimati / Etc-GMT+12 五个时区（含 UTC+14 与 UTC−12 两个极端）实测 `DateOf` 均无漂移。
- 边界：`9999-12` 的 `LastDate()` 正确得 `9999-12-31` 且可往返解析（注释所述「临时构造 10000-01-01 再回退」的实现无越界）；闰年 / 世纪年（2000-02 得 29 日、1900-02 得 28 日）/ 上下边界月末日全部正确；`AddMonths` / `AddDays` 在 `0001-01` 与 `9999-12` 两端均**报错而非静默回绕**。
- 不变式 1b：`结束月 = 起始月 + 月数 - 1` 在 1 / 2 / 12 / 24 个月及跨年场景下成立，闭区间两端点都被 `Contains` 覆盖，`Months()` 长度与 `Len()` 一致。
- 字典序 = 时间序（定长零填充）在 Date 与 Month 上均成立，`Scan` 接受 nil / string / []byte / time.Time 并拒绝错误类型与非规范格式（`2026-1-2`、`2026-02-30`）。

**`decimal`**（除上述缺陷外，43 例通过）
- T39 分摊恒等式 `商 × 除数 + 余 = 原值` 在正/负被除数、正/负除数、除不尽（100/3、1/7、0.05/3）各组合下均成立。
- T38 舍入：0/1/2 位本位币下 half-up 与 truncate 行为正确，负数对称（`-200.205` 与 `200.205` 镜像）。
- 除零、非法 scale（负数 / 超上限）、非法舍入模式（零值）均报错。JSON 接受字符串与数字两种形态、`null` 与缺字段落到零值，零值全方法可用。

**`errs`**（除上述缺陷外，32 例通过）
- 五档 `Kinds()` 与 middleware 映射表穷尽匹配；未分档错误（含 `database/sql` 直吐）一律归 `KindInternal` + `KeyInternal`，不泄露表名 / SQL 片段。
- `errors.Is` 可穿透 `pkg/errors.Wrap` 与 `fmt.Errorf("%w")` 混合多层包装取回 `sql.ErrNoRows`；已有栈时再 `Wrap` 不重复补栈（实测 `%+v` 中只有 1 份栈）。
- `Params` 为浅拷贝：顶层键值隔离，但嵌套 map 仍共享。当前 `Params` 只承载 i18n 占位符（字符串 / 数字），此边界不构成实际风险，**建议在后续引入嵌套结构时复核**。

**`pwdhash`**（17 例通过）
- 形态：`argon2id_v1$<43 字符 base64>` + 22 字符盐，解码后 32 字节密钥 / 16 字节盐，与设计一致。
- 错误分类清晰：密码错返回 `(false, nil)`，格式损坏返回 `(false, err)`——调用方可区分「密码错」与「数据坏」。9 种损坏形态（空、缺版本前缀、未知版本、base64 非法、长度不符、带填充的 base64）全部正确归类。
- 无 bcrypt 式截断：10 万字符明文与其加一字符的变体可正确区分；Unicode 明文可往返；两次 Hash 盐与哈希均不同，盐哈希错配不匹配。
- `RandBytes` / `RandIndex` / `RandString` 对非正长度与空字符集均报错，多字节字符集按 rune 计数正确。

**`idgen`**（19 例通过）
- 5 个入口均产出 18 位正整数；顺序 5000 次生成无重复且严格单调递增。
- `String` / `ParseString` 互逆，`ParseString` 拒绝前导零、正号、空白、小数、十六进制、全角数字与 int64 溢出。
- **已确认的下游约束**：18 位 ID 超出 IEEE-754 双精度安全整数范围，实测经 `float64` 往返 `260907121100095756` → `260907121100095744` 失真。裸 `int64` 序列化会被 JS 前端读坏，dto 层必须用 `json:"id,string"`。**建议在 L5 dto 落地时以用例锁死**。

**`config` / `log`**（24 例通过）
- 必填与格式校验到位：`token_secret` 留空 / 全空白拒绝启动；`listen_address` 拒绝漏端口并接受 `:4747` / `127.0.0.1:4747` / `[::1]:4747` 三种写法；未知键、YAML 语法错、重复键均报错；密钥字段不裁剪空白而结构性字段裁剪；`String()` 对两个密钥脱敏（只露长度）。
- 级别校验与 logrus 7 档一致；`log.Init` 的四步（先解析级别 → 落服务名 → 清空 hook → 重做日志）与幂等性经用例覆盖。

### 四、两处一致性观察（不影响正确性，未改动）

按「只改被点名范围、不做无关重构」的原则，以下两处仅记录，未修改：

1. **默认级别常量重复**：`log.DefaultLevel = "info"`（`log.go:72`）与 `config.DefaultLogLevel = "info"`（`config.go:49`）各自定义。当前取值一致，但两处可独立漂移。
2. **级别校验未复用 `log.ParseLevel`**：`config.check` 直接调 `logrus.ParseLevel`（`config.go:193`），而 `log.ParseLevel` 额外做了 `TrimSpace` 与空串取默认。因 `config.fillDefault`（`config.go:161`）已先 `ToLower + TrimSpace` 并回填默认值，**当前两者在实际输入上等价**；但若将来 `fillDefault` 的顺序或内容变动，二者会不一致。`log.ParseLevel` 的注释自称「供 base/config 在读配置阶段提前校验」，而 config 实际并未调用它——注释与实现存在偏差。

两处均属「L0 层内 config 不应依赖 log」的取向权衡（若 config 改调 `log.ParseLevel`，会在 L0 层内引入包间依赖，与前述零依赖现状冲突）。**建议由你确认取向后再动**：是接受常量重复以保持层内零依赖，还是允许 config → log 的单向依赖。

### 七、结论
