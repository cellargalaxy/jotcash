### 一、承载边界（依据来源）

### 二、第三方库评估（prompt 要求「优先采用 star 多的成熟库」）

#### 2.1 实测数据（2026-09-08 实测，GitHub 页面 + Go module proxy）

| 库 | star | 许可 | 最近提交 | 最新版本 | 结论 |
| --- | --- | --- | --- | --- | --- |

| `github.com/lestrrat-go/jwx` | 2423 | MIT | 2024-08-13 | v3.3.0 | 否决 |
| `github.com/cristalhq/jwt` | 688 | MIT | 2024-07-10 | v5.4.0 | 否决 |
| `github.com/o1egl/paseto` | 941 | MIT | — | — | 否决 |
| `github.com/aidantwoods/go-paseto` | 494 | MIT | — | — | 否决 |
| `github.com/kataras/jwt` | 211 | MIT | — | — | 否决 |

**选定 `golang-jwt/jwt/v5 v5.3.1`**：star 数量级领先（9217，是次席的 3.8 倍），是 `dgrijalva/jwt-go` 官方交接后的延续仓库，唯一在 2026 年仍有提交的候选。依赖面实测为**零非标准库依赖**（`go list -deps` 仅标准库），对一个 SQLite 单体应用是最轻的引入。

**否决理由（逐条对应实测，不是印象）**：
- `lestrrat-go/jwx`：面向 JWK/JWE/JWS 全家桶，本包只需 HS256 签发解析一种能力，引入的是数量级更大的表面积；且最近提交停在 2024-08。
- `cristalhq/jwt`、`kataras/jwt`：star 与维护活跃度均不及，无差异化收益。
- PASETO 两家：换协议本身是可辩护的技术取向，但**与既有代码冲突**——`base/config.TokenSecret` 的报错文案已写死「令牌是无状态的，其不可伪造性完全依赖此密钥」并给出 `openssl rand -base64 48`（config.go:186-188），是对称密钥语义；换 PASETO v4.public 需改 config 的参数形态与文案，属超出本轮 prompt 的改动。故沿用 JWT + HMAC。

#### 2.2 关键取舍：不复用 go_common 的 `util.EnJwt` / `util.DeJwt`

仓库已统一使用 `github.com/cellargalaxy/go_common`，且 `go.mod` 里**已存在** `github.com/golang-jwt/jwt v3.2.2+incompatible // indirect`（go.mod:35，经 go_common 引入）。「复用优先」原则下必须先评估它，实测结论是**不可用**，三条硬伤：

1. **载荷放不下「角色」**。实测 `model.Claims` 序列化结果为 `{"exp":...,"iat":...,"sub":"..."}`，字段为 `Ip/ServerName/LogId/ReqId` + 内嵌 `jwt.StandardClaims`，**没有角色字段也没有开放扩展位**。而承载明写载荷含「角色」。
2. **错误不可判定**。实测 `DeJwt` 对「过期」与「签名错」分别返回 `JWT解密异常: token is expired by 1h0m0s` 与 `JWT解密异常: signature is invalid`——它用 `errors.Errorf` 重造错误，**哨兵链已断**，`errors.Is` 无法命中任何库哨兵。上层只能靠匹配错误文本区分，这是 `service/auth` 区分「过期」与「伪造」所不能建立在的基础。
3. **底层是 v3.2.2**，且 v3 实测**默认放行无 `exp` 的令牌**（`err=<nil>`）。

另：`DeJwt` 失败时会**自己打一条 ERRO 日志**（实测 `codec.go:123`），本包在被 A-6 每请求调用的位置上不能接受这种由库决定的日志行为。

因此本包直接依赖 `golang-jwt/jwt/v5`。副作用：v3 仍作为 go_common 的 indirect 依赖留在 `go.mod`，**本仓库代码不再有任何路径可达它**（有 `TestNoLegacyJwtImport` 钉住）。这是本轮唯一未消除的残留，已登记在第六节。

### 三、实测出来的九个陷阱（决定接口形状的依据）

以下全部在 `golang-jwt/jwt v5.3.1` 上实测，是接口设计与参数选择的直接理由，不是照抄文档。

| # | 实测现象 | 本包对策 |
| --- | --- | --- |
| 1 | **默认放行无 `exp` 令牌**：不带 `exp` 的令牌解析 `err=<nil>`，即一个永不过期的令牌被放行 | 解析恒开 `WithExpirationRequired()`，缺 `exp` 报 `ErrTokenRequiredClaimMissing` |
| 2 | **默认不校验 `iat`**：`iat` 在未来 1 小时的令牌 `err=<nil>` | 恒开 `WithIssuedAt()`；且因 `iat` 缺失时该选项**也放行**（实测 `err=<nil>`、`IssuedAt` 为 `nil`），本包**另加显式判空** |
| 3 | **算法混淆面**：`alg=none` 可签出令牌；把 header 改成 `none` 并去掉签名段后，库虽拒（`'none' signature type is not allowed`），但该拒绝依赖库的内置特判 | 恒开 `WithValidMethods([]string{"HS256"})`，白名单收口；实测此时报 `signing method none is invalid` |
| 4 | **签名校验失败时 claims 已被填充**：篡改签名后 `err` 非 nil，但传入的 claims 结构体里 `sub`/`role` 已被写入攻击者的值（把 `sub` 改成 `999` 后实测填充出 `sub="999"`） | `Parse` 在 `err != nil` 时**只返回零值 `Payload`**，绝不返回已填充的结构；调用方拿不到「解析失败但有载荷」的中间态 |
| 5 | **秒级截断**：`NewNumericDate` 按 `TimePrecision=time.Second` 截断，`10:00:00.987654321` 落为 `10:00:00` | `Issue` 入参 `now` 先 `Truncate(time.Second)` 再计算 `exp`，使返回的 `IssuedAt/ExpiresAt` 与令牌内实际值**逐字节一致**（否则调用方按返回值推进基线时间会错半秒，见下条） |
| 6 | **秒级截断会连带毁掉基线时间比对**：基线 `10:00:00.950`、改密前令牌 `iat=10:00:00.900`、重登令牌 `iat=10:00:00.990`，三者的 `iat` 全部落为 `10:00:00`；朴素判据 `iat < baseline` 实测把**新令牌也判失效**（用户改密后立刻重登仍被踢），而基线也截断到秒则**旧令牌反被放行** | 比对不在本包，但本包必须让它可实现：`Payload.IssuedAt` 返回**已截断的秒级时间**，并在注释中把这条实测结论与「基线应向上取整到秒」的处置写给 `service/auth`（见第六节待确认项 1） |
| 7 | **空密钥 / nil 密钥可签发**：`[]byte("")` 与 `[]byte(nil)` 均能签出可验证的令牌（`err=<nil>`），库对密钥长度**无任何门槛**（1/8/16/31/32/64 字节全部通过） | `New` 在构造时校验密钥非空并要求最小长度，构造失败即返回错误，让 `app` 启动时失败而不是运行期签出弱令牌 |
| 8 | **库不校验业务码值**：`role` 为 `""`/`"root"` 与 `sub` 为 `""`/`"abc"`/`"0"`/`"-1"`/`"007"` 全部解析成功 | 签发前校验 `enum.Role.Valid()` 与 `idgen.IsValid`；解析后用 `enum.ParseRole` + `idgen.ParseString` 复校，非法即报错 |
| 9 | **库不管 TTL 上限**：`exp = iat + 365 天` 的令牌解析 `err=<nil>`（实测 `exp-iat=8760h`） | 解析时显式断言 `exp - iat == 12h`，超出即拒——否则拿到密钥的任何一方都能自签长期令牌绕过 A-5 |

补充实测（写入代码注释作为依据）：
- `sub` 必须用**字符串**：`int64(260906160443337625)` 经 `float64` 往返变成 `260906160443337632`，与 `base/idgen.String` 的注释（idgen.go:151-154）同一条理由。
- 载荷是**明文 base64**，无需密钥即可读出（实测 `{"role":"user","sub":"...","exp":...,"iat":...}`）→ 载荷内**不得**放密码、盐、基线时间。
- 过期边界：`exp = now` 即判过期，`exp = now+1s` 通过；`12h` 整点实测已过期，`11h59m59s` 通过 → 有效期是**左闭右开** `[iat, iat+12h)`。
- 默认 leeway 为 0（过期 1 秒即拒）。
- HMAC 密钥回调返回 `string` 会失败（`HMAC verify expects []byte`）；RSA 公钥混淆同样被 `ErrInvalidKeyType` 拦下。
- 畸形输入一律归 `ErrTokenMalformed`（空串、`.`、`..`、`a.b.c`、`Bearer <token>`、100 万个句点均是）；v5 对 100 万个句点耗时 1µs，无 v3 时代的分配放大问题。
- 同一 `(用户, 秒, 密钥)` 两次签发得到**完全相同**的令牌（HMAC 确定性，无 `jti`）→ 令牌不是会话标识，不能用于「单端登出」，与终版 §五 3 一致。

### 四、接口方案

```go
package token   // internal/token，L3 边界包

const TTL = 12 * time.Hour   // A-5，写死在本包（约定 8）

type Payload struct {        // 载荷四元组，与承载逐项对应
    UserID    int64          // 用户ID
    Role      enum.Role      // 角色
    IssuedAt  time.Time      // 签发时间（秒级）
    ExpiresAt time.Time      // 过期时间（= IssuedAt + TTL）
}

type Issuer struct{ ... }                                  // 持密钥，构造后只读
func New(secret string) (*Issuer, error)                   // 密钥由 app 注入
func (i *Issuer) Issue(p Payload, now time.Time) (string, Payload, error)
func (i *Issuer) Parse(token string, now time.Time) (Payload, error)
```

设计要点与理由：
- **`Issuer` 结构体而非包级变量**：密钥是注入参数，包级 `var secret` 会让「注入」变成可被任意包改写的全局可变状态，也让单测无法并行。与 `fxrate.Registry`「构造时填好、之后只读、无写入口」同一手法（registry.go:14-32）。
- **`now` 显式入参而非 `time.Now()`**：本包是被 A-6 每请求调用的判定点，时间必须可控才能测「12h 边界」与「过期 1 秒」。仓库无既有时钟注入先例，故选最简形式——入参，不引入 Clock 接口。
- **`Issue` 返回 `(string, Payload, error)`**：第二个返回值是**实际写进令牌的**秒级载荷。理由是陷阱 5/6——调用方（`service/auth` 记录最后登录时间、将来推进基线时间）必须拿到与令牌内逐字节一致的时间，不能自己拿 `time.Now()` 推算。
- **错误用哨兵，不在本包分档**：与同层 `fxrate`（fxrate.go:198-201）、`i18n` 一致。理由是**档位随调用方而变**：`Parse` 失败在 A-6 中间件是 `KindUnauthorized`（`errs` kind.go:83-85 已明写「无令牌、令牌过期、基线作废」归此档），而 `Issue` 失败是编程错误，属 `KindInternal`；同一个错误两档，不能在本包定死。
- **不打日志、不 import logrus**：与 `fxrate` 同理（fxrate.go:141）——A-6 每请求调用，端口层打日志会在「令牌过期」这种最正常的事件上刷满日志。
- **依赖边界**：非测试文件只 import `enum`（承载依赖列）+ `base/idgen`（`sub` 的字符串化与形态校验，避免本包自己写一套 ID 文本规范）+ 标准库 + `golang-jwt/jwt/v5`。**不** import `base/errs`（哨兵，档位归上层）、**不** import `base/config`（约定 8）、**不** import `entity`（不读 `User`，基线比对不在此包）、**不** import 同层 `store`/`fxrate`/`parser`/`i18n`（层内互不依赖）。

> `base/idgen` 是否在承载依赖列之外，是需要确认的一项，见第六节待确认项 2。

### 六、待确认项与已登记残留

**待确认项（不阻塞本轮编码，均已按「就地取最保守解 + 写进注释」处理）**

1. **基线时间比对的秒级口径归属**（陷阱 6）。本包把 `iat` 定为秒级已是既定事实（JWT `NumericDate` 规范如此）。`service/auth` 那一轮需决定「基线时间是否向上取整到秒」：实测不取整会误杀改密后立即重登的用户，取整则用户须等到下一秒才能登入（最多 1 秒）。本轮把结论写进 `Payload.IssuedAt` 的注释，**不在本包实现**（承载明写不在此包）。
2. **`base/idgen` 是否可进本包依赖列**。分层 §六 L3 `token` 行依赖列只写 `enum`。本包引 `base/idgen` 的理由是 `sub` 需要「ID ↔ 规范文本」的唯一互逆实现（`idgen.String`/`ParseString`，idgen.go:149-196），自己再写一份等于把同一规范实现两遍。若判定必须严守依赖列，则改为本包内联 `strconv` 转换 + 自校验（代价：ID 文本规范出现第二处实现）。**当前按引入 `base/idgen` 实现**，并在 `allowedImports` 表中标注此项待文档追认。

**已登记残留**

- `golang-jwt/jwt v3.2.2+incompatible` 仍在 `go.mod` 作为 go_common 的 indirect 依赖，本仓库代码无路径可达（`TestNoLegacyJwtImport` 钉住）。彻底移除需 go_common 升级其 JWT 依赖，不在本轮范围。
- 令牌无 `jti`，同一用户同一秒内签发的令牌完全相同；「单端登出」不可实现——终版 §五 3 已明写「本轮不建」。
- `base/config` 对 `TokenSecret` 只校验「去空白后非空」（config.go:184-189），而本包 `New` 会再要求最小长度。两处门槛不同是刻意的：config 管「填了没」，本包管「够不够强」。若希望启动即拦弱密钥，可由 `app` 在装配时把 `New` 的错误直接上抛（本包已返回可读错误）。

### 八、与方案的两处差异

1. **`classify` 是包级函数，不是 `Issuer` 的方法**。它只做错误映射，不碰密钥，与 `Issuer` 状态无关；作为包级函数可被单测直接喂错误，从而钉住下面那条顺序契约。
2. **`Parse` 的 `switch` 分支顺序本身成了一条被测契约**。这是本轮**新查明的库事实**，方案阶段未掌握：库源码 `parser.go:120` 把所有校验错误统一包在 `ErrTokenInvalidClaims` 之下，实测过期令牌的 `errors.Is(err, jwt.ErrTokenInvalidClaims)` **同样为真**（缺 claim、未来签发亦然；签名错则不命中）。故 `ErrTokenInvalidClaims` 分支必须留在最后——一旦上移，**所有过期令牌都会被归成「载荷不符」**，「登录已过期，请重新登录」这句提示再也不会出现。已加注释与 `TestClassifyOrderIsLoadBearing`，并实测「把该分支上移」会让 `TestExpiryBoundary` 与该用例双双失败。

### 九、验证方式与结果

不止跑通，而是**逐条验证「防护失效时测试会不会失败」**——共 14 项变异，做法是删掉或反转某项防护后重跑：

| --- | --- |
| 去掉 `WithIssuedAt` | ✅ `TestParseBeforeIssuedAt` 失败 |
| 去掉 `WithValidMethods` 白名单 | ✅ `TestParseRejectsAlgorithmConfusion` 失败 |
| 去掉 `exp - iat == TTL` 断言 | ✅ `TestParseRejectsInvalidClaimValues` 失败 |
| 去掉 `iat` 判空 | ✅ 同上 |
| 解析侧不复校用户ID / 不复校角色 | ✅ 同上（各自失败） |

其余验证：

- `gofmt -l ./internal/` 干净；`go build ./...`、`go vet ./...` 通过。

- token 包 34 个用例全通过，语句覆盖率 **96.8%**。未覆盖的是两条**刻意不可达的防御性分支**（`SignedString` 报错、`exp` 判空被库选项挡在前面），已在注释标明「正常不可达」。

### 十、`TestNoImplementationSubPackage` 抓到的一个真问题

该用例初版判据是「包目录下有没有子目录」，实跑即失败：`internal/token/log`。查证后确认是 go_common 的日志按**相对工作目录**落盘，而 `go test` 的工作目录就是包目录，跑一次测试就生成一个——`internal/base/idgen/log`、`internal/store/log` 同样存在，属既有现象。判据已改为「子目录里**有没有 `.go` 文件**」，理由写进注释。已清理这些运行期目录。

### 十一、govulncheck：一条独立佐证

修复 `store` 编译问题后（本轮未改动 store，是并行轮次补完的）终于跑通 `govulncheck`，结果反过来印证了选型：

- **GO-2025-3553**「Excessive memory allocation during header parsing」命中 `golang-jwt/jwt@v3.2.2`，且标注 **`Fixed in: N/A`** —— v3 分支不修，修复途径就是升 v5。这与上一轮实测吻合：同样喂句点，v3 处理 10 万个耗时 2.1ms，v5 处理 100 万个仅 1µs。
- **选定的 v5.3.1 未被任何告警点名**（`grep -c "golang-jwt/jwt/v5"` 于告警输出中为 0）。
- 两条 affected 告警（另一条 GO-2026-5676 来自 `quic-go@v0.59.0`，可升 v0.59.1）**均非本轮引入**：调用链是 `idgen.init → util.init → jwt.init`，即包初始化就链入二进制。实测凡 import `base/idgen` 的包（`store`、`idgen` 自身）都报这两条，而不 import 它的 `fxrate` / `entity` / `enum` 报 `No vulnerabilities`。已 grep 确认全仓库无一处调用 `util.EnJwt` / `util.DeJwt`。

结论：本包代码无路径可达 v3，彻底消除需 go_common 升级，仍属已登记残留。

### 十三、第六节两项待确认项的现状

两项**均未因编码而消解**，仍需拍板：

1. **基线时间比对的取整口径**：本轮把正确解（基线**向上取整到秒**）固化成了一条**可执行用例** `TestConsumerUsageAuthVerifyWithBaseline`——它在测试里模拟那一步比对，验证本包交出的 `IssuedAt` 足以支撑，并把「同秒重登也会被拦、下一秒即可通过、代价最多 1 秒」三点断言下来。生产实现仍不在本包（承载明写属 `service/auth`）。
2. **`base/idgen` 是否可进依赖列**：当前按引入实现，`allowedImports` 表中已标注待文档追认。若判定必须严守依赖列，改动面仅限 `Issue`/`Parse` 各一行。

   本轮另查明该依赖的一项**副作用**，可作为拍板时的参考：引入 `base/idgen` 会经 `go_common/util` 的包初始化带上日志装置，于是 `go test ./internal/token/` 会在**包目录下**生成 `log/<ID>/log.log`（实测：只跑 `enum`、`fxrate` 不生成，只跑 `token` 即生成；`store` 因同样 import `idgen` 也有此现象）。仅影响测试期工作目录，生产运行时工作目录是部署目录，落在已被 `.gitignore` 忽略的 `/log/`；且 `*.log` 已被忽略，不会误入版本库。这不构成阻塞，但若改为包内 `strconv` 自校验，本包将不再有此副作用。
