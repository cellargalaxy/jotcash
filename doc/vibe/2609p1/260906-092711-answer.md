# 复查 internal/currency 与 internal/enum

## 一、结论

两个包的**功能实现与文档要求一致**，测试与注释质量确实高于一般水准，但复查发现**两处实质缺陷**（均已修复并补带刃回归用例）和**一处流程问题**（前两轮 answer 的申报不完整）。

三项发现按严重度排序：

| # | 位置 | 性质 | 本包内能否发现 | 状态 |
|---|---|---|---|---|
| 1 | `enum` 四条出入口 | 写出侧不校验码值，与读入侧不对称 → 数据「写得进去、读不出来」 | 不能，要到 L3/L5 才炸 | 已修 |
| 2 | `currency` 哨兵构造 | 用 `pkg/errors.New` 造包级哨兵 → `%+v` 栈顶指向 `currency.init`，真实出错点不在栈里 | 不能，要到 L5+middleware 才暴露 | 已修 |
| 3 | `base/decimal` | 工作区有未提交改动，但前两轮 answer 均称「未改 `base/*`」 | — | 见 §四 |

两轮 answer 里「测试全绿 + 覆盖率 99.4% / 100%」在修复前后完全一致——这两处缺陷都不是覆盖率能发现的，下面每一处都给出可复现的实测形态。

## 二、缺陷 1：`enum` 写出侧与读入侧不对称

### 现象

7 个枚举的底层类型都是 `string`，因此 `enum.Role("root")` 这类强转在**包外编译通过**。修复前，`Scan` / `UnmarshalJSON`（读入）校验码值，`Value` / `MarshalJSON`（写出）不校验。实测一次「落库 → 读回」往返：

```
Role(合法 admin)              往返成功 ("admin")
Role(未知 root)               落库成功("root") 但读回失败: 未知的枚举码值  ← 该行永久不可读
Role(大小写变体 Admin)         落库成功("Admin") 但读回失败: 未知的枚举码值  ← 该行永久不可读
ObjectType(未知 audit_log)    落库成功("audit_log") 但读回失败              ← 该行永久不可读
ParserType(已删除的键)         落库成功("removed_bank_pdf") 但读回失败       ← 该行永久不可读
```

JSON 出口同理：`json.Marshal(Role("root"))` 得到 `"root"` 并下发给前端，**前端原样回传即报 `ErrUnknownCode`**——一个前端拿得到却用不了的值。

### 为什么这是实质缺陷而非风格问题

`enum` 的包注释本已写明设计意图是「反序列化即校验」，理由是「一个拼错的角色名就能一路写进库，之后所有按角色的判定都会静默走 else 分支」。**这条理由对写出侧同等成立，但只在读入侧落实了。**

后果的严重性在于错误发生的时机被推迟：非法值在**写入那一刻**没被拦下，错误被推到**下一次读**才爆发，届时已无从判断是谁写坏的。而 K-3 整库导出与 K-2 审计分页会因一行坏数据**整页失败**。

对照 `currency.Code`：它用私有字段 `entry *entry` 把非法值堵在编译期，包外根本造不出非法 `Code`——所以 `currency` 没有这个问题，`enum` 因选了 `string` 底层类型（取舍 2，为了 K-3 导出可读，理由正当）才需要在运行期补这道校验。

### 修复

在 `value` / `marshalJSON` 两个泛型内核函数中补校验，零值（`ObjectType` 的合法取值）照常放行：

```go
func value[T code](c T, s *set[T]) (driver.Value, error) {
	if c == "" {
		return "", nil          // 零值是 ObjectType 的合法取值，必须放行
	}
	if !s.valid(c) {
		return nil, fmt.Errorf("%w: %q 不可落库（写得进去也读不回来）", ErrUnknownCode, string(c))
	}
	return string(c), nil
}
```

改动落在共用内核而非抄 7 遍，7 个类型的 14 处调用点同步传入各自的 `set`。修复后同一往返：

```
Role(未知 root)          落库被拒: 未知的枚举码值: "root" 不可落库  ← 写入侧拦下
ObjectType(合法零值)      往返成功 ("")                          ← 未收紧过头
```

## 三、缺陷 2：`currency` 哨兵自带包初始化栈

### 现象

`currency` 是本仓库**唯一**用 `github.com/pkg/errors` 造包级哨兵的包：

```go
ErrEmptyCode = errors.New("currency: 币种代码为空")   // pkg/errors.New
```

`pkg/errors.New` 在**变量初始化那一刻**抓栈，而包级变量初始化发生在 `init` 阶段，于是这四个哨兵**永久携带一份指向 `currency.init` 的栈**。

这与 `base/errs` 的实现直接冲突：`errs.Wrap` 里的 `hasStack`（`errs.go:107`）见「链上已有栈」就跳过补栈。实测一次 L5 排错路径（`service/preference` 把哨兵映射成五档，middleware 打 `%+v`）：

```
[用户输入错误] preference.base_not_candidate: … : currency: 该币种不能作为本位币
github.com/cellargalaxy/jotcash/internal/currency.init      ← 栈顶是包初始化
	<autogenerated>:1
runtime.doInit1 …
```

栈顶是包初始化，**真正的出错调用点根本不在栈里**——排错时被引向完全错误的方向。同层三个包的对照实测：

| 包 | 哨兵构造 | `%+v` 栈顶 | 真实调用点在栈里？ |
|---|---|---|---|
| `currency`（修复前） | `pkg/errors.New` | `currency.init` | ❌ |
| `decimal` / `calendar` / `enum` | 标准库 `errors.New` | `errs.Wrap` | ✅ |

这也解释了为什么本包内完全看不出来：`errors.Is` 照常成立、错误文案照常正确、12 处 `errors.Is` 断言全过——问题只在跨包 + `%+v` 时显形。

### 修复

哨兵改标准库 `errors.New`，5 处 `errors.Wrapf` 改 `fmt.Errorf("%w: …")`，与同层三包对齐。`MustParse` 的 panic 文案改 `fmt.Sprintf`。修复后 `currency` 的栈顶与另外三包完全一致。

顺带说明：`pwdhash` 也 import `pkg/errors`，但它只用 `errors.Errorf` 在**函数内**造错误（抓的是调用点的栈，正确），没有包级哨兵——故不受影响，无需改动。

### 一处刻意不改

`currency` / `calendar` 的 `UnmarshalJSON` 手工剥引号，因此拒绝 JSON 转义写法（`"\u0043NY"` 是合法 JSON，等价于 `"CNY"`，但被判非法）。实测确认**已提交的 `calendar` 有完全相同的行为**，属仓库既有口径而非本轮引入；且码值都是 ASCII 字母数字、正常客户端不会转义。改它属于扩大改动范围、且会造成本包与 `calendar` 不一致，故只记录不改。

## 四、`base/decimal` 的未申报改动

工作区中 `internal/base/decimal/` 有 4 个文件未提交改动（`decimal.go` / `round.go` 及对应测试，共 +95/-7），但**前两轮 answer 都写了「未改 `base/*`」**。

核查改动内容：把溢出判定的中间量从 `int32` 提到 `int64`。这个修复是**必要且正确**的——实测旧实现的回绕：

```
1e2147483647  : 旧 int32 算 intDigits = -2147483648（回绕为负 → 放行），新 int64 = 2147483648
1e-2147483648 : 旧 int32 算 scale     = -2147483648（回绕 → 判为 0 位 → 放行），新 int64 = 2147483648
```

即旧实现会让两个极端指数值绕过 `MaxIntDigits` / `MaxScale` 校验。修复本身没有问题，`go.mod` / `go.sum` 也已 tidy。

**问题只在申报**：跨层改动（L0 基础包）未出现在任何一轮 answer 的改动清单里。若后续有人按 answer 认定「`base/*` 未动」而直接提交，这段改动会以无人知晓的方式混入 L0。本节即为补充申报。

## 五、回归验证

改动后全量重跑，全绿：

```
gofmt -l internal/     无输出
go vet ./...           ok
go build ./...         ok
go test ./...          9 个包全部 ok
go test -race          currency / enum / decimal 全部 ok
覆盖率                  currency 99.4%，enum 100.0%（与修复前持平）
```

两条新增回归用例都**用回退验证过有刃**——把修复改回旧写法后必定失败：

| 用例 | 回退后表现 |
|---|---|
| `enum` 的「写出侧与读入侧对称」（泛型驱动，7 类型各跑一遍） | 7 个类型**全部** FAIL |
| `currency` 的 `TestSentinelCarriesNoInitStack` | FAIL 并指出 `currency.go import 了 github.com/pkg/errors` |

第二条用 AST 扫 import + 行为侧查 `StackTrace()` 双保险：扫 import 防「怎么造」这个根因、且能盖住将来新增的哨兵；行为断言防「换个库照样带栈」。

最终规模：`currency` 生产 758 行 / 测试 1855 行 / 43 个顶层用例；`enum` 生产 1056 行 / 测试 1598 行 / 37 个顶层用例；两包合计 294 个子测试通过。

## 六、未修复项与后续建议

1. **JSON 转义写法被拒**（§三 末）：`currency` / `calendar` 一致的既有口径，如要改应作为独立一轮统一处理两个包，不宜只改新包。
2. **`base/decimal` 改动需要正式提交说明**：建议在下一轮把 §四 的实测回绕数据补进该包自己的 answer，而不是留在本轮文档里。
3. `enum` 写出侧校验新增了 `set` 参数，`value` / `marshalJSON` 的签名变了。这是包内私有函数，无对外影响，但后续新增第 8 个枚举时**必须**同步传 `set`——漏传会编译失败，不会静默出错，这一点是安全的。
