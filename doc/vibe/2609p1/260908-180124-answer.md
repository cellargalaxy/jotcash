# 260908-180124 五包交叉复查

## 对话1

### 一、任务与范围

复查前五轮（`204913` store、`204914` fxrate、`204919` parser、`204920` token、`204921` i18n）产出的代码，查错、查漏、查逻辑一致性，修掉有问题的部分，为 commit 做准备。

五个包全部是新增未跟踪目录（`git status` 显示 `?? internal/{store,fxrate,parser,token,i18n}/`），除此之外工作区只有文档与 `go.mod`/`go.sum` 变动。

### 二、基线：单包全绿，问题只可能在包与包之间

动手前先取基线，结论是**五个包各自的测试全部通过**：

```
go build ./...   → 通过
go vet ./...     → 通过
go test ./...    → 20 个包全部 ok
```

这一步决定了复查的方向。既然每个包在自己的测试下都是绿的，那么剩下的缺陷只可能落在**单包测试照不到的地方**——即跨包契约：A 包声明了什么、B 包是否真的兑现了。后面的检查因此围绕「声明方 ↔ 消费方」逐对核对，而不是重读每个包的内部逻辑。

### 三、确认的缺陷：14 个文案键声明了、但语言文件里没有词

#### 3.1 事实

`store` 与 `parser` 各自声明了一批 i18n 文案键，`i18n` 的语言文件 `internal/i18n/locales/zh-CN.json` 一个都没有：

| 声明方 | 声明位置 | 键 | 语言文件 |
|---|---|---|---|
| store | `store/errors.go:41,54,62,76,92` | `store.not_found`、`store.username_conflict`、`store.category_name_conflict`、`store.category_in_use`、`store.owner_required` | 缺 |
| store | `store/column.go:104,109` | `store.amount_out_of_range`、`store.rate_out_of_range` | 缺 |
| parser | `parser/errors.go:44,51,59,68,76,89,104` | `parser.type_mismatch`、`parser.decrypt_failed`、`parser.format_mismatch`、`parser.content_corrupt`、`parser.field_missing`、`parser.type_unsupported`、`parser.not_registered` | 缺 |

修复前语言文件只有 38 个键：`i18n.display_name` 1 + `errs.*` 5 + `passwd.*` 5 + `currency.name.*` 27。

这不是推断。修复前我写了一个临时探针（用完即删），直接 import 两个包拿它们导出的键常量去查 `Messages()`，14 个键**逐个报 MISSING**。

#### 3.2 两处白纸黑字的契约都被违反

- `store/errors.go:7`：「本包声明的文案键。**语言文件必须包含它们全部**（与 parser、rule/passwd 同例）」
- `parser/errors.go:21`：「它们同时是 K-4 语言文件的键，**语言文件必须包含全部 7 个键**」

#### 3.3 后果

`base/errs` 的三件套（档位 / 文案键 / 占位参数）经 middleware 取词后进响应体。取不到词时 `Render` 回落为**文案键本身**（`i18n.go:40` 的「第一个返回值恒非空」）。也就是说，用户在界面上看到的会是：

```
store.category_in_use
parser.field_missing
```

而不是「支出类型已被 N 笔明细引用，无法删除」。受影响的是 G-1/G-4 类型维护、A-7 账户管理、D-3 文件解析报错——恰好是错误提示最需要说清楚的几条链路。

#### 3.4 为什么五轮测试全绿却没拦住

`i18n` 那轮**建了**这道防线（`consumer_check_test.go` 的 `declaredKeys()` + 四个用例），但清单里只登记了 `base/errs`、`rule/passwd`、`currency` 三个来源。而按文件时间戳，`i18n`（15:19）**早于** `store`（16:26）完成——store、parser 后来新增的键，没有任何机制把它们追加进那份清单。

所以这不是「谁写错了一行」，而是**分轮实现下的顺序缺口**：防线本身是对的，只是它的输入清单是手工维护的，晚完成的包不会自动进入。这也解释了为什么它在单包视角下完全隐形——`store`/`parser` 的测试不会去检查语言文件，`i18n` 的测试不知道该检查它们。

### 四、修复

#### 4.1 补 14 条文案（`internal/i18n/locales/zh-CN.json`）

按既有风格（面向用户、可行动、不暴露内部细节）补齐，并分组留空行与既有段落一致。

两处刻意的处理：

- **`store.not_found` 不带 `{{.Entity}}` 占位符**。`errors.go:26` 明写该键「刻意不带 ID」，且实体名是 `"Expense"`/`"AuditLog"` 这类**英文内部标识**，直接渲染给用户没有意义。文案写成「未找到相关记录，或该记录不属于当前用户」，同时**贴合红线 2**：不存在与归属不符共用一个键、对外不可区分，文案也不能把两者说破。
- **`store.owner_required` 与 `parser.not_registered` 用通用的系统异常措辞**。两者档位分别是 `KindInternal`（500），成因是接线错误（漏传归属用户ID、漏注册解析器实现），用户改不了任何东西，故不暴露内部细节，与 `errs.internal` 的口径保持一致。

#### 4.2 关键实测：`nil` 参数会渲染出 `<no value>`，且不报错

`column.go` 的多个调用点传的是 `"Amount": nil`、`"Scale": nil`（如 `column.go:143-147, 214-217`）。我用一个最小 `text/template` 程序实测了 `missingkey=error` 下的三种形态：

| 形态 | 输出 | err |
|---|---|---|
| 键存在、值为 `nil` | `金额 <no value> 超范围` | **nil（不报错）** |
| 键不存在 | 截断 | 报错 |
| `nil` map | 截断 | 报错 |

即 `missingkey=error` 只管「键在不在」，**不管值是不是 nil**。若给 `store.amount_out_of_range` 写上 `{{.Amount}}`，用户会看到「金额 `<no value>` 超出范围」，而且这条路径**不会报错**，测试也照样绿。

因此两个越界键的文案**不使用占位符**，只给稳定可读的整句。这是依据实测行为做的取舍，不是省事。

#### 4.3 把防线补成「以后不会再漏」（`internal/i18n/consumer_check_test.go`）

只补 14 条词是不够的——下一个新增键的包会再次掉进同一个缺口。故把 `store` 与 `parser` 登记进 `declaredKeys()`：

- 新增两组来源，键**全部取自两个包导出的常量**（`store.KeyNotFound`、`jcparser.KeyFieldMissing` …），不硬编码字面量——这正是该文件开头写明的原则：硬编码会让清单与真实声明脱钩。
- 仓库内的 `parser` 包以别名 `jcparser` 引入：该文件已 import 标准库 `go/parser` 做 AST 扫描，会撞名。
- `TestAllDeclaredKeysRender` 的 `paramsFor` 补上带参键的参数，参数名逐个对齐各构造函数（`store/errors.go`、`parser/errors.go`）。
- `TestKeyCountMatchesExpectation` 的期望值补 `wantStore = 7`、`wantParser = 7`，总数 38 → **52**。

依赖方向安全：`i18n` 的**生产代码**仍是零仓库内依赖（`TestNoRepoImportsInProductionCode` 只扫非测试文件，仍通过），新增 import 只在测试文件里；`store`/`parser` 都不依赖 `i18n`，无环——已由编译通过实证。

### 五、验证

不止「跑通了」，而是用**会失败的动作**验证：

1. **修复前探针**：14 个键逐个报 MISSING（见 3.1）。
2. **端到端渲染**（模拟 middleware 真实链路）：用 `store.NewCategoryInUseError("餐饮", 3)`、`parser.NewContentCorruptError(...)` 等**真实错误对象**，经 `errs.MsgKeyOf` + `errs.ParamsOf` 取出键与参数再 `Render`，13 条全部渲染出正确中文，无 `{{`、`}}`、`<no value>` 残留。例：
   - `store.category_in_use` → 支出类型「餐饮」已被 3 笔明细引用，无法删除
   - `parser.content_corrupt` → 第 12 行「金额」的内容无法识别：abc
   - `store.amount_out_of_range` → 金额超出可记录的范围，请检查后重新填写（走的正是传 `nil` 参数的路径）
3. **变异测试**（确认新防线不是摆设，而非只看它变绿）：
   - 删掉 `store.category_in_use` 一条词 → `TestLocaleCoversAllDeclaredKeys` 与 `TestKeyCountMatchesExpectation` 双双失败；
   - 把文案里的 `{{.Count}}` 改成 `{{.Cnt}}`（模拟两侧参数名漂移）→ `TestAllDeclaredKeysRender` 失败并指出 `map has no entry for key "Cnt"`。
4. **全量**：`go build ./...`、`go vet ./...` 通过；`go clean -testcache` 后 `go test ./...` **20 个包全部 ok**；`gofmt -l internal/` 无输出；语言文件 JSON 合法，52 键。
5. **完整性交叉核对**：扫描全仓库非测试代码的 `Key* = "..."` 常量与传给 `errs.New*/errs.Wrap` 的字面量（结果：**无任何硬编码字面量**，全部走常量），与语言文件比对——**声明 24 个业务键 = 语言文件 24 个业务键，双向零差**。

### 六、复查了但确认无需改动的部分

避免「没发现问题=没检查」，逐项列出结论与依据：

- **`fxrate` / `token` 不需要文案键**：两包**刻意**只返回哨兵错误、不 import `base/errs`，档位与文案键由 L5 按调用链路判定（`fxrate.go:149-153`、`token.go:115-123`）。它们不在语言文件的覆盖范围内，是设计，不是遗漏。
- **`enum` 的中文名不进语言文件**：`OperationType.String()` 等是**日志面**文案（`audit.go:141` 明写「不要直接用本方法的返回值」渲染给用户）；K-2 页面标签属 L6 未来轮次。`ParserType` 则明确「不走 i18n」（`file.go:112`，K-4 不含数据内容翻译）。
- **`store.DedupKey` ↔ `rule/dedup.Key`**：字段与顺序逐项一致（`OwnerUserID/SpendDate/Amount/Currency`），可零成本互转，已有 `TestDedupKeyConvertibleToRuleKey` 用反射钉住。
- **`fxrate.Registry` 构造期自校验**：全覆盖 + 无孤儿源 + 空实现拦截，`Fetch` 另有 `IsPositive` 兜底，与「I-5 禁止静默 1:1」一致；`fixed` 占位实现以 Warn 日志 + `Note()` 显式化，未掩盖失败。
- **`token` 的解析口径**：`classify` 中 `ErrTokenInvalidClaims` 必须留在最后（它是过期等错误的父错误），已有 `TestClassifyOrderIsLoadBearing` 钉住；`exp - iat == TTL` 断言、`iat` 必存在、失败即零值载荷，均已实现。
- **`store` 接口形状**：`User` 仓储无归属参数且无删除方法、`AuditLog` 无改删、`File` 元信息与内容分接口、`Category` 只有 `DeleteTx`（TOCTOU）——与分层承载逐条对应。
