# internal/store 实现记录

## 对话1

### 一、任务与承载边界

本轮实现 `internal/store`，即分层文档 §六 L3 表 `store` 行。它是**端口包**——表头明写端口包「只有接口、类型与注册表，实现在 L4」，§十一 阶段 4 对本包的完成标志是：

> `store` 的方法集合须通过「前提 8 + 不变式 3 + 前提 3 无角色旁路 + 十条查询口径 + **两种软删除形态** + 两项唯一约束 + 数值列口径 + 事务句柄」走查

故本轮**不写一行 SQL**，不引入任何数据库驱动。承载七项与落点：

| 承载 | 落点 |
|---|---|
| ① 归属型仓储 4 个，按 ID 方法签名强制带归属用户ID，无管理员旁路 | `expense.go` / `file.go` / `audit.go` / `category.go` 四个接口 |
| ② `User` 仓储，不带归属参数，无删除方法 | `user.go` |
| ③ 删除能力按前提 8 裁剪；`Expense` 两种软删除形态 | 各接口的方法集合本身 |
| ④ 十条查询口径 | `query.go`（筛选/排序/分页/聚合条件类型） |
| ⑤ 两项唯一约束 + 唯一冲突档 | `errors.go` |
| ⑥ 数值列口径（金额 2 位、汇率 8 位，禁浮点） | `column.go` |
| ⑦ 事务执行器 + 事务句柄类型 | `tx.go` |

### 三、关于「优先采用 GitHub 成熟库」的判定

本轮**不引入任何第三方库**，这不是「造轮子」，而是本包的性质决定的：

1. **本包不含实现**。端口包的产物是「接口 + 条件类型」，即本仓库自己的领域词汇（`entity.Expense`、`currency.Code`、`calendar.Month`、`dedup.Key`）。`sqlc` / `ent` / `GORM` / `squirrel` 这类库解决的是「SQL 怎么写、怎么映射」，而按准则 4 与 §十一 阶段 4，那些属于 `store/sqlite`（L4）的选型，本轮不涉及。
2. **引入 ORM 会直接违反分层**。`GORM`/`ent` 的仓储接口以自己的模型与查询 DSL 表达，一旦出现在 L3，L5 的 11 个 service 就全部编译期依赖某个具体 ORM，而分层 §十二 的「换/加存储引擎」明写代价应为「新增 `store/pg` 等平级子包 + `app` 改一行」。注：`go.mod` 里已有的 `gorm.io/gorm v1.31.2` 是 `go_common` 带进来的 **indirect** 依赖，本仓库 `internal/` 无一处 import。
3. **L4 阶段的驱动选型已调研，登记备查不占本轮**：`modernc.org/sqlite`（纯 Go，无需 CGO，交叉编译简单）与 `mattn/go-sqlite3`（CGO，单点查询略快）。分层 §六 L4 已定死 SQLite 三条特有口径（写连接单例 + WAL + busy_timeout、金额与汇率禁 REAL、`File.文件内容` BLOB 同库），两个驱动都能满足，选型留给 L4 那一轮。

**复用现有实现**这条落在仓库内部：本包的注册表形态、错误构造形态、包注释结构、`consumer_check_test.go` 走查形态一律沿用同层的 `internal/parser` 与 `internal/fxrate`。

### 四、关键设计取舍

#### 1. 数值列口径：`Amount` 列不能是「恒 2 位」——这是承载 ⑥ 字面读法的一处硬伤

承载 ⑥ 写的是「金额 2 位定点、汇率 8 位定点」。**按字面对 `Expense.支出金额` 落地会直接丢数**，已实测：

```
KWD 12.345 → Units(2) → 报错：值 12.345 需 3 位, 目标 2 位
KWD 12.345 → Units(3) → 12345 ✓
```

`currency` 表刻意保留了 KWD（3 位小数），且分层 §六 L1.0 明写「支出币种不受 T38 限制，3 位币种仍可正常记账与摊分」。故本包把「金额」拆成两个口径，而不是一个：

| 列 | 位数 | 依据 |
|---|---|---|
| `Expense.支出金额` | **随支出币种** `currency.Code.Scale()`（0/2/3） | 原币金额，`rule/amortize` 的均分基准同源 |
| `Expense.本位币金额` | 恒 **2** 位 = `decimal.BaseAmountStoreScale` | T38 保证本位币 ≤ 2 位，0/1/2 位结果可被 2 位无损容纳 |
| `Expense.折算汇率` | 恒 **8** 位 = `decimal.RateScale` | T39 |

承载 ⑥ 的「金额 2 位」对应的是**本位币金额**（`decimal.BaseAmountStoreScale` 的注释即如此定义），支出金额一侧是承载的措辞省略。这与 `rule/dedup` 的既有裁定完全一致——`dedup.Key.Amount` 的注释已经写明「**不是**定点文本：8.3 的金额是原币金额，位数随支出币种而定——KWD 是 3 位，按本位币存储的 2 位会直接报错」。本包沿用该口径，不制造第二套。

#### 2. 入口宽度 > 列容量：本包必须显式给出「落库前必须过的一道校验」

`decimal` 的入口上限是 `MaxIntDigits = 16` 位整数。但落 `int64` 最小单位列时，容量随位数收缩（实测）：

```
scale=0 → 安全整数位 16 / 入口 16
scale=2 → 安全整数位 16 / 入口 16
scale=3 → 安全整数位 15 / 入口 16   <<< 入口宽于列容量
scale=8 → 安全整数位 10 / 入口 16   <<< 入口宽于列容量
```

即：一个 16 位整数的 KWD 金额、或一个 11 位整数的汇率，**能过 `decimal` 入口，落库时才溢出**。这与 `rule/passwd` 那一轮修掉的缺陷同类——错误没有在造成它的那一次请求里失败。

本包的处理：`column.go` 提供 `AmountUnits` / `BaseAmountUnits` / `RateUnits` 三个转换函数与配套的 `CheckXxx` 校验，把「该值能否无损落这个列」变成端口层的一次显式判定，返回 `KindInvalidInput`（用户输入的金额过大是输入错误，不是系统故障）。**这是本包唯一带行为的代码**，其余全是类型与接口；放在这里的理由是它就是「数值列口径」本身，L4 各实现照抄一遍必然漂移。

#### 3. 排序键用整数最小单位，不用定点文本

承载 ⑥ 允许「整数最小单位**或**定点文本」两种落地形态。本包在注释里明确推荐前者，因为后者的字典序不等于数值序（实测）：

```
定点文本按字典序   [-1.00 100.00 12.00 2.00 9.99]
数值序应为        [-1.00 2.00 9.99 12.00 100.00]
最小单位按数值序   [-100 200 999 1200 10000]  ✓
```

F-3 明写「支持按日期、金额等排序」、F-4 有金额区间筛选，两者都依赖数值序。日期与年月一侧相反——`calendar.Date`/`Month` 是**定长**文本（`%04d` 格式化，`MinYear`/`MaxYear` 注释已说明定长是「字典序 = 时间序」的前提），文本形态可直接走索引，故日期列沿用其 `Value()` 的文本形态。

#### 4. 归属参数放在**首参**且类型具名

不变式 3 的编译期兜底靠「签名强制带归属用户ID」。若写成 `Get(ctx, id, ownerUserID int64)`，两个相邻的 `int64` 可以被静默传反——传反的后果是「用明细ID 当归属用户查」，恒查不到，表现为「数据莫名消失」而非报错。

本包定义 `type OwnerUserID int64`，并统一放在 `ctx` 之后的第一个参数位。这样传反是**编译错误**。同理 `TxHandle` 作为首参（约定 7）时排在 `ctx` 之后、`OwnerUserID` 之前。

#### 5. 游标迭代用 `iter.Seq2`，不自定义 Cursor 接口

Go 1.23 起标准库有 `iter` 包（本仓库 `go 1.27.0`）。`Expense` 的游标迭代（I-7 与 K-3 不全量装载）用 `func(ctx, ...) (iter.Seq2[entity.Expense, error], error)` 形态，调用方 `for row, err := range seq` 即可，`break` 自动触发清理。自定义 `Next()/Close()` 接口需要调用方自觉 `defer Close()`，漏写就泄漏连接。

#### 6. 事务句柄是**不透明接口**，不暴露 `*sql.Tx`

`TxHandle` 只有一个未导出方法作为标记（sealed interface 形态），L3 以下与 L2 不感知其内部。若把 `*sql.Tx` 暴露在端口上，L5 就能直接写 SQL，「唯一知道 SQL 的地方是 store/sqlite」立即失效。

#### 7. 唯一冲突用 `errs.KindConflict` + 两个具名文案键

承载 ⑤ 明写「冲突返回 `base/errs` 的『唯一冲突』档」。两项约束各一个键：`store.username_conflict`（`User.用户名` 全局唯一）、`store.category_name_conflict`（`ExpenseCategory.(归属用户ID, 名称)` 唯一）。另加 `store.not_found`（按 ID 取不到，含归属不符——**归属不符与不存在返回同一个错误**，否则错误本身成了「这个 ID 存在但不属于你」的存在性预言，等于旁路泄漏）。

#### 7.4 实施中的三处修正（方案与实测不符之处）

三处都是先写下断言、再被实测推翻，故记录在此而非默默改掉：

1. **`decimal` 对小数位数做规范化**（剥尾随零）。实测 `Parse("0.00").Scale() = 0`、`Parse("100.50").Scale() = 1`、`FromUnits(1e8, 8).Scale() = 0`——即 `Scale()` 返回「表示该数值所需的最小位数」，不是构造时声明的位数。故「读回值的 `Scale()` 等于列位数」是一条**不成立**的性质，最初的 `TestRoundTrip` 断言它而假失败。改为断言 ① `Equal` 数值相等 ② `FitsScale` 可无损容纳 ③ 最小单位往返稳定。**这条已写进 `column.go` 的包注释**，因为它对 L4/L6 有直接约束：金额与汇率对外呈现必须走 `StringFixed(位数)`，用 `String()` 会把 `100.50` 输出成 `100.5`、`0.00` 输出成 `0`，在对账场景下是显性错误。

2. **`reflect` 对接口类型会列出未导出方法**。实测 `interface{ isX() }` 的 `NumMethod() = 1`、`Method(0).Name = "isX"`，故 `NumMethod() == 0` 不能作为 sealed 判据。改为逐方法用 `IsExported()` 区分，并同时断言两条性质：有未导出方法（包外无法实现）且无导出方法（拿不到底层对象）。

3. **`iter.Seq2` 的 `String()` 不含 `func` 字样**（实测为 `iter.Seq2[...]`），按字符串判形状会假失败。改为按 `Kind() == Func` + 入参也是 `Func` + `yield` 收 2 个参数来判 range-over-func 形态。

#### 7.5 一处依赖边界的裁定（分层文档两句话的合并读法）

`base/idgen` 是否可被本包 import，文档有两句话需要合起来读：

- `§六 L0` 表 `idgen` 行：「**`store` 不生成 ID、不依赖自增回填**——不变式 4 的「先落审计取 ID → 明细挂载」因此不需要 DB 回传」；
- `idgen.IsValid` 的函数注释：「供三处使用：**`store` 的按 ID 访问方法在下压 SQL 前做前置断言**；……」。

合并结论是「**可以判、不可以生成**」：`OwnerUserID.IsValid()` 复用 `idgen.IsValid`（避免第二处「什么样的 ID 算有主」的口径），而任何 `Gen*` 生成函数一律禁止。后者由 `TestStoreDoesNotGenerateIDs` 用 AST 精确扫 `idgen.Gen*` 调用锁死——因为若 store 生成 ID，不变式 4 的「先落审计取 ID → 业务数据挂载」就无从谈起。
