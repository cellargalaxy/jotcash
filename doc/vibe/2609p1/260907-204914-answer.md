# internal/fxrate 实现记录

## 一、任务与承载边界

本轮实现 `internal/fxrate`，即分层文档 §六 L3 表 `fxrate` 行的四件承载：

| 承载 | 落地 |
|---|---|
| 日汇率获取接口（按币种对 + 日期） | `Fetcher` 接口 + `Query`（`From`/`To`/`Date`） |
| 按 `currency` 的汇率源标识路由的注册表（与 `parser` 注册表同构，注册项由 `app` 从 L4 注入） | `Registry` / `NewRegistry` / `Registry.Fetch` |
| 失败语义：失败即返回错误，**禁止静默 1:1**（I-5） | 六个哨兵错误；`Fetch` 无任何一条返回 1 的路径 |
| **返回值精度不设限**——规整到 8 位由 `rule/convert` 统一完成（T39，单一规整点） | 本包不 import `RateScale`、不调 `RoundRate` |

依赖列 `currency`、`base/*` 全部落实为 `currency` + `base/calendar` + `base/decimal` 三项。

`fxrate` 是**端口包**（分层 §六 L3 表头：「只有接口、类型与注册表，实现在 L4」；§十一 阶段 4 的完成标志同为「只有接口、类型与注册表，可编译」），因此本包不含任何汇率源实现、不含日汇率缓存。

prompt 要求的「汇率先写死返回 1」落在 **L4 的 `fxrate/fixed`**，而不是端口里，理由见 §三-2。

产出七个文件（三个实现 + 四个测试）：

| 文件 | 内容 | 行数 |
|---|---|---|
| `fxrate.go` | 包注释、六个哨兵、`Query`（`Validate`/`String`）、`Fetcher` 接口 | 389 |
| `registry.go` | `Registry`、`NewRegistry`（三项构造校验）、`Fetch`（四步）、`Sources`、`Fetcher` 查找 | 231 |
| `fixed/fixed.go` | L4 占位实现：`Rate`、`Note`、`Fetcher`、`New`（构造告警） | 166 |
| `fxrate_test.go` | 入参校验、精度不规整、非正数拦截、**失败路径全覆盖断言**、同币种不短路、取消穿透 | 390（12 个用例） |

## 三、关键设计取舍

### 1. 不引入任何第三方汇率库（本层）

prompt 要求「优先采用 github 上成熟稳定 star 多的代码库」。按 GitHub API 实测（2026-09 查询）核对了候选：

| 库 | Star | 最近推送 | 性质 |
|---|---|---|---|
| Rhymond/go-money | 1912 | 2026-04 | 货币计算，**无汇率获取能力** |
| bojanz/currency | 644 | 2026-09 | 含汇率类型，已在 `currency` 那一轮被否决为运行时依赖 |
| mattevans/dinero | 86 | 2026-03 | Open Exchange Rates 客户端（单一源、含内存缓存） |
| govalues/money | 56 | 2025-01 | 货币计算，**无汇率获取能力** |
| openprovider/ecbrates | 37 | 2016-11 | ECB，**十年未更新** |
| peterhellberg/fixer | 17 | 2020-04 | Fixer.io |
| wowsignal-io/go-forex | 10 | 2024-06 | 多央行日汇率 |
| jieggii/ecbratex | 2 | 2024-07 | ECB，作者自述 WIP |

**结论：本层一个都不引入**，理由与「库好不好」无关，而在于本包是端口：

1. 端口的职责恰是「不绑定选型」（准则 4）。在 L3 引入任何一家源的客户端，等于把选型钉死在换选型时不该动的那一层，且 L5 会经本包间接依赖它。
2. 上表**全部候选都是某一家源的客户端**（ecbrates / fixer / dinero 各对一家），而本包要的是「按币种路由到不同源」的注册表——那是它们上面的一层，没有一家提供。
3. **汇率源尚未选定**（分层 §四 + 配置文件注释）。选源之前引入客户端，引进来的多半就是要被换掉的那一个。

「该用则用」的对照仍然成立并已写入代码注释：选定汇率源后，L4 的 `fxrate/<源>` **应当**优先采用该源的成熟客户端库——若选 Open Exchange Rates，`mattevans/dinero`（86★，自带按基准币种的内存缓存）与 L4 承载的「日汇率缓存」正好对齐，值得认真评估。

### 2. 写死的 1 放在 L4 的 `fxrate/fixed`，不放在端口

prompt 说「汇率先直接在代码里写死返回 1」。放哪一层是本轮最实质的一个取舍。

放在端口会同时破坏两条已定的约束：

- 准则 4 规定「换选型 = 加平级子包 + 改 `app` 一行」。1 写在端口里，选定真实汇率源那天要改的就是所有人都依赖的那一层。
- 承载明写「失败即返回错误，**禁止静默 1:1**」。端口里一旦存在返回 1 的代码路径，这条承载在结构上就不再可验证——无法再断言「本包没有返回 1 的路径」。

放在 L4 则两条都保住：`fxrate/fixed` 是一个平级子包，由 `app` 显式注册（约定 2「实现子包只被 `app` import」）；换源那天的动作是加 `fxrate/<真实源>` + 改 `app` 一行，**端口与 L5 一行不改**。

**恒返回 1 与 I-5「静默 1:1」的区别**（二者数值相同，必须讲清）：I-5 禁止的是「自动获取或重拉**失败时**……静默按 1:1 处理」，关键词是「失败」与「静默」。`fixed` 不掩盖任何失败——它压根没去取汇率，返回的 1 是显式配置的占位值，且这件事在四处写着：① 包名就叫 `fixed`，导入路径出现在 `app` 装配代码里；② `New` 打一条 **Warn 级**日志（每进程一次）；③ `Note()` 返回性质说明供启动日志记录；④ 必须由 `app` 显式注册才生效。

**已知代价（本轮显式接受）**：真实汇率源接入前，支出币种 ≠ 本位币时本位币金额不正确（100 USD 会记成 100 CNY）。该代价**可回收**——用户可经 I-5 手填汇率纠正，或在接入真实源后跑一次 I-7 逐笔重算一次性收敛，不需要数据迁移。这正是 I-7 存在的意义。

### 3. 端口不做 I-4 同币种短路

分层 §四 修正 ② 写死了落点：「`service/fx` 承载补终版 I-4 的短路判据『支出币种 = 当前本位币时汇率直接取 1，**不调 `fxrate`**』」。

因此 `Registry.Fetch` 对 `From == To` **既不返回 1、也不报错**，照常路由。两个方向都有理由：

- 返回 1 就是在端口造出一条返回 1 的路径，与承载「禁止静默 1:1」直接冲突。同币种取 1 是「数学上恰好为 1」，静默 1:1 是「拿不到汇率却假装是 1」，数值相同、性质相反，而代码分不清调用它的是哪一种。
- 反过来拒绝同样有害：真出现 `From == To`（`service/fx` 短路失效）时报错，会让一笔本币记账被 I-5 判成「汇率转必填」，把服务层的接线错误变成用户面前的表单故障。

### 4. 汇率非正数必须在端口拦下

这是六个哨兵里最容易被认为「多余」的一条，但它拦的是一条 **`err == nil` 的静默错账路径**：

- 源返回 **0**（某些源以 0 表示「无此币种对」）：放行后本位币金额算成 0，而恒等式 `本位币金额 = 支出金额 × 折算汇率` **照样成立**——钱没了，不变式却没被打破，任何校验都发现不了。
- 源返回**负数**：符号整体翻转，退款变支出。

`rule/convert` 有同名哨兵兜底，但那时错误已离开现场：`service/fx` 看到的是「折算失败」而不是「某某汇率源返回了 0」，而两者的处置完全不同（前者查代码，后者换源或报障）。

### 5. 注册表没有 `Register` 方法

不是风格取舍，而是**仓库内已记录的一条实测故障**的直接结论：`currency/currency.go` 与 `rule/convert/convert.go` 的包注释都记着否决 `bojanz/currency` 的第一条理由是「`Register` 改包级 map、与读并发即 DATA RACE」。

本包若提供 `Register`，同一形态会在自己身上重演：I-7 逐笔重算并发调 `Fetch`（读 map），任何一次运行期 `Register`（写 map）都足以让进程崩在 runtime 的并发写检测上。加锁能消除 race，但换来每笔重算都过一次锁，而「运行期换源」本身并无需求——承载写的是「注册项由 `app` 从 L4 注入」，启动装配时注入一次即可。

于是用**结构**表达约束：构造后无写入口，就没有并发写。`NewRegistry` 深拷贝入参，`TestRegistryHasNoWriteMethod` 以反射把「没有写入口」变成 CI 约束。

### 6. 构造时做全覆盖校验（本包与 `parser` 注册表的唯一实质差别）

承载说两者「同构」，但本包多做一项：`NewRegistry` 校验 `currency.All()` 的每个币种都能路由到实现。

理由是**汇率源标识对用户不可见**。`parser` 的解析器类型是用户在 D-2 从下拉里选的，选到未注册的类型会当场报错、影响面止于那一次上传；而汇率源由币种表决定，漏注册一个源**不会有任何征兆**，直到某用户第一次记该币种的支出——那时表现为 I-5「汇率转必填」，与「网络不通」的表象完全一致，会被当成外部故障查很久。

校验口径取 `All()` 而非 `Enabled()`：终版 I-7 明写重算含已软删除明细，历史明细可能引用已停用币种（I-1「枚举项只能停用不能删除」），它们同样要能取到汇率。

另补一项反向校验（注册了却无币种指向），拦「标识写错一个字母」。

### 7. 路由取 `From` 一侧（**待确认项，见 §五**）

承载写「按 `currency` 的汇率源标识路由」，而一次查询有两个币种。取 `From`（原币）的理由是汇率源差异来自被定价的那一侧：`To` 恒为本位币、受 T38 约束只能是候选币种（已启用且小数位 ≤ 2），而 `From` 是支出币种、**不受该限制**（分层 §六 L1.0「支出币种不受此限」），KWD 这类币种只会出现在 `From`。

当前 `currency` 表 27 项全部指向 `RateSourceDefault`，两侧取谁**在行为上无法被任何用例区分**。处理方式见 §四-2。

### 8. 错误是哨兵，不返回 `base/errs`

与 `base/decimal`、`base/calendar`、`currency`、`enum`、`rule/convert`、`rule/amortize` 一致。理由与 `rule/convert` 相同——**同一个错误在两条链路上分属不同档位**：

| 错误 | 经 D-7 录入 / F-5 编辑 | 经 I-7 批量重算 |
|---|---|---|
| `ErrFetch` | 用户输入错误档，触发 I-5「汇率转必填」 | 系统错误档，计入失败笔数、不打扰用户 |
| `ErrDateEmpty` | 用户输入错误档（支出日期必填） | 系统错误档（库里存着无日期的明细，属数据损坏） |

需留意本包与同层 `parser` 在这点上**刻意不同**：`parser` 的承载明写「一律返回带文案键的 `base/errs`」，因为 D-3 已把五类解析错误的档位定死；本包承载只写「失败即返回错误」，未定档位，故按仓库内多数包的取向走哨兵。

### 9. 端口不打日志

I-7 会以**每笔明细一次**的频率调用本包：一个汇率源故障，在端口打一行日志就是 N 行几乎相同的记录，真正的根因反而被淹没。失败一律以错误返回，由 `service/fx` 在批处理收尾汇总成一条审计（§六 5.2「记成功/失败笔数」）。

例外在 L4：`fixed.New` 在**构造时**打一条 Warn，那是每进程一次而非每笔一次；`fixed.Fetch` 同样零日志。

### 3. 「禁止静默 1:1」的结构性验证

这条承载用**两类互补断言**锁死，而不是只测几个分支：

- **行为面**：`TestFetchNeverReturnsOneOnFailure` 遍历全部 6 条失败路径，逐条断言「err ≠ nil」「返回值 ≠ 1」「返回值为零值」，末尾附一条**路径计数断言**——新增失败路径而忘了登记时失败。
- **结构面**：`TestNoLiteralOneReturn` 以 AST 扫描源码，拦下任何 `decimal.FromInt(1)` / `MustParse("1")` 构造。这拦的是将来新增的、尚未被行为用例覆盖的返回点。

### 4. AST 走查覆盖的约束

`consumer_check_test.go` 用源码扫描锁死 6 条无法用运行期断言表达的约定：依赖边界（双向：越界 + 依赖列虚高）、不依赖 L4 及以上与同层、零 IO、零日志、不碰 `time`（前提 7）、不做精度规整（T39）、无缓存 API（L4 承载）、导出面不外溢。

其中「不做规整」与「不引用 `DeletedAt`」同一手法：扫 AST 而非文本匹配，否则包注释里解释「为什么不规整」的段落会被判为违规，逼后来人删注释来让测试通过——那恰恰把设计决策的理由抹掉了（沿用 `rule/dedup/consumer_check_test.go` 的既有做法）。

### 5. 下游走查

`consumer_check_test.go` 模拟 `service/fx` 的四条真实用法并断言可走通：

| 走查 | 断言要点 |
|---|---|
| I-3/I-4 自动取汇率 | 端口交出 9 位汇率**未规整**，调用方自行 `RoundRate()` 后落在 8 位内；端口未改写 `Query` 任何字段 |
| I-5 兜底 | `errors.Is(err, ErrFetch)` 判据成立；拿不到 1、拿不到任何正数；源的原始错误可穿透 |

| I-7 逐笔重算 | 部分失败时整批继续，成功数 + 失败数 = 总数（对应 5.2「记成功/失败笔数」） |

### 6. 与 prompt 的一致性复核
