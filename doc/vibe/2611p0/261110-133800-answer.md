# 对话1 · 全部解析器迁到浏览器：可行性与技术选型

> 范围：只做可行性分析与技术选型，不写正式代码。
> 标注约定：【已确认】有代码/文档出处；【待确认】需要你拍板或补资料；【不可推断】本机条件下无法验证。

## 一、结论

1. **可行**。4 个解析器都是纯计算（CSV 文本 / PDF 文本 / OCR 文字块 → 明细），不依赖数据库、网络、密钥，放到浏览器里没有原理上的障碍。
2. **推荐方案 A：把现有 Go 解析器编译成 WebAssembly（标准 Go 工具链，`GOOS=js GOARCH=wasm`），在浏览器里运行**。不推荐用 JS 重写。
   - 主要原因：两个 PDF 解析器靠的是 `ledongthuc/pdf` 的文本提取行为（坐标、`GetPlainText` 的换行切分）。换成 pdf.js，提取出来的文本块和顺序都会变。而**现在仓库里没有真实 PDF 样例**（`resource/` 目录不存在，`rangeSamplePdf` 会直接 Skip），重写之后无法验证结果一致。WASM 方案跑的是同一份 Go 代码，这个风险不存在。
   - 代价：要把解析器包和 `go_common/util`、`jotcash/config`、`model`、`expense` 这些服务端依赖拆开，并在构建里多一步 wasm 编译。
3. 服务端只保留「接收结构化明细 → 校验 → 派生（汇率、摊销）→ 落库 + 原文件留档」。汇率获取（`exchange_rate`）和 `Derive` **必须留在服务端**。
4. 有一处**冲突**和几项**待确认**需要你拍板（第七、八节）。其中最关键的一项：上传接口字段是否允许变化，因为对话8 定过「接口以后不再改」。

## 三、目标与边界

- **目标**：`base_csv`、`cmb_debit`、`icbc_credit`、`unionpay_screenshot` 四个解析器全部在浏览器执行；服务端只接收结构化明细。
- **服务端必须保留的部分**（这些不是"解析"）：
  - 汇率在线获取与 `Derive`（摊销起止月、记账金额、`AmountScale` 舍入）：要用到服务端配置和网络。
  - ID 生成、版本号、落库、FileMeta/FileBlob 留档、审计。
  - **入参校验**：浏览器的结果不能直接信任，至少要校验日期、金额、币种枚举、汇率为正、摊销月数 ≥1、字段长度、单次条数上限。
- **不在范围内**：`hsbc_pulse_credit`（未注册）是否一起迁移【待确认】。

## 四、逐个解析器的可行性

| 解析器 | 浏览器里的输入 | 难点 | 可行性 |
| ------ | -------------- | ---- | ------ |
| `base_csv` | `File.text()` | ① Go `encoding/csv` 的严格行为（裸引号报错、BOM、字段数）；② 日期按本地时区解析 | 高。JS 重写也容易（mock.js 已有一份），WASM 方案则零差异 |
| `cmb_debit` | `File.arrayBuffer()` | 依赖 `ledongthuc/pdf` 解释内容流得到的**原始 Tm/Td 坐标**（不乘 CTM）；容差 1 和 12 是绝对单位。pdf.js 的 `getTextContent` 给出的是乘过 CTM 的变换矩阵，文本项的拆分粒度也不一样（相邻 TJ 可能合并，也可能拆开） | WASM：高。JS 重写：**中低**，必须用真实样例逐块对比 |
| `icbc_credit` | 同上 | 依赖 `GetPlainText` 的换行语义（`\n` 切行 + `strings.Fields`）。pdf.js 只能靠 `hasEOL` 和坐标重建行，语义不同；中文 CID 字体还要带 cMaps 文件 | WASM：高。JS 重写：**中低**，同样需要真实样例 |
| `unionpay_screenshot` | `ocr.js` 已有的文字块 | 解析逻辑约 230 行（正则、聚类、年份推断），用到 `time.Now()` 和 `time.Local` | 高。OCR 已经在前端，只是把后半段也搬过来 |

## 五、技术选型

### 5.1 候选方案

**方案 A：Go → WASM（推荐）**
- 新建 `//go:build js && wasm` 的入口包（例如 `wasm/parser/main.go`），通过 `syscall/js` 暴露一个函数 `jotcashParse(parserName, Uint8Array) → JSON`。
- 编译产物 `parser.wasm` 和 Go 自带的 `wasm_exec.js` 放进 `static/lib/parser/`，继续由 `go:embed` 托管，前端动态 import、按需加载。这和 `ocr.js` 的做法一致。
- 解析器包要**去掉服务端依赖**：
  - `go_common/util`：它里面有 gin、gorm、配置加载等，初始化时会读写 `resource/`、`log/`；测试的 `TestMain` 专门清理这两个目录，说明副作用确实存在。
  - `jotcash/config`、`jotcash/expense`（这个包会引入 `exchange_rate`，需要网络）、`model`（它引入 gorm 和 `go_common/util`）。
  - 改法：`CsvData2Strs` 换成 `encoding/csv`，`ParseStr2Time` 换成 `time.ParseInLocation`，再新建一个只放解析结果的轻量 DTO 包。`logrus` 是纯 Go，可以保留，日志会打到浏览器控制台。
- Go 单测基本照旧，仍然用 `go test` 原生跑。前端测试用 Node 加载同一个 wasm（Node 可以直接跑 `wasm_exec.js`）。

**方案 B：JS 重写**
- `base_csv`：手写 CSV 解析，或复用 mock.js 里的 `parseCsv`。
- 两个 PDF 解析器：pdf.js（`pdfjs-dist`，Apache-2.0，ESM 版 `pdf.min.mjs` + `pdf.worker.min.mjs`，另带 cMaps）。
- `unionpay_screenshot`：直接翻译成 JS；decimal 用现有的 `decimal.min.js`。
- 约 1100 行 Go 解析逻辑和约 1100 行 Go 单测要翻译成 JS。

**方案 C：混合**（CSV 和截图用 JS，PDF 用 WASM）：要同时维护两套技术栈和两套测试，不推荐。

### 5.2 对比

| 维度 | A：Go → WASM | B：JS 重写 |
| ---- | ------------ | ---------- |
| 与现有行为一致性 | 同一份代码，PDF 提取逐字节一致 | PDF 提取库换了，**没有样例就无法证明一致** |
| 复用 | 解析逻辑和单测全部复用 | 全部重写 |
| 改动量 | 中：拆依赖 + wasm 入口 + 构建步骤 + 前端加载器 | 大：逻辑 + 测试 + pdf.js 接入 |
| 前端体积 | 预估 3~6MB wasm（gzip 后约 1~2MB）+ `wasm_exec.js` 约 20KB【不可推断，需 PoC 实测】 | pdf.js 约 1.5MB + worker + cMaps 约 1.5MB；CSV 和截图几乎不增加 |
| 构建 | 多一步 `GOOS=js GOARCH=wasm go build`，产物要在 `go build` 主程序之前生成（被 `go:embed` 引用）；Dockerfile builder 阶段加一行 | 无构建步骤，与现在的"无打包"风格一致 |
| 时区 | Go 的 js/wasm 运行时把 `time.Local` 设成浏览器**当前**的固定偏移，没有夏令时规则；所以输出要用"本地墙钟字符串"，见 6.2 | `new Date` 也是浏览器时区，问题相同，处理方式相同 |
| 演示模式 | mock 也能调同一个 wasm，**所有识别器在演示模式下都可用**，mock.js 里那份 CSV 复刻可以删掉 | mock 复用同一套 JS，效果相同 |
| 风格 | 新增一种前端产物（wasm），但 `static/lib` 里已经有 onnxruntime 的 wasm，有先例 | 和现有前端风格最一致 |

**结论**：选 A。决定性因素是正确性：PDF 文本提取层没有测试样例，A 不会改变这一层，B 会。如果你能重新提供真实 PDF 样例，B 的主要风险可以验证掉，但改动量仍然明显大于 A。

## 六、服务端改造要点（草案）

### 6.1 职责

```
浏览器：选识别器 →（OCR）→ wasm 解析 → 结构化明细 JSON → 预览/提交
服务端：校验结构化明细 → fillExpense/Derive（汇率、摊销）→ 落库 + 原件留档 + 审计
```

- `expense.Parse` 拆开：服务端不再注册解析器，改为一个"结构化明细校验"函数。它沿用 `base_csv.parseExpense` 里的那组规则（日期、金额、汇率与记账币种的关系、摊销月数），再加上 `CheckCurrency`。
- 服务端不再能核对"内容与所选识别器相符"（对话8 的 `Support` 防线），这道防线搬到浏览器。对单用户、口令即密钥的系统（设计文档前提 1、3）来说，这是可以接受的取舍，但**需要你确认**。

### 6.2 结构化明细契约（草案，字段名复用 `model.Expense` 的 json tag）

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| `bank_name`、`card_last_4`、`counterparty`、`remark`、`expense_type` | string | 原样 |
| `expense_date` | string | **本地墙钟时间 `2006-01-02 15:04:05`，不带时区**。服务端按 `time.Local`（Asia/Shanghai）解析，和现在的语义一致，避免浏览器时区和服务端不同时日期漂移 |
| `expense_currency`、`accounting_currency` | string | ISO 4217 代码 |
| `expense_amount`、`exchange_rate` | string | 十进制字符串，不经过 JS number，避免精度损失；汇率留空表示由服务端去取 |
| `amortization_months` | int | 0 表示用默认值 |

载体可以有两种选择：
- ① 上传表单的 `content` 字段，内容改为这份 JSON；
- ② 新增字段，例如 `expenses`。

① 不新增字段，但改变了 `content` 的语义。另外也可以考虑直接用本系统标准 CSV 作为结构化载体（设计文档里"CSV 是唯一批量录入形态"），这样服务端只需要保留一个 CSV 校验器。这几种选择都要你拍板（第八节第 1 问）。

# 对话2 · 采纳方案A：识别器编译成 wasm 在浏览器运行，服务端只收明细数组

## 一、需求对齐

| 要求 | 落点 |
| ---- | ---- |
| 采纳方案A | 4 个识别器原样保留为 Go 代码，编译成 `static/wasm/parser.wasm` 在浏览器运行 |
| 浏览器只负责解析，汇率等附加数据由服务端填充 | 识别器输出 `parser.Expense`（只有文件里能读到的字段）；服务端 `expense.Fill` 校验后走原有的 `fillExpense`/`Derive` |
| 上传接口改为 expense 数组，去掉 content | 表单字段为 `file` + `expense`（JSON 数组）；`parser`、`content` 两个字段都删除 |
| 服务端不再核对内容与识别器是否相符 | 服务端不引用任何识别器（有契约测试守着）；识别器严格口径：内容不符、解析不出明细都报错，页面在报错后追加「请检查是否选错了识别器」 |
| 删除 hsbc_pulse_credit | 整个包删除 |
| wasm 在 builder 阶段生成，仓库不提交；支持预编译二进制上传 | `go generate ./static` 生成；wasm 经 `go:embed` 内嵌进二进制，`build-docker.sh` 产出的二进制自带 wasm |
| 文件页预览支持图片/PDF/CSV/JSON，图片可旋转、缩放 | PDF/CSV/JSON 原本已支持；新增图片预览，带左转、右转、缩小、放大、适应宽度 |

## 二、方案与结构

```
浏览器：选识别器 →（截图先本地 OCR 成文字块）→ wasm: jotcashParse(识别器名, 字节) → 明细数组
        → POST /api/expense/insert  [file=原文件, expense=明细数组JSON]
服务端：反序列化 parser.Expense → expense.Fill（逐笔校验 → 汇率/摊销/ID/版本）→ 落库 + 原件留档 + 审计
```

| 包或文件 | 职责 |
| -------- | ---- |
| `service/expense/parser`（新） | 浏览器与服务端之间的明细契约 `Expense`，以及识别器注册表 `Register/Parse/Names`。必须能编进 wasm，所以只引用纯计算依赖 |
| `service/expense/parsers`（新） | 生效识别器的唯一清单（匿名引入 4 个包），只有 wasm 入口和测试引用它 |
| `service/expense/{base_csv,cmb_debit,icbc_credit,unionpay_screenshot}` | 解析逻辑不动，只把依赖换掉：`go_common/util` → 标准库（`encoding/csv`、`time.ParseInLocation`），`model.Expense` → `parser.Expense`，`expense.Register` → `parser.Register` |
| `wasm/main.go`（新，`js && wasm`） | 挂出 `jotcashParse`、`jotcashParsers`。报错以 `{error}` 返回而不是抛异常：Go 一旦 panic，整个 wasm 实例就退出了 |
| `service/expense/expense.go` | 删掉注册表，新增 `Fill(ctx, []*parser.Expense, 记账币种)`：不信任浏览器的结果，契约规则全部重新校验，报错带笔数 |
| `static/js/expense_parse.js`（新，替代 `expense_extract.js`） | 按需加载 wasm（失败可重试）；截图先 OCR 再交给识别器；`createParser(bytes)` 可注入，Node 测试与浏览器共用 |
| `static/static.go` | `//go:generate` 编译 wasm 并拷贝 Go 自带的 `wasm_exec.js` 到 `static/wasm/` |

### 关键取舍

- **支出日期以墙钟字符串 `2006-01-02 15:04:05` 传输，不带时区**。依据：服务端 `util.ParseStr2Time` 用的是东八区（`go_common/util/time.go` 的 `E8Loc`），而 Go 在 js/wasm 下的 `time.Local` 取的是浏览器时区。带时区传输会让日期随浏览器所在时区漂移。识别器统一用 `parser.Loc`（UTC+8），与 `E8Loc` 一致。
- **base_csv 的列名在识别器里另写一份**。原因：`model` 依赖 `go_common/util` 和 gorm，编不进 wasm。实测 `GOOS=js GOARCH=wasm go build` 报 `go_common/util/os.go: undefined: syscall.SIGHUP`。三处（前端 `CSV_FIELDS`、识别器 `col*`、`model.Csv*`）由 `contract_test.js` 逐字对账。
- **单笔补录也走 wasm 的 base_csv**。入库口径只有一套，留档的仍是那份 CSV。
- **演示模式（mock）也走同一个 wasm**。以前只认 CSV，现在 4 个识别器都能用。`mock.insertExpense` 改为接收明细数组，校验口径与 `expense.Fill` 对齐。
- **`.dockerignore` 排除 `static/wasm`**。builder 阶段总是重新生成，避免把本地的旧产物带进镜像。
