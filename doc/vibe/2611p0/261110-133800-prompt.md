# 执行流程

> 你是一位拥有跨学科背景的顶尖资深专家，请以深厚的专业洞察力和严谨的大师视角进行回复
> 流程冲突时以「任务 Prompt」为准
> 关键结论/方案取舍/验证结果统一记录至`261110-133800-answer.md`(`prompt.md`路径相同)

## 步骤

- 背景调研
  - 研读prompt中提及的文档/代码/配置
  - 对齐背景，梳理核心逻辑/组件依赖/改动点
- 需求分析与方案
  - 提取核心目标/交付物/范围边界/关键约束
  - 制定方案：最小改动/复用优先/任务拆解；说明模块职责/输入输出/关键逻辑/异常处理
  - 评估对现有链路/性能/兼容性/下游的副作用
  - 写入`answer.md`：依据来源/方案取舍/实施步骤/验证说明
- 实施
  - 按方案执行，命名/注释/文案与项目风格一致
  - 中文注释与日志，处理边界与异常分支
  - 同步更新类型定义/关联配置/文档
  - 复杂任务使用主agent调度子agent的方式实施
- 验证与交付
  - 执行测试/逻辑校验/数据校验/文档校对
  - 重读`prompt.md`，检查与交付结果是否一致
  - 核心产出同步至`answer.md`
  - 清理临时文件/调试代码/冗余产物，但无须提交变更

## 约束

- 依据：结论只能来自文档/代码/表结构/日志/SQL等明确来源；严厉禁止猜测业务逻辑/捏造接口字段，不能断言的内容都询问用户
- 引用：关键事实引用到具体章节/字段名/代码路径或枚举值，禁止笼统援引
- 信息不足：区分「已确认/待确认/不可推断」并标注，不得脑补
- 历史资料：历史Prompt/answer/旧方案仅供参考，必须与代码交叉核对后才能使用
- 冲突：资料冲突时列出冲突点与采用依据，不得默默取一方
- 风格：命名/注释语言/代码组织与项目既有风格一致，优先复用现有实现

### 对话2

- 开始正式编写代码
  - 需要注意代码风格与层级结构需要保存一致
  - 需要编写相应的单测
  - 我在resource下面提供了PDF文档，这些文档都是真实数据，切忌不能泄露
- 采纳方案A
- 浏览器只负责解析用户上传的文件，其余附加数据（例如汇率等），还是由服务端负责填充
- 上传接口字段进行改造，改造为expense数组，去除content，浏览器需要负责将从用户上传的文件解析到的数据，转为标准的expense，服务端只需要负责接受处理expense即可
- 服务端不再核对"内容与识别器相符"，改为在页面由用户手段选择识别器，识别器需要以严格口径实现，用户所上传的文件与识别器的解析定义有一点出入，都不进行解析/报错，发现解析不到expense/报错，页面需要提醒用户，让用户检查是否选错了识别器
- hsbc_pulse_credit删除，已经没有用了
- 采纳：wasm 产物是在 Dockerfile builder 阶段生成，仓库不提交二进制
  - 由于服务端性能有限，实际线上部署时不会在服务端进行编译，而是将编译好的二进制文件上传到服务器
  - 例如：[text](../../../build-docker.sh)
  - 因此新增的这个编译二进制也需要支持该情况
- 文件页面的预览，需要支出图片/PDF/CSV/JSON，其中图片需要支持在页面进行旋转与缩放，以方便观看
